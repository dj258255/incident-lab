## 2. 만들어 둔 도구

**`tools/repeat-runs.sh`** — 세션 하나를 여러 회차 돌려 편차를 봅니다.
```
tools/repeat-runs.sh <세션디렉토리> <컨테이너이름> <회차수> <스크립트...>
예: tools/repeat-runs.sh sessions/A02-mdl-storm a02-mysql 3 scripts/run-all-cases.sh
```
`cpus` 초과와 컨테이너 기동 실패를 시작 전에 막고, 회차마다 `uptime`과 `nproc`을 파일로 남깁니다. 회차별 산출물은 `results/run{N}-*`로 보관됩니다.

**`incident-lab-render`** (도커 이미지, Pillow + 나눔폰트) — `results/render.json`으로 콘솔 카드와 막대그래프 PNG 생성
```
docker run --rm -u $(id -u):$(id -g) -v $PWD:/work incident-lab-render sessions/<세션>/results
```

**`incident-lab-plot`** (도커 이미지, matplotlib + 나눔폰트) — 세션의 `scripts/report.py`가 matplotlib을 쓸 때
```
docker run --rm -u $(id -u):$(id -g) -v $PWD:/work -w /work/sessions/<세션> incident-lab-plot python scripts/report.py
```
재생성한 PNG는 `../IT-Oasis/public/uploads/incident/<슬러그>/`로 복사해야 블로그에 반영됩니다.

**`../check-incident-posts.sh`** — 블로그 글의 이미지 누락, 본문 H1 잔여, 변환 안 된 상대링크, 프론트매터 필수 필드를 한 번에 검사

**`../incident-blog-spec.md`** — 세션 README를 블로그 글로 옮기는 변환 명세
**`../incident-fix-orders.md`** — 22편 정정 지시서. 어느 지적이 확인됐고 어느 것이 반증됐는지 기록
**`audit/UNFINISHED-AUDIT.md`** — "못 한 것" 128건 전수 분류

## 3. 하다가 멈춘 것

### 3-1. 반복 측정 (진행 중, 최우선)

`audit/UNFINISHED-AUDIT.md`에서 가장 위험하다고 판정한 자리입니다. 조건마다 한 번씩만 재고 결론을 낸 세션 10곳입니다.

**그런데 시작하고 나서 알게 된 것이 있습니다.** `cpus: 4`인 세션 8개는 이 서버(2코어)에서 실행이 아예 안 됩니다.

```
A01, A22, B52, R04, R12, R13, R16, R17  ← cpus=4, 이 서버에서 실행 불가
A02, A08, A09, A17                       ← cpus=2, 실행 가능
```

도커가 `range of CPUs is from 0.01 to 2.00`으로 거부합니다. 이 여덟은 12코어 맥에서 만들어진 세션입니다. `cpus`를 낮춰 돌리면 원 측정과 조건이 달라져 회차 비교가 성립하지 않으므로, 큰 장비가 없으면 손대지 마세요. **`audit/UNFINISHED-AUDIT.md`의 분류에서 이 여섯 건(A01·B52·R04·R13·R16·R17의 반복 측정)을 C에서 B로 정정해야 합니다. 아직 안 고쳤습니다.**

**A02가 실행 중이었고 중단했습니다.** 절차는 완성돼 있습니다.
```
cd sessions/A02-mdl-storm
../../tools/repeat-runs.sh sessions/A02-mdl-storm a02-mysql 3 scripts/run-all-cases.sh
```
회차당 적재 145초 + 네 조건 각 60초라 약 6.5분, 3회면 20분입니다.
확인할 것은 이것입니다. README가 **"겹침 조건의 평시 초당 처리가 2,462건으로 다른 조건(3,464~3,658건)보다 낮게 나온 것을 실행 간 편차 말고 다른 것으로 설명할 방법이 없습니다"**라고 적어 두었습니다. 그 30% 차이가 진짜 편차인지 실재하는 차이인지가 이 측정의 목적입니다. 실재하면 조건 비교 자체가 흔들립니다.

그다음은 A09, A17, A08 순서입니다. A08은 12조건 × (워밍업 30초 + 60초) × 3회라 한 시간 넘게 걸리니 마지막에 하세요.

### 3-2. F03 재측정 (데이터는 있고 본문 반영 안 됨)

데이터가 `sessions/F03-market-open-connection-storm/results/raw/`에 쌓여 있습니다. VU를 리틀의 법칙으로 2,600까지 올리고(1차는 900이라 3,401회가 발사되지 못했습니다), 앱 로그를 통째로 저장하고, `TOMCAT_MAX_THREADS`를 10·50·1000으로 바꿔 계층별 몫을 갈랐습니다. 그림도 재생성해 uploads에 넣었습니다.

**남은 일: 그 데이터로 본문과 README를 갱신하는 것입니다.** 확인할 것은 이것입니다.

- 중앙값 3.38초 중 풀 대기(상한 2초)와 Tomcat 스레드 계층의 몫이 각각 얼마인가

## 5. 오늘 반증된 것 (다시 고치지 마세요)

리뷰가 지적했지만 1차 문서로 확인하니 원래 글이 맞았던 것들입니다.

- **CFTC 배상액.** 리뷰가 "IB 실지급이 1억 200만 달러가 넘는데 글이 뺐다"고 했으나 명령서와 보도자료에 그 수치가 없습니다. 원문은 "272 customers for losses exceeding $82.57 million"입니다. 1억 달러대는 IB 자체 공시·언론 계열이고 CFTC 근거가 없습니다
- **RFC 9562의 규범 강도.** 리뷰가 무작위 시드를 MUST급으로 봤으나 RFC 2119 키워드 없는 평서형이고, 오히려 MAY로 완화돼 있습니다. 롤오버 MUST는 Method 1 전용이 아니라 1·2 공통입니다
- **금융감독원 집계.** 제가 지시서에 "금감원 출처 링크를 추가하라"고 썼는데 그 전제가 틀렸습니다. MTS 장애 190건은 국회 정무위 의원실이 증권사에서 제출받은 자료입니다
- **Netty 기본값.** 32/64KiB는 맞지만 javadoc에 없습니다. 상수가 private이라 소스가 출처여야 합니다
