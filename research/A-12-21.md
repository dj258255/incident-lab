- 출처: GitHub Blog "October 21 post-incident analysis" https://github.blog/2018-10-30-oct21-post-incident-analysis/ : 43초 단절, 서비스 저하 24시간 11분, 양쪽 DC에 서로 없는 쓰기 존재로 페일백 불가, Orchestrator가 Raft 쿼럼으로 US West 승격 — 카탈로그 수치 전부 일치 (원문)
- 판정: E1·축소 유지 : 원문 포스트모템 실재·수치 일치, 실제는 대륙 간 DC라 Docker 네트워크 축소 재현이 타당
- 메모: 정확 표기는 "24시간 11분". Orchestrator/Raft·GTID 분기 디테일도 원문에 있어 재현 설계와 부합

- 판정: E1·축소 유지 : 원문 실재·"5중 실패" 일치, Azure 실환경은 재현 불가라 복제 재구축 축소 재현이 타당
- 메모: 데이터 유실 규모 원문 수치 = 약 5,000 프로젝트·5,000 코멘트·700 계정, 다운타임 약 18시간. 재현 초점(pg_basebackup 재구축)은 사건 경위와 정확히 부합

## A14 XID
- 주장: XID wraparound는 PG 최악 장애급, 프로덕션 셧다운 실사례 존재 (E2, Percona 인용)
- 출처: Sentry Blog "Transaction ID Wraparound in Postgres" https://blog.sentry.io/transaction-id-wraparound-in-postgres/ : 2015-07-20 Sentry가 미국 업무시간 대부분 다운, wraparound 방어로 PG가 쓰기 거부("stop accepting commands when fewer than one million transactions left") 확인 (원문)
- 판정: 승격 제안 E2→E1 : 벤더 문서 경고(E2)를 넘어 Sentry 1차 포스트모템 원문이 실재 — "○○사가 공개한 장애"로 쓸 수 있음
- 메모: BattleMetrics 2022-03-27 등 후속 공개 사례도 존재. 재현이 방어선(경고·aggressive vacuum)까지만인 설계는 사건과 모순 없음

## A15 fsyncgate
- 주장: 리눅스 fsync 실패 후 조용한 유실, 2018년 PG의 PANIC 전환 (E1·축소, danluu.com)
- 출처: Dan Luu "fsync error handling" 아카이브 https://danluu.com/fsyncgate/ : Craig Ringer의 2018-03-28 pgsql-hackers 스레드("PostgreSQL's handling of fsync() errors is unsafe...") 원문 수록. fsync EIO 후 커널이 더티 페이지를 clean 처리해 재시도 fsync가 성공으로 둔갑 → 조용한 유실, 대응은 "PANIC on fsync() EIO" 확인 (원문 아카이브)
- 판정: E1·축소 유지 : 사건·연도·메커니즘·PANIC 전환 모두 일치. 실제 디스크 I/O 오류는 그대로 재현 불가라 dm-flakey/EIO 주입 축소 재현이 타당
- 메모: 성격상 기업 포스트모템이 아니라 공개 메일링리스트 스레드(1차 사료)임. 진짜 원문은 postgresql.org 아카이브고 danluu는 정리 아카이브. 재현의 data_sync_retry GUC는 2018년 말 PANIC 기본화 커밋과 함께 추가된 실제 파라미터로 설계와 부합

## A16 OOM Killer
- 주장: DB 프로세스는 oom_score 최상위 타깃, Percona·Crunchy "The Linux Assassin" 경고 (E2)
- 출처: Crunchy Data "Deep PostgreSQL Thoughts: The Linux Assassin" https://www.crunchydata.com/blog/deep-postgresql-thoughts-the-linux-assassin : Joe Conway, 2021-02-09. oom_score = 호스트 메모리 점유율×10 + oom_score_adj → 최대 메모리 소비자인 DB가 1순위 타깃, postmaster에 oom_score_adj=-1000·vm.overcommit_memory=2 권고 확인 (원문)
- 판정: E2 유지 : 특정 사건이 아닌 반복 함정 + 벤더 공식 블로그 경고 구도가 정확히 E2 정의에 부합
- 메모: Percona 측 근거는 "What To Do When MySQL Runs Out of Memory"(percona.com/blog) 존재를 검색 결과로 확인(본문 직접 접속은 안 함). 재현 항목(oom_score_adj·overcommit)이 Crunchy 권고와 일치

## A17 UUID 스플릿
- 주장: 랜덤 UUIDv4 PK가 페이지 스플릿·충전율 붕괴·테이블 비대·insert 절벽 유발, Percona·PlanetScale 반복 경고 (E2)
- 출처: PlanetScale "The Problem with Using a UUID Primary Key in MySQL" https://planetscale.com/blog/the-problem-with-using-a-uuid-primary-key-in-mysql : 순차 PK는 페이지 약 94% 충전, 랜덤 PK는 50%까지 하락, B+트리 리밸런싱 비용, UUIDv6/v7 권고 확인 (원문)
- 출처: Percona "UUIDs are Popular, but Bad for Performance, Let's Discuss" https://www.percona.com/blog/uuids-are-popular-but-bad-for-performance-lets-discuss/ : 검색 결과로 존재·논지(비순차 insert→페이지 스플릿→낮은 충전율) 확인, 본문 직접 접속은 안 함 (2차 확인)
- 판정: E2 유지 : 특정 사건 아닌 반복 함정 + 벤더 공식 블로그 2곳 경고로 E2 정의 부합
- 메모: "테이블 2배"는 PlanetScale 본문에 명시 문구로는 확인 못 함 — 충전율 94%→50%에서 도출되는 근사치(약 1.9배)이므로 블로그화 시 "2배 가까이"로 완곡 표현 권장. insert 절벽 실측치는 Percona 벤치마크 쪽이므로 수치 인용하려면 원문 재확인 필요

## A19 SLRU 절벽
- 주장: GitLab의 랜덤 재발 "네시" 장애 — SAVEPOINT 다중 중첩+롱 트랜잭션으로 replica TPS 360k→50k, 공개 재현 스크립트 존재 (E1)
- 출처: GitLab Blog "Why we spent the last month eliminating PostgreSQL subtransactions" https://about.gitlab.com/blog/2021/09/29/why-we-spent-the-last-month-eliminating-postgresql-subtransactions/ : 2021-06-24부터 랜덤 재발한 스톨을 "Nessie"로 명명, subtrans SLRU 캐시 오버플로 메커니즘, Nikolay Samokhvalov 재현에서 replica 약 360k→50k TPS 절벽, 재현 케이스 공개 확인 (원문)
- 판정: E1 유지 : 1차 포스트모템 원문 + 수치·별명·재현 스크립트까지 전부 일치
- 메모: 정확한 트리거는 두 갈래 — (1) 트랜잭션당 서브트랜잭션 64개(PGPROC_MAX_CACHED_SUBXIDS) 초과 오버플로, (2) replica에서는 롱 트랜잭션+동시 쓰기 조건이면 SAVEPOINT 단 1개로도 발동. 재현 설계(SAVEPOINT 중첩)는 (1) 경로라 원문과 부합하나 글에서 "64개 초과가 유일 조건"처럼 쓰지 말 것
