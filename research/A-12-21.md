## A17 UUID 스플릿
- 주장: 랜덤 UUIDv4 PK가 페이지 스플릿·충전율 붕괴·테이블 비대·insert 절벽 유발, Percona·PlanetScale 반복 경고 (E2)
- 출처: PlanetScale "The Problem with Using a UUID Primary Key in MySQL" https://planetscale.com/blog/the-problem-with-using-a-uuid-primary-key-in-mysql : 순차 PK는 페이지 약 94% 충전, 랜덤 PK는 50%까지 하락, B+트리 리밸런싱 비용, UUIDv6/v7 권고 확인 (원문)
- 출처: Percona "UUIDs are Popular, but Bad for Performance, Let's Discuss" https://www.percona.com/blog/uuids-are-popular-but-bad-for-performance-lets-discuss/ : 검색 결과로 존재·논지(비순차 insert→페이지 스플릿→낮은 충전율) 확인, 본문 직접 접속은 안 함 (2차 확인)
- 판정: E2 유지 : 특정 사건 아닌 반복 함정 + 벤더 공식 블로그 2곳 경고로 E2 정의 부합
- 메모: "테이블 2배"는 PlanetScale 본문에 명시 문구로는 확인 못 함 — 충전율 94%→50%에서 도출되는 근사치(약 1.9배)이므로 블로그화 시 "2배 가까이"로 완곡 표현 권장. insert 절벽 실측치는 Percona 벤치마크 쪽이므로 수치 인용하려면 원문 재확인 필요
- 추가 출처(2026-07-29, A17 세션 구축 중): RFC 9562 https://www.rfc-editor.org/rfc/rfc9562.html 에서 세 대목 확인(원문). (1) UUIDv7 기본형은 타임스탬프 뒤 74비트를 난수로 채우고, 카운터는 "Alternatively, implementations MAY fill the 74 bits, jointly, with a combination of the following subfields ... to guarantee additional monotonicity within a millisecond" 로 선택 사항 (2) 6.2절 Method 1: "If present, a fixed bit-length counter MUST be positioned immediately after the embedded timestamp." (3) "Time-ordered monotonic UUIDs benefit from greater database-index locality because the new values are near each other in the index ... can be one order of magnitude or more."
- A17 실측으로 확인된 것(수치는 sessions/A17-uuid-page-split/): 랜덤 PK의 대가가 둘로 분리된다. 페이지 충전율(공간)은 밀리초 안 순서가 없으면 UUIDv7도 UUIDv4와 같이 무너진다(54.7% 대 56.7%). 인덱스 지역성(시간)은 밀리초 단위 정렬만으로도 지켜진다(적재 중 디스크 읽기 115쪽 대 12,613쪽). 밀리초 안 카운터를 넣으면 충전율이 91.4%로 순차 BIGINT(91.9%)와 같아진다
- 인용 주의: RFC의 "one order of magnitude" 는 인덱스 지역성에 대한 서술이고 충전율 이야기가 아니다. 충전율이 카운터 유무로 갈린다는 것은 RFC에도 PlanetScale에도 없는 자체 실측이므로 남의 주장으로 인용하지 말 것. 또 이 결과는 "밀리초당 20행" 조건에 묶여 있다(적재 속도 초당 약 2만 행). 처리량이 다르면 밀리초당 행 수가 달라져 결과가 달라진다

## A19 SLRU 절벽
- 주장: GitLab의 랜덤 재발 "네시" 장애 — SAVEPOINT 다중 중첩+롱 트랜잭션으로 replica TPS 360k→50k, 공개 재현 스크립트 존재 (E1)
- 출처: GitLab Blog "Why we spent the last month eliminating PostgreSQL subtransactions" https://about.gitlab.com/blog/2021/09/29/why-we-spent-the-last-month-eliminating-postgresql-subtransactions/ : 2021-06-24부터 랜덤 재발한 스톨을 "Nessie"로 명명, subtrans SLRU 캐시 오버플로 메커니즘, Nikolay Samokhvalov 재현에서 replica 약 360k→50k TPS 절벽, 재현 케이스 공개 확인 (원문)
- 판정: E1 유지 : 1차 포스트모템 원문 + 수치·별명·재현 스크립트까지 전부 일치
- 메모: 정확한 트리거는 두 갈래 — (1) 트랜잭션당 서브트랜잭션 64개(PGPROC_MAX_CACHED_SUBXIDS) 초과 오버플로, (2) replica에서는 롱 트랜잭션+동시 쓰기 조건이면 SAVEPOINT 단 1개로도 발동. 재현 설계(SAVEPOINT 중첩)는 (1) 경로라 원문과 부합하나 글에서 "64개 초과가 유일 조건"처럼 쓰지 말 것

## A20 데브시스터즈 CockroachDB 쿼럼 손실
- 주장: 데브시스터즈 쿠키런: 킹덤에서 CockroachDB 클러스터가 과반 노드 손실로 Raft 쿼럼을 잃어 SQL이 전면 중단됐고 약 36시간 만에 복구했다
- 출처: 데브시스터즈 기술블로그 "쿠키런: 킹덤 데이터베이스 스토리지 레이어 복원기" https://tech.devsisters.com/posts/crk-launch-storage-postmortem/ : 쿼럼 손실 메커니즘 — "CockroachDB는 Raft라는 컨센서스 알고리즘을 차용하므로 동작하려면 적어도 과반 이상의 노드가 필요한데, 하필 그 이상의 노드가 영향을 받게 되었으므로 노드 단위 장애에서 클러스터 전역적인 장애로 번지게 됩니다." 전면 중단 — "새벽 2시 42분, 다시 데이터베이스에서 모든 쿼리와 요청이 실패하는 것을 관측하자마자 2차 긴급 점검에 들어갈 수 밖에 없었습니다." 시간 — "런칭 후 4일 만에 기술적인 문제로 인해 발생했던 약 36시간 동안의 서비스 장애", "오전 8시 30분, 총 점검 시간 36시간 29분 만에 임시점검을 종료하게 되었습니다." 규모 — "총 24대의 노드로 클러스터를 구성하였으므로", "저희의 경우는 과반 이상인 16대의 노드가 영향을 받게 되었습니다", "7개의 복제본을 저장하도록 설정되어". 원인 — "Ballast 파일을 생성하기 위해 미리 작성해둔 스크립트를 실행하였는데 Ballast 파일의 경로가 잘못 설정되어 Block Device를 가리키고 있었고", "스크립트의 실행 결과 파티션을 덮어 쓰게 되었습니다." 손실율 — "남아있는 노드가 7대이므로 우선 데이터의 완전 손실율이 C(16, 7) / C(24, 7) ~= 3.3%에 불과" (원문)
- 판정: E1 유지 : 기업 기술블로그 포스트모템 원문이 존재하고 "Raft 쿼럼 과반 손실 → 클러스터 전역 SQL 중단"이라는 핵심 메커니즘이 원문 문장으로 직접 뒷받침된다. 36시간도 원문과 일치
- 메모: (1) "36시간 복구"는 정확하나 원문에 시간이 둘이다 — 서비스 재개는 "이튿날 23시 37분, 30시간 50분", 임시점검 완전 종료가 "총 점검 시간 36시간 29분". 36시간을 쓸 거면 "총 점검 36시간 29분"으로 붙여 쓸 것 (2) 검색하면 "쿠키런: 킹덤, 총 56시간의 긴급 점검 회고"가 같이 나오는데 이건 2021-02 AWS 도쿄 리전 AZ 장애(crk-aws-az-failure-postmortem)로 완전히 다른 사건이다. 절대 섞지 말 것 (3) 카탈로그 재현 설계 "3노드 → 2노드 kill"은 원문 사실이 아니다. 원문은 24노드 중 16노드 영향, replication factor 7이며 노드를 kill한 게 아니라 ballast 스크립트 경로가 Block Device를 가리켜 파티션을 덮어쓴 사고다. 글에서는 "원문은 24노드/16노드 영향, 우리는 3노드→2노드 kill로 축소 재현"이라고 반드시 구분할 것. 원인을 "노드를 죽였다"로 쓰면 오보 (4) 인용 가능 = 24노드, 16노드 영향, 복제본 7개, 36시간 29분, 완전 손실율 3.3%. 인용 금지 = 56시간, "3노드", RF=3

## A21 Figma식 수직 분할·논리 복제 이전
- 주장: Figma가 단일 RDS 포화로 테이블을 그룹 단위 수직 분할하고, PostgreSQL 논리 복제로 특정 테이블만 무중단 이전한 뒤 커넥션을 스위칭했다
- 출처: Figma "The growing pains of database architecture" https://www.figma.com/blog/how-figma-scaled-to-multiple-databases/ : 단일 RDS 포화 — "We were still using a single, large Amazon RDS database to persist most of our metadata", "We observed upwards of 65% CPU utilization during peak traffic due to the volume of queries serviced by one database.", 이미 "from r5.12xlarge to r5.24xlarge"까지 올린 상태. 테이블 그룹 선정 — "There were two important factors: 1. Impact ... 2. Isolation", "We looked at average active sessions (AAS) for queries". 논리 복제 선택 이유 — "We chose logical replication because it allows us to: 1. Port over a subset of tables ... 2. Replicate to a database which is running a different Postgres major version ... 3. Set up reverse replication". 인덱스 — "By removing indexes in the destination database and rebuilding the indexes after the initial copying of data, we reduced the copy time to a matter of hours." 컷오버 — "While PgBouncer pauses new connections, we revoke clients' query privileges on the partitioned tables in the original database.", "we sample an LSN from our original database once we're confident that there are no new writes, we can then wait for the replica to replay past this LSN.", "we stop replication and promote the replica to a new database." 영향 — "During each operation, we observed a ~30 second period of partial availability impact (~2% of requests dropped).", "Our first operation involved moving two high-traffic tables, while our final operation in October 2022 involved 50." (원문)
- 출처: Figma "How Figma's Databases Team Lived to Tell the Scale" https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/ : 배경 규모 — "In 2020, we were running a single Postgres database hosted on AWS's largest physical instance", "by the end of 2022, we had built out a distributed architecture with caching, read replicas, and a dozen vertically partitioned databases", "Figma's database stack has grown almost 100x since 2020". 후속 수평 샤딩은 별건 — "shipped our first horizontally sharded table in September 2023" (원문)
- 판정: E1 유지 : Figma 엔지니어링 블로그 원문 2편이 존재하고 "단일 RDS 포화 → 테이블 그룹 수직 분할 → 논리 복제 → PgBouncer pause 후 커넥션 스위칭" 전 단계가 원문 문장으로 확인된다. 다만 "무중단" 표현은 원문과 어긋난다(메모 참조)
- 메모: (1) "무중단"은 원문 주장이 아니다. 원문은 "~30 second period of partial availability impact (~2% of requests dropped)"라고 명시하므로 카탈로그 문구를 그대로 쓰면 과장이다. "약 30초 부분 가용성 저하(요청 약 2% 드롭)로 이전"으로 쓸 것 (2) "단일 RDS 포화"의 근거 수치는 피크 CPU 65%다. 100% 포화가 아니라 "피크 65%에서 이미 위험 신호로 보고 움직였다"가 정확하고, 인스턴스를 r5.24xlarge까지 이미 올린 상태였다는 점을 같이 써야 설득력이 산다 (3) 카탈로그의 "PG 2대"는 재현 축소판이고 원문 최종 상태는 "a dozen vertically partitioned databases", 1회 작업 단위도 처음 2개 → 2022-10 마지막엔 50개 테이블이었다. "2대"를 Figma의 사실처럼 쓰지 말 것 (4) 재현에 꼭 넣을 원문 디테일 셋 = 대상 선정이 AAS 기반이었다는 점, 대상 DB 인덱스를 지우고 초기 복사 후 재생성해 복사 시간을 시간 단위로 줄인 점, 롤백용 역방향 복제를 걸어둔 점(특히 역방향 복제는 세션의 차별점) (5) 컷오버 순서는 원문 그대로 = PgBouncer pause → 원본 권한 revoke → 잔여 쿼리 cancel → LSN 샘플링 후 replica가 그 LSN을 넘어설 때까지 대기 → 복제 중단·replica 승격 → 역방향 복제 설정 → PgBouncer resume (6) 인용 금지 = "ten seconds of partial availability"와 "September 2023 첫 수평 샤딩"은 수평 샤딩 단계 수치다.
