## B39 XXE·billion laughs
- 주장: DTD 엔티티 재귀 확장으로 소량의 XML 입력이 GB급으로 팽창해 메모리를 고갈시키고, 외부 엔티티(XXE)까지 허용되면 파일 유출·SSRF로 번진다
- 출처: OWASP XML External Entity Prevention Cheat Sheet https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html : "An XXE attack occurs when untrusted XML input with a reference to an external entity is processed by a weakly configured XML parser, and this attack could be used to stage multiple incidents, including: A denial of service attack on the system / A Server Side Request Forgery (SSRF) attack / The ability to scan ports from the machine where the parser is located / Other system impacts." 및 "Disabling DTDs also makes the parser secure against denial of services (DOS) attacks such as Billion Laughs.", "The safest way to prevent XXE is always to disable DTDs (External Entities) completely." (원문)
- 출처: OWASP www-community "XML External Entity (XXE) Processing" https://owasp.org/www-community/vulnerabilities/XML_External_Entity_(XXE)_Processing : "This attack may lead to the disclosure of confidential data, denial of service, server side request forgery, port scanning from the perspective of the machine where the parser is located, and other system impacts." **이 페이지에는 billion laughs라는 명칭도, 팽창 크기 수치도 없다**(확인한 사실) (원문)
- 출처: CWE-776 "Improper Restriction of Recursive Entity References in DTDs('XML Entity Expansion')" https://cwe.mitre.org/data/definitions/776.html : "If the DTD contains a large number of nested or recursive entities, this can lead to explosive growth of data when parsed, causing a denial of service." / 예제 "Ultimately, we reach entity THIRTYTWO, which will expand to 2^32 characters in length, or 4 GB." / "recursive entity references allow the attacker to expand data exponentially, quickly consuming all system resources." (원문)
- 출처: NVD CVE-2003-1564 https://nvd.nist.gov/vuln/detail/CVE-2003-1564 (NVD API 2.0으로 조회) : "libxml2, possibly before 2.5.0, does not properly detect recursion during entity expansion, which allows context-dependent attackers to cause a denial of service (memory and CPU consumption) via a crafted XML document containing a large number of nested entity references, aka the 'billion laughs attack.'" CVSS v3.1 6.5 MEDIUM / v2.0 9.3 HIGH, 공개 2003-12-31 (원문)
- 판정: E2 유지 : 특정 기업 장애 포스트모템은 없지만 OWASP 공식 치트시트 + MITRE CWE-776 전용 항목 + "billion laughs attack"을 이름으로 박아둔 실제 CVE까지 확보했다. E2 정의에 정확히 부합하고 근거 밀도는 E2 중에서도 상위다
- 메모: 인용 가능 = CWE-776의 "2^32 characters in length, or 4 GB"(단 **32단계 이중화 예제 기준**임을 반드시 병기 — 고전 billion laughs와 다른 변형이다), CVE-2003-1564의 CVSS 6.5/9.3. 인용 금지 = 흔히 도는 "1KB 입력이 3GB로"(10단계×10배=10^9) 계산은 위키피디아 계열 서술이고 이번에 원문 확인 못 했다. 쓰려면 "일반적으로 인용되는"이라고 완충하거나 CWE 예제 수치로 갈아탈 것. **표기 주의 = billion laughs를 OWASP www-community 페이지 근거로 인용하면 틀린다**(거기 없음). 명칭이 나오는 OWASP 문서는 Cheat Sheet 쪽이고 거기서도 위키 링크 한 줄뿐이므로, 팽창 메커니즘 설명의 1차 근거는 CWE-776으로 잡을 것. "XXE로 RCE까지"는 www-community에 해당 섹션이 있긴 하나 특수 조건부이므로 일반화 금지 — 카탈로그가 "파일 유출·SSRF까지"로 멈춘 건 정확한 선택이니 그대로 둘 것. 재현 주의 = "기본 파서에 billion laughs"라는 서술은 최신 런타임에서 안 맞을 수 있다(다수 파서가 DTD 기본 비활성 또는 엔티티 확장 한도 내장). 착수 시 사용할 파서·버전의 기본값을 직접 찍어보고 "기본값" 표현을 확정할 것

## B43 expand-contract 마이그레이션 실패
- 주장: 컬럼 추가·삭제 순서가 뒤집히면 배포 중 없는 컬럼을 참조하고, 수백만 행 테이블에 `ADD COLUMN NOT NULL`을 걸면 ACCESS EXCLUSIVE 락이 전 쿼리를 차단한다
- 출처: PostgreSQL 18 문서 ALTER TABLE https://www.postgresql.org/docs/current/sql-altertable.html : "Note that the lock level required may differ for each subform. An ACCESS EXCLUSIVE lock is acquired unless explicitly noted. When multiple subcommands are given, the lock acquired will be the strictest one required by any subcommand." 예외로 명시된 것은 ADD FOREIGN KEY(SHARE ROW EXCLUSIVE), SET STATISTICS·VALIDATE CONSTRAINT(SHARE UPDATE EXCLUSIVE) 등이며 **ADD COLUMN은 예외 목록에 없다 → ACCESS EXCLUSIVE가 맞다.** 또한 "Adding a CHECK or NOT NULL constraint requires scanning the table to verify that existing rows meet the constraint, but does not require a table rewrite." (원문)
- 출처: PostgreSQL 18 문서 ALTER TABLE Notes(같은 페이지) : "When a column is added with ADD COLUMN and a non-volatile DEFAULT is specified, the default value is evaluated at the time of the statement and the result stored in the table's metadata... **The value will be only applied when the table is rewritten, making the ALTER TABLE very fast even on large tables.** If no column constraints are specified, NULL is used as the DEFAULT. **In neither case is a rewrite of the table required.**" (원문)
- 출처: PostgreSQL 11 릴리스 노트 https://www.postgresql.org/docs/release/11.0/ (릴리스일 2018-10-18) : "Allow ALTER TABLE to add a column with a non-null default without doing a table rewrite (Andrew Dunstan, Serge Rielau) — This is enabled when the default value is a constant." (원문)
- 출처: PostgreSQL 18 문서 Explicit Locking https://www.postgresql.org/docs/current/explicit-locking.html : ACCESS EXCLUSIVE는 "Conflicts with locks of all modes" / "This mode guarantees that the holder is the only transaction accessing the table in any way." / "The SELECT command acquires a lock of this mode on referenced tables."(ACCESS SHARE) → **SELECT조차 충돌한다는 "전 쿼리 차단"은 정확하다** (원문)
- 출처: PostgreSQL 18 문서 Client Connection Defaults https://www.postgresql.org/docs/current/runtime-config-client.html : "lock_timeout — Abort any statement that waits longer than the specified amount of time while attempting to acquire a lock... **A value of zero (the default) disables the timeout.**" / "Setting lock_timeout in postgresql.conf is not recommended because it would affect all sessions." (원문)
- 판정: E2 유지, 단 **카탈로그 서술 후반부 정정 필수** : 락 수준(ACCESS EXCLUSIVE)과 "SELECT까지 전부 차단"은 현재 PG 18 공식 문서로도 그대로 참이다. 그러나 **"대형 테이블이라서 오래 잡힌다"는 인과는 PG 11(2018-10-18) 이후 상수 기본값 케이스에서 더 이상 성립하지 않는다** — 공식 문서가 "making the ALTER TABLE very fast even on large tables"라고 정면으로 반박한다. 행 수에 비례해 락이 길어지는 경우는 (a) PG 10 이하 (b) volatile 기본값 등 테이블 재작성을 유발하는 형태 (c) 컬럼 타입 변경 (d) 기존 컬럼에 대한 NOT NULL/CHECK 추가(재작성은 없지만 전체 스캔 필요)로 한정된다. 이 조건을 명시하면 E2로 충분히 유효하고, 명시하지 않으면 사실관계가 틀린 글이 된다
- 메모: 인용 가능 = 위 원문 인용 5건 전부, PG 11 릴리스일 2018-10-18, `lock_timeout` 기본값 0(=무제한). 이 기본값 0이 "락 대기 타임아웃" 서사의 핵심 훅이다. 인용 금지 = "수백만 행이면 ALTER가 N초/N분 걸린다" 류 구체 수치(어떤 공식 문서에도 없음). 쓰려면 직접 측정값으로 쓰고 PG 버전·행 수·기본값 종류(상수/volatile)를 함께 적을 것. **재현 설계 지침 = 그냥 최신 PG에 상수 기본값으로 `ADD COLUMN`을 걸면 밀리초 단위로 끝나서 재현에 실패한다.** 세션에서 쓸 PG 버전을 먼저 못 박고 "PG 11 이전 vs 이후"를 대비시키거나 volatile 기본값으로 재작성을 유도해야 카탈로그가 말한 장시간 락이 실제로 나온다. **확인 못 한 것(단정 금지)** = ① 장기 실행 쿼리 뒤에 대기하던 ALTER가 후속 쿼리까지 줄세우는 락 큐잉/head-of-line blocking은 원문 문장을 확보하지 못했다(explicit-locking은 "충돌한다"까지만) ② 비어 있지 않은 테이블에 DEFAULT 없이 `ADD COLUMN ... NOT NULL`을 걸면 에러로 실패한다는 동작도 원문 미확인 — 직접 실행해 로그를 증거로 남길 것 ③ 주장 전반부("컬럼 추가·삭제 순서가 뒤집히면 배포 중 없는 컬럼 참조")는 **이번 조사에서 아무 출처도 확보하지 않았다.** 자명한 배포 순서 문제라 폐기할 성질은 아니지만 공식 문서 근거가 있는 것처럼 쓰지 말고 원리 설명과 자체 재현 로그로만 뒷받침할 것

## B47 Roblox 2021 73시간 장애
- 주장: 2021년 10월 Roblox 73시간 장애의 원인은 Consul streaming 경합 + BoltDB freelist가 삭제 페이지를 회수 못 한 것이며, 텔레메트리가 Consul에 순환 의존해 진단이 54시간 지연됐다
- 출처: Roblox "Roblox Return to Service 10/28-10/31 2021" https://about.roblox.com/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021/ (blog.roblox.com → corp.roblox.com → about.roblox.com 301 두 번) : "Starting October 28th and fully resolving on October 31st, Roblox experienced a 73-hour outage." / BoltDB — "This 4.2GB log store is only storing 489MB of actual data (including all the index internals). 3.8GB is 'empty' space." / "That means, for every log append (each Raft write after some batching), a new 7.8MB freelist was also being written out to disk even though the actual raw data being appended was 16kB or less." / streaming — "While streaming was overall more efficient, it used fewer concurrency control elements (Go channels) in its implementation than long polling." (원문)
- 출처: 같은 문서, 순환 의존 : "There was a circular dependency between our telemetry systems and Consul, which meant that when Consul was unhealthy, we lacked the telemetry data that would have made it easier for us to figure out what was wrong." / "Critical monitoring systems that would have provided better visibility into the cause of the outage relied on affected systems, such as Consul. - 판정: E1·축소 유지 : "73시간", "4.2GB 중 실데이터 489MB", "텔레메트리-Consul 순환 의존"은 원문 문장으로 확인됐다. 다만 **"진단 54시간 지연"은 원문에 없는 수치**라 그 부분만 근거 없음이다. 데모 범위를 "순환 의존 최소 재현"으로 좁힌 판단은 그대로 타당하다

## B48 Prometheus 라벨 카디널리티 폭발
- 주장: `user_id` 같은 고유값을 라벨로 붙이면 시계열이 곱셈으로 폭증해 Prometheus가 OOM에 빠지며, 그 규모 예시로 "customer_id 1만 값이면 카운터 1개가 1,200만 시계열"이 된다
- 출처: Prometheus 공식 문서 "Metric and label naming" https://prometheus.io/docs/practices/naming/ : CAUTION 박스 — "Remember that every unique combination of key-value label pairs represents a new time series, which can dramatically increase the amount of data stored. Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values." (원문)
- 출처: Prometheus 공식 문서 "Instrumentation / Do not overuse labels" https://prometheus.io/docs/practices/instrumentation/ : "Each labelset is an additional time series that has RAM, CPU, disk, and network costs." / "try to keep the cardinality of your metrics below 10, and for metrics that exceed that, aim to limit them to a handful across your whole system." (원문)
- 출처: (반증) OpenObserve "The Prometheus Cardinality Bomb" https://openobserve.ai/blog/prometheus-data-cardinality/ : 여기 실린 예시는 "3 environments × 5 services × 10 status codes yields 150 time series" → "× 1,000,000 user_ids = 150,000,000 series"로 **카탈로그의 1,200 × 10,000 = 1,200만과 전제도 숫자도 다르다.** 검색 상위 나머지도 벤더 공식 문서가 아닌 SEO성 블로그였고 1,200만의 1차 출처는 확보하지 못했다 (원문 / 나머지는 2차)
- 판정: E2 유지, 단 **"1,200만 시계열" 수치는 E4로 분리 강등** : 현상 자체는 Prometheus 공식 문서가 CAUTION 박스로 "user ID를 라벨로 쓰지 마라"라고 명시적으로 경고하는 교과서적 함정이라 E2 조건을 충분히 만족한다. 그러나 카탈로그가 인용한 구체 수치 1,200만은 1차 출처가 없다
- 메모: 인용 가능 = 위 Prometheus 공식 문서 두 문장(특히 "such as user IDs, email addresses, or other unbounded sets of values"와 "keep the cardinality of your metrics below 10"). 이 둘만으로 E2 논지는 완결된다. **인용 금지 = "customer_id 1만 값이면 카운터 1개가 1,200만 시계열"을 남의 말처럼 인용하는 것**(출처 없음). 둘 중 하나로 처리할 것 — (a) 전제를 드러낸 자기 계산으로 바꿔 쓴다("method 4 × status_code 6 × endpoint 50 = 카운터 1개당 1,200 시계열, 여기에 customer_id 1만을 곱하면 1,200만"처럼 곱셈 재료를 다 보여주고 "가정한 수치"라고 밝힘) (b) 아예 빼고 데모에서 실측한 `prometheus_tsdb_head_series` 값을 쓴다. 이 행은 재현 난도가 "쉬움"이라 **(b)를 권한다** — 내 서버에서 직접 뽑은 숫자가 남의 블로그 숫자보다 훨씬 강하다. "시계열당 RAM 3~4KB", "100만 시계열이면 4~6GB" 같은 흔히 도는 수치도 1차 출처를 못 찾았으니 실측치로 대체할 것

## B49 Protobuf 필드 번호 재사용
- 주장: 삭제해 은퇴시킨 필드 번호를 재사용하면 구 바이너리가 새 정의로 값을 조용히 잘못 해석해 크래시 없이 틀린 결과가 나오며, 대책은 `reserved`와 스키마 레지스트리의 BACKWARD 호환성 검사다
- 출처: Protocol Buffers 공식 문서 "Language Guide (proto3)" https://protobuf.dev/programming-guides/proto3/ : (Reserved Fields) "Field numbers should never be reused." / "Never take a field number out of the reserved list for reuse with a new field definition." / "If you update a message type by entirely deleting a field, or commenting it out, future developers can reuse the field number when making their own updates to the type. This can cause severe issues, as described in Consequences of Reusing Field Numbers." / (Consequences) "Reusing a field number makes decoding wire-format messages ambiguous." / 결과 목록 그대로 "Developer time lost to debugging", "A parse/merge error (best case scenario)", "Leaked PII/SPII", "Data corruption" / "The protobuf wire format is lean and doesn't provide a way to detect fields encoded using one definition and decoded using another." (원문)
- 출처: Protocol Buffers 공식 문서 "Proto Best Practices" https://protobuf.dev/best-practices/dos-donts/ : "Never re-use a tag number. It messes up deserialization. Even if you think no one is using the field, don't re-use a tag number." / "When you delete a field that's no longer used, reserve its tag number so that no one accidentally re-uses it in the future. Just `reserved 2, 3;` is enough." / "Almost never change the type of a field; it'll mess up deserialization, same as re-using a tag number." (원문)
- 판정: E2 유지(강력) : protobuf.dev가 별도 절(Reserved Fields, Consequences of Reusing Field Numbers)을 할애해 "Data corruption", "Leaked PII/SPII"까지 명시적으로 경고한다. E2 정의의 교과서적 사례. 특정 사건 문서가 없으므로 E1 승격은 불가
- 메모: **표현 정확도 주의 = 카탈로그의 "크래시 없이 틀린 결과"는 원문보다 세다.** 원문은 오히려 "A parse/merge error (**best case scenario**)"를 결과 중 하나로 넣는다. 즉 파싱 에러로 시끄럽게 터지는 건 운이 좋은 경우고 조용한 오염은 그보다 나쁜 경우다. 조용한 오염을 재현하려면 **와이어 타입이 같은 재사용**(int32 → bool/enum/int64/uint32 등 varint 계열끼리)을 골라야 한다. int32 → string처럼 와이어 타입이 바뀌면 대개 파싱 에러가 나서 "조용히"가 성립하지 않는다. 이 선택 이유를 글에 적으면 깊이가 산다. 인용 가능 = "Data corruption", "Leaked PII/SPII", "makes decoding wire-format messages ambiguous", "reserved 2, 3;" 전부 공식 문서 원문. 인용 금지 = 재사용 사고의 발생 빈도·업계 통계(확인된 출처 없음). BACKWARD 호환성 검사는 protobuf.dev가 아니라 스키마 레지스트리(Confluent 등) 쪽 개념이므로 별도 출처를 달거나 "레지스트리를 쓰면 CI에서 막을 수 있다"는 우리 제안으로 분리할 것 — 이번 조사에서 레지스트리 문서는 확인하지 않았다

## B51 ForkJoinPool commonPool 오염
- 주장: parallelStream이 JVM 전역 commonPool을 공유하므로 거기서 블로킹 IO를 돌리면 무관한 병렬 작업까지 굶으며, 국내 실장애 회고 "parallelStream 남용으로 인한 장애 경험기"(2019)가 존재한다
- 출처: Java SE 21 API `java.util.concurrent.ForkJoinPool` javadoc https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ForkJoinPool.html : 전역 공유 — "A static `commonPool()` is available and appropriate for most applications. The common pool is used by any ForkJoinTask that is not explicitly submitted to a specified pool." 블로킹 경고 — "However, no such adjustments are guaranteed in the face of blocked I/O or other unmanaged synchronization. The nested `ForkJoinPool.ManagedBlocker` interface enables extension of the kinds of synchronization accommodated." 종료 불가 — "Returns the common pool instance.
