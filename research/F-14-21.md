## F15 WebSocket 시세 슬로우 컨슈머
- 주장: 백프레셔가 없으면 느린 클라이언트 하나로 서버 송신 버퍼가 무한 증가해 OOM에 이르며, 바운디드 큐·conflation·느린 소비자 절단이 해법이다
- 출처: Spring Framework Reference "Performance"(WebSocket/STOMP) https://docs.spring.io/spring-framework/reference/web/websocket/stomp/configuration-performance.html : "If they are slow or on low bandwidth, they take longer to consume messages and put a burden on the thread pool." / "two additional properties relate to the sending of messages: `sendTimeLimit` and `sendBufferSizeLimit`. You can use those methods to configure how long a send is allowed to take and how much data can be buffered when sending messages to a client." / "at any given time, only a single thread can be used to send to a client. All additional messages, meanwhile, get buffered" (원문)
- 출처: Spring Javadoc `ConcurrentWebSocketSessionDecorator` https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/socket/handler/ConcurrentWebSocketSessionDecorator.html : "If a `send` is slow, subsequent attempts to send more messages from other threads will not be able to acquire the flush lock, and messages will be buffered instead. At that time, the specified buffer-size limit and send-time limit will be checked, and **the session will be closed if the limits are exceeded**." / overflowStrategy = "the overflow strategy to use; **by default the session is terminated**" — **"느린 소비자 절단"이 프레임워크 기본 동작이라는 직접 근거** (원문)
- 출처: Netty `Channel` Javadoc https://netty.io/4.1/api/io/netty/channel/Channel.html : "Any write requests made when this method returns `false` are queued until the I/O thread is ready to process the queued write requests." 큐잉은 명시하나 한도·OOM 언급은 없음 (원문)
- 출처: Netty `WriteBufferWaterMark` Javadoc : 고수위 초과 시 "Channel.isWritable() will start to return false". **DEFAULT 필드는 있으나 실제 기본 바이트값은 이 페이지에 표시되지 않았다** (원문, 기본값 미확인)
- 판정: E2 유지 : Spring 공식 문서·Javadoc이 "느린 클라이언트 → 버퍼링 → 한도 초과 시 세션 종료"라는 인과와 대응책을 직접 서술한다. 단 **"WebSocket 서버 OOM의 대표 원인"을 그대로 뒷받침하는 공식 문서는 못 찾았다** — 어떤 벤더 문서도 OOM을 명시하지 않는다
- 실측 결과(2026-07-29, F15 세션 완료). OOM은 자체 재현으로 확인했다: 힙 128MB, 초당 3,000틱, 느린 구독자 1명(32KB/s)에서 무제한 큐가 86초에 java.lang.OutOfMemoryError. 느린 구독자 몫 큐가 95.58MB로 힙의 75%를 차지. 카탈로그 행에서 OOM을 벤더 근거로 적던 서술은 이 실측 기준으로 고쳤다
- 더 중요한 실측: **OOM보다 앞에 더 흔한 실패가 있다.** 큐 없이 브로드캐스트 스레드가 직접 sendMessage를 부르면 힙은 45.5MB로 멀쩡한데 발행량이 2,909에서 142/s로 무너진다(생산자 정지 44.0초/45초). 정상 구독자 5명의 최종 수신 시퀀스가 3,265로 대조군 129,138의 40분의 1. 메모리 지표만 보는 관측으로는 안 잡힌다
- 반직관 실측: 아무것도 안 읽는 구독자(1,630/s)가 초당 32KB만 읽는 구독자(142/s)보다 서버에 덜 해롭다. 완전 정지 쪽은 최대 지연이 3회 모두 20,028~20,101ms로 20초에서 끊기는데, 내장 Tomcat이 블로킹 송신을 포기하는 지점으로 보인다. **문서에서 기본값을 확인하지 않았으므로 "Tomcat 기본값이 20초다"라고 단정해 쓰지 말 것**
- 절단 임계값도 수치가 갈린다: 1MB/3초 판정은 정상 구독자 p95가 175ms(3회 중 한 회차는 1,209ms)까지 오르고, 512KB/1초는 4.3초에 끊고 p95 1ms. Spring 데코레이터에 같은 512KB를 주면 4.3초 절단에 p95 2ms로 직접 구현과 사실상 같다
- 메모: **B09과는 중복 아님** — B09은 Kafka 컨슈머 그룹 프로토콜(stop-the-world 리밸런스)로 lag이 커지는 얘기라 데이터는 브로커 디스크에 있고 서버 메모리는 안 는다. F15는 서버 힙에 클라이언트별 팬아웃 버퍼가 쌓이는 얘기다 — 고장 지점(브로커 디스크 vs 서버 힙)과 해법(cooperative rebalancing vs conflation·절단)이 다르므로 각도만 명확히 갈라 쓰면 된다. **진짜 중복 위험은 F08(Nasdaq flash freeze)** — 재현 하니스가 "시세 서버 + 정상 소비자 N + 문제 클라 1"로 거의 같다. F08은 "거부 경로가 정상 경로와 큐를 공유", F15는 "클라이언트별 송신 버퍼"로 분리하거나 한쪽을 흡수할 것. 인용 가능 = 위 Spring 두 문장, "the session will be closed if the limits are exceeded", "by default the session is terminated". **인용 금지 = `15*1000`/`512*1024`를 기본값처럼 쓰는 것**(문서의 예제 코드일 뿐 기본값이 아님), Netty 워터마크 기본값(열어본 페이지에 숫자가 없다). OOM은 "공식 문서가 경고했다"가 아니라 **"한도를 안 걸면 어디까지 가는지 직접 재현했다"**로 쓸 것. conflation은 근거를 못 찾았으니 자체 설계로 표기

## F16 FIX 시퀀스 갭과 재전송 중복
- 주장: MsgSeqNum이 기대보다 크면 유실로 보고 복구하며, 관리 메시지는 SequenceReset(GapFillFlag=Y)로 채우고, PossDupFlag를 무시하면 주문이 중복 접수된다
- 출처: FIXimate(FIX Trading Community 공식 스펙 브라우저) FIX.4.4 Field #43 PossDupFlag https://fiximate.fixtrading.org/legacy/en/FIX.4.4/tag43.html : 정의 "Indicates possible retransmission of message with this sequence number" / Y = "Possible duplicate", N = "Original transmission"(둘 다 Added FIX.2.7), StandardHeader 구성요소 (원문)
- 출처: FIXimate FIX.4.4 Field #123 GapFillFlag https://fiximate.fixtrading.org/legacy/en/FIX.4.4/tag123.html : "Indicates that the Sequence Reset message is replacing **administrative or application messages** which will not be resent." / Y = "Gap Fill message, MsgSeqNum field valid", N = "Sequence Reset, ignore MsgSeqNum" (원문)
- 출처: FIX Trading Community 세션 계층 스펙 본문 https://www.fixtrading.org/standards/fix-session-layer-online/ 및 /online-specification/session-protocol/ : **둘 다 HTTP 404. 갭 감지·ResendRequest(35=2)·중복 처리 의무를 서술한 Volume 2 본문은 확보 실패** (접속 시도했으나 문서 없음)
- 판정: E2 유지 : PossDupFlag·GapFillFlag의 정의와 허용값은 FIX Trading Community 자체 도구(FIXimate) 원문으로 확인됐고 E2 기준을 충족한다. 단 근거는 **필드 사전 수준**이지 세션 프로토콜 서술이 아니다
- 메모: **카탈로그 서술 수정 2건.** (1) "관리 메시지는 SequenceReset(GapFillFlag=Y)"은 스펙보다 좁다 — 원문은 "administrative **or application** messages which will not be resent"라 재전송하지 않을 애플리케이션 메시지도 GapFill 대상이다 (2) **"PossDupFlag를 무시하면 주문 중복 접수"는 스펙이 그 문장으로 경고한 내용이 아니다** — 필드 정의는 "재전송 가능성 표시"까지만 말한다. 스펙 인용처럼 쓰지 말고 "필드 의미상 도출되는 결과이고 실제로 무시하도록 만들어 중복 접수를 재현했다" 구조로 쓸 것. 인용 가능 = 위 두 필드의 정의문·값·"Added FIX.2.7". **인용 금지 = MsgSeqNum 갭 판정 규칙, ResendRequest 동작, "PossDup=Y면 이미 처리한 MsgSeqNum은 버려야 한다"류 문장** — 전부 Volume 2 본문에서 와야 하는데 원문 확보 실패다. 쓰려면 FIX 4.4 스펙 PDF(Volume 2 "Message Recovery" 절)를 별도로 구해 대조할 것. QuickFIX/J 동작은 스펙이 아니라 구현이므로 "QuickFIX/J가 이렇게 처리한다"로 분리 표기

## F19 마감(cutoff) 경계
- 주장: 서버 두 대 시계가 수백 ms 어긋나면 한 대는 마감 후 주문을 수용하며, 국내 구체 사고 사례는 없어 설계 과제로만 다룬다
- 출처: FINRA Rule 4590 "Synchronization of Member Business Clocks" https://www.finra.org/rules-guidance/rulebooks/finra-rules/4590 : NMS 종목·OTC 주식 기록용 컴퓨터 시계는 "must be synchronized **within a 50-millisecond tolerance** of the NIST clock", 그 밖의 업무 시계는 "**one second tolerance**". 동기화 주기는 "Computer system and mechanical clocks must be synchronized **every business day before market open**" (원문)
- 출처: Commission Delegated Regulation (EU) 2017/574 (MiFID II RTS 25) https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32017R0574 : Article 1 "shall synchronise the business clocks they use to record the date and time of any reportable event with the Coordinated Universal Time (UTC)". Annex Table 2 최대 허용 편차 = 고빈도 알고리즘 거래 **100 microseconds**(분해능 1μs 이하), 그 밖의 거래활동 **1 millisecond**, 음성거래·인적개입 RFQ **1 second** (원문)
- 출처: 국내 사례 확인용 한국어 검색 : 2026-03-09 한국거래소 매칭엔진 오류, 키움증권 MTS 장애 등은 나오지만 **시계 동기화 오차에서 비롯된 마감 경계 사고는 검색 결과에 없음** (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지하되 **근거란 보강 권고** : "국내 사고 사례 없음, 설계 과제로만" 판단은 이번에도 뒤집히지 않았다. 다만 현재 행의 근거란은 인용 출처 없이 자체 서술만 있어 E2 정의를 충족한다고 보기 애매하다. **FINRA 50ms와 RTS 25의 100μs/1ms를 근거란에 넣으면 "규제기관이 시계 오차를 명시적으로 규제할 만큼 실재하는 위험"이 되어 E2가 근거로 뒷받침된다**
- 메모: 인용 가능 = FINRA의 50ms·1초 허용오차와 개장 전 매일 동기화 요구, RTS 25의 100μs·1ms·1초 3단 기준과 UTC 동기화 의무. **"수백 ms"는 규제 허용치를 수십 배 넘는 값이라 정상 NTP 환경이 아니라 동기화가 고장 난 상태를 가정한 수치다** — "규제는 50ms 이내를 요구하는데 재현 환경에서 의도적으로 수백 ms를 벌려 무슨 일이 나는지 본다"로 조건을 밝히고 쓸 것. NTP 실제 정확도 수치는 출처를 확보하지 않았으니 인용 금지. 국내 사례가 없다는 서술은 "찾지 못했다"로 쓰고 단정하지 말 것. **이미 완성된 F13(단일 시퀀서로 시간우선 위반 제거)과 해법이 같으므로**, 중복을 피하려면 F19는 "위반 탐지"가 아니라 **"마감 경계에서의 수용·거부 판정 일관성"**으로 관찰 지표를 다르게 잡을 것

## F20 규제 대응 DR
- 주장: 전자금융감독규정 제23조가 "핵심업무의 복구목표시간은 3시간 이내, 보험회사는 24시간 이내"를 규정하고, 제11·36조는 전산실·재해복구센터 보안성심의와 국내 설치 의무를 규정한다
- 출처: 국가법령정보센터 전자금융감독규정 https://www.law.go.kr/행정규칙/전자금융감독규정 외 2경로 : **3종 모두 접속했으나 조문 본문 확보 실패** — 웹페이지는 목차·네비게이션만 렌더링(본문이 JS 로드), 오픈API는 "일치하는 행정규칙이 없습니다" 오류. 시행일 2025-2-5(금융위 고시 2025-4호) 판본 존재까지만 확인 (원문 접속했으나 조문 미확보)
- 출처: IT위키 "전자금융감독규정 제23조" https://itwiki.kr/w/전자금융감독규정_제23조 : 제23조는 ①~⑨항 구성, **제9항이 "핵심업무의 복구목표시간은 3시간 이내로 하되, 「보험업법」에 의한 보험회사의 핵심업무의 경우에는 24시간 이내로 한다."** (2차 — 위키가 옮긴 조문 텍스트이며 law.go.kr 원문 대조는 못 함)
- 판정: E2 유지, 단 **"조문 확인" 표기는 "2차 확인"으로 강등** : 카탈로그가 인용한 문장은 조문과 사실상 일치하고 조 번호도 맞다. 다만 **§12에 적힌 "조문 확인"은 이번에도 1차 대조가 안 됐다** — 법령 인용을 블로그에 싣기 전 반드시 원문 대조가 필요하다
- 메모: **정확한 조문 위치는 제23조 제9항**이고, 제8항이 재해복구센터 설치 대상 기관 열거, 제9항이 RTO다. 인용할 땐 "제23조"가 아니라 **"제23조 제9항"**으로 쓰고 "보험회사"도 원문대로 **"「보험업법」에 의한 보험회사"**로 쓸 것. **제11조·제36조는 이번 조사에서 전혀 확인하지 못했다** — 특히 "보안성심의"는 제도 자체의 존폐 이력이 있으니 현행 조문에 그 표현이 남아 있는지 확인 전에는 쓰지 말 것. 법령은 개정이 잦으므로 **시행일(2025-2-5, 금융위 고시 제2025-4호) 병기 필수**. 원문 대조 방법 = law.go.kr은 JS 렌더링이라 자동 수집이 안 되니 조문 HWP/PDF 첨부를 내려받거나 브라우저로 직접 열 것. **재현 주의 = RTO 3시간은 "재해 시 핵심업무 복구" 기준이지 컨테이너 페일오버 시간의 규제 상한이 아니다.** 측정한 전환 시간을 "규정 준수/미준수"로 판정하지 말고 "규정이 요구하는 자릿수와 내가 측정한 자릿수" 비교로만 제시할 것

## F21 시퀀스 채번 병목
- 주장: 단조증가 시퀀스를 PK로 쓰면 인덱스 우측 리프 블록 경합이 생기고 RAC에선 인스턴스 간 블록 이동으로 악화되며, Reverse Key·해시 파티션·큰 캐시+NOORDER가 해법이다
- 출처: Oracle Database Concepts 19c "Indexes and Index-Organized Tables" https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/indexes-and-index-organized-tables.html : "**Reversing the key solves the problem of contention for leaf blocks in the right side of a B-tree index. This problem can be especially acute in an Oracle Real Application Clusters (Oracle RAC) database in which multiple instances repeatedly modify the same block.**" / "For example, in an `orders` table the primary keys for orders are sequential. One instance in the cluster adds order 20, while another adds 21, with each instance writing its key to the same leaf block on the right-hand side of the index." — **카탈로그 주장과 정확히 일치하고 예시 테이블이 하필 `orders`다** (원문)
- 출처: Oracle SQL Language Reference 19c CREATE SEQUENCE https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/CREATE-SEQUENCE.html : "If you omit both `CACHE` and `NOCACHE`, then the database caches **20** sequence numbers by default." / "Specify `NOORDER` if you do not want to guarantee sequence numbers are generated in order of request. **This is the default.**" / "Oracle recommends using the `CACHE` setting to enhance performance if you are using sequences in an Oracle RAC environment." (원문)
- 출처: Oracle Administrator's Guide 19c "Managing Sequences"(Scalable Sequences) https://docs.oracle.com/en/database/oracle/oracle-database/19/admin/managing-views-sequences-and-synonyms.html : "**Scalable sequences significantly reduce the sequence and index block contention and provide better data load scalability compared to the solution of configuring a very large sequence cache using the `CACHE` clause**" / "a **6 digit numeric scalable sequence offset number is prefixed** to the digits of the sequence" / "Oracle recommends that you should not specify ordering for a scalable sequence" (원문)
- 출처: PostgreSQL 소스 `src/backend/access/nbtree/nbtinsert.c` 주석 : "The fastpath optimization avoids most of the work of searching the tree repeatedly when a single backend inserts successive new tuples on the rightmost leaf page of an index." / "The optimization helps with indexes on an auto-incremented field." / "the fastpath optimization acquires the lock on the page **conditionally** as a way of reducing extra contention when there are concurrent insertions into the rightmost page" — **PostgreSQL도 최우측 페이지 동시 삽입 경합을 코드 주석에서 인정한다** (원문)
- 판정: E2 유지 : Oracle Concepts가 "right side of a B-tree index"의 리프 블록 경합과 RAC 악화를 문자 그대로 서술하고, Admin Guide가 이를 "index block contention"으로 명명하며 전용 기능(SCALE)까지 만들었다. E1은 특정 사건 기록이 필요하니 승격 불가
- 메모: **카탈로그 해법 목록 갱신 권고** — Oracle은 18c부터 scalable sequence(SCALE 절)를 내놨고 문서가 **"큰 시퀀스 캐시보다 낫다"고 명시**하므로 카탈로그의 "큰 캐시+NOORDER"는 구식 처방이다. 그리고 **카탈로그가 자체 아이디어처럼 적은 "해시 프리픽스"가 곧 Oracle의 6자리 offset prefix다** — 자기 발상이 아니라 벤더 기능과 같은 원리라고 밝히면 오히려 글이 강해진다. **NOORDER는 옵션이 아니라 기본값이므로 "NOORDER로 바꿔서 좋아졌다"고 쓰면 오류**(ORDER를 명시했던 경우에만 유효한 처방). 인용 가능 = 위 네 출처 문장, 기본 캐시 20, "NOORDER ... This is the default", 6자리 프리픽스. 인용 금지 = 경합 배수·TPS 같은 수치(어느 문서에도 없다 — 전부 직접 측정). **재현 설계 경고 2건** = (1) 이 저장소에서 Oracle RAC를 띄울 수 없다면 "인스턴스 간 블록 이동" 부분은 재현 불가다. PostgreSQL로 하면 경합이 버퍼 락 수준이라 효과가 훨씬 약하고 fastpath가 알아서 물러서므로 **"Oracle 문서가 경고한 현상을 PG에서 축소 재현했다"**고 범위를 정직하게 좁힐 것. PG엔 reverse key index가 없으니 대안은 프리픽스 컬럼·해시 파티션 (2) **B06보다 R13(슬롯 카운터, 완료)과 더 겹친다** — 둘 다 "경합을 키 공간에 흩뿌린다"가 해법이라 결론 문단이 똑같아지기 쉽다. R13은 같은 행의 락 대기, F21은 같은 페이지/블록의 삽입 위치 경합(락 대상이 행이 아니라 인덱스 리프)이라는 점을 초반에 못 박고, 측정 지표도 R13의 락 대기 시간이 아니라 **buffer busy waits·페이지 분할 횟수** 같은 인덱스 지표로 갈 것
