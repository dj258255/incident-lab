## B27 exactly-once
- 주장: 네트워크 계층의 진짜 exactly-once는 불가능, Kafka 기본은 at-least-once, 트랜잭션 경계 밖 외부 시스템은 보장 안 됨
- 출처: Confluent 블로그 "Exactly-once Semantics are Possible" https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/ : 0.11 이전 기본 at-least-once, EOS는 멱등 프로듀서+트랜잭션+Streams 내부 범위 한정이고 외부 RPC 부수효과는 보장 안 됨을 명시 (원문)
- 판정: E2 유지 : 벤더 공식 포스트가 행 주장 3요소(불가능 논쟁·기본 등급·외부 시스템 한계)를 전부 뒷받침
- 메모: Kafka 3.0+는 프로듀서 멱등성이 기본 활성이지만 컨슈머 쪽 중복(오프셋 커밋 직전 kill 후 재소비)은 그대로 유효, 재현 설계 영향 없음. kafka.apache.org/documentation은 클라이언트 렌더링이라 WebFetch로 본문 추출 불가였음

## B28 poison DLQ
- 주장: 잘못된 1건이 6시간·1만 회 재시도로 파티션 전체를 막은 결제사 사례, DLQ replay가 장애를 재생산하는 안티패턴
- 출처: Uber Engineering "Building Reliable Reprocessing and Dead Letter Queues with Apache Kafka"(2018-02-16) https://www.uber.com/blog/reliable-reprocessing/ : 실패 메시지가 오프셋 커밋을 막아 배치가 계속 재소비되며 막히는 문제 + retry topic·DLQ 격리 해법 명시 (원문)
- 출처: OneUptime "How to Handle Poison Messages in Kafka" https://oneuptime.com/blog/post/2026-01-21-kafka-poison-messages/view : 포이즌 메시지 패턴 일반론만, 결제사 사례·replay 루프 언급 없음 (2차)
- 판정: E2 유지 : 핵심 메커니즘(1건이 파티션 블로킹 → DLQ 격리)은 대기업 원문급 근거 확보. 단 "결제사·6시간·1만 회" 구체 사건은 확인 실패
- 메모: 해당 수치의 추정 출처 abstractalgorithms.dev는 403(접속 실패)이고 저자 불명 저신뢰 블로그 → "결제사 6시간·1만 회"는 §12 수치 인용 금지 목록 추가 제안. 글에서는 Uber 사례+일반 메커니즘으로 서술 권장. 재현 설계 영향 없음

## B29 스케줄러 중복
- 주장: 파드 여럿이 같은 cron을 동시 실행해 이중 정산, Quartz 클러스터 모드에서도 트리거 이중 획득 사례, ShedLock이 표준 해법
- 출처: ShedLock GitHub README https://github.com/lukas-krecan/ShedLock : "executed at most once at the same time" 보장 + 시계 동기화 가정, lockAtMostFor보다 작업이 길면 중복 실행 가능 경고 (원문)
- 출처: Quartz 공식 클러스터링 문서 https://www.quartz-scheduler.org/documentation/quartz-2.2.2/configuration/ConfigJDBCJobStoreClustering.html : 노드 시계 1초 이내 동기화 필수, "Only one node will fire the job for each firing" (원문)
- 출처: quartz-scheduler/quartz 이슈 #731 https://github.com/quartz-scheduler/quartz/issues/731 : 4노드 클러스터(MongoDB 잡스토어)에서 중복 트리거 실행 보고, acquireTriggersWithinLock 미지원이 원인 지목, stale 종료 (원문)
- 판정: E2 유지 : 문제(멀티 인스턴스 중복)와 해법(분산 락) 모두 공식 문서·실제 이슈로 확인
- 메모: Quartz 공식 문서는 "정상 구성이면 1회만 실행"이 공식 입장 → 글에서 "Quartz도 이중 획득"은 시계 비동기화·비표준 잡스토어 등 조건부 사례로 한정해 서술해야 정확

## B30 무한큐 OOM
- 주장: Executors.newFixedThreadPool()이 무제한 LinkedBlockingQueue를 써서 유입>처리면 큐 무한 증가("무제한 큐는 프로덕션의 조용한 살인자")
- 출처: JDK 21 Javadoc Executors https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html : newFixedThreadPool은 "operating off a shared unbounded queue" 명시 (원문)
- 출처: JDK 21 Javadoc ThreadPoolExecutor https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html : "admits the possibility of unbounded work queue growth when commands continue to arrive on average faster than they can be processed" + CallerRunsPolicy는 제출 속도를 늦추는 피드백 제어 (원문)
- 판정: E2 유지 : JDK 공식 문서가 메커니즘과 해법(바운디드 큐+CallerRunsPolicy)을 그대로 뒷받침
- 메모: "조용한 살인자"는 공식 문구가 아닌 업계 관용 표현 → 글에서 직접 인용부호 없이 일반 서술 권장
