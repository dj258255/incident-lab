## B27 exactly-once
- 주장: 네트워크 계층의 진짜 exactly-once는 불가능, Kafka 기본은 at-least-once, 트랜잭션 경계 밖 외부 시스템은 보장 안 됨
- 출처: Confluent 블로그 "Exactly-once Semantics are Possible" https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/ : 0.11 이전 기본 at-least-once, EOS는 멱등 프로듀서+트랜잭션+Streams 내부 범위 한정이고 외부 RPC 부수효과는 보장 안 됨을 명시 (원문)
- 판정: E2 유지 : 벤더 공식 포스트가 행 주장 3요소(불가능 논쟁·기본 등급·외부 시스템 한계)를 전부 뒷받침
- 메모: Kafka 3.0+는 프로듀서 멱등성이 기본 활성이지만 컨슈머 쪽 중복(오프셋 커밋 직전 kill 후 재소비)은 그대로 유효, 재현 설계 영향 없음. kafka.apache.org/documentation은 클라이언트 렌더링이라 WebFetch로 본문 추출 불가였음

## B30 무한큐 OOM
- 주장: Executors.newFixedThreadPool()이 무제한 LinkedBlockingQueue를 써서 유입>처리면 큐 무한 증가("무제한 큐는 프로덕션의 조용한 살인자")
- 출처: JDK 21 Javadoc Executors https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html : newFixedThreadPool은 "operating off a shared unbounded queue" 명시 (원문)
- 출처: JDK 21 Javadoc ThreadPoolExecutor https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html : "admits the possibility of unbounded work queue growth when commands continue to arrive on average faster than they can be processed" + CallerRunsPolicy는 제출 속도를 늦추는 피드백 제어 (원문)
- 판정: E2 유지 : JDK 공식 문서가 메커니즘과 해법(바운디드 큐+CallerRunsPolicy)을 그대로 뒷받침
- 메모: "조용한 살인자"는 공식 문구가 아닌 업계 관용 표현 → 글에서 직접 인용부호 없이 일반 서술 권장

## B31 ThreadLocal·ClassLoader 누수
- 주장: ThreadLocal.remove() 누락 시 워커 스레드가 웹앱 클래스로더를 붙잡아 재배포를 반복하면 Metaspace OOM이 나고, Tomcat이 이에 대해 경고를 찍는다
- 출처: Apache Tomcat 소스 `java/org/apache/catalina/loader/LocalStrings.properties` https://raw.githubusercontent.com/apache/tomcat/main/java/org/apache/catalina/loader/LocalStrings.properties : 경고 메시지 원문이 실제로 존재 — `webappClassLoader.checkThreadLocalsForLeaks=The web application [{0}] created a ThreadLocal with key of type [{1}] (value [{2}]) and a value of type [{3}] (value [{4}]) but failed to remove it when the web application was stopped. Threads are going to be renewed over time to try and avoid a probable memory leak.` 또한 `webappClassLoader.addExportsThreadLocal=You need to add "--add-opens=java.base/java.lang={0}" to the JVM command line arguments to enable ThreadLocal memory leak detection.`와 누수가 아닌 경우를 구분하는 `...checkThreadLocalsForLeaksNone=... Since keys are only weakly held by the ThreadLocal Map this is not a memory leak.`까지 확인 (원문)
- 출처: Apache Tomcat 9 Configuration Reference — Context https://tomcat.apache.org/tomcat-9.0-doc/config/context.html : `clearReferencesThreadLocals` — "If `true`, Tomcat attempts to clear `java.lang.ThreadLocal` variables that have been populated with classes loaded by the web application. If not specified, the default value of `true` will be used." (원문)
- 출처: Apache Tomcat Wiki — MemoryLeakProtection https://cwiki.apache.org/confluence/display/TOMCAT/MemoryLeakProtection : "Classloader leaks because of uncleaned ThreadLocal variables are quite common." / "If the spawned thread is not properly terminated when the application is stopped, the webapp classloader will leak because of the strong reference held by the spawned thread." 단 이 페이지에 OOM·PermGen·Metaspace라는 단어는 없음 (원문)
- 출처: Apache Tomcat Wiki — OutOfMemory https://cwiki.apache.org/confluence/display/TOMCAT/OutOfMemory : "Hard references to classes can prevent the garbage collector from reclaiming the memory allocated for them when a ClassLoader is discarded." / "This will occur on JSP recompilations, and webapps reloads. If these operations are common in a webapp having these kinds of problems, it will be a matter of time, until the PermGen space gets full and an Out Of Memory is thrown." / "if a ThreadLocal is left on the thread at the end of the request there may be no opportunity for the web application to clean it up." (원문)
- 판정: E2 유지 : 벤더가 전용 탐지 코드와 전용 경고 메시지를 넣을 만큼 공식 경고를 낸 함정이 원문으로 확인됐다. 특정 기업 포스트모템은 없으므로 E1 승격 불가. 트랙 B에서 근거 강도가 가장 확실한 축에 속한다
- 메모: 인용 가능 = 위 네 개 원문 문장, 특히 `checkThreadLocalsForLeaks` 메시지는 영문 그대로 박을 것(로그 캡처와 대조 가능해야 함). **인용 금지 = "Metaspace OOM"을 Tomcat 원문 인용처럼 쓰는 것** — Tomcat 위키 원문은 "PermGen space"라고만 쓴다(Java 7 시절 문서). Java 8+ 재현이면 "원문은 PermGen이라 표현하나 Java 8 이후로는 Metaspace에 해당"이라고 구분할 것. **재현 함정 둘** = (1) `clearReferencesThreadLocals` 기본값이 true이고 경고 메시지 자체가 "Threads are going to be renewed over time"이라고 하므로 최신 Tomcat은 스스로 정리·스레드 갱신을 해버려 순진하게 돌리면 OOM이 안 난다. 재현하려면 이 보호장치를 끄거나 Tomcat 밖의 자체 스레드풀을 써야 하고, 이 사실 자체를 글의 하이라이트로 삼는 게 낫다("JVM이 아니라 WAS가 대신 막아주고 있었다") (2) JDK 9+에서는 `--add-opens=java.base/java.lang=ALL-UNNAMED`를 안 붙이면 탐지 자체가 동작하지 않고 addExportsThreadLocal 경고만 뜬다 — JDK 버전과 JVM 옵션을 반드시 명시할 것. "Tomcat 6.0.24부터 탐지" 같은 버전 수치는 위키 서술 기반이므로 "위키 서술 기준"이라고 달 것
- **정정(세션 수행 후, Tomcat 10.1.x 소스 확인)**: 위 메모의 "최신 Tomcat은 스스로 정리·스레드 갱신을 해버린다"와 하이라이트 제안("JVM이 아니라 WAS가 대신 막아주고 있었다")은 반만 맞다. `clearReferencesThreadLocals`가 `true`여도 Tomcat은 살아 있는 `ThreadLocalMap` 엔트리를 지우지 않는다. `WebappClassLoaderBase.checkThreadLocalsForLeaks()`는 `expungeStaleEntries()`(이미 키가 끊긴 엔트리만 대상)를 부른 뒤 `checkThreadLocalMapForLeaks()`로 훑고 `log.error(...)`를 찍는 것으로 끝나며 제거 호출이 없다. 즉 이 설정이 켜고 끄는 것은 **경고**다. 회수를 거는 것은 별개로 `ThreadLocalLeakPreventionListener`(배포본 `conf/server.xml`에 기본 포함) + `Context`의 `renewThreadsWhenStoppingContext`(기본 `true`) + `Executor`의 `threadRenewalDelay`(기본 1,000ms, 음수면 갱신 안 함)이고, 갱신은 해당 스레드가 작업을 하나 더 끝내고 풀로 돌아올 때 `StopPooledThreadException`으로 일어난다. 따라서 재현 방해 요인을 끄려면 `clearReferencesThreadLocals`가 아니라 갱신 쪽 스위치를 봐야 한다. 그리고 "WAS가 막아주고 있었다"는 이 세션이 **측정한 명제가 아니다**. 측정한 것은 최소 재현에서 워커 스레드를 직접 종료하면 300개가 회수된다는 것까지이므로, 글에서는 문서·소스 확인분과 실측분을 분리해 적었다

## B32 파일 디스크립터 누수
- 주장: close 누락으로 `Too many open files`가 발생하며, 원인은 HTTP·JDBC 커넥션 미반환·스트림 미종료·JNI 누수다. 대표 단일 사건은 없다
- 출처: Oracle "Detecting File Descriptor Leaks"(Oracle Commerce Platform Installation Guide) https://docs.oracle.com/cd/E69533_01/Platform.11-3/ATGInstallGuide/html/s0907detectingfiledescriptorleaks01.html : "It is important to ensure that files that are opened always get closed. Failing to close files can result in file descriptor leaks." / "You may notice a lot of `IOExceptions` with the message 'Too many open files.'" / "During load testing, you periodically run a profiling script, such as `lsof` (on UNIX), and you notice that the list of file descriptors grows continually." 단 이 페이지에 `/proc/[PID]/fd`와 `ulimit`은 등장하지 않는다 (원문)
- 출처: Linux man-pages `getrlimit(2)` https://man7.org/linux/man-pages/man2/getrlimit.2.html : RLIMIT_NOFILE — "This specifies a value one greater than the maximum file descriptor number that can be opened by this process. Attempts (open(2), pipe(2), dup(2), etc.) to exceed this limit yield the error EMFILE." (원문)
- 출처: Oracle Support Doc 2780049.1 "Experiencing java.net.SocketException: Too many open files and JDBC connection leak" : JDBC 커넥션 미반환이 FD 고갈로 이어진다는 벤더 공식 KB가 존재함을 확인 (2차, 검색 결과 제목으로만 확인·로그인 벽으로 직접 접속 안 함)
- 판정: E2 유지 + "대표 단일 사건 없음" 판단도 유지 : 벤더 공식 문서(Oracle)가 "닫지 않으면 누수"를 명시하고 리눅스 커널 man page가 EMFILE 임계를 규정하므로 E2 요건 충족. 반면 검색 상위는 전부 오픈소스 이슈 트래커(Jetty·Airflow·gunicorn·InfluxDB 등)일 뿐 기업 포스트모템이 아니어서 E1 근거는 여전히 없다
- 메모: **가장 중요 — "구글 셰익스피어 검색 장애(Shakespeare Sonnet++ Postmortem)"를 실제 사건으로 인용하지 말 것.** 이번 검색에서 이게 FD 고갈 대표 사례처럼 상위에 뜨는데, 이건 Google SRE Book 부록의 **가공된 교육용 예시**다(존재하지 않는 서비스, "1.21 billion queries lost" 같은 수치도 창작). 검색으로 발견해 "구글 사례"로 쓰면 §12 경고를 정면으로 어기는 셈이다. 인용하려면 "SRE 책의 교육용 예시"라고 명시할 때만. 인용 가능 = `EMFILE` 정의 원문, Oracle 문서의 탐지 2가지 방법. 인용 금지 = 특정 회사 이름, 장애 시간·손실 건수 등 모든 정량 피해 수치(출처 없음). 카탈로그 재현 절차의 `/proc/[PID]/fd`는 실무상 맞지만 위 두 원문에는 없으므로 `proc(5)` man page를 따로 확인해 인용하거나 "출처 없이 실습 도구로만" 제시할 것. try-with-resources 대조는 JDK 공식 근거(AutoCloseable javadoc / JLS 14.20.3)를 아직 확인 안 했다. Oracle 근거가 JDK 코어 문서가 아니라 Oracle Commerce(ATG) 설치 가이드라는 점은 정직하게 밝힐 것 — 벤더 공식 문서는 맞지만 "자바 공식 문서"라고 부르면 과장이다

## B33 LB idle timeout < 앱 keep-alive → 간헐 502
- 주장: 프록시(LB)의 idle timeout이 백엔드 keep-alive보다 길면 백엔드가 이미 닫은 유휴 커넥션을 프록시가 재사용하려다 간헐적 502가 나며, 이는 "간헐적 502의 1순위 원인"이다
- 출처: AWS Application Load Balancer 사용 설명서 "Connection idle timeout" https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html : "We also recommend that you configure the idle timeout of your application to be larger than the idle timeout configured for the load balancer. Otherwise, if the application closes the TCP connection to the load balancer ungracefully, the load balancer might send a request to the application before it receives the packet indicating that the connection is closed. If this is the case, then the load balancer sends an HTTP 502 Bad Gateway error to the client." / "By default, Elastic Load Balancing sets the idle timeout value for your load balancer to 60 seconds." — 기전과 결과(502)를 벤더 공식 문서가 그대로 명시 (원문)
- 출처: AWS ALB 사용 설명서 "Load balancer attributes" https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html : "idle_timeout.timeout_seconds — The idle timeout value, in seconds. The default is 60 seconds." / "client_keep_alive.seconds — The client keepalive value, in seconds. The default is 3600 seconds." (원문)
- 출처: Ivan Velichko(iximiuz) "Reverse Proxy, HTTP Keep-Alive Timeout, and sporadic HTTP 502s" https://iximiuz.com/en/posts/reverse-proxy-http-keep-alive-and-502s/ : "While one endpoint (the proxy) can still be thinking that the connection is totally fine, the other endpoint may have already started closing the connection (the upstream)." 대책 1항 "Make sure the upstream (application) idle connection timeout is longer than the downstream (proxy) connection timeout." 게시 2021-09-30(갱신 2024-05-05). 글은 실재하고 기전·권고도 일치. **단 "1순위 원인"이라는 서열 주장은 이 글에 없고**("The problem is actually quite generic" 정도), **gunicorn 사례도 없다**(저자 예시는 ALB 뒤 Node.js, Traefik 뒤 Python/uWSGI) (원문)
- 판정: E2 유지(트랙 B 최상위급 근거), 단 **제목 부등호가 뒤집혀 있어 수정 필수** : 벤더 공식 문서가 502라는 결과까지 명시해 별도 경고를 내는 전형적 E2다. 그러나 AWS 권고는 "앱 idle > LB idle"이므로 카탈로그 제목 `LB idle timeout < 앱 keep-alive`는 오히려 **안전한** 구성이다. 장애 조건은 `앱 keep-alive < LB idle timeout`이다. 재현 칸("백엔드 keep-alive를 프록시 idle보다 짧게")은 맞으므로 제목만 뒤집으면 된다. "간헐적 502의 1순위 원인"과 "gunicorn 사례"는 원문 근거가 없으니 iximiuz에게 귀속시키지 말 것 — 우리 각색이다
- 메모: 인용 가능 = ALB 기본 idle timeout 60초, 유효 범위 1~4000초, ALB HTTP client keepalive 기본 3600초. 인용 금지 = "Node.js 기본 keepAliveTimeout 5초", "ELB 60초 vs Node 5초라서 502" 같은 조합 — 2차 블로그에서만 봤고 Node.js 공식 문서로 확인하지 않았다. 쓰려면 Node 공식 문서를 따로 열거나 우리 재현 환경(nginx `keepalive_timeout` vs 백엔드 설정)의 실측값으로 대체할 것. 서술 순서는 "AWS 공식 문서가 502를 콕 집어 경고한다 → 그대로 재현했다 → 부등호를 뒤집으니 사라졌다"로 가면 근거가 가장 세다. iximiuz는 "기전을 잘 정리한 커뮤니티 글" 위치로만 쓰고 권위 근거는 AWS 문서로 세울 것

## B34 클라이언트 타임아웃 < 서버 타임아웃
- 주장: 클라이언트가 서버보다 먼저 타임아웃되어 재시도하는데 서버는 원 요청을 계속 처리하므로 인플라이트가 배가되고, 원칙은 계층 정렬(클라 타임아웃 > 각 홉 합)이며 방어책은 데드라인 전파다
- 출처: Google SRE Book Ch.22 "Addressing Cascading Failures" https://sre.google/sre-book/addressing-cascading-failures/ : (Missing Deadlines) "Servers spend resources handling requests that will exceed their deadlines on the client. As a result, resources are spent while no progress is made: you don't get credit for late assignments with RPCs." / "it would be unwise for the server to attempt to handle this request, because it would be doing work for which no credit will be granted—the client doesn't care what work the server does after the deadline has passed, because it's given up on the request already." / (Deadline Propagation) "With deadline propagation, a deadline is set high in the stack (e.g., in the frontend). The tree of RPCs emanating from an initial request will all have the same absolute deadline." / (Retries) "The volume of retries grows: 100 QPS of retries in the first second leads to 200 QPS, then to 300 QPS, and so on." (원문)
- 출처: gRPC 공식 문서 "Deadlines" https://grpc.io/docs/guides/deadlines/ : "In these cases where your server also acts as a client you would want to honor the deadline set by the original client." / "Please note that the server application is responsible for stopping any activity it has spawned to service the RPC." / "Since a deadline is set point in time, propagating it as-is to a server can be problematic as the clocks on the two servers might not be synchronized. To address this gRPC converts the deadline to a timeout from which the already elapsed time is already deducted." 언어별로 자동 전파 여부가 다르다(C++는 명시적 활성화 필요, Java·Go는 기본 활성화)는 서술도 있음 (원문)
- 판정: E2 유지 : Google SRE Book과 gRPC 공식 문서가 "클라가 포기한 뒤에도 서버가 계속 일한다"는 낭비와 그 대책(데드라인 전파)을 정면으로 다룬다. 강등 사유 없음. 다만 **카탈로그의 "계층 정렬(client > 각 홉 합)"이라는 정식화는 두 원문 어디에도 그 문장으로는 없다** — 원문이 미는 원칙은 "합을 계산해 클라 타임아웃을 크게 잡아라"가 아니라 "프론트엔드에서 정한 절대 데드라인을 트리 전체가 공유하라"다. 실무 휴리스틱으로 소개하는 건 좋지만 SRE Book 인용처럼 보이게 쓰지 말 것
- 메모: 인용 시 성격 명시 = SRE Book의 "100 QPS → 200 QPS → 300 QPS"는 **책의 예시(illustrative)이지 측정 통계가 아니다.** "SRE Book이 재시도 증폭을 설명하며 든 예"라고 밝힐 것. 인용 금지 = 재시도 배수·인플라이트 증가율은 반드시 우리 재현 실측치로(원문에 근거 수치 없음). AWS Builders' Library "Timeouts, retries, and backoff with jitter"를 추가 근거로 잡으려 했으나 URL이 builder.aws.com으로 301된 뒤 본문이 렌더되지 않아 **확인 실패했으므로 인용하지 말 것**. gRPC 문서는 데드라인 자동 전파가 언어별로 다르다고 하므로 재현 코드가 Java·Go면 "자동", C++면 "명시 활성화"로 서술이 갈린다 — 우리 스택에 맞춰 확인하고 쓸 것

## B35 Spring Actuator /heapdump 노출
- 주장: 노출된 Spring Actuator `/heapdump`에서 자격증명을 뽑아 폭스바겐 텔레매틱스 GPS 데이터 9TB가 유출됐고, Wiz 조사상 클라우드 환경의 11%가 공개 노출돼 있다
- 출처: Wiz Blog "Exploring Spring Boot Actuator Misconfigurations"(Danielle Aminov, 2024-12-16) https://www.wiz.io/blog/spring-boot-actuator-misconfigurations : 11% 수치는 Wiz 공식 리서치로 실재 확인. 다만 원문은 "60% of cloud environments have at least one instance of Spring Boot Actuator" / "11% of such environments have instances that are publicly exposed to the Internet" / "2.3% of exposed Spring Boot Actuator instances in cloud environments have their heap dump endpoint exposed without authentication". **즉 11%는 "클라우드 환경 전체"가 아니라 "Actuator를 보유한 환경 중 11%가 인터넷 공개"이고, heapdump 무인증 노출은 별도로 2.3%다.** 또 같은 글이 "Surprisingly, as far as we know there is currently no widely documented real-world threat activity known to exploit specific Spring Boot Actuator misconfigurations such as exposed heapdump files."라고 명시 — 이 글은 CCC 공개(12/27~30)보다 11일 앞서 나왔으므로 폭스바겐 사건의 근거가 될 수 없다 (원문)
- 출처: Wiz Threat DB "Volkswagen data leak through Spring Boot Actuator misconfiguration"(pub. 2024-12-30) https://threats.wiz.io/all-incidents/volkswagen-massive-data-leak-through-spring-boot-actuator-misconfiguration : "Java Spring application exposing its Heap dump file", "The heap dump contained active AWS credentials stored in plain text." → heapdump → AWS 키 → S3 접근이라는 인과 사슬 자체는 벤더 위협DB가 지지. 단 이 페이지는 유출량(TB)·차량 대수를 적지 않으며 근거로 CCC 38C3 발표 영상을 인용한다. `/actuator/heapdump` 경로를 명시하지도 않음 (원문)
- 출처: CCC 보도자료 "Wir wissen, wo dein Auto steht" https://www.ccc.de/en/updates/2024/wir-wissen-wo-dein-auto-steht : 사건 실재는 확인되나 기술적 진입 경로·데이터 용량은 적혀 있지 않고 Der Spiegel 기사로 넘긴다. 1차 기술 근거는 38C3 발표 영상인데 **그 영상은 열지 않았다** (원문, 단 내용 부족)
- 출처: 9TB / "메모리 덤프 안에서 AWS 키 발견" 서술(BleepingComputer, ReynardSec 등) : 검색 결과 스니펫에만 등장. **9TB라는 숫자를 명시한 원문은 하나도 확인하지 못했다** (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E1 유지(사건 자체는 실재 — CCC 공개·Cariad 공식 인정·38C3 발표라는 1차 자료 존재) + **수치 2건 모두 수정·삭제 권고** : 9TB는 원문 미확보이므로 삭제하거나 "수 테라바이트 규모"로 낮출 것. 11%는 출처는 진짜지만 카탈로그 문장이 모집단을 잘못 적었으므로 반드시 재작성. 또한 폭스바겐 유출의 최종 노출면은 Cariad가 스스로 "cloud misconfiguration"이라 한 **비보호 S3 버킷**이고 heapdump는 그 앞단의 자격증명 획득 경로다. "Actuator 때문에 9TB가 샜다"는 단일 원인 서술은 과장
- 메모: 인용 가능 = "Actuator를 보유한 클라우드 환경의 11%가 인터넷에 공개 노출(Wiz, 2024-12)", "노출된 Actuator 인스턴스의 2.3%가 heapdump를 무인증 공개", "60%의 클라우드 환경에 Actuator가 하나 이상 존재". **인용 금지 = "클라우드 환경 11%가 공개 노출"(모집단 왜곡), "GPS 9TB"(원문 미확인), "80만 대·10cm 정밀도"(언론 보도만 봄)**. 글에는 Wiz 블로그가 사건 직전에 "실제 악용 사례는 널리 문서화된 게 없다"고 썼다가 열흘 뒤 폭스바겐 건이 터졌다는 타임라인을 쓰면 오히려 설득력이 있다. 인과를 단정하려면 38C3 영상을 직접 확인한 뒤에 쓸 것

## B36 JWT alg=none / 서명 미검증
- 주장: 초기 다수 JWT 라이브러리가 `alg: none`을 유효한 서명으로 취급했고(CVE-2015-9235 계보), RS256↔HS256 confusion까지 이어진다
- 출처: NVD CVE-2015-9235 https://nvd.nist.gov/vuln/detail/CVE-2015-9235 : CVE 실재 확인. 설명 원문은 "In jsonwebtoken node module before 4.2.2 it is possible for an attacker to bypass verification when a token digitally signed with an asymmetric key (RS/ES family) of algorithms but instead the attacker send a token digitally signed with a symmetric algorithm (HS* family)." CVSS 3.0 9.8 CRITICAL, 등재일 2018-05-29(사건은 2015년). **설명 어디에도 `alg: none`은 나오지 않는다 — 이 CVE는 알고리즘 컨퓨전 건이다.** 참조 링크에 timmclean.net/2015/02/25/jwt-alg-none.html과 auth0 블로그가 걸려 있음 (원문)
- 출처: Auth0 Blog "Critical vulnerabilities in JSON Web Token libraries"(Tim McLean, 원 게시 2015-03-31 / 현 페이지 갱신 2020-08-21) https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/ : alg=none 1차 문헌 확인 — "Unfortunately, some libraries treated tokens signed with the `none` algorithm as a valid token with a verified signature." / "Anyone can create their own 'signed' tokens with whatever payload they want, allowing arbitrary account access on some systems." 키 컨퓨전은 "If a server is expecting a token signed with RSA, but actually receives a token signed with HMAC, it will think the public key is actually an HMAC secret key." 영향 라이브러리로 node-jsonwebtoken, pyjwt, namshi/jose, php-jwt, jsjwt 열거 (원문)
- 판정: E2 유지 : 특정 기업 사건이 아니라 CVE + 연구자 1차 공개문이 근거인 전형적 E2. 두 축(alg=none, 알고리즘 컨퓨전) 모두 원문 확인됨
- 메모: 인용 가능 = CVE-2015-9235(jsonwebtoken < 4.2.2, CVSS 9.8), 위 Auth0 인용문 두 개, 영향 라이브러리 5종. **인용 금지 = "alg:none = CVE-2015-9235"라는 등식** — 그 CVE 본문은 RS/ES → HS* 컨퓨전만 다루고 alg=none은 같은 Auth0/Tim McLean 글에서 함께 공개된 별개 결함이다. "CVE-2015-9235 계보"라고 뭉뚱그리면 리뷰어가 NVD를 열어보는 순간 틀린 게 드러난다. "2015년 Tim McLean이 두 결함을 함께 공개했고 그중 알고리즘 컨퓨전 쪽이 CVE-2015-9235로 등재됐다"로 쓸 것. 카탈로그의 "대소문자 변형(nOnE 등)"은 이번 조사에서 출처를 확인하지 못했으므로 근거 없이 쓰지 말 것. CVE 등재가 2018년인 점(공개 3년 뒤)도 정확히 적을 것

## B37 압축 폭탄(gzip/zip bomb)
- 주장: 수 KB가 수 GB로 팽창하며, 42.zip과 4.5PB 플랫 폭탄이 대표 사례이고 OpenTelemetry Collector·Fluentd에 실제 CVE가 있다
- 출처: David Fifield "A better zip bomb"(2019) https://www.bamsoftware.com/hacks/zipbomb/ : "The best-known zip bomb, 42.zip, expands to a formidable 4.5 PB if all six of its layers are recursively unzipped" — 4.5 PB 수치 확인, **단 재귀 6계층 해제 기준이지 플랫이 아니다.** 저자 본인의 비재귀(플랫) 폭탄은 zbsm.zip 42 kB → 5.5 GB, zblg.zip 10 MB → 281 TB, zbxl.zip 46 MB → 4.5 PB(Zip64). DEFLATE 이론 한계 1032:1을 zip 컨테이너 내 파일 겹치기로 우회한다고 설명 (원문)
- 출처: GitHub Security Advisory GHSA-c74f-6mfw-mm4v / **CVE-2024-36129**(OpenTelemetry Collector, 2024-06-05, CVSS 8.2 High) https://github.com/open-telemetry/opentelemetry-collector/security/advisories/GHSA-c74f-6mfw-mm4v : "A malicious attacker could leverage this weakness to crash the collector by sending a small request that, when uncompressed by the server, results in excessive memory consumption." confighttp < 0.102.0, configgrpc < 0.102.1 영향. PoC에서 zstd로 10GB를 329KB로 압축 → 해제 시 32GB 메모리 전량 소진. 패치는 "wrapping the decompressed data reader inside an io.LimitedReader" (원문)
- 출처: GitHub Security Advisory GHSA-j9cw-hwqf-85w7 / **CVE-2026-44160**(Fluentd, 2026-06-26, CVSS 7.5 High) https://github.com/fluent/fluentd/security/advisories/GHSA-j9cw-hwqf-85w7 : `in_http`·`in_forward` 대상. "Fluentd correctly enforces size limits on the incoming compressed payloads (e.g., via `body_size_limit` or `chunk_size_limit`), it was discovered that there is no limit enforced on the size of the decompressed data." 영향 <= 1.19.2, 수정 1.19.3 (원문)
- 출처: CVE-2026-44162(fluent-plugin-s3) / CVE-2026-44163(fluent-plugin-opentelemetry) : 같은 2026-06 Fluentd 계열 압축 폭탄 묶음으로 보이나 어드바이저리 본문은 열지 않음 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 카탈로그가 "실 CVE가 있다"고 주장한 두 건 모두 GitHub Security Advisory 원문에서 번호까지 특정됐다(CVE-2024-36129, CVE-2026-44160). 특정 기업 포스트모템은 없으므로 E1 승격 근거는 없다
- 메모: 인용 가능 = "42.zip: 6계층 재귀 해제 시 4.5 PB", "zbsm.zip 42 kB → 5.5 GB", "zblg.zip 10 MB → 281 TB", "zbxl.zip 46 MB → 4.5 PB(플랫, Zip64)", OTel PoC의 "329 KB → 10 GB, 32 GB 메모리 소진". **인용 금지 = "42.zip·4.5PB 플랫 폭탄"처럼 둘을 붙여 쓰는 것** — 42.zip은 재귀형이고 4.5 PB 플랫 폭탄은 Fifield의 zbxl.zip(46 MB)으로 서로 다른 물건인데 공교롭게 숫자가 같아 오해하기 딱 좋다. 카탈로그의 "수 KB가 수 GB로"는 zbsm.zip(42 kB → 5.5 GB)과 정확히 맞으니 그대로 써도 된다. 재현의 "LimitReader 상한"은 OTel 실제 패치(io.LimitedReader)와 일치하므로 "업스트림이 실제로 택한 수정과 같은 방식"이라고 쓸 수 있다 — 이 세션의 가장 강한 카드. Fluentd CVE는 2026년 6월 건으로 아주 최신이니 날짜를 명시할 것
