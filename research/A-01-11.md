## A02 온라인 DDL MDL 폭풍
- 주장: 롱 쿼리/트랜잭션이 잡은 메타데이터 락에 ALTER가 대기하고, 그 뒤 SELECT까지 전부 블록되는 MySQL 대표 함정
- 출처: MySQL 8.0 Reference Manual "Metadata Locking" https://dev.mysql.com/doc/refman/8.0/en/metadata-locking.html : 트랜잭션 종료까지 MDL 유지, 미완료 트랜잭션이 쓰는 테이블에 DDL 불허, ALTER/DROP이 MDL 해제까지 블록되는 예시 명시 (원문)
- 판정: E2 유지 : 벤더 공식 문서가 메커니즘을 직접 경고, 특정 사건 인용 없음도 행과 일치
- 메모: "뒤의 SELECT까지 블록"은 ALTER의 배타적 MDL 대기 뒤로 큐잉되는 표준 동작이라 재현으로 보여주기 적절. lock_wait_timeout·LOCK=NONE 비교도 공식 문서 범위
- 재확인(2026-07-29, A02 세션 구축 중): 8.4 매뉴얼에서 네 문장 확인(원문). metadata-locking.html: "acquiring metadata locks on tables used within a transaction and deferring release of those locks until the transaction ends" / "In autocommit mode, each statement is in effect a complete transaction, so metadata locks acquired for the statement are held only to the end of the statement" / "If there are multiple waiters for a given lock, the highest-priority lock request is satisfied first ... Write lock requests have higher priority than read lock requests"
- 핵심 인용(A02의 서사 전체를 지탱): innodb-online-ddl-performance.html "Additionally, a pending exclusive metadata lock requested by an online DDL operation blocks subsequent transactions on the table." 및 "In the commit table definition phase, the metadata lock is upgraded to exclusive ... Once granted, the duration of the exclusive metadata lock is brief." / "an online DDL operation may have to wait for concurrent transactions that hold metadata locks on the table to commit or rollback" (원문)
- 8.4 고유 조건: innodb-online-ddl-operations.html "INSTANT is the default algorithm in MySQL 8.4." → ADD COLUMN은 실행 자체가 0.09초로 끝나는데도 배타적 MDL 대기 때문에 20초 정지가 난다. "느린 DDL이 문제"라는 통념과 반대 방향의 그림이라 A02의 중심에 둠
- 미확인: lock_wait_timeout은 metadata-locking.html 본문에 언급이 없다. 기본값 31536000초는 세션에서 SELECT @@lock_wait_timeout으로 실측했고 문서 인용은 붙이지 않았다. 인용이 필요하면 server-system-variables.html 앵커를 따로 열 것

## A03 utf8 vs utf8mb4
- 주장: MySQL utf8은 3바이트 축소판이라 이모지(보조 평면) 저장 불가, utf8mb4 전환 시 인덱스 767바이트 제한 이슈
- 출처: MySQL 8.0 Reference Manual "The utf8mb3 Character Set" https://dev.mysql.com/doc/refman/8.0/en/charset-unicode-utf8mb3.html : 문자당 최대 3바이트·BMP만 지원(보조 문자 불가)·utf8=utf8mb3 별칭·deprecated 명시 (원문)
- 출처: MySQL 8.0 Reference Manual "Limits on InnoDB Tables" https://dev.mysql.com/doc/refman/8.0/en/innodb-limits.html : REDUNDANT/COMPACT 행 포맷 인덱스 키 프리픽스 767바이트, DYNAMIC/COMPRESSED는 3072바이트, utf8mb4 4바이트 기준 191자 예시까지 문서에 명시 (원문)
- 판정: E2 유지 : 두 주장 모두 벤더 공식 문서로 확인
- 메모: 재현 주의 = MySQL 8.0 기본 행 포맷은 DYNAMIC(3072바이트)이라 767 제한을 보이려면 ROW_FORMAT=COMPACT 지정 또는 5.x 계열 필요. "가짜 UTF-8"이라는 표현은 블로그식 수사이고 공식 용어는 BMP-only

## A04 MSSQL 락 에스컬레이션
- 주장: 단일 문이 약 5,000개 락 초과 시 테이블 락으로 승격, LOCK_ESCALATION 옵션·배치 분할로 완화
- 출처: Microsoft Learn "Transaction locking and row versioning guide" https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17 : "단일 T-SQL 문이 한 테이블 참조에 최소 5,000개 락 획득 시 에스컬레이션", 로우/페이지 락은 페이지가 아니라 곧장 테이블 락으로 승격, ALTER TABLE SET LOCK_ESCALATION(AUTO/TABLE/DISABLE) 명시 (원문)
- 판정: E2 유지 : 벤더 공식 문서에 임계값·동작·완화책 전부 명시
- 메모: 인용 가능 수치 = 5,000(최소치, "약 5,000 초과"보다 "5,000개 이상"이 정확), 승격 실패 시 1,250개마다 재시도. 재현 주의 = 최신 SQL Server의 optimized locking 활성 시 에스컬레이션이 잘 안 일어나므로 재현 환경에선 꺼야 함

## A06 갭 락 데드락
- 주장: REPEATABLE READ에서 갭 락은 서로 충돌하지 않고 공존, insert intention이 갭 락에 대기 → 범위 겹친 두 세션 + INSERT 조합이 대표 데드락
- 출처: MySQL 8.0 Reference Manual "InnoDB Locking" https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html : "갭 락은 공존 가능, 공유/배타 구분 없이 서로 충돌하지 않음" + insert intention lock이 기존 갭 락에 대기하는 SHOW ENGINE INNODB STATUS 예시("lock_mode X locks gap before rec insert intention waiting")까지 문서에 수록 (원문)
- 출처: Tecoble "데드락 해결 모험기"(2022-11-01) https://tecoble.techcourse.co.kr/post/2022-11-01-mysql-dead-lock/ : 실무 데드락 사례 글 실재 확인 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 데드락 성립 메커니즘 전체가 벤더 공식 문서로 증명됨
- 메모: "실무 데드락 최다 빈출"은 통계가 아니라 경험칙이므로 블로그화 시 단정 표현 피할 것. 카탈로그가 언급한 우형(우아한형제들) 글은 이번 검색에선 미확인 — 인용하려면 별도 확인 필요

## A08 buffer pool 사이징
- 주장: innodb_buffer_pool_size는 DBA 파라미터 튜닝의 대표 주제이며(특정 사건 아님), 값을 극단적으로 바꾸고 동일 부하를 걸면 buffer pool hit ratio와 p95가 전후로 갈린다
- 출처: MySQL 8.0 Reference Manual "The Buffer Pool"(17.5.1) https://dev.mysql.com/doc/refman/8.0/en/innodb-buffer-pool.html : "Ideally, you set the size of the buffer pool to as large a value as practical, leaving enough memory for other processes on the server to run without excessive paging. The larger the buffer pool, the more InnoDB acts like an in-memory database" / "On dedicated servers, up to 80% of physical memory is often assigned to the buffer pool." 같은 페이지가 "Buffer pool hit rate"를 "The buffer pool page hit rate for pages read from the buffer pool vs from disk storage."로 정의하고 Innodb_buffer_pool_read_requests·Innodb_buffer_pool_reads를 함께 제시 (원문)
- 출처: MySQL 8.0 Reference Manual "Optimizing InnoDB Disk I/O" https://dev.mysql.com/doc/refman/8.0/en/optimizing-innodb-diskio.html : "it is typically recommended that innodb_buffer_pool_size is configured to 50 to 75 percent of system memory." (원문)
- 출처: MySQL 8.0 Reference Manual "Configuring InnoDB Buffer Pool Size" https://dev.mysql.com/doc/refman/8.0/en/innodb-buffer-pool-resize.html : 버퍼 풀 크기는 innodb_buffer_pool_chunk_size * innodb_buffer_pool_instances의 배수로 자동 조정되며, 온라인 리사이즈 중에는 "new transactions and operations that require access to the buffer pool must wait until the resizing operation finishes." chunk_size 기본값 128M (원문)
- 출처: MySQL 8.0 Reference Manual "InnoDB Startup Options and System Variables" https://dev.mysql.com/doc/refman/8.0/en/innodb-parameters.html : 접속했으나 페이지가 커 innodb_buffer_pool_size 항목 본문이 잘려 기본값(통칭 128MB)을 원문에서 확인하지 못함 (접속했으나 해당 대목 미확인)
- 재확인(2026-07-29, A08 세션 구축 중): 위 미확인 항목을 8.4 매뉴얼에서 해소했다. https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html 의 innodb_buffer_pool_size 속성 표에 Default Value `134217728`(128MB) 명시 (원문). 아래 세 인용도 8.4에서 문구 그대로 유지됨을 확인: "up to 80% of physical memory ... on dedicated servers"(innodb-buffer-pool.html), "50 to 75 percent of system memory"(optimizing-innodb-diskio.html), chunk_size 배수 자동 조정과 chunk 기본 128M(innodb-buffer-pool-resize.html)
- 재확인 추가 수확: 8.4 innodb-buffer-pool-resize.html이 확대와 축소의 동시성 차이를 나눠 적는다. 확대는 "While these operations are in progress, other threads are blocked from accessing the buffer pool.", 축소는 "Of these operations, only defragmenting the buffer pool and withdrawing pages allow other threads to access to the buffer pool concurrently." (원문). 리사이즈를 "무중단"으로 쓰면 안 되는 근거이자, 확대와 축소를 따로 재야 하는 근거
- 미확인 잔여: innodb_flush_method의 O_DIRECT 항목 본문(운영체제 캐시 이중 버퍼링 언급 여부)은 페이지가 잘려 확인 실패. O_DIRECT가 페이지 캐시를 건너뛴다는 서술을 벤더 문서 인용으로 쓰지 말 것. 쓰려면 자기 실측(블록 I/O 계측)으로만
- 판정: E2 유지 : 벤더 공식 문서가 사이징 권고·측정 지표·리사이즈 부작용을 직접 문서화하나 특정 회사 장애 사례는 없음. 행의 [E2] 표기와 정확히 일치
- 메모: 인용 가능 = "50 to 75 percent of system memory", "up to 80% of physical memory ... on dedicated servers", chunk 배수 자동 조정 규칙, chunk_size 기본 128M, "Buffer pool hit rate" 정의. 인용 금지 = (1) innodb_buffer_pool_size 기본값 128MB — 이번에 원문 확인 실패, 쓰려면 innodb-parameters.html 해당 앵커를 다시 열 것 (2) "hit ratio 99% 이상이 정상" 같은 업계 통설 임계값은 공식 문서에 없으므로 자기 실측 그래프로만 말할 것. 주의: 공식 문서 안에서 권고가 50~75%와 80%로 갈리므로 "공식 권고는 80%"로 단정하지 말고 두 페이지를 함께 밝힐 것. 리사이즈는 진행 중 신규 트랜잭션을 대기시키므로 "무중단 튜닝"으로 쓰면 틀리고, 그 대기 자체가 좋은 관찰 포인트. Standard Monitor의 초당 평균값은 직전 출력 이후 경과 시간 기준이라 전후 비교 시 출력 타이밍에 왜곡될 수 있음

## A09 통계 오염 플랜 붕괴
- 주장: 분포가 왜곡된 컬럼에서 ANALYZE(자동 포함)가 잘못된 통계를 만들어 실행 플랜이 뒤집히고 장애로 이어진다. 근거로 GoCardless 사례와 Clerk 2026-02 실장애(ANALYZE 샘플이 NULL만 잡아 오판)를 든다
- 출처: Clerk "Postmortem: Clerk System Outage (February 19, 2026)" https://clerk.com/blog/2026-02-19-system-outage-postmortem : 사건 실재 확인. "On February 19, 2026 at 8:11 AM PST" 시작, "Service was restored approximately 90 minutes later"(ANALYZE 수동 재실행으로 이전 플랜 복귀). 원인은 자동 analyze가 유발한 plan flip이며 "the planner's sample size was too low and it only found NULL values, which led it to erroneously conclude that 100% of the values were NULL." 실제 NULL 비율은 "very high (99.9996%)", 플래너는 non-null 0건을 예상했으나 "in fact it returned over 17,000". 영향은 "over 95% of traffic returning 429 without being handled." 재발 방지에 plan flip 알럿·statistics target 상향 포함 (원문)
- 출처: GoCardless "Debugging the Postgres query planner"(Lawrence Jones) https://gocardless.com/blog/debugging-the-postgres-query-planner/ : 프로덕션 장애(async worker·API 양쪽 영향). 약 5억 행 payment_transitions에서 payout_id의 n_distinct가 25,650으로 잡혔으나 실제 약 350만 — 매칭 행을 2,688건으로 추정(실제 통상 20건대)하고 인덱스 대신 비효율 플랜 선택. 원인은 PG의 2단계 샘플링(페이지를 고른 뒤 그 안에서 행 선택)이 같은 payout 행의 디스크 인접성 탓에 편향된 것. 조치는 "ALTER TABLE payment_transitions ALTER COLUMN payout_id SET STATISTICS 1666", 부족해 5000까지 상향 (원문)
- 판정: E1 유지 : 카탈로그가 주장한 Clerk 2026-02 실장애가 회사 공식 포스트모템 원문과 메커니즘·문구 수준까지 일치. GoCardless도 당사자 엔지니어의 1차 기록이라 E1 요건 충족

## A10 복제 지연 관측
- 주장: 대량 UPDATE로 복제 지연을 유발하면 Seconds_Behind_Master(8.0은 Seconds_Behind_Source)가 실제 지연을 못 따라가고 0과 큰 값 사이를 진동하므로, R/W 분리 환경에서 이 값만 보고 판단하면 안 되고 GTID 기반 실지연과 병렬 복제 파라미터로 접근해야 한다
- 출처: MySQL 8.0 Reference Manual 15.7.7.35 SHOW REPLICA STATUS https://dev.mysql.com/doc/refman/8.0/en/show-replica-status.html : 신뢰 불가 조건 4가지 명시. 느린 네트워크 — "If the network is slow, this is not a good approximation; the replication applier thread may quite often be caught up with the slow-reading replication receiver thread, so Seconds_Behind_Source often shows a value of 0, even if the replication receiver thread is late compared to the source. In other words, this column is useful only for fast networks." 시계 변동 — "Any changes, including NTP updates, can lead to clock skews that can make calculation of Seconds_Behind_Source less reliable." 캐스케이드 — "the Seconds_Behind_Source value randomly fluctuates because sometimes the last event from M1 originates from M0 and sometimes is the result of a direct update on M1." 병렬 복제 — "When using a multithreaded replica, you should keep in mind that this value is based on Exec_Source_Log_Pos, and so may not reflect the position of the most recently committed transaction." (원문)
- 출처: MySQL 8.0 Reference Manual 19.1.7.1 Checking Replication Status https://dev.mysql.com/doc/refman/8.0/en/replication-administration-status.html : 진동 현상을 공식 문서가 그대로 서술 — "when the replication SQL (applier) thread has caught up on I/O, Seconds_Behind_Source displays 0; but when the replication I/O (receiver) thread is still queuing up a new event, Seconds_Behind_Source may show a large value until the replication applier thread finishes executing the new event. This is especially likely when the events have old timestamps; in such cases, if you execute SHOW REPLICA STATUS several times in a relatively short period, you may see this value change back and forth repeatedly between 0 and a relatively large value." (원문)
- 출처: MySQL 8.0 Reference Manual replication_applier_status_by_worker 테이블 https://dev.mysql.com/doc/refman/8.0/en/performance-schema-replication-applier-status-by-worker-table.html : 대안 계측 근거. APPLYING_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP = "A timestamp ... that shows when the transaction this worker is currently applying was committed on the original source." 단 이 페이지에 "이 값으로 복제 지연을 측정하라"는 문장은 없다(그 해석은 우리 것) (원문)
- 판정: E2 유지 : 특정 기업 장애가 아니므로 E1이 아니나, 공식 매뉴얼이 한 필드에 대해 신뢰 불가 조건을 네 갈래로 경고하고 별도 운영 챕터에서 진동 현상까지 예고한다. E2 정의에 정확히 부합
- 메모: 인용 가능 = 위 네 개 신뢰 불가 조건과 진동 서술. 특히 "this column is useful only for fast networks"는 매뉴얼이 이탤릭으로 강조한 문장이라 인용 효과가 크다. 인용 금지 = 병렬 복제 파라미터(replica_parallel_workers 기본값, replica_parallel_type, binlog_transaction_dependency_tracking)는 이번에 확인 못 함. "8.0.27부터 기본 4" 같은 기억 속 수치를 쓰지 말고 replication-options-replica.html에서 다시 확인할 것. 용어 = 카탈로그는 Seconds_Behind_Master지만 8.0 매뉴얼 표기는 Seconds_Behind_Source다. 인용문은 Source로 가고 본문에서 "5.7까지의 Seconds_Behind_Master"로 한 번 연결할 것, 인용문 안의 필드명을 바꿔 쓰면 안 된다. 실험 설계 = 매뉴얼이 말하는 진동은 느린 네트워크나 오래된 타임스탬프 이벤트에서 잘 나오므로 tc/netem으로 복제 링크를 느리게 하거나 릴레이 로그가 쌓인 상태에서 관측할 것. 대량 UPDATE만으로는 진동이 안 나올 수 있으니 "재현 실패"도 결과로 적을 각오를 할 것

## A11 세미싱크 페일오버 유실
- 주장: 2노드 semi-sync에서 레플리카 응답이 끊겨 타임아웃이 만료되면 마스터가 async로 폴백하고, 그 구간의 커밋은 어떤 레플리카도 받지 않은 채 클라이언트에 성공 응답이 나간다. 이때 마스터가 죽고 레플리카가 승격되면 커밋 응답을 받은 트랜잭션이 사라지며 GTID로 증명 가능하다
- 출처: MySQL 8.0 Reference Manual 19.4.10 Semisynchronous Replication https://dev.mysql.com/doc/refman/8.0/en/replication-semisync.html : 폴백 동작 — "If a timeout occurs without any replica having acknowledged the transaction, the source reverts to asynchronous replication. When at least one semisynchronous replica catches up, the source returns to semisynchronous replication." 기본 대기 지점 — "By default, the source waits for replica acknowledgment of the transaction receipt after syncing the binary log to disk, but before committing the transaction to the storage engine." 페일오버 경고(Important 블록) — "With semisynchronous replication, if the source crashes and a failover to a replica is carried out, the failed source should not be reused as the replication source, and should be discarded. It could have transactions that were not acknowledged by any replica, which were therefore not committed before the failover." (원문)
- 출처: MySQL 8.0 Reference Manual 19.1.6.2 Replication Source Options and Variables https://dev.mysql.com/doc/refman/8.0/en/replication-options-source.html : rpl_semi_sync_source_timeout = "A value in milliseconds that controls how long the source waits on a commit for acknowledgment from a replica before timing out and reverting to asynchronous replication.", Default Value 10000. AFTER_COMMIT 모드에 대해서는 클라이언트 관점 유실을 문서가 직접 인정 — "If something goes wrong such that the replica does not process the transaction, then in the event of an unexpected source server exit and failover to the replica, it is possible for such clients to see a loss of data relative to what they saw on the source." (원문)
- 출처: PlanetScale Engineering Blog "MySQL semi-sync replication: durability, consistency and split brains"(Shlomi Noach, 2020-10-02) https://planetscale.com/blog/mysql-semi-sync-replication-durability-consistency-and-split-brains : 글 실재. "The primary waits up to rpl_semi_sync_master_timeout, after which it falls back to asynchronous replication mode, committing and responding to the user even if not all expected replicas have acknowledged receipt." 세미싱크의 약속을 "We promised that 'if the primary tells you a commit is successful, then the data is durable elsewhere'."로 요약. 다만 이 글의 대표 시나리오는 폴백 직후 마스터 사망이 아니라 primary와 ack한 레플리카가 같은 DC에서 함께 격리되는 스플릿브레인 쪽이다 (원문 — 단 격리 시나리오 대목은 페치 요약이 문장을 이어붙여 돌려줬으므로 인용문으로 옮기지 말고 원문 재확인할 것)
- 판정: E2 유지, 단 출처 표기 수정 필요 : 공식 매뉴얼이 async 폴백 동작과 구 마스터 폐기 경고를 직접 내므로 E2 조건은 충분. 그러나 PlanetScale 글은 자사 장애 포스트모템이 아니라 엔지니어링 해설이므로 E1로 승격할 수 없고 "PlanetScale이 겪은 장애"로 소개하면 사실 왜곡이다. 카탈로그 행의 출처 표기를 "PlanetScale(Shlomi Noach) 기술 해설"로 좁힐 것
- 메모: 인용 가능 = rpl_semi_sync_source_timeout 기본값 10000ms(매뉴얼 Default Value 명시). 인용 금지 = rpl_semi_sync_master_wait_for_slave_count 기본값, 세미싱크 성능 오버헤드 수치, PlanetScale 실제 운영 노드 수 — 이번에 확인 안 함. 논리 주의 = (1) AFTER_COMMIT의 "clients ... see a loss of data" 문장은 AFTER_COMMIT 한정이다. 기본값 AFTER_SYNC에서의 유실은 "타임아웃 후 async 폴백 → 아무도 ack 안 한 커밋에 성공 응답" 경로로 설명해야 하며, 두 문장을 섞어 "매뉴얼이 AFTER_SYNC에서도 유실을 인정한다"고 쓰면 오독 (2) 매뉴얼 Important 블록의 트랜잭션은 "커밋되지 않았다"고 적혀 있고 우리가 재현하려는 건 폴백 이후 커밋되고 응답까지 나간 트랜잭션이다. 이 차이를 뭉개지 말고 "매뉴얼이 경고하는 케이스보다 한 단계 더 나쁜 구간이 폴백 창"이라는 각도로 쓰는 편이 정직하고 강하다. 실험 설계 = 폴백 유도는 레플리카 IO를 죽이거나 멈춘 뒤 타임아웃(기본 10초, 실험에선 짧게)을 넘기고 Rpl_semi_sync_master_status가 ON→OFF로 떨어지는 것을 상태값으로 캡처. 증명은 승격 레플리카의 Executed_Gtid_Set에 문제 트랜잭션 GTID가 빠져 있음을 보이는 방식. 2노드면 폴백 조건 만들기는 쉽지만 "3노드면 안 나는 문제 아니냐"는 반문이 가능하므로, 노드를 늘려도 wait_for_slave_count를 못 채우면 같은 폴백이 난다는 점을 한 줄 짚을 것
