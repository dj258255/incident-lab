## A02 온라인 DDL MDL 폭풍
- 주장: 롱 쿼리/트랜잭션이 잡은 메타데이터 락에 ALTER가 대기하고, 그 뒤 SELECT까지 전부 블록되는 MySQL 대표 함정
- 출처: MySQL 8.0 Reference Manual "Metadata Locking" https://dev.mysql.com/doc/refman/8.0/en/metadata-locking.html : 트랜잭션 종료까지 MDL 유지, 미완료 트랜잭션이 쓰는 테이블에 DDL 불허, ALTER/DROP이 MDL 해제까지 블록되는 예시 명시 (원문)
- 판정: E2 유지 : 벤더 공식 문서가 메커니즘을 직접 경고, 특정 사건 인용 없음도 행과 일치
- 메모: "뒤의 SELECT까지 블록"은 ALTER의 배타적 MDL 대기 뒤로 큐잉되는 표준 동작이라 재현으로 보여주기 적절. lock_wait_timeout·LOCK=NONE 비교도 공식 문서 범위

## A03 utf8 vs utf8mb4
- 주장: MySQL utf8은 3바이트 축소판이라 이모지(보조 평면) 저장 불가, utf8mb4 전환 시 인덱스 767바이트 제한 이슈
- 출처: MySQL 8.0 Reference Manual "The utf8mb3 Character Set" https://dev.mysql.com/doc/refman/8.0/en/charset-unicode-utf8mb3.html : 문자당 최대 3바이트·BMP만 지원(보조 문자 불가)·utf8=utf8mb3 별칭·deprecated 명시 (원문)
- 출처: MySQL 8.0 Reference Manual "Limits on InnoDB Tables" https://dev.mysql.com/doc/refman/8.0/en/innodb-limits.html : REDUNDANT/COMPACT 행 포맷 인덱스 키 프리픽스 767바이트, DYNAMIC/COMPRESSED는 3072바이트, utf8mb4 4바이트 기준 191자 예시까지 문서에 명시 (원문)
- 판정: E2 유지 : 두 주장 모두 벤더 공식 문서로 확인
- 메모: 재현 주의 = MySQL 8.0 기본 행 포맷은 DYNAMIC(3072바이트)이라 767 제한을 보이려면 ROW_FORMAT=COMPACT 지정 또는 5.x 계열 필요. "가짜 UTF-8"이라는 표현은 블로그식 수사이고 공식 용어는 BMP-only

## A04 MSSQL 락 에스컬레이션
- 주장: 단일 문이 약 5,000개 락 초과 시 테이블 락으로 승격, LOCK_ESCALATION 옵션·배치 분할로 완화
- 출처: Microsoft Learn "Transaction locking and row versioning guide" https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17 : "단일 T-SQL 문이 한 테이블 참조에 최소 5,000개 락 획득 시 에스컬레이션", 로우/페이지 락은 페이지가 아니라 곧장 테이블 락으로 승격, ALTER TABLE SET LOCK_ESCALATION(AUTO/TABLE/DISABLE) 명시 (원문)
- 판정: E2 유지 : 벤더 공식 문서에 임계값·동작·완화책 전부 명시
- 메모: 인용 가능 수치 = 5,000(최소치, "약 5,000 초과"보다 "5,000개 이상"이 정확), 승격 실패 시 1,250개마다 재시도. 재현 주의 = 최신 SQL Server의 optimized locking 활성 시 에스컬레이션이 잘 안 일어나므로 재현 환경에선 꺼야 함

## A05 커넥션 폭풍 + PgBouncer
- 주장: PG 프로세스-퍼-커넥션 모델에서 대량 재연결 시 DB 자체는 정상인데 락 경합·컨텍스트 스위치로 서비스가 마비, 풀러(PgBouncer)로 해소
- 출처: PostgreSQL Wiki "Number Of Database Connections" https://wiki.postgresql.org/wiki/Number_Of_Database_Connections : 과다 커넥션의 해악(스핀락·LW락 경합, 컨텍스트 스위치, 캐시라인 경합) 설명, 커넥션 줄이고 외부 풀링 권장, 최적 활성 커넥션 공식 ((core_count*2)+effective_spindle_count) 명시 (원문)
- 판정: E2 유지 : 공식 위키가 메커니즘과 풀링 권장을 직접 서술
- 메모: max_connections 초과 시 에러 문구는 "FATAL: sorry, too many clients already"가 정식 표기(행의 "too many connections"는 MySQL식 문구와 혼동 주의). 풀 공식은 인용 가능하되 SSD 환경 단서 있음

## A06 갭 락 데드락
- 주장: REPEATABLE READ에서 갭 락은 서로 충돌하지 않고 공존, insert intention이 갭 락에 대기 → 범위 겹친 두 세션 + INSERT 조합이 대표 데드락
- 출처: MySQL 8.0 Reference Manual "InnoDB Locking" https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html : "갭 락은 공존 가능, 공유/배타 구분 없이 서로 충돌하지 않음" + insert intention lock이 기존 갭 락에 대기하는 SHOW ENGINE INNODB STATUS 예시("lock_mode X locks gap before rec insert intention waiting")까지 문서에 수록 (원문)
- 출처: Tecoble "데드락 해결 모험기"(2022-11-01) https://tecoble.techcourse.co.kr/post/2022-11-01-mysql-dead-lock/ : 실무 데드락 사례 글 실재 확인 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 데드락 성립 메커니즘 전체가 벤더 공식 문서로 증명됨
- 메모: "실무 데드락 최다 빈출"은 통계가 아니라 경험칙이므로 블로그화 시 단정 표현 피할 것. 카탈로그가 언급한 우형(우아한형제들) 글은 이번 검색에선 미확인 — 인용하려면 별도 확인 필요

## A07 롱 트랜잭션 2차 피해
- 주장: idle in transaction 하나가 MySQL은 undo(history list length) 폭증, PG는 VACUUM 무력화(dead tuple 누적)를 유발
- 출처: MySQL 8.0 Reference Manual "Purge Configuration" https://dev.mysql.com/doc/refman/8.0/en/innodb-purge-configuration.html : "롱 트랜잭션이 History list length를 증가시킨다" + MVCC가 의존 트랜잭션 종료까지 undo 보존, autocommit 끄고 COMMIT 잊은 SELECT가 대표 사례로 명시 (원문)
- 출처: Cybertec "VACUUM won't remove dead rows: 4 reasons why" https://www.cybertec-postgresql.com/en/reasons-why-vacuum-wont-remove-dead-rows/ : 롱 트랜잭션(스냅샷 유지)이 dead row 제거를 막는 원인 1순위로 설명 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : MySQL 쪽은 벤더 공식 문서로 완전 확인, PG 쪽 메커니즘도 다수 문헌 일치
- 메모: 현행 PG 공식 문서 routine-vacuuming.html에는 "롱 트랜잭션이 VACUUM을 막는다" 직접 경고 문장이 없음(문서 개편) — 블로그화 시 PG 근거는 공식 문서 대신 pg_stat_activity의 idle in transaction 상태 + n_dead_tup 실측으로 보이는 편이 안전
