## B05 리트라이 폭풍 / metastable
- 주장: 짧은 타임아웃 + 무제한 재시도가 work amplification을 만들어, 부하(트리거)를 걷어내도 회복하지 못하는 준안정 상태에 빠진다 — HotOS 2021 논문이 개념화했고 AWS 장애의 복구 지연 원인이다
- 출처: Bronson·Aghayev·Charapko·Zhu "Metastable Failures in Distributed Systems" HotOS '21, DOI 10.1145/3458336.3465286 https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf : PDF를 내려받아 본문 텍스트로 확인. §1 — "Metastable failures occur in open systems with an uncontrolled source of load where a trigger causes the system to enter a bad state that persists even when the trigger is removed. In this state the goodput ... is unusably low, and there is a sustaining effect—often involving work amplification or decreased overall efficiency—that prevents the system from leaving the bad state." §2.1 — "One of the most common failure-sustaining mechanisms is request retries. ... it also results in work amplification, which can lead to additional failures." / "Recovery from the metastable state requires reducing the web application load to under 150 QPS or limiting retries to less than 20 QPS." (원문)
- 출처: Marc Brooker "Exponential Backoff And Jitter" AWS Architecture Blog 2015-03-04 https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/ : "With N clients contending, the total amount of work done by the system increases with N2." / "The solution isn't to remove backoff. It's to add jitter." (원문)
- 출처: Google SRE Book Ch.22 "Addressing Cascading Failures" https://sre.google/sre-book/addressing-cascading-failures/ : "Missed RPC deadlines. As a server becomes overloaded, its responses to RPCs from its clients arrive later, which may exceed any deadlines those clients set. The work the server did to respond is then wasted, and clients may retry the RPCs, leading to even more overload." (원문)
- 출처: AWS Builders' Library "Timeouts, retries, and backoff with jitter" https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/ : 301로 builder.aws.com 이동, 본문이 스크립트 렌더링이라 텍스트를 못 읽음 → 내용 확인 실패, 인용 불가 (미확인)
- 판정: E2 유지, 단 회사 귀속 수정 필요 : 논문 원문과 AWS 공식 블로그가 실재하고 메커니즘을 정확히 서술하므로 E2 요건은 충족. 그러나 카탈로그의 "AWS 장애 복구 지연의 원인"은 확인하지 못했다 — 논문은 AWS를 한 번도 언급하지 않고, 저자 소속은 Rockset·Facebook(전)·Penn State·UNH이며, 논문이 참조하는 실사례는 Facebook Engineering의 link imbalance 글(2014)과 Ben Maurer "Fail at Scale"(ACM Queue 2015)이다. retry budget 각주 [4]도 AWS가 아니라 Google SRE Book이다. **"AWS 장애" → "Facebook 계열 하이퍼스케일 운영 경험 + AWS 공식 백오프·지터 권고"로 고칠 것**
- 메모: 인용 가능 = 논문 예시의 300 QPS/100ms, 1s 타임아웃, 280→560 QPS, 안정 구간 150 QPS 이하, 재시도 20 QPS 제한. **단 이건 논문이 든 가상 예시지 실측이 아니므로 "논문이 예로 든 수치"라고 명시할 것.** 인용 금지 = AWS Builders' Library의 재시도 예산 서술(본문 확인 실패), Marc Brooker 글의 실험 표 숫자(요약본만 봄, 인용 가능한 건 N² 문장뿐), "AWS 장애 사례"라는 표현. 승격을 노린다면 Facebook Engineering의 link imbalance 글을 열어보면 E1 가능성이 있다

## B06 핫 로우 카운터 경합
- 주장: 단일 카운터 행에 UPDATE가 몰리면 행 락 대기로 처리량이 붕괴한다. 카운터 샤딩·Redis 집계로 해결한다
- 출처: PostgreSQL 공식 문서 13.3.2 Row-Level Locks https://www.postgresql.org/docs/current/explicit-locking.html : "Row-level locks do not affect data querying; they block only writers and lockers to the same row." / "other transactions that attempt UPDATE, DELETE, SELECT FOR UPDATE ... of these rows will be blocked until the current transaction ends" / "two transactions can never hold conflicting locks on the same row" (원문)
- 출처: CockroachDB 공식 문서 "Understand Hotspots" https://www.cockroachlabs.com/docs/stable/understand-hotspots : "A row hotspot is a hotspot where an individual point in the keyspace becomes throughput limiting, often due to high activity on a single row." / "Since rows are inherently indivisible, a hotspot on a row cannot be split." (원문)
- 출처: 2차 자료 다수(Medium "Ultra fast asynchronous counters in Postgres", oneuptime, outof.fish) : 카운터 있을 때 처리량 1/5, bin 카운터로 4배 개선 같은 수치가 돌아다님 (2차, 검색 결과 스니펫으로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 특정 사건은 없지만 "동일 행 writer는 직렬화된다"를 PG 공식 문서가 규범으로 명시하고, "단일 행이 처리량 한계가 된다·행은 쪼갤 수 없다"를 CockroachDB 공식 문서가 안티패턴으로 명명해 경고한다. E2 정의에 정확히 부합
- 메모: 인용 가능 = 위 PG·CRDB 원문 두 덩어리. **인용 금지 = "5배 느려진다", "샤딩하면 4배" 같은 블로그 숫자** — 스니펫으로만 봤고 벤치 조건도 불명이다. 처리량 붕괴 그래프는 이 랩에서 직접 측정한 값으로만 그릴 것. CockroachDB는 PG 와이어 호환일 뿐 다른 엔진이니 "CRDB 문서가 이 안티패턴을 hot row라 부른다"까지만 쓰고 PG 동작으로 확대 해석하지 말 것. MySQL/InnoDB 공식 문서는 이번 예산으로 확인 못 했으므로 실험을 MySQL로 할 거면 InnoDB 락 근거를 따로 채울 것

## B07 핫 파티션 + request coalescing
- 주장: Discord가 인기 채널 쏠림(핫 파티션)을 동일 키 요청 합치기로 해결했다 — 출처 InfoQ, 등급 E1
- 출처: Bo Ingram(Discord) "How Discord Stores Trillions of Messages" Discord 공식 블로그 2023-03-06 https://discord.com/blog/how-discord-stores-trillions-of-messages : 핫 파티션 — "Lots of concurrent reads as users interact with servers can hotspot a partition, which we refer to imaginatively as a 'hot partition'." coalescing — "If multiple users are requesting the same row at the same time, we'll only query the database once. The first user that makes a request causes a worker task to spin up in the service. Subsequent requests will check for the existence of that task and subscribe to it." 라우팅 — "consistent hash-based routing to our data services to enable more effective coalescing. ... For messages, this is a channel ID, so all requests for the same channel go to the same instance." 규모 = 2017년 12노드 → 2022년 초 177노드 → ScyllaDB 마이그레이션(2022-05) 후 72노드. 지연 = 읽기 p99 40~125ms → 15ms, 쓰기 p99 5~70ms → 5ms (원문)
- 출처: Rafał Gancarz "Discord Migrates Trillions of Messages from Cassandra to ScyllaDB" InfoQ 2023-06-22 https://www.infoq.com/news/2023/06/discord-cassandra-scylladb/ : Bo Ingram 인용 "When we encountered a hot partition, it frequently affected latency across our entire database cluster." 이 기사는 1차 출처로 위 Discord 블로그를 링크한다 (원문 확인, 다만 매체 성격은 2차)
- 판정: E1 유지 + 출처 표기 수정 필수 : 1차 출처(Discord 자사 블로그)가 실재하고 저자·날짜·인용문이 확인됐다. 카탈로그가 출처를 "(InfoQ)"로 적은 건 2차 매체를 1차처럼 세운 것이니 "Discord 공식 블로그(2023-03-06, Bo Ingram), InfoQ는 요약 보도"로 바꿀 것. 다만 이 글은 **단일 사건 포스트모템이 아니라 만성 운영 문제 + 마이그레이션 회고**이므로 "Discord가 공개한 ○년 ○월 장애"처럼 사건화하면 원문과 다르다
- 메모: 인용 가능 = 12→177→72노드, 읽기 p99 40~125ms → 15ms, 쓰기 p99 5~70ms → 5ms, 2022-05 마이그레이션. **인용 금지 = 저 지연 개선을 coalescing의 효과로 쓰는 것** — 원문에서 저 수치는 Cassandra→ScyllaDB 마이그레이션 전체의 결과고 coalescing 단독 효과 수치는 없다. coalescing은 "DB 쿼리를 1회로 합친다"는 정성적 서술까지만 근거가 있다. 라우팅 키가 채널 ID라는 점(같은 키를 같은 인스턴스로 몰아야 합쳐진다)은 랩 설계에 그대로 쓸 핵심

## B08 GC 스톨 연쇄 타임아웃
- 주장: JVM stop-the-world 정지가 상류의 타임아웃·재시도 연쇄를 유발한다
- 출처: Oracle "Java Garbage Collection Basics" https://www.oracle.com/webfolder/technetwork/tutorials/obe/java/gc01/index.html : "Stop the World Event - All minor garbage collections are 'Stop the World' events. This means that all application threads are stopped until the operation completes." / "Major garbage collections are also Stop the World events" (원문)
- 출처: Google SRE Book Ch.22 https://sre.google/sre-book/addressing-cascading-failures/ : "Increased rate of garbage collection (GC) in Java ... A vicious cycle can occur in this scenario: less CPU is available, resulting in slower requests, resulting in increased RAM usage, resulting in more GC, resulting in even lower availability of CPU. This is known colloquially as the 'GC death spiral.'" + missed RPC deadlines·in-flight requests 서술 (원문)
- 출처: Netflix Hystrix Wiki https://github.com/Netflix/Hystrix/wiki : "With high volume traffic a single backend dependency becoming latent can cause all resources to become saturated in seconds on all servers." (원문)
- 출처: Oracle "HotSpot VM GC Tuning Guide"(Java SE 17) https://docs.oracle.com/en/java/javase/17/gctuning/introduction-garbage-collection-tuning.html : 접속했으나 STW 정의 문장은 이 페이지에 없었다. 쓸 만한 건 "The red line is an application spending only 1% of the time in garbage collection on a uniprocessor system. This translates to more than a 20% loss in throughput on systems with 32 processors."뿐(처리량 손실이지 지연 스파이크가 아님) (원문)
- 출처: Bo Ingram "How Discord Stores Trillions of Messages" https://discord.com/blog/how-discord-stores-trillions-of-messages : 실운영 사례 — "GC pauses affecting latency, all the way to super long consecutive GC pauses that got so bad that an operator would have to manually restart and babysit the node"(원문 동사는 restart가 아니라 재기동 표현) (원문, B07에서 연 문서 교차 인용)
- 판정: E2 유지 : STW 존재는 Oracle이, "느려진 응답 → 상류 데드라인 초과 → 재시도 → 추가 과부하"는 Google SRE Book이, "단일 의존성 지연이 초 단위로 전 서버 리소스를 포화시킨다"는 Hystrix 공식 위키가 명시. 다만 **"JVM STW가 원인이라고 특정한 기업 포스트모템"은 확보 못 했으므로 E1 승격 불가**
- 메모: 인용 가능한 수치는 사실상 없다 — 유일한 숫자인 "1% GC → 32프로세서에서 20% 이상 처리량 손실"은 멀티코어 확장성 맥락의 그림 설명이라 **"GC 1%면 응답이 20% 느려진다"로 바꿔 쓰면 오독**. 쓰려면 원문 조건을 그대로 붙일 것. 글의 인과 사슬은 세 출처를 이어 붙여 만드는 구성이므로 "○○사 장애였다"는 문장은 쓰지 말고, 실사례가 필요하면 Discord의 Cassandra GC 사례를 각주로만. 정지 시간·서킷브레이커 임계값은 전부 직접 측정값으로 채울 것

## B09 Kafka 슬로우 컨슈머·리밸런스 스톰
- 주장: 느린 컨슈머가 있는 상태에서 컨슈머를 추가하면 리밸런스(stop-the-world)가 반복되어 오히려 lag이 커지고, cooperative rebalancing·백프레셔가 해법이다
- 출처: Apache Kafka 4.0 KafkaConsumer Javadoc "Detecting Consumer Failures" https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html : "Basically if you don't call poll at least as frequently as the configured max interval, then the client will proactively leave the group so that another consumer can take over its partitions." / "increasing this value may delay a group rebalance since the consumer will only join the rebalance inside the call to poll." / 공식 권고 — "The recommended way to handle these cases is to move message processing to another thread, which allows the consumer to continue calling poll while the processor is still working." (원문)
- 출처: KIP-429 Kafka Consumer Incremental Rebalance Protocol https://cwiki.apache.org/confluence/display/KAFKA/KIP-429%3A+Kafka+Consumer+Incremental+Rebalance+Protocol : "Recently Kafka community is promoting cooperative rebalancing to mitigate the pain points in the stop-the-world rebalancing protocol" / "when rebalance starts, all stream threads would Join group with all currently assigned tasks revoked." / 목표 "Reduce unnecessary downtime due to unnecessary partition migration". 상태 Accepted(2.4.0) (원문)
- 출처: Confluent Platform 문서 Consumer https://docs.confluent.io/platform/current/clients/consumer.html : "As new group members arrive and old members leave, the partitions are re-assigned" / "If no heartbeat is received before expiration of the configured session timeout, then the coordinator will kick the member out of the group" (원문, 이 두 문장만 축자 인용)

## B10 클럭 스큐(시간 역행)
- 주장: 2017년 윤초 때 Cloudflare에서 음수 duration으로 panic이 났고, 이 사건이 Go monotonic clock 도입의 계기였다
- 출처: Cloudflare 공식 포스트모템, John Graham-Cumming "How and why the leap second affected Cloudflare DNS" 2017-01-01 https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/ : "At midnight UTC on New Year's Day, deep inside Cloudflare's custom RRDNS software, a number went negative when it should always have been, at worst, zero. A little later this negative value caused RRDNS to panic. This panic was caught using the recover feature of the Go language." / 근본 원인 — "The root cause of the bug that affected our DNS service was the belief that time cannot go backwards." / "this function does not guarantee monotonicity. Go currently doesn't offer a monotonic time source (see issue 12914 for discussion)." / panic 지점 — "rand.Int63n promptly panics if its argument is negative." / 영향 — "At peak approximately 0.2% of DNS queries to Cloudflare were affected and less than 1% of all HTTP requests to Cloudflare encountered an error." / "The most affected machines were patched in 90 minutes and the fix was rolled out worldwide by 0645 UTC." (원문)
- 출처: Russ Cox "Proposal: Monotonic Elapsed Time Measurements in Go" 최종 수정 2017-01-26 https://github.com/golang/proposal/blob/master/design/12914-monotonic.md : "A Go program measuring a negative elapsed time during a leap second caused CloudFlare's recent DNS outage." / "Entering a leap second, the clock might report 23:59:59.995 at one instant and then report 23:59:59.005 ten milliseconds later; subtracting these to compute elapsed time results in −990 ms instead of +10 ms." (원문)
- 출처: golang/go issue #12914 https://github.com/golang/go/issues/12914 (GitHub API로 메타데이터 조회) : created_at 2015-10-13, closed_at 2017-02-03, milestone Go1.9. **즉 이슈는 Cloudflare 장애보다 약 15개월 먼저 열려 있었다** (원문 메타데이터)
- 출처: Go 1.9 Release Notes https://go.dev/doc/go1.9 : "The release adds transparent monotonic time support" — Go 1.9(2017-08) 반영 확인 (원문)
- 판정: E1 유지, 단 "도입 계기" 표현 수정 필수 : Cloudflare 공식 포스트모템 원문이 존재하고 panic·음수 duration·영향 비율까지 원문에 그대로 있다
- 메모: 인용 가능 = 0.2%(DNS 쿼리), 1% 미만(HTTP 요청), 90분/0645 UTC 롤아웃, rand.Int63n panic, time.Now().Sub(start) 코드. **인용 금지 = "이 사건 때문에 Go에 monotonic clock이 생겼다"** — 타임라인이 반증한다(이슈 #12914는 2015-10-13에 열렸고 Cloudflare 글 자체가 "see issue 12914 for discussion"이라며 이미 논의 중이던 이슈를 가리킨다). 정확한 표현은 "1년 넘게 방치돼 있던 제안이 이 장애를 실증 사례로 삼은 Russ Cox의 설계 문서(2017-01-26) 뒤 2017-02-03에 Go 1.9 마일스톤으로 닫혔다" — "계기"가 아니라 "결정타/실증 사례". Cloudflare는 panic을 recover로 잡았다고 명시했으므로 "서버가 죽었다"고 쓰면 오류. 영향 범위도 "CNAME 레코드를 쓰는 고객, 일부 머신"으로 한정할 것

## B11 우형 Redis New Connection
- 주장: 커넥션 풀의 LIFO 정책과 eviction 설정이 맞물려 신규 커넥션이 계속 생성됐다는 우아한형제들 사례
- 출처: 우아한형제들 기술블로그, 이병훈 "Redis New Connection 증가 이슈 돌아보기" 2025-10-14 https://techblog.woowahan.com/23121/ : 환경 — "Spring Boot 3.2.4 / lettuce 6.3.2 / elasticache valkey 8", "commons-pool2:2.12.0", "풀의 개수 설정은 최대 20개". LIFO — "GenericObjectPool을 사용하는 경우, 커넥션풀에서 커넥션을 가져오는 전략은 기본적으로 LIFO 전략입니다. 즉, 커넥션 풀 내부에 있는 모든 커넥션을 고르게 사용하는 것이 아닌, 최근에 사용한 커넥션 위주로 사용하는 전략입니다." eviction — "timeBetweenEvictionRuns의 기본값은 -1입니다. ... minEvictableIdleDuration의 기본값은 30분입니다. 프로젝트 설정 내에서는 위 두 설정이 존재하지 않아 IDLE 커넥션이 계속해서 남아있는 상태였습니다." 결정적 방아쇠 — "Elasticache 기준으로 timeout 파라미터가 100으로 설정되어 있어, 100초간 idle 커넥션을 사용하지 않으면 Elasticache에서 커넥션을 제거하고 있었습니다." / "서버 기준에서는 elasticache에서 커넥션을 닫으면, 서버의 ConnectionWatchDog에 의해 재연결이 되고 있었습니다." 풀이 쓰인 이유 — "executePipelined 메소드를 사용하는 경우, 파이프라이닝 처리를 위한 전용 커넥션을 할당받게 됩니다." 해결 — 2번안(minEvictableIdleDuration 30s + timeBetweenEvictionRuns 30s) 채택 (원문 전문 확인 — techblog.woowahan.com이 직접 접속을 403 차단해 Wayback Machine 스냅샷 20251014134112로 본문 전체를 읽음)
- 판정: E1 유지, 단 "장애"가 아님 : 회사가 자기 프로덕션 문제를 설정값·코드까지 공개한 1차 기록이다. 다만 사용자 영향이나 다운타임 서술은 글에 없고 지표 이상을 추적해 원인을 밝힌 분석기다. "우아한형제들 장애"가 아니라 "우아한형제들이 공개한 커넥션 지표 이상 분석"으로 부를 것
- 메모: 인용 가능 = Elasticache timeout=100초, 풀 maxActive=20, timeBetweenEvictionRuns 기본 -1, minEvictableIdleDuration 기본 30분, DEFAULT_LIFO=true, Spring Boot 3.2.4/Lettuce 6.3.2/commons-pool2 2.12.0/ElastiCache Valkey 8, 해결안 30초/30초. 인용 금지 = 신규 커넥션 수·지연·장애 시간 같은 정량값(글에는 그래프만 있고 숫자가 없다). **카탈로그 서술 수정 3건**: (1) 풀 LIFO·eviction만으로는 신규 커넥션이 안 생긴다 — 서버 쪽 Redis timeout이 idle 커넥션을 끊어야 ConnectionWatchdog 재연결이 돌고 New Connection이 찍힌다. 재현 시나리오에 서버 timeout 설정을 반드시 넣을 것 (2) **Jedis는 이 글에 전혀 나오지 않는다** — 전부 Lettuce + commons-pool2 사례이므로 "Lettuce/Jedis 비교"로 쓰려면 Jedis 쪽은 자체 실험이라고 분리 표기할 것 (3) Lettuce는 기본적으로 커넥션 하나를 공유하므로, 풀이 개입한 이유가 RedisTemplate.executePipelined()의 전용 커넥션 할당이라는 점을 빼면 재현이 안 된다

## B12 Facebook memcache lease
- 주장: NSDI 2013 "Scaling Memcache at Facebook" 논문이 제시한 lease가 thundering herd의 해법이다
- 출처: Nishtala 외 12인(Facebook) "Scaling Memcache at Facebook" NSDI '13, pp.385–398, §3.2.1 Leases : "We introduce a new mechanism we call leases to address two problems: stale sets and thundering herds. ... A thundering herd happens when a specific key undergoes heavy read and write activity. As the write activity repeatedly invalidates the recently set values, many reads default to the more costly path." 토큰 — "The lease is a 64-bit token bound to the specific key the client originally requested. ... Leases prevent stale sets in a manner similar to how load-link/store-conditional operates." 스탬피드 억제 — "Each memcached server regulates the rate at which it returns tokens. By default, we configure these servers to return a token only once every 10 seconds per key. Requests for a key's value within 10 seconds of a token being issued results in a special notification telling the client to wait a short amount of time." 실측 — "Without leases, all of the cache misses resulted in a peak database query rate of 17K/s. With leases, the peak database query rate was 1.3K/s." (원문 — usenix.org 직접 링크는 403이라 동일 USENIX 조판 PDF(pdos.csail.mit.edu/6.824/papers/memcache-fb.pdf)를 내려받아 §3.2.1 전문 확인. 페이지 헤더가 NSDI '13 pp.385–398로 찍혀 있어 정식 판본과 동일)
- 판정: 승격 제안 E2→E1 : 등급 정의상 E1은 "학술 논문 원문이 존재"를 포함하고, 이 논문은 Facebook 자사가 자기 프로덕션 문제와 실측 수치(17K/s → 1.3K/s)를 직접 공개한 1차 문헌이다. 벤더 문서의 일반 경고(E2)보다 근거 강도가 한 단계 위다. 다만 "장애 포스트모템"은 아니므로 "○○사가 공개한 장애"라는 표현은 쓰지 말고 "Facebook이 NSDI에 공개한 자사 프로덕션 문제와 해법"으로 부를 것
- 메모: 인용 가능 = 64-bit 토큰, "once every 10 seconds per key", 17K/s → 1.3K/s. **인용 시 조건을 반드시 붙일 것** — 전체 트래픽이 아니라 "a set of keys particularly susceptible to thundering herds"에 한정된 수치이고 평균이 아니라 peak다. 조건을 떼고 "13배 감소"만 쓰면 왜곡. 구현 주의 = 논문의 lease는 (a) stale set 방지와 (b) thundering herd 억제 두 기능이 한 메커니즘에 붙어 있다. B02에서 "스탬피드 해법 4안째"로 비교할 때 (b)만 구현하면 논문 lease의 절반이므로 그 사실을 명시할 것

## B13 Notion식 샤딩·재샤딩
- 주장: Notion이 Postgres 모놀리스 한계로 여러 대 PG + workspace_id 라우팅 수평 샤딩으로 전환했고, 더블 라이트 → 백필 → 검증 → 스위치오버 절차를 밟았다
- 출처: Notion 공식 블로그 "Herding elephants: Lessons learned from sharding Postgres at Notion"(Garrett Fidalgo, 2021-10-06) https://www.notion.com/blog/sharding-postgres-at-notion : 동기 — "Engineers on-call often woke up to database CPU spikes, and simple catalog-only migrations became unsafe and uncertain." 결정타는 "the Postgres VACUUM process began to stall consistently, preventing the database from reclaiming disk space from dead tuples"로 인한 TXID wraparound 위험. 규모 = 480 logical shards / 32 physical databases(DB당 15), 파티션 키 workspace ID, 설계 상한 table당 500GB·물리 DB당 10TB. 더블 라이트는 audit log 방식 — "Create an audit log table to keep track of all writes to the tables under migration. A catch-up process iterates through the audit log and applies each update to the new databases."(직접 이중 쓰기는 "too flaky", logical replication은 속도 미달로 기각). 백필 — "With all 96 CPUs on the m5.24xlarge instance we provisioned, our final script took around three days to backfill the production environment." 스위치오버 — "five minutes of scheduled maintenance" (원문)
- 출처: Notion 공식 블로그 "The Great Re-shard: adding Postgres capacity (again) with zero downtime"(2023-07-17) https://www.notion.com/blog/the-great-re-shard : 물리 DB 32 → 96, DB당 logical schema 15 → 5. 동기 — "Some of the shards were exceeding 90% CPU utilization at peak traffic", IOPS 포화, "We were running into connection limits scaling our PgBouncer deployment". 방식은 2021년과 달리 PG 내장 logical replication + dark read 검증, 동기화 "from 3 days to 12 hours", "there was no report or observation in our metrics of perceived user downtime" (원문)
- 판정: E1 유지 : 공식 블로그 두 편을 직접 확인했고 "샤딩·재샤딩" 두 단계 모두 각각의 글이 뒷받침한다. 규모·시점·절차 수치가 전부 인용 가능한 형태로 존재
- 메모: 프레이밍 주의 — 두 글은 포스트모템이 아니라 성공한 마이그레이션 회고다. "Notion의 장애"라고 쓰면 원문과 어긋나므로 "VACUUM 정지 → TXID wraparound 직전에 멈춘 사례"로 쓸 것. 인용 가능 = 480/32/15, workspace ID 파티션 키, 500GB·10TB 상한, 백필 3일(m5.24xlarge 96 vCPU), 스위치오버 5분(2021) / 32→96, 15→5, 90% CPU·IOPS·PgBouncer connection limit, 동기화 3일→12시간, 무중단(2023). **섞어 쓰면 안 되는 것** = 더블 라이트 방식이 두 글에서 다르다(2021은 audit log catch-up, 2023은 logical replication). 2021년엔 logical replication을 속도 때문에 기각했다는 점까지 같이 써야 앞뒤가 맞는다. 재현 난이도 "이틀+"는 타당 — 라우터·audit log·백필·dark read 네 부품을 다 만들어야 한다
