## B01 HikariCP
- 주장: 우형 메시지 플랫폼 실장애(풀 데드락) + pool size 공식의 출처 [E1]
- 출처: 우아한형제들 기술블로그 "HikariCP Dead lock에서 벗어나기 (이론편)" https://woowabros.github.io/experience/2020/02/06/hikaricp-avoid-dead-lock.html : 공통시스템개발팀 메시지 플랫폼에서 실장애, 한 태스크가 동시에 커넥션 2개 요구(@GeneratedValue)해 데드락 (원문)
- 출처: 같은 시리즈 "(실전편)" https://woowabros.github.io/experience/2020/02/06/hikaricp-avoid-dead-lock-2.html : "마법의 공식" pool size = Tn x (Cm - 1) + 1 명시, 출처로 HikariCP 공식 wiki About-Pool-Sizing 링크. 재현 환경 스레드 16 + pool 10 + 태스크당 커넥션 2개 (원문)
- 판정: E1 유지 : 기업 공식 기술블로그 원문에서 실장애·공식·wiki 출처 모두 확인
- 메모: techblog.woowahan.com/2664 는 WebFetch 403(접속 실패) — github.io 미러로 확인. 카탈로그 재현안(pool 10, 커넥션 2개)은 원문 수치와 일치, k6 20은 원문 스레드 16의 변형이라 문제 없음

## B02 스탬피드
- 주장: 인기 키 TTL 동시 만료 → DB 직행 폭주, 실무 빈출 함정 [E2]
- 출처: Vattani·Chierichetti·Lowenstein "Optimal Probabilistic Cache Stampede Prevention", PVLDB Vol.8 No.8 pp.886-897 (2015) http://www.vldb.org/pvldb/vol8/p886-vattani.pdf : VLDB 공식 아카이브에서 PDF 실재 확인(409KB 다운로드 성공, 본 환경에서 텍스트 추출만 불가). ACM DL 검색 결과로 제목·저자·게재지 교차 확인 (원문)
- 판정: E2 유지 : 현상 자체가 VLDB 논문으로 정식화돼 있어 "논문이 경고하는 반복 함정" 요건 충족
- 메모: 재현안의 3안 중 "확률적 조기 갱신"의 원 출처가 이 논문(XFetch 알고리즘) — 세션 README에서 인용 가치 있음. dl.acm.org·semanticscholar는 403/빈 페이지(접속 실패)

## B03 read-your-writes
- 주장: 복제 지연으로 "방금 쓴 게 안 보여요"가 나는 read-your-writes 미보장 문제 [E2]
- 출처: AWS RDS 공식 문서 "Working with DB instance read replicas" https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html : "Amazon RDS copies them asynchronously to the read replica" — 비동기 복제 명시, replica 데이터가 stale일 수 있다는 서술 확인 (원문)
- 출처: Azure Cosmos DB 공식 문서 "Consistency level choices" https://learn.microsoft.com/en-us/azure/cosmos-db/consistency-levels : "reads are guaranteed to honor the read-your-writes ... guarantees" — read-your-writes가 벤더 공식 문서에 정의된 표준 보장 용어임을 확인 (원문)
- 판정: E2 유지 : 비동기 복제 지연은 클라우드 벤더 공식 문서가 직접 서술, read-your-writes는 공식 정의된 일관성 보장 용어
- 메모: 해법 3안(세션 고정/임계 라우팅/primary)은 Cosmos DB session consistency의 세션 토큰 방식과 같은 계열이라 설계 타당

## B04 페이지네이션
- 주장: OFFSET 딥 페이지는 건너뛴 행도 서버가 전부 계산해 비용이 큼 [E2]
- 출처: PostgreSQL 공식 문서 "7.6. LIMIT and OFFSET" https://www.postgresql.org/docs/current/queries-limit.html : "The rows skipped by an OFFSET clause still have to be computed inside the server; therefore a large OFFSET might be inefficient." 경고 문장 원문 그대로 확인 (원문)
- 판정: E2 유지 : 벤더 공식 문서가 별도 경고를 내는 전형 사례, 요건 정확히 충족
- 메모: 행의 "OFFSET 100만"은 재현 설계값이지 출처 수치가 아님 — 문제 없음
