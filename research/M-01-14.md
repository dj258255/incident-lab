## M01 푸시 herd
- 주장: FCM 공식 문서가 정각 발송 시 첫 30초~2분 트래픽 2배 이상을 경고하며 해당 윈도 회피를 권고.
- 출처: Firebase "Best practices when sending FCM messages at scale" https://firebase.google.com/docs/cloud-messaging/scale-fcm : "FCM receives more than double traffic during the first 30 seconds to 2 minutes of each hour" 원문 확인. ":00, :15, :30, :45 각 마크의 2분 윈도 내 발송 회피" 권고, 서버측 스로틀링·"flatten the curve" 권고도 동일 문서에 존재 (원문)
- 판정: E2 유지 : 벤더 공식 문서의 명시적 경고와 수치·주체가 행과 정확히 일치.
- 메모: 원문은 정각뿐 아니라 15분 단위 마크 전부를 회피 대상으로 명시 — 블로그화 시 "정각·15분 단위"로 쓰면 더 정확. 수치 인용 금지 목록의 Apple ThunderingHerdPolicy와는 무관(이 행은 FCM만 인용).

## M02 멱등성
- 주장: 앱 타임아웃 재시도 시 서버는 이미 처리한 상태라 중복 주문 발생. 모바일 백엔드 실무 빈출 문제.
- 출처: AWS Builders Library "Making retries safe with idempotent APIs" https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/ : 재시도가 중복 워크로드를 만들 수 있음("Simply retrying the request could result in multiple workloads"), 클라이언트 제공 멱등 토큰 + 토큰 기록·변이 연산의 ACID 결합 요구를 명시 (원문)
- 출처: Stripe idempotency 문서 https://stripe.com/docs/idempotency (검색 결과로 존재 확인, 직접 페치는 안 함) : 연결 오류 시 같은 키로 안전 재시도, 24시간 후 키 정리 (원문·보조)
- 판정: E2 유지 : 벤더 공식 문서(AWS·Stripe)가 재시도-중복 문제와 멱등키 설계를 별도로 다룰 만큼 정착된 함정.
- 메모: "실무 빈출 1위"는 순위 통계 출처가 없는 수사적 표현 — 블로그에선 "가장 흔한 축에 드는"으로 완화 권장. AWS 문서는 동시 요청 레이스는 직접 다루지 않으므로 "순진한 멱등키가 동시 요청에서 깨진다" 부분은 재현 실험 자체가 근거(설계 오류 아님).

## M03 토큰 레이스
- 주장: 동시 401 → 같은 리프레시 토큰으로 동시 갱신 → RTR 재사용 탐지가 패밀리 전체 무효화 → 강제 로그아웃. Auth0류가 60초 유예를 두는 이유.
- 출처: Auth0 "Configure Refresh Token Rotation" https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation : leeway(Rotation Overlap Period)가 "네트워크 동시성 문제" 때문에 존재함을 명시, 재사용 탐지 시 이후 요청 전부 거부(재인증 필요)도 문서화. 단 "By default leeway is disabled. Configurable in seconds" — 60초 기본값 아님 (원문)
- 출처: Okta/Ory Hydra 문서 (검색 결과로 확인) : Okta는 grace period 기본 30초·설정 범위 0~60초, Ory Hydra는 문서 예시가 60초 grace period (원문·보조)
- 판정: E2 유지 : 메커니즘(동시 갱신 레이스·재사용 탐지·유예 설정)은 복수 IdP 공식 문서로 확인. 재현 설계 유효.
- 메모: "60초"를 Auth0 기본값처럼 쓰면 오류 — Auth0는 기본 비활성(초 단위 설정), Okta 기본 30초(최대 60초), 60초는 Ory Hydra 예시 값. 블로그에선 "주요 IdP가 수십 초 단위 유예(leeway/grace period)를 제공"으로 표현 권장.

## M04 인증서 피닝
- 주장: 백엔드 인증서 갱신만으로 전 버전 앱이 동시 단절. Cloudflare가 2024 Q3만으로 2023년 3개 분기 합계 수준의 피닝 장애 신고를 받았다고 공개.
- 출처: Cloudflare Blog "Avoiding downtime: modern alternatives to outdated certificate pinning practices" https://blog.cloudflare.com/why-certificate-pinning-is-outdated/ : "we are part way through July and Q3 has already seen as many outages as the last three quarters of 2023 combined" 원문 확인. 원인은 DigiCert 이탈 + 2024-06 Let's Encrypt·Google Trust Services 중간 CA 교체. 피해 고객 대부분이 핀 존재 자체를 몰랐다는 서술, Apple·Google이 피닝을 경고한다는 내용 포함 (원문)
- 판정: E2 유지 : 행의 수치·주체(Cloudflare 공개 통계)가 원문과 일치. 특정 단일 사건이 아닌 벤더 공개 통계이므로 E2가 적정.
- 메모: 원문 시점이 "7월 중순인데 이미"이므로 "Q3 절반도 안 지나서"로 쓰면 더 강한 표현도 가능. "앱 업데이트 전까지 복구 불가"는 이 문서에 명시적 문장은 없으나 피닝 메커니즘상 자명(클라이언트에 핀 하드코딩).
