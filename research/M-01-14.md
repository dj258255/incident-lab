## M02 멱등성
- 주장: 앱 타임아웃 재시도 시 서버는 이미 처리한 상태라 중복 주문 발생. 모바일 백엔드 실무 빈출 문제.
- 출처: AWS Builders Library "Making retries safe with idempotent APIs" https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/ : 재시도가 중복 워크로드를 만들 수 있음("Simply retrying the request could result in multiple workloads"), 클라이언트 제공 멱등 토큰 + 토큰 기록·변이 연산의 ACID 결합 요구를 명시 (원문)
- 출처: Stripe idempotency 문서 https://stripe.com/docs/idempotency (검색 결과로 존재 확인, 직접 페치는 안 함) : 연결 오류 시 같은 키로 안전 재시도, 24시간 후 키 정리 (원문·보조)
- 판정: E2 유지 : 벤더 공식 문서(AWS·Stripe)가 재시도-중복 문제와 멱등키 설계를 별도로 다룰 만큼 정착된 함정.
- 메모: "실무 빈출 1위"는 순위 통계 출처가 없는 수사적 표현 — 블로그에선 "가장 흔한 축에 드는"으로 완화 권장. AWS 문서는 동시 요청 레이스는 직접 다루지 않으므로 "순진한 멱등키가 동시 요청에서 깨진다" 부분은 재현 실험 자체가 근거(설계 오류 아님).

## M03 토큰 레이스
- 주장: 동시 401 → 같은 리프레시 토큰으로 동시 갱신 → RTR 재사용 탐지가 패밀리 전체 무효화 → 강제 로그아웃. Auth0류가 60초 유예를 두는 이유.
- 출처: Auth0 "Configure Refresh Token Rotation" https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation : leeway(Rotation Overlap Period)가 "네트워크 동시성 문제" 때문에 존재함을 명시, 재사용 탐지 시 이후 요청 전부 거부(재인증 필요)도 문서화. 단 "By default leeway is disabled. Configurable in seconds" — 60초 기본값 아님 (원문)
- 출처: Okta/Ory Hydra 문서 (검색 결과로 확인) : Okta는 grace period 기본 30초·설정 범위 0~60초, Ory Hydra는 문서 예시가 60초 grace period (원문·보조)
- 판정: E2 유지 : 메커니즘(동시 갱신 레이스·재사용 탐지·유예 설정)은 복수 IdP 공식 문서로 확인. 재현 설계 유효.
- 메모: "60초"를 Auth0 기본값처럼 쓰면 오류 — Auth0는 기본 비활성(초 단위 설정), Okta 기본 30초(최대 60초), 60초는 Ory Hydra 예시 값. 블로그에선 "주요 IdP가 수십 초 단위 유예(leeway/grace period)를 제공"으로 표현 권장.

## M05 IAP 영수증 검증·환불 웹훅 누락
- 주장: 검증과 지급 사이가 끊기면 결제는 됐는데 지급이 안 되고, 재시도가 멱등하지 않으면 이중 지급이 나며, 환불 웹훅을 받지 않으면 환불된 사용자가 재화를 계속 쓴다
- 출처: Apple App Store Server Notifications `notificationType` https://developer.apple.com/documentation/appstoreservernotifications/notificationtype : REFUND = "A notification type that indicates the App Store successfully refunded a transaction...", REFUND_REVERSED = "...the App Store reversed a previously granted refund due to a dispute" + "If your app revoked content or services as a result of the related refund, it needs to reinstate them.", CONSUMPTION_REQUEST도 존재 (원문 — HTML이 JS 렌더링이라 Apple 문서 JSON 엔드포인트로 확인)
- 출처: Google Play Real-time developer notifications reference https://developer.android.com/google/play/billing/rtdn-reference : `VoidedPurchaseNotification` 타입 존재, 필드 `purchaseToken`·`orderId`·`refundType`(FULL_REFUND=1, QUANTITY_BASED_PARTIAL_REFUND=2). "**You must call the Google Play Developer API after receiving Real-time developer notifications to get the complete status**... These notifications tell you only that the purchase state changed. They do not give you complete information about the purchase." (원문)
- 출처: Google Play Voided Purchases API https://developers.google.com/android-publisher/voided-purchases : "provides a list of orders associated with voided purchases to help implement a revocation system" / "**The API can only show voided purchases that have occurred during the past 30 days.**" (원문)
- 출처: Google Play Billing 연동 가이드 https://developer.android.com/google/play/billing/integrate : "This is done by acknowledging the purchase and **must be done within three days so that the purchase isn't automatically refunded and entitlement revoked**." / "you must check your secure backend server to verify that each purchase token hasn't been used so your app doesn't grant entitlement multiple times for the same purchase." (원문)
- 판정: E2 유지(트랙 M 중 근거가 가장 두꺼움, 특정 기업 포스트모템이 아니라 E1 불가) : 카탈로그가 주장한 세 가지가 모두 벤더 공식 문서로 뒷받침된다. 환불 웹훅은 실존하는 공식 기능이고, "환불된 사용자가 재화를 계속 사용"은 추론이 아니라 Google이 직접 "revocation system"을 구현하라고 지시하는 대목이며, 멱등성 요구도 Google이 명문화했다
- 메모: 인용 가능 = 위 네 문서의 영문 문장 전부. 특히 "3일 내 acknowledge 안 하면 자동 환불되고 권한이 회수된다"는 "검증과 지급 사이가 끊기면"이라는 주장의 가장 구체적인 물증이라 본문 앞부분에 배치할 만하다. 인용 금지 = "환불 때문에 매출 N% 손실" 류(어느 문서에도 피해 규모 수치 없음). **재현 설계 보완 3건** = (1) Voided Purchases API의 30일 조회 한계를 가짜 스토어 컨테이너에도 넣어야 실제와 닮는다 (2) 순서 역전 방어에 Apple의 REFUND_REVERSED(환불이 다시 취소돼 재화를 복구해야 하는 케이스)를 반드시 포함할 것 — 단순 "환불되면 회수"만 만들면 실무 난이도를 절반만 보여주는 셈 (3) RTDN이 상태 변경만 알려준다는 게 문서에 못박혀 있으므로 재현 코드도 "웹훅 수신 → 서버 API 재조회 → 상태 반영" 2단계여야 한다. 웹훅 페이로드만 믿는 구조를 만들면 그 자체가 결함

## M06 오프라인 큐 flush storm
- 주장: 복구 즉시 쌓인 작업을 전부 밀어넣어 하류를 무너뜨리며, "무차별 재시도가 0.5초에 수만 번으로 SMS 플랫폼을 압도한 사례가 MS 안티패턴 문서에 기록"돼 있다
- 출처: Microsoft Learn, Retry Storm Antipattern https://learn.microsoft.com/en-us/azure/architecture/antipatterns/retry-storm/ : 전문을 읽었고 **SMS 플랫폼 사례도, "0.5초"도, "수만 번"도 이 문서에 존재하지 않는다.** 실제 내용은 "When a service becomes unavailable or busy, frequent client retries can prevent the service from recovering and worsen the problem." / "Excessive connection attempts during recovery can overwhelm the service and intensify the original problem. This situation is sometimes called a ***thundering herd***." / 해법으로 "Limit the number of retry attempts and duration", "exponential backoff strategy", "Use the Circuit Breaker pattern", "Honor response headers... `retry-after`", "Throttle requests at your gateway". **문서에 등장하는 유일한 수치는 진단 스크린샷 설명이다** — "over 21,000 failed connection attempts to a dependency within a short time"(30분 구간), "One IP address generates 81,608 events"(1시간 bin). 둘 다 특정 사건이 아니라 문서용 진단 예시 (원문)
- 출처: (수치 출처 추적) Leapcell "7 Retry Patterns Every Backend Engineer Should Know" https://leapcell.io/blog/seven-retry-patterns : "This brute-force code triggered tens of thousands of retries within 0.5 seconds, overwhelming the SMS platform and triggering a circuit breaker" — 카탈로그 문장과 정확히 일치. 이 글은 Microsoft를 포함해 **어떤 1차 출처도 인용하지 않으며** 링크·각주·사건명이 전혀 없다 (원문)
- 판정: 행은 E2 유지, 단 **"0.5초에 수만 번 SMS" 수치는 즉시 삭제 권고**(해당 문장만 놓고 보면 E4) : MS 안티패턴 문서가 실재하고 thundering herd·백오프·서킷브레이커·retry-after를 공식 경고하므로 등급 자체는 정당하다. 그러나 카탈로그는 **무출처 블로그의 일화를 Microsoft 공식 문서의 기록인 것처럼 귀속시켰다.** 등급 문제가 아니라 출처 오귀속이라 그대로 실으면 확인 가능한 허위가 된다
- 메모: 인용 가능 = MS 문서의 영문 문장 전부(thundering herd 정의, 백오프·서킷브레이커·retry-after 권고, `while(true)` 안티패턴 코드). **인용 금지 = "0.5초", "수만 번", "SMS 플랫폼".** 조건부 = 21,000 / 81,608(반드시 "MS 문서의 진단 예시 스크린샷 수치"라는 꼬리표와 함께). 재현에 그대로 쓸 재료 = MS가 제시한 방어책 목록이 곧 재현 성공 기준이다. 특히 **"Honor response headers"가 카탈로그 재현안에 빠져 있으니** 서버가 429 + Retry-After를 내려주고 클라가 지키는지까지 넣으면 원문과 1:1로 맞는다. **주의 = 이 문서에는 지터(jitter)라는 단어가 없다** — 지터를 MS 권고로 적으면 또 한 번의 오귀속이다(지터는 AWS Builders' Library 쪽 표현)

## M07 API 계약 파괴
- 주장: 구버전 앱은 강제 업데이트 전까지 영원히 남으므로 breaking change가 치명적이며, Google AIP-180이 하위 호환을 공식 규범화한다
- 출처: Google API Improvement Proposals, AIP-180 Backwards compatibility https://google.aip.dev/180 : State "Approved". "APIs are fundamentally contracts with users, and users often write code against APIs that is then launched into a production service with the expectation that it continues to work." / 최상위 규범 "**Existing client code must not be broken by a service updating to a new minor or patch release.**" / 금지 목록(모두 must not) — 컴포넌트 제거, 이름 변경("semantically equivalent to 'remove and add'"), oneof 안팎 이동, 파일 간 이동, 타입 변경, 리소스 이름 변경, "**APIs must not change the expected format or algorithm used to construct the value of an existing field**", "**Changing the default value is considered breaking**", 기존 요청 메시지에 필수 필드 추가 금지 (원문)
- 판정: E2 유지 : AIP-180은 실재하고 "하위 호환을 규범화"가 정확히 맞다. 다만 표현 하나는 조여야 한다 — AIP는 RFC나 국제 표준이 아니라 **Google이 자사 API 설계 규칙을 공개한 문서**이므로 "업계 공식 규범"이 아니라 "Google이 공개한 API 설계 규범"으로 쓸 것
- 메모: 인용 가능 = 위 must not 목록과 "APIs are fundamentally contracts with users..." 문장. 이 목록은 그 자체로 CI 체크리스트가 되므로 재현 설계에 그대로 매핑하면 글이 강해진다. 인용 금지 = AIP-180을 "표준"·"스펙"·"업계 규범"으로 격상시키는 표현. **AIP-180에 없는 것을 있는 것처럼 쓰지 말 것** — 이 문서는 "구버전 앱이 영원히 남는다"거나 강제 업데이트를 논하지 않는다. 그 부분은 카탈로그 작성자의 모바일 도메인 논거이지 AIP 인용이 아니므로 문장을 분리할 것. **재현 설계 심화 포인트** = 카탈로그의 "JSON Schema diff·컨트랙트 테스트"로는 **못 잡는 금지 항목이 셋** 있다 — 타입은 유지한 채 의미·포맷만 바꾸기, 기본값 변경, oneof 이동. 이 셋은 스키마 diff를 통과하므로 "diff만으로는 부족하다"는 반례로 쓰면 재현물의 깊이가 확 올라간다(구버전 DTO를 고정한 골든 테스트가 대안)

## M08 강제 업데이트·kill switch 부재
- 주장: Remote Config에 의존하면 그게 죽을 때 앱 진입이 막히고, 스토어 노출 전 플래그를 켜면 업데이트 대상 없이 잠기며, iOS는 심사 때문에 롤백이 5분이 아니다
- 출처: Firebase Remote Config loading strategies https://firebase.google.com/docs/remote-config/loading : 확보한 직접 인용은 두 문장뿐 — "**Do set in-app default parameter values so that your app always behaves as expected.**" / "**Remote Config's one-minute timeout may be too long for a quality app startup experience for users.**" (원문 — 페이지 일부만 추출돼 fetch 실패 시 캐시 우선순위나 `fetchTimeoutMillis`·`minimumFetchInterval` 기본값은 이번에 확인 못 함)
- 출처: Apple 심사 소요 시간 https://developer.apple.com/app-store/review/ : 접속했으나 본문이 JS 렌더링이라 **원문 확인 실패**. 검색 수준에서 "On average, 90% of submissions are reviewed in less than 24 hours."가 반복 인용되는 것만 확인 (2차, 검색 결과로만 확인·직접 접속 안 함)

- 메모: 인용 가능 = Firebase의 두 문장. **인용 금지 = "Apple 심사 24시간/90%"** — developer.apple.com 원문을 직접 열기 전까지 쓰지 말 것. 검색 스니펫 재인용은 이 프로젝트의 근거 기준을 스스로 깨는 짓이다. **다음 회차 확인 목록** = (1) developer.apple.com/app-store/review/를 렌더링 우회로 열어 심사 시간·expedited review 확인 (2) FirebaseRemoteConfigSettings API 레퍼런스에서 `fetchTimeoutInSeconds` 기본 60초와 `minimumFetchInterval` 기본 12시간 원문 확인 — 이 둘을 확보하면 "원격 설정이 죽으면 최대 60초 부팅 지연"이라는 정량 서사가 생겨 E2로 되살릴 수 있다. **글의 중심을 "사건"이 아니라 "설계 결정"으로 옮길 것** — fail-open vs fail-closed 트레이드오프, 마지막 성공 정책의 로컬 캐시 유효기간, 짧은 타임아웃, kill switch가 스스로를 잠그지 않게 하는 안전장치. "롤백이 5분이 아니다"를 살리려면 심사 시간 대신 **"서버 플래그로 되돌릴 수 있는 것과 앱 바이너리를 바꿔야만 되돌릴 수 있는 것의 경계"**를 논지로 잡는 편이 출처 없이도 방어된다

## M09 대량 발송 병렬화·Redis 파티셔닝
- 주장: 국내 공개 수치로 1,053만 명 발송 시 첫 6분·마지막 11분이던 것을 비동기화 + 1만 파티션 분산으로 1,124만 명에 첫 1초·마지막 51초까지 줄였다
- 출처: 개인 기술블로그 "천만 명의 사용자에게 1분 내로 알림 보내기(병렬프로세스의 최적화)"(2019-01-02, 저자 '태태태') https://taetaetae.github.io/2019/01/02/faster-parallel-processes/ : 측정표 4단계 원문 확인 — 기존 "약 10,530,000명 / 첫발송 약 6분 / 마지막 발송 약 11분", 1차 "약 10,570,000명 / 6분 / 7분", 2차 "약 11,120,000명 / 첫발송 약 1초 / 마지막 약 5분 30초", 3차 "약 11,240,000명 / 첫발송 약 1초 / 마지막 발송 51초". 기법도 원문 확인 — "AsyncRestTemplate를 사용해서 비동기 호출로 변경", "redis는 Single thread 방식으로 처리하기 때문에", "중복 발송을 막기 위한 redis 키를 기존에는 하나를 사용하고 있었는데 이를 user 값 기준으로 여러 개의 키로 파티셔닝 … 하나의 키에 1,000개씩 총 10,000개의 키", 중복 체크는 "redis의 zscore 연산(시간 복잡도 O(1))" (원문)
- 판정: **E1 → E2 강등 제안(수치 자체는 인용 가능)** : 카탈로그의 두 수치는 원문에 실재하므로 삭제 대상이 아니다. 그러나 이 글은 기업 공식 포스트모템도, 규제기관 문서도, 학술 논문도 아닌 **개인 기술블로그의 성능 개선기**이고, 본문에 "사내 발송 플랫폼"이라고만 적혀 어느 회사인지 특정되지 않는다. E1 정의에 해당하지 않는다
- 메모: (1) "국내 공개 수치"라는 표현은 유지 가능하되 출처는 **"개인 기술블로그(2019)의 자체 공개 실측, 회사·서비스명 미공개"**로 정직하게 적을 것. 회사명 추정·특정 금지 (2) **재현 설계 수정 필요 — 원문은 Set이 아니라 Sorted Set(ZSCORE)로 중복 체크한다.** 카탈로그의 SISMEMBER/SADD는 다른 자료구조다. ZSCORE/ZADD로 맞추거나 "원문은 ZSCORE, 실험은 Set으로 단순화"라고 밝힐 것 (3) **인과를 한 줄로 합치면 왜곡된다** — 첫발송 6분→1초는 2차 단계(약 1,112만)에서 이미 일어났고, 마지막 5분 30초→51초가 3차 단계에서 일어났다. "1만 파티셔닝 덕분에 51초"는 표와 맞지만 "첫 1초"까지 파티셔닝 공으로 돌리면 틀린다 (4) 원문 표현이 "user 값을 10,000으로 나누어 … 총 10,000개의 키"라 나머지(%)인지 몫(/)인지 모호하므로 인용할 땐 원문 문장 그대로 쓸 것

## M10 무효·좀비 토큰 누적
- 주장: Firebase가 2024-05-15부터 270일 미사용 토큰을 정리하므로 정리 로직이 없으면 발송 대상 상당수가 영구 실패로 쿼터만 소모한다
- 출처: Firebase "Best practices for FCM registration management" https://firebase.google.com/docs/cloud-messaging/manage-tokens : "**For Android, when a registration has been inactive for 270 days, FCM considers it expired and garbage collects it.**" / "these error messages may indicate that your send request targeted invalid or expired registrations: `UNREGISTERED` (HTTP 404) [and] `INVALID_ARGUMENT` (HTTP 400)" / "it is safe to delete your record of this registration, since it will never again be valid." / "By default, FCM considers a registration to be stale if its app instance hasn't connected for a month." **단 이 문서에 "2024-05-15" 시행일은 없다.** 270일은 Android 한정이며 "For other platforms like iOS, FCM relies on the underlying push service (e.g., APNs), which does not have the same 270-day inactivity-based expiration." (원문)
- 출처(날짜 근거): Batch 블로그 https://batch.com/blog/posts/android-push-updates-fcm-api : "Starting May 15, 2024, any push token from a device that remains inactive for more than 270 days will be considered expired." 페이지는 직접 열었으나 **구글 공식 발표를 링크·인용하지 않는다.** firebase-talk 구글그룹도 열었으나 날짜는 일반 사용자의 전언이고 구글 직원 공식 게시가 아니다 (페이지는 원문 접속, 날짜 내용은 2차 전언)
- 판정: E2 유지, 단 **날짜·플랫폼 범위 수정 필수** : 270일 만료와 UNREGISTERED(404) 삭제 권고는 벤더 공식 문서 원문으로 확인된다. 그러나 "2024-05-15부터"는 공식 문서·릴리스노트에서 확인되지 않았고 3자 블로그와 전언만 존재한다
- 메모: (1) **"2024-05-15"는 인용 금지 또는 "2024년경 시행(공식 발표 문서 미확인)"으로 완화.** 안전한 대체는 원문 그대로 "270일 비활성이면 만료·GC 대상" (2) **주어를 "Firebase가"로 두면 부정확** — Android 한정이고 iOS는 APNs를 따르며 같은 규칙이 없다. 행에 플랫폼을 명시할 것 (3) **"쿼터만 소모"는 확인하지 못했다** — 무효 토큰 발송이 FCM 쿼터를 잡아먹는다는 명시 문장을 못 찾았으므로 "쿼터 소진" 대신 "실패 응답 누적·발송 완료 시간 증가"로 바꿔 쓸 것(재현으로 직접 보여줄 수 있는 값이기도 하다) (4) 재현 설계는 원문 권고와 정확히 일치한다. 보너스로 "한 달 미접속 = stale" 기준을 정리 배치 트리거로 쓰면 문서 근거가 그대로 붙는다

## M11 백그라운드 전환·좀비 소켓
- 주장: WebSocket에 내장 keep-alive가 없고 캐리어 NAT 유휴 타임아웃이 흔히 30초라, 백그라운드에선 하트비트도 멈춰 유령 연결이 누적된다
- 출처: RFC 6455 §5.5.2/5.5.3 https://www.rfc-editor.org/rfc/rfc6455.txt : "An endpoint **MAY** send a Ping frame any time after the connection is established" / "A Pong frame **MAY** be sent unsolicited. This serves as a unidirectional heartbeat." — 전부 MAY이고 자동 하트비트 주기를 규정한 조항은 없다 (원문)
- 출처: RFC 5382 REQ-5 https://datatracker.ietf.org/doc/html/rfc5382 : "the value of the 'established connection idle-timeout' **MUST NOT be less than 2 hours 4 minutes**", "The value of the 'transitory connection idle-timeout' MUST NOT be less than 4 minutes" (원문)
- 출처(30초 주장): CGN·셀룰러 미들박스 측정 연구(arXiv 1605.05606, SIGCOMM 2011 "An Untold Story of Middleboxes in Cellular Networks") : "탐지된 NAT의 74%가 유휴 **UDP** 상태를 1분 이하에 만료", "셀룰러 CGN 매핑 타임아웃 중앙값 65초", "TCP 바인딩 타임아웃은 UDP보다 훨씬 길다" (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: 전반부 E2 유지 / **"캐리어 NAT 유휴 타임아웃 흔히 30초"는 강등·수정 권고(현 문장 그대로는 E4)** : "WebSocket에 내장 keep-alive 없음"은 RFC 6455 원문으로 확정된다. 반면 30초 수치는 (a) 규범인 RFC 5382가 established TCP에 최소 2시간 4분을 요구하므로 정면으로 어긋나고 (b) 30초·1분대 실측치는 전부 **UDP 매핑** 기준인데 WebSocket은 TCP다. 출처 없이 TCP에 갖다 붙인 수치로 보인다
- 메모: (1) **"흔히 30초"는 삭제하거나 UDP 한정임을 명시할 것.** 정직한 대체 문장: "RFC 5382는 established TCP에 2시간 4분 이상 유지를 요구하지만 실제 경로의 유휴 타임아웃은 훨씬 짧게 잡히는 경우가 많다(측정 연구는 UDP 기준 1분 이하가 다수)" (2) 더 안전한 길은 근거를 **문서로 확인 가능한 미들박스 값**(로드밸런서·리버스 프록시의 기본 idle timeout)으로 갈아타는 것 — 재현도 똑같이 되고 출처도 붙는다 (3) 재현 설계(프록시 down/up → 좀비 연결·FD 누적) 자체는 유효하지만 이건 "NAT 타임아웃"이 아니라 **"경로 중간 상태 소실"**을 만드는 실험이다. 원인을 NAT 타임아웃으로 단정하지 말고 "중간 장비가 상태를 잃으면 양끝이 서로 다른 사실을 믿는다"로 서술할 것 (4) "백그라운드에선 하트비트도 멈춘다"는 iOS/Android 백그라운드 제약에 기댄 주장인데 벤더 문서로 확인하지 않았다 — 단정 금지

Instead, they send these requests to an Apple-managed content delivery network" / "Apple's content delivery network requests the apple-app-site-association file for your domain within 24 hours." (원문)
- 출처: Android "Add Android App Links" https://developer.android.com/training/app-links/configure-assetlinks : "The assetlinks.json file is served with content-type application/json." / "must be accessible over an HTTPS connection" / "**The assetlinks.json file must be accessible without any redirects (no 301 or 302 redirects).**" (원문)
- 출처: Android "Verify Android App Links" https://developer.android.com/training/app-links/verify-android-applinks : 검증 트리거는 `adb shell pm verify-app-links --re-verify PACKAGE_NAME`, **결과 조회는 `adb shell pm get-app-links PACKAGE_NAME`**이며 출력에 "Domain verification state:"와 도메인별 상태(none / verified / approved / denied / migrated / restored / legacy_failure / 1024 이상 커스텀 에러코드) (원문)
- 판정: E2 유지, 단 **근거란 전면 교체 필요** : 제목은 Android인데 근거로 든 문장은 Apple AASA 얘기라 행이 자기모순이다. 다행히 Android 공식 문서가 "no 301 or 302 redirects"와 "content-type application/json"을 똑같이 명시하므로, 근거란을 Android 문서 인용으로 바꾸면 등급을 낮추지 않고 앞뒤가 맞는다. Apple 문장은 "같은 함정이 iOS에도 있다"는 보조 근거로 옮길 것
- 메모: **재현 절차에도 오류가 있다** — 상태 출력을 보는 명령은 `pm get-app-links`이고 `pm verify-app-links`는 재검증을 시키는 명령이다. 카탈로그의 "`adb shell pm verify-app-links` 출력 차이"는 "`--re-verify`로 재검증 후 `pm get-app-links`로 상태 비교"로 고칠 것. 관찰 지표는 정상 도메인 `verified` 대 실패 도메인 `none`/`legacy_failure`/에러코드 대비. Content-Type 오탑재가 실제로 검증을 실패시키는지는 문서상 요구사항일 뿐이므로 **그 실측이 이 세션의 고유 가치**다. Apple 쪽을 언급할 때 iOS 14 이후 앱이 서버를 직접 치지 않고 Apple CDN이 대신 가져간다는 점을 빼면 "왜 서버 로그에 요청이 안 보이는가"가 설명되지 않는다

## M14 다중 기기 세션·푸시 토큰
- 주장: 단일 IP·기기 지문 기반 세션은 기기 교체 시 붕괴하고, 푸시 토큰도 기기 단위라 교체 시 중복 알림이 발생한다
- 출처: OWASP Session Management Cheat Sheet https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html : **원문은 오히려 바인딩을 권장한다** — "it is highly recommended to bind the session ID to other user or client properties, such as the client IP address, User-Agent, or client-based digital certificate". 한계로 적힌 것은 공격자 우회뿐. **"IP 변동·기기 교체로 정상 사용자 세션이 깨진다"는 서술은 이 문서에 없다.** 다중 기기 쪽은 근거가 붙는다 — "It is recommended for web applications to add user capabilities that allow checking the details of active sessions at any time, monitor and alert the user about concurrent logons, provide user features to remotely terminate sessions manually, and track account activity history" (원문)
- 출처: Firebase FCM Android 클라이언트 문서 https://firebase.google.com/docs/cloud-messaging/android/client : "On initial startup of your app, the FCM SDK generates a registration token for the client app instance." 토큰이 바뀌는 경우로 "The app is restored on a new device", "The user uninstalls/reinstall the app", "The user clears app data" 명시. **다만 "기기 교체 시 중복 알림"을 경고하는 문장은 없다** (원문)
- 판정: **E2 → "설계 과제"로 강등 권고**(전반부는 사실상 E4) : 후반부(다중 기기 세션 관리, 토큰이 앱 인스턴스 단위)는 공식 문서 근거가 있으나 **일반 권고이지 장애 경고가 아니다**. 전반부 "단일 IP·기기 지문 세션은 기기 교체 시 붕괴"는 OWASP 원문에 없고, 문서가 오히려 바인딩을 권장하므로 이 문서를 근거로 달면 출처 왜곡이 된다
- 메모: (1) **OWASP를 근거로 "IP 바인딩은 나쁘다"라고 쓰면 원문과 반대 방향이다.** 정확한 요약은 "OWASP는 IP·User-Agent 바인딩을 권장하되 공격자 우회 가능성을 한계로 든다"이고, 기기 교체 시 정상 사용자가 튕기는 문제는 출처 없이 설계 논거로만 다룰 것 (2) 인용 가능한 건 OWASP의 다중 세션 권고 4종(활성 세션 조회·동시 로그인 알림·원격 수동 종료·활동 로그)뿐인데, 이게 그대로 이 세션의 **산출물 명세**로 쓰기 좋다 — 근거 문단 대신 "설계 요구사항" 절로 배치할 것 (3) 푸시 토큰은 "client app instance" 단위이고 새 기기 복원 시 바뀐다는 데까지만 인용하고, 중복 알림은 "서버가 (user, token) 관계를 정리하지 않으면 생기는 결과"로 재현 결과에서 보여줄 것 (4) 결론: 사건 근거를 억지로 붙이지 말고 **[E2] → [설계]로 표기를 바꿔 "재현으로 증명하는 설계 결함" 프레임**으로 가면 글은 정직하게 성립한다
