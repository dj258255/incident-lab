## S01 매핑 폭발
- 주장: Elastic이 전용 문서를 낼 만큼 흔한 함정(기본 상한 1000필드) + Blinkit 실장애 포스트모템(HN 화제)
- 출처: Elastic 공식 문서 "Mapping limit settings" https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping-settings-limit.html : index.mapping.total_fields.limit 기본값 1000, "prevent documents from causing a mapping explosion" 문구와 "Limit of total fields [X] has been exceeded" 에러 명시 (원문)
- 출처: Blinkit 포스트모템 HN 스레드 https://news.ycombinator.com/item?id=10729776 : "Postmortem: Outage due to Elasticsearch's flexibility and our carelessness" HN 토론 실재, 원 글은 Blinkit(구 Grofers) Lambda 블로그 2015-12-14 발행, 사건은 11-25 (2차, 검색 결과로 확인)
- 판정: E1+E2 유지 : 공식 문서 상한 1000·에러 메시지·mapping explosion 용어 전부 일치, Blinkit 사건 실재·HN 화제 확인
- 메모: 기존 검증 로그대로 Blinkit 본문은 403이라 본문 수치 인용 금지 유지. 글에서는 제목·HN 스레드·발행일까지만 인용

## S02 딥 페이지네이션
- 주장: max_result_window 기본 10000, scroll 비권장, search_after+PIT 권장, tie-breaker 누락 시 문서 누락·중복
- 출처: Elastic 공식 문서 "Paginate search results" https://www.elastic.co/guide/en/elasticsearch/reference/current/paginate-search-results.html : "By default, you cannot use from and size to page through more than 10,000 hits"(index.max_result_window 기본 10000), "We no longer recommend using the scroll API for deep pagination", "If you don't include a tiebreaker field, your paged results could miss or duplicate hits", PIT 사용 시 _shard_doc 자동 tiebreaker (원문)
- 판정: E2 유지 : 행의 수치(10000)·scroll 비권장·search_after+PIT·tie-breaker 함정까지 전부 공식 문서 문구와 일치
- 메모: tie-breaker 누락 재현은 공식 문서가 명시적으로 경고하는 시나리오라 재현 설계 근거 충분

## S03 워터마크
- 주장: flood stage 95% 초과 시 read_only_allow_delete로 쓰기 전면 차단, 디스크를 비워도 자동 해제 안 되던 구버전으로 악명
- 출처: Elastic 공식 문서 "Disk-based shard allocation" https://www.elastic.co/guide/en/elasticsearch/reference/current/disk-allocator.html : flood stage watermark "defaults to 95%", 초과 시 read-only index block 부여, 현행 버전은 "automatically released when the disk utilization falls below the high watermark" (원문)
- 출처: Elastic 7.4 breaking changes(Allocation Changes)/Mincong Huang 블로그 https://mincong.io/2021/04/10/disk-watermarks-in-elasticsearch/ : 7.4 이전엔 블록을 수동 해제해야 했고 7.4부터 자동 해제로 변경 (2차, 검색 결과로 확인)
- 판정: E2 유지 : 95%·블록 이름·"구버전은 수동 해제" 서사 모두 사실과 일치, 7.4가 분기점
- 메모: 재현 시 최신 ES를 쓰면 high watermark 아래로 내려가는 순간 자동 해제됨. "자동 해제 안 됨"을 보여주려면 7.4 미만 이미지가 필요하다는 점을 reproduce 설계에 반영해야

## S04 bulk 리젝션
- 주장: write 큐 포화 시 리젝션 발생, 조용히 문서 유실
- 출처: Elastic 공식 블로그 "Why am I seeing bulk rejections in my Elasticsearch cluster?" https://www.elastic.co/blog/why-am-i-seeing-bulk-rejections-in-my-elasticsearch-cluster : 큐가 차면 bulk 서브요청 리젝션, "It is possible, and even likely, that only a portion of the documents within a bulk request might have been rejected", "Make sure you inspect the full response and retry the appropriate documents" (원문)
- 판정: E2 유지 : 공식 블로그가 부분 리젝션과 응답 검사·재시도 필요를 명시, 재현 설계(rejected 관측·백오프)와 정합
- 메모: 정확한 메커니즘은 "ES가 조용히 버림"이 아니라 per-item 429를 돌려주는데 클라이언트가 부분 실패 응답을 안 보면 유실. 글에서는 "클라이언트가 무시하면 조용한 유실"로 표현해야 정확
