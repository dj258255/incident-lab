## I01 인증서 만료
- 주장: MS Teams 2020(인증서 만료, 수백만 사용자, 5시간) + Ericsson 2018(O2 등 약 3,200만 가입자, 보상 1.3억 달러)
- 출처: TechCrunch(Ericsson 원인) https://techcrunch.com/2018/12/07/heres-what-caused-yesterdays-o2-and-softbank-outages : 만료된 소프트웨어 인증서가 원인, Ericsson이 전적 책임 인정 성명 (2차, 벤더 성명 인용)
- 출처: TechCrunch(Teams) https://techcrunch.com/2020/02/03/microsoft-teams-has-been-down-this-morning/ : 2020-02-03 인증 인증서 만료로 Teams 중단, MS 공식 트윗 인용 (2차, 검색 결과로 확인)
- 출처: iTnews https://www.itnews.com.au/news/expired-ericsson-cert-causes-uk-and-japan-mega-outages-516617 : 영국 약 3,200만 가입자(O2+MVNO) 영향, SoftBank 일본 전국 장애 (2차, 검색 결과로 확인)
- 판정: E1 유지 : 두 사건 모두 실재하고 벤더 공식 성명 존재. 단 보상 수치는 손질 필요
- 메모: 1) Teams 중단은 대부분 사용자 기준 약 3시간, 수정 배포 완료까지 약 5시간 — "5시간"은 완전 복구 기준으로 명시 권장. 2) "보상 1.3억 달러"는 확인 실패 — 보도된 것은 O2가 최대 1억 파운드(약 1.25억 달러) 보상을 협상했다는 2차 보도이며 최종 합의액은 비공개. "최대 1억 파운드 보상 협상 보도" 수준으로 완화 권장

## I02 K8s CPU 스로틀링 (CFS 쿼터)
- 주장: limit 1 CPU면 100ms 주기당 100ms 쿼터 소진 시 다음 주기까지 강제 대기, p99만 튀는 원인 1순위
- 출처: 리눅스 커널 공식 문서 CFS Bandwidth Control https://docs.kernel.org/scheduler/sched-bwc.html : 쿼터 소진 시 다음 주기 보충까지 스레드 스로틀, 기본 cpu.cfs_period_us=100ms 명시 (원문)
- 출처: groundcover 블로그 https://www.groundcover.com/blog/kubernetes-cpu-throttling : throttled_periods 비율 기반 진단, tail latency 악화 메커니즘 다수 실무 문서 공통 서술 (2차, 검색 결과로 확인)
- 판정: E2 유지 : 메커니즘·기본값이 커널 공식 문서 원문과 일치, 특정 사건 아님
- 메모: "p99만 튀는 원인 1순위"는 정량 근거 없는 순위 표현 — 블로그화 시 "꼬리 지연의 대표 원인"으로 완화 권장. 메커니즘 수치(100ms 주기)는 정확

## I03 conntrack 테이블 고갈
- 주장: 테이블이 차면 커널이 조용히 새 연결을 드롭, K8s 클러스터를 마비시킨 사례 공개
- 출처: Mark Betz "Exhausting conntrack table space crippled our k8s cluster" https://medium.com/@betz.mark/exhausting-conntrack-table-space-crippled-our-k8s-cluster-98564f6f34e0 : 2023-12 실제 프로덕션 K8s에서 conntrack 고갈로 DNS 실패·타임아웃, "table full, dropping packet" 로그 확인 (원문에 준하는 1차 실무 회고)
- 출처: Red Hat KB "ip_conntrack or nf_conntrack: table full, dropping packet" https://access.redhat.com/solutions/8721 : 테이블 만석 시 패킷 드롭이 벤더 공식 문서화된 동작 (원문, 검색 결과로 확인)
- 판정: E2 유지 : 커널 동작이 벤더 문서로 확인되고 공개 실무 사례 실재. 기업 공식 포스트모템은 아니므로 E1 승격은 부적절
- 메모: "조용히"는 앱 관점(타임아웃만 발생) 기준. 커널은 dmesg에 "nf_conntrack: table full, dropping packet"을 남기므로 재현 시 dmesg 관측 포인트로 활용 가능 — 카탈로그 재현 설계와 모순 없음

## I04 에페메랄 포트·TIME_WAIT 고갈
- 주장: 고트래픽 리눅스에서 클라이언트 포트가 말라 연결 실패하는 절벽
- 출처: Cloudflare 공식 블로그 "How to stop running out of ephemeral ports..." https://blog.cloudflare.com/how-to-stop-running-out-of-ephemeral-ports-and-start-to-love-long-lived-connections/ : 기본 ip_local_port_range 32768~60999(약 2.8만 포트), 고갈 시 "Cannot assign requested address"/EAGAIN 실패 문서화 (원문)
- 출처: Microsoft Learn "TCP/IP port exhaustion troubleshooting" https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/tcp-ip-port-exhaustion-troubleshooting : 포트 고갈이 벤더 공식 트러블슈팅 문서로 존재 (원문, 검색 결과로 확인)
- 판정: E2 유지 : 벤더 공식 문서·대형 인프라 기업 원문이 현상과 대응을 직접 경고
- 메모: Cloudflare 원문의 1차 해법은 keep-alive보다 포트 공유(IP_BIND_ADDRESS_NO_PORT 등) 쪽 — 재현 설계의 keep-alive·풀링·tw_reuse 비교도 표준 완화책이라 모순은 아니나, 블로그화 시 "포트 재사용 계열 해법도 있다"고 한 줄 언급하면 깊이가 생김
