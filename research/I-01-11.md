## I05 컨테이너 메모리 한계와 JVM
- 주장: 컨테이너 메모리 limit을 인식하지 못하는 JVM이 호스트 물리메모리 기준으로 힙 상한을 잡아 cgroup에 의해 OOMKilled(exit 137)되며, 이 문제 때문에 `UseContainerSupport`가 등장했다
- 출처: Oracle JDK 10 Release Notes https://www.oracle.com/java/technologies/javase/10-relnote-issues.html : "The JVM has been modified to be aware that it is running in a Docker container and will extract container specific configuration information instead of querying the operating system... This new support is enabled by default and can be disabled in the command line with the JVM option: `-XX:-UseContainerSupport`" (원문)
- 출처: Oracle JDK 25 `java` Tool man page https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html : "**Linux only:** The VM now provides automatic container detection support... The default for this flag is `true`, and container support is enabled by default. It can be disabled with `-XX:-UseContainerSupport`." 진단용으로 "Use `-Xlog:os+container=trace` for maximum logging of container information." (원문)
- 출처: OpenJDK master `src/hotspot/os/linux/globals_linux.hpp` https://raw.githubusercontent.com/openjdk/jdk/master/src/hotspot/os/linux/globals_linux.hpp : `product(bool, UseContainerSupport, true, "Enable detection and runtime container configuration support")` — 현재 소스에서 플래그·기본값 직접 확인 (원문)
- 출처: Red Hat Developer "Java 17: What's new in OpenJDK's container awareness" : "If you run Java 11 (any version lower than 11.0.16) or Java 8 (any version lower than 8u372) on a system that has only cgroups v2, no container detection will be in place and the host values will be used instead." (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 벤더 공식 문서가 전용 플래그·전용 로깅 옵션까지 별도 문서화했으므로 E2 기준 충족. 특정 기업 포스트모템은 없어 E1 불가
- 메모: **재현 설계 이슈.** (1) `-XX:-UseContainerSupport`는 JDK 25에도 살아있어 재현은 되지만, 이건 "옛날 JVM 재현"이 아니라 **인위적으로 스위치를 끄는 것**이다. "JDK 10 이후 기본 활성이라 오늘날 기본 설정에선 발생하지 않는다"를 먼저 밝힐 것 (2) **호스트 RAM ≫ 컨테이너 limit이어야 차이가 난다** — 기본 힙 상한이 물리메모리의 1/4이므로 호스트 8~16GB에 limit 256~512Mi 정도로 벌려야 안정 재현 (3) 대비 포인트: ON이면 `OutOfMemoryError: Java heap space`(JVM이 스스로 던짐), OFF면 **exit 137 / OOMKilled**. "OOM인데 스택트레이스가 없다"가 이 세션의 그림 (4) **오늘도 살아있는 변종은 cgroup v2 + 구버전 JDK** — JDK 11.0.16 미만·8u372 미만은 감지 실패. 훨씬 현실적인 시나리오지만 근거가 2차뿐이니 JDK-8230305 릴리스 노트를 직접 열어 확인 후 쓸 것. 인용 금지 = "MaxRAMPercentage 기본 25%"(검색 스니펫만 봄 — `java -XX:+PrintFlagsFinal -version`으로 직접 찍을 것), "8u191부터 백포트"(원문 미확인)

## I06 헬스체크 설계 실패로 무한 재시작
- 주장: liveness probe에 외부 의존성 검사를 넣으면 의존성 장애가 앱 재시작 루프를 유발하며, 이는 Kubernetes 공식 안티패턴이다
- 출처: Kubernetes 공식 문서 "Liveness, Readiness, and Startup Probes" https://kubernetes.io/docs/concepts/workloads/pods/probes/ — Caution 블록 원문: "Liveness probes can be a powerful way to recover from application failures, but they should be used with caution... **Incorrect implementation of liveness probes can lead to cascading failures.** This results in restarting of container under high load; failed client requests as your application became less scalable; and increased workload on remaining pods due to some failed pods." (원문)
- 출처: 같은 문서 "When should you use a readiness probe?" : "When your app has a strict dependency on back-end services, you can implement both a liveness and a readiness probe. The liveness probe passes when the app itself is healthy, but **the readiness probe additionally checks that each required back-end service is available.**" — 공식 문서가 의존성 검사를 readiness에 명시적으로 배치 (원문)
- 출처: 같은 문서 "When should you use a liveness probe?" : "A common pattern for liveness probes is to use the same low-cost HTTP endpoint as for readiness probes, but with a higher `failureThreshold`." (원문)
- 판정: E2 유지 : 공식 문서에 별도 Caution 블록과 처방까지 원문 명시. E2 정면 충족
- 메모: **용어 주의 — 공식 문서는 "anti-pattern"이라는 단어를 쓰지 않는다.** 쓰는 표현은 "should be used with caution", "can lead to cascading failures"다. "K8s가 공식 안티패턴으로 규정했다"고 쓰면 과장이니 "공식 문서가 Caution 블록을 따로 달아 경고한다"로 낮출 것. **재현 설계 이슈 — startupProbe는 이 시나리오의 해법이 아니다.** 공식 문서상 용도는 "Pods that have containers that take a long time to come into service"로, 기동이 느린 앱을 보호하는 것이지 운영 중 DB 지연과 무관하다. 다만 "부팅 시 마이그레이션·풀 워밍업이 오래 걸려 liveness가 먼저 터지는" 변종은 startupProbe가 정답이므로 **두 시나리오를 분리하면** 글이 풍부해진다(초기 기동 지연 = startupProbe, 운영 중 의존성 지연 = readiness). 인용 가능 = "The default for `periodSeconds` is 10s." 인용 금지 = 임계 수치 전반(공식 문서에 없음). 재시작 백오프 상한 5분은 미확인

## I07 롤링 업데이트 중 요청 유실
- 주장: preStop·graceful shutdown이 없으면 롤링 업데이트 중 in-flight 요청이 잘리며, 근본 원인은 엔드포인트 제거와 컨테이너 종료가 동시에 시작되기 때문이다
- 출처: Kubernetes 공식 문서 "Pod Lifecycle" https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/ — **이 세션의 핵심 근거**: "**At the same time as the kubelet is starting graceful shutdown of the Pod, the control plane evaluates whether to remove that shutting-down Pod from EndpointSlice objects**, where those objects represent a Service with a configured selector." 그 외 "Terminating endpoints always have their `ready` status as `false` (for backward compatibility with versions before 1.26)", "**The default `terminationGracePeriodSeconds` setting is 30 seconds.**" (원문)
- 출처: Kubernetes 공식 문서 "Container Lifecycle Hooks" https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/ : "**PreStop hooks are not executed asynchronously from the signal to stop the Container; the hook must complete its execution before the TERM signal can be sent.**" / "If a `PreStop` hook hangs during execution, the Pod's phase will be `Terminating` and remain there until the Pod is killed after its `terminationGracePeriodSeconds` expires." 훅 핸들러로 "Sleep - Pauses the container for a specified duration."도 존재 (원문)
- 출처: KEP-3960(PodLifecycleSleepAction) : 네이티브 sleep preStop이 1.29 알파 → 1.30 beta → GA 1.34 목표 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 카탈로그 핵심 주장이 공식 문서 문장으로 **정확히 그대로** 확인됐다. I 트랙에서 근거 대응이 가장 깔끔
- 메모: **재현 설계 이슈 4건.** (1) **"0건 만들기"를 목표로 걸지 마라** — 엔드포인트 전파는 비동기라 확률적이다. "N회 반복 배포에서 실패 X건 → 0건" 식으로 측정 횟수와 함께 쓸 것 (2) **k6에서 5xx만 세면 절반을 놓친다** — in-flight가 잘리면 대부분 TCP RST/EOF/connection refused로 나타난다. `http_req_failed` + 상태코드 0까지 집계하고 5xx와 연결 오류를 나눠 보여줄 것 (3) **`exec: ["sleep","5"]`는 distroless·scratch 이미지에서 안 먹는다** — K8s 1.30+면 네이티브 sleep 액션을 쓰고, 구버전이면 shell 있는 베이스 이미지를 쓸 것. 클러스터 버전 명시 필수 (4) preStop이 동기적이므로 `preStop sleep(S) + graceful shutdown < terminationGracePeriodSeconds(기본 30초)`를 지켜야 한다. 넘기면 SIGKILL로 더 심하게 잘린다 — 이 함정을 실험으로 하나 더 보여주면 밀도가 올라감 (5) 카탈로그의 "readiness 해제"는 표현이 모호하다. 실무에서 in-flight를 보호하는 건 **preStop sleep이 엔드포인트 전파 시간을 벌어주는 것**이므로 문장을 그렇게 고칠 것

## I08 디스크 풀 (로그·WAL이 채운다)
- 주장: 디스크가 100%가 되면 PostgreSQL이 쓰기를 멈추고 로그도 남기지 못해 원인 파악까지 마비된다
- 출처: PostgreSQL 공식 문서 "29.2. Disk Full Failure" https://www.postgresql.org/docs/16/disk-full.html : "**A filled data disk will not result in data corruption, but it might prevent useful activity from occurring. If the disk holding the WAL files grows full, database server panic and consequent shutdown might occur.**" / Tip: "Some file systems perform badly when they are almost full, so do not wait until the disk is completely full to take action." (원문)
- 출처: PostgreSQL 공식 문서 "26.3. Continuous Archiving and PITR" https://www.postgresql.org/docs/16/continuous-archiving.html : "**(If the file system containing `pg_wal/` fills up, PostgreSQL will do a PANIC shutdown. No committed transactions will be lost, but the database will remain offline until you free some space.)**" — 재현 트리거(아카이브 실패 → WAL 적재 → PANIC)가 공식 문서에 그대로 있다 (원문)
- 판정: E2 유지 : 공식 문서가 "PANIC shutdown", "the database will remain offline until you free some space"라고 결과까지 못 박고 재현 경로까지 명시. E2 넉넉히 충족
- 메모: **카탈로그 문구 부정확 2건.** (1) "디스크 100%면 DB가 쓰기를 멈춘다"는 **어느 파일시스템이 찼느냐에 따라 다르다** — 데이터 디스크가 차면 "will not result in data corruption, but it might prevent useful activity"(쿼리는 에러를 뱉지만 서버는 살아 있음)이고, **PANIC 셧다운은 `pg_wal`을 담은 파일시스템이 찼을 때**다. 오히려 "데이터 디스크 풀 vs pg_wal 풀"을 나눠 두 번 재현하면 이 세션이 가장 좋은 글이 된다(기본 설치는 pg_wal이 PGDATA 안이라 볼륨 하나만 채워도 둘 다 터진다는 점을 짚으면 됨) (2) **"로그도 못 써져 원인 파악까지 마비"는 공식 문서에 근거가 없다** — 로그 디렉터리가 같은 볼륨일 때만 성립하는 운영 현실이므로 조건을 붙여 쓸 것. **재현 권고** = WAL 폭주를 안정적으로 만들려면 (a) `archive_mode=on` + 반드시 실패하는 `archive_command`(공식 문서가 이 시나리오를 직접 기술하므로 인용까지 붙는다) 또는 (b) 아무도 소비하지 않는 replication slot. 볼륨은 도커 볼륨 크기 제한이 파일시스템에 따라 안 먹으니 loop device로 작은 ext4(1~2GB)를 만드는 쪽이 확실. 인용 금지 = 임계 알림 기준(80%/85% 등, 공식 근거 없음). **URL 주의 = `/docs/current/disk-full.html`과 `/docs/17/`은 404였고 `/docs/16/`만 정상이다**

## I09 DNS 캐시·TTL 함정
- 주장: JVM이 DNS 조회 결과를 사실상 무한 캐시해서 페일오버로 IP가 바뀐 뒤에도 앱이 죽은 구 IP를 계속 붙든다
- 출처: AWS SDK for Java 개발자 가이드 "Set the JVM TTL for DNS name lookups" https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/jvm-ttl-dns.html : "On some Java configurations, the JVM default TTL is set so that it will *never* refresh DNS entries until the JVM is restarted" / "we recommend that you configure your JVM with a TTL value of 5 seconds" / "`networkaddress.cache.ttl` is a *security property*, not a system property, i.e., it cannot be set with the `-D` command-line flag" (원문)
- 출처: Oracle Java SE 17 Networking Properties https://docs.oracle.com/en/java/javase/17/core/java-networking.html : "The default value is `-1` (forever) **if a security manager is installed** and implementation-specific if no security manager is installed." — **"무한 캐시"는 시큐리티 매니저가 있을 때만 기본값**이고, 없으면 구현 의존(OpenJDK는 30초) (원문)
- 판정: E2 유지 / **R02와 통합 권고** : 근거는 AWS 공식 문서로 탄탄하나 이 저장소의 R02(Multi-AZ 페일오버 DNS vs JVM 캐시)와 근거 문서·실패 메커니즘·재현 설계가 전부 동일하다. 별도 세션으로 두면 같은 글을 두 번 쓰게 된다
- 메모: **차별화하려면 계층을 나눌 것** — R02 = JVM 레이어(`networkaddress.cache.ttl`, RDS 페일오버), I09 = 컨테이너/쿠버네티스 레이어(`/etc/resolv.conf` ndots, CoreDNS 캐시 TTL, 사이드카 DNS 캐시). 통합한다면 I09를 폐기하고 R02에 컨테이너 DNS 절을 추가하는 쪽이 깔끔하다. **재현 경고 — "컨테이너 DNS를 바꿔도 앱이 구 IP 유지"는 요즘 JVM 기본값으로는 재현되지 않는다.** SecurityManager는 Java 17에서 deprecated·18+에서 사실상 비활성이라 일반 Spring Boot 앱의 실효 TTL은 30초다. 재현하려면 `Security.setProperty("networkaddress.cache.ttl","-1")`을 명시적으로 걸어야 하고, "요즘은 기본 30초라 무한 캐시 괴담은 절반만 맞다"를 짚는 게 오히려 이 글의 차별점

## I10 cgroup·IOPS 제한과 DB
- 주장: 클라우드 볼륨은 버스트 크레딧 소진 시 IOPS가 절벽처럼 떨어지고, 도커 `--device-write-bps`로 같은 절벽을 재현할 수 있다
- 출처: AWS EBS 사용 설명서 "General Purpose SSD volumes" https://docs.aws.amazon.com/ebs/latest/userguide/general-purpose.html : gp2는 "Baseline IOPS performance scales linearly between a minimum of 100 and a maximum of 16,000 at a rate of 3 IOPS per GiB" / "the volume **spends I/O credits** to burst to the required performance level (up to 3,000 IOPS)" / "Volumes have an **I/O credit accrual limit** of 5.4 million I/O credits". 공식 표에 **100 GiB gp2 = baseline 300 IOPS, 3,000 IOPS 버스트 지속 2,000초, 빈 크레딧 재충전 18,000초**. 반면 "**gp3 volumes do not use burst performance.**" (원문)
- 출처: Docker CLI 레퍼런스 `docker container run` https://docs.docker.com/reference/cli/docker/container/run/ : `--device-write-bps` "Limit write rate (bytes per second) to a device" 옵션 존재만 확인. **공식 문서에 스토리지 드라이버·cgroup 버전 제약 서술은 없음** (원문)
- 출처: **로컬 실측**(이 서버에서 직접 실행, 웹 출처 아님) — Docker 29.4.2 / 커널 5.14.0(el9) / cgroup v2 / overlay2 + XFS on LVM: 무제한 77.0 MB/s → `--device-write-bps /dev/sda:1mb` 적용 시 direct IO 1023.3 KB/s. **버퍼드 라이트(`conv=fsync`)도 200MB가 200.15초(1023.2 KB/s)로 정확히 스로틀됨.** `/dev/dm-0` 지정해도 동일
- 판정: E2 유지 / **재현 가능 확정** : 버스트 절벽은 AWS 원문 수치로 완전 뒷받침되고, "overlay2에서 `--device-write-bps`가 안 먹는다"는 통설은 **이 환경(cgroup v2)에서 반증됨**
- 메모: **재현 설계는 그대로 가되 세 가지를 지킬 것.** (1) **cgroup v2가 전제다** — 흔히 인용되는 "안 된다" 사례는 cgroup v1 얘기고, v1의 `blkio.throttle`은 버퍼드 라이트가 커널 writeback 스레드로 처리돼 cgroup에 귀속되지 않아 direct IO에만 걸린다. v2는 cgroup writeback으로 버퍼드도 잡는다. 글에 `stat -fc %T /sys/fs/cgroup` → `cgroup2fs` 확인 단계를 넣을 것 (2) **파티션이 아니라 디스크 전체를 지정할 것** — 도커 포럼의 `no such device` 에러는 `/dev/nvme0n1p7` 같은 파티션 지정 케이스다. `/dev/sda`나 `/dev/dm-0`을 쓸 것 (3) **gp3에는 버스트가 없다** — "burst 소진 후 절벽"은 gp2 한정이므로 행 문구를 "gp2 버스트 소진"으로 좁히지 않으면 사실 오류. 인용 가능 = 3 IOPS/GiB, 최소 100·최대 16,000, 버스트 3,000, 크레딧 상한 540만, 100GiB 표의 300/2,000초/18,000초. 위 실측치는 자기 환경 측정값으로 표기할 것
