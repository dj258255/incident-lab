## B16 Soft Delete unique 충돌
- 주장: 탈퇴(soft delete)한 이메일로 재가입 불가 + deleted_at 필터 누락 시 삭제 데이터 누수. 해법은 PG partial index vs MySQL generated column
- 출처: php[architect] "Advanced Unique Index Patterns for Soft Deletes (MySQL and PostgreSQL)"(2026-02) https://www.phparch.com/2026/02/advanced-unique-index-patterns-for-soft-deletes-mysql-and-postgresql/ : 재가입 차단 시나리오, PG `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`, MySQL generated column+복합 unique 우회까지 행의 재현 설계와 정확히 일치 (2차·실무 문서)

## B17 Vancouver 지수 절삭 (FLOAT 돈 계산)
- 주장: 1982년 시작된 절삭 누적으로 밴쿠버 증권거래소 지수가 22개월 만에 절반으로 떨어졌다
- 출처: English Wikipedia "Vancouver Stock Exchange" https://en.wikipedia.org/wiki/Vancouver_Stock_Exchange : "In January 1982 the index was initialized at 1000 and iteratively updated with each subsequent trade. After each update, the index was truncated to three decimal places. The truncated value was used to calculate the next value of the index. Updates occurred approximately 3000 times each day. The accumulated truncations led to an erroneous loss of around 25 points per month. Over the weekend of November 25–28, 1983, the error was corrected, raising the value of the index from its Friday closing figure of 524.811 to 1098.892." (원문)
- 출처: 위 문단이 인용하는 1차 보도 — Quinn, Kevin (1983-11-08) "Ever Had Problems Rounding Off Figures? This Stock Exchange Has" The Wall Street Journal p.37 / Lilley, Wayne (1983-11-29) "Vancouver stock index has right number at last" The Toronto Star p.35 : 위키 각주의 서지사항만 확인했고 지면 원문은 접근 못 함 (2차, 검색 결과·위키 각주로만 확인·직접 접속 안 함)
- 판정: 사건 근거는 E1 유지, 다만 **B17 세션 자체는 폐기 권고(F17에 흡수)** : 근거에는 문제가 없다. 문제는 중복이다. 이미 완성된 `sessions/F17-bigdecimal-money`가 (a) 밴쿠버 1982 사건 서사, (b) 절삭(RoundingMode.DOWN) vs HALF_EVEN 60,000회 누적 시뮬레이션, (c) double vs BigDecimal 100만 건 합계 오차를 전부 다루고 있어 B17의 재현 계획 "float 절삭 누적 시뮬레이션 + FLOAT vs DECIMAL 합계 오차"와 사실상 100% 겹친다. 같은 사건 서사를 두 세션에 쓰면 포트폴리오에서 오히려 감점이다. **차별화로 살릴 유일한 각도는 애플리케이션 레벨이 아니라 DB 레벨로 옮기는 것** — Postgres `double precision`/MySQL `DOUBLE` 컬럼에 돈을 넣고 `SUM()` 했을 때 `NUMERIC`·`DECIMAL`과 갈라지는 것, 집계 순서에 따라 SUM 결과가 달라지는 것, JDBC `getDouble()` 경유 손실 등. 이건 F17이 안 건드린 영역이라 별도 세션이 될 수 있지만, 그럴 경우 이름과 서사를 "밴쿠버"에서 "DB 컬럼 타입이 돈을 잃는 법"으로 갈아야 한다. 밴쿠버 인용은 F17 하나로 끝낼 것
- 메모: 카탈로그 수치 대조 = "22개월"은 위키 본문에 없는 파생값이다(1982-01 → 1983-11을 세면 맞지만 계산 결과이므로 "약 22개월"로 쓰거나 시작·종료 시점을 그대로 쓸 것). "절반으로"는 1000 → 524.811이므로 맞다. 인용 가능 = 1000 초기값, 소수 셋째 자리 절삭, 하루 약 3,000회, 월 약 25포인트 손실, 524.811 → 1098.892, 1983-11-25~28 주말. **인용 금지 = 검색 결과에 도는 "524.881"(위키 원문은 524.811)과 "true value should have been 1009.811"(위키가 밝힌 정정값은 1098.892)** — 둘 다 오탈자가 퍼진 것으로 보이며 서로 모순된다. F17 README가 이미 지적했듯 정정 직전 지수를 520.638로 적은 자료(TUM Huckle 모음)도 있으니, 특정 소수점 값을 단정하려면 위키가 인용한 Toronto Star 계열(524.811) 하나로 통일하고 출처를 명시할 것

## B18 DST 존재하지 않는 시간
- 주장: DST spring-forward로 존재하지 않는 시각(HOUR_OF_DAY)을 다루다 예외가 나는 함정이 반복적이라 Jira가 공식 KB를 낼 정도다
- 출처: Atlassian 공식 지원 문서 "Jira Data Center throws IllegalArgumentException: HOUR_OF_DAY exception with MySQL" https://support.atlassian.com/jira/kb/jira-data-center-throws-illegalargumentexception-hour_of_day-exception-with-mysql/ : 증상으로 `java.lang.IllegalArgumentException: HOUR_OF_DAY: 1 -> 2`, `HOUR_OF_DAY: 2 -> 3`, `HOUR_OF_DAY: 3 -> 4` 세 가지 명시. 원인 — "In localities that observe Daylight Saving Time (DST), there is an annual 'spring forward' event where the clock skips one hour." 시간대 정렬이 어긋나면 "timezones can be misaligned, resulting in MySQL timestamps during the lost hour". 영향 범위 = Jira Data Center 7.3 이상 / MySQL Server 5.7 이상 / MySQL Connector/J 8.0 이상. 해결책은 영향 컬럼 스캔 → Jira 정지 → 백업 → `ADDTIME`으로 손상된 타임스탬프를 1시간 앞으로 미는 저장 프로시저. 문서 갱신일 "Updated on July 7, 2026" (원문)
- 출처: 같은 주제의 구 confluence.atlassian.com KB 문서들 : 검색 결과에 제목·URL이 있으나 접속 시 Atlassian 로그인으로 리다이렉트되어 본문을 열지 못함 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지 : 벤더 공식 문서가 실재하고 직접 열어 본문·예외 문자열·영향 버전·복구 절차까지 확인했다. 특정 기업의 공개 장애는 아니므로 E1 근거는 없고 E2 정의에 정확히 들어맞는다
- 메모: **재현 설계에 치명적인 함정이 하나 있다.** 이 KB의 `IllegalArgumentException: HOUR_OF_DAY`는 MySQL Connector/J(구 `java.util.Calendar` 계열 경로)가 던지는 것이지 현대 `java.time` API가 던지는 게 아니다. 카탈로그 계획대로 "TZ America/New_York에서 DST 갭 시각 저장 → 예외 재현"을 `java.time`으로 짜면 **예외가 안 난다** — `ZonedDateTime.of(2024, 3, 10, 2, 30, ...)`는 조용히 03:30 EDT로 밀어버리고 아무 신호도 주지 않는다. 예외를 실제로 보려면 (a) MySQL DATETIME 컬럼에 갭 시각을 넣고 Connector/J로 읽거나 (b) `GregorianCalendar`에 `setLenient(false)`를 걸어야 한다. 오히려 이 두 경로("시끄럽게 터지는 쪽"과 "조용히 시각이 바뀌는 쪽")를 나란히 보여주는 게 함정의 본질에 더 맞고 설득력도 올라간다. 인용 가능 = 예외 문자열 3종, 영향 버전 조합(Jira DC 7.3+ / MySQL 5.7+ / Connector/J 8.0+), "spring forward"·"lost hour" 표현, ADDTIME 복구 절차의 존재. **인용 금지 = "Jira가 이 버그로 장애를 냈다" 류** — KB는 사건 보고서가 아니라 데이터 오염 대응 가이드다. "반복 함정"이라는 표현도 본문을 연 KB가 한 건뿐이므로 "Atlassian이 별도 KB와 복구 SQL까지 제공한다" 정도로만 쓰고 빈도 주장은 피할 것

## B19 Knight Capital 플래그 재사용
- 주장: 45분에 4.6억 달러 손실, 폐기 코드(Power Peg)의 플래그를 신기능에 재사용한 데다 8대 중 1대에 배포가 누락됐다
- 출처: U.S. SEC "Order Instituting Administrative and Cease-and-Desist Proceedings... In the Matter of Knight Capital Americas LLC" Securities Exchange Act Release No. 70694 / 2013-10-16, Admin. Proc. File No. 3-15570 https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf : sec.gov에서 PDF를 직접 내려받아 18페이지 전문을 텍스트로 확인(WebFetch는 403이라 직접 다운로드했고 제3자 미러본과 md5 동일). (1) 규모 — "While processing 212 small retail orders that Knight had received from its customers, SMARS routed millions of orders into the market over a 45-minute period, and obtained over 4 million executions in 154 stocks for more than 397 million shares. ... Ultimately, Knight lost over $460 million from these unwanted positions." (2) 플래그 재사용 — "the new RLP code in SMARS was intended to replace unused functionality called 'Power Peg,' which Knight had discontinued using many years earlier. Despite the lack of use, the Power Peg functionality remained present and callable at the time of the RLP deployment. The new RLP code also repurposed a flag that was formerly used to activate the Power Peg code." (3) 배포 누락 — "During the deployment of the new code, however, one of Knight's technicians did not copy the new code to one of the eight SMARS computer servers. Knight did not have a second technician review this deployment... Knight had no written procedures that required such a review." / "The seven servers that received the new code processed these orders correctly. However, orders sent with the repurposed flag to the eighth server triggered the defective Power Peg code still present on that server." (4) 제재 — Exchange Act Rule 15c3-5 위반, "a civil money penalty in the amount of $12,000,000" (원문)
- 판정: E1 유지 : 카탈로그가 주장한 세 수치("45분", "4.6억 달러", "8대 중 1대")가 모두 SEC 원문과 정확히 일치한다. 1차 규제기관 문서 전문을 확인했으므로 최상위 등급 유지
- 메모: **통설과 원문의 차이** — 인터넷에 가장 널리 도는 숫자는 "$440 million"인데 이는 Knight 자사 공시(8-K)의 세전 손실이고 SEC 원문은 "lost over $460 million"이다. 즉 카탈로그의 4.6억 달러가 SEC 기준으로 맞다. 글에 "SEC 문서 기준 4억 6천만 달러(널리 도는 4억 4천만 달러는 회사 공시 기준)"라고 한 줄 붙이면 신뢰가 올라간다. 인용 가능 = 212건 부모 주문, 400만 건 체결, 154종목, 3억 9,700만 주, 45분, 순매수 약 35억 달러(80종목)·순매도 약 31억 5,000만 달러(74종목), 과태료 1,200만 달러, 개장 전 "Power Peg disabled" BNET reject 이메일 97건이 나갔지만 시스템 경보로 설계돼 있지 않았다는 사실. **인용 금지 = "개발자 한 명의 실수"라는 프레임** — SEC는 개인 과실이 아니라 절차 부재를 지적한다("Knight did not have a second technician review this deployment", "Knight had no written procedures that required such a review"). 재현 세션의 결론도 "리뷰 없는 수동 배포 + 폐기 코드 잔존 + 플래그 재사용"이라는 구조 문제로 잡을 것. **미니 재현에 꼭 넣을 장면** — 되돌리기가 사태를 키웠다: "In one of its attempts to address the problem, Knight uninstalled the new RLP code from the seven servers where it had been deployed correctly. This action worsened the problem, causing additional incoming parent orders to activate the Power Peg code that was present on those servers, similar to what had already occurred on the eighth server." 8대 중 1대만 폭주하던 상황이 되돌린 직후 8대 전부 폭주로 번지는 그림은 "이상하면 일단 되돌린다"는 통념을 정면으로 깨는 소재라 난이도 대비 임팩트가 가장 크다

## B20 500마일 이메일 (타임아웃=거리)
- 주장: sendmail의 connect timeout이 0/3ms로 죽어 "500마일 밖으로는 메일이 안 간다"는 현상이 실제로 있었고, 지연이 곧 거리라는 걸 보여주는 실장애 사례다
- 출처: Trey Harris "The Case of the 500-Mile Email" https://www.ibiblio.org/harris/500milemail.html : 2002-11-24 sage-members 메일링리스트 게시글. 본문 서두에 "The story is slightly altered in order to protect the guilty, elide over irrelevant and boring details, and generally make the whole thing more entertaining." 기술 핵심 — "One of the settings that was set to zero was the timeout to connect to the remote SMTP server." / "a zero timeout would abort a connect call in slightly over three milliseconds." / "time to connect to a lightly-loaded remote host on a nearby network would actually largely be governed by the speed of light distance to the destination." 단위 환산 "3 millilightseconds" = 약 558.85 miles (원문)
- 출처: Trey Harris "The Case of the 500-Mile Email FAQ" https://www.ibiblio.org/harris/500milemail-faq.html : 사실 여부에 대해 "Yes, it happened."라고 답하지만 동시에 "I took license. - 판정: 강등 제안 E1→E2 : 등급 정의상 E1은 "기업 포스트모템·규제기관 문서"인데 이 글은 개인이 메일링리스트에 올린 회고담이고, 저자 스스로 각색을 인정하며 로그·메모가 남아 있지 않다고 밝혔다. 다만 저자 본인이 20년 넘게 원문과 FAQ를 유지하며 "일어난 일"임을 확인하고 있고, 기저 메커니즘(connect timeout이 0에 가까우면 RTT가 임계값을 넘는 원격지만 실패 → 도달 가능 반경이 생김)은 tc netem으로 그대로 재현·검증 가능하다. 등급만 내리고 항목은 유지 권고. 굳이 라벨을 붙이면 "E2·일화(anecdote)"가 정확하다

## B24 Redis 분산 락 만료 + 펜싱 토큰
- 주장: Redis 기반 분산 락은 GC/프로세스 정지가 락 리스보다 길어지면 클라이언트가 만료를 모른 채 쓰기를 수행하며, Redlock은 펜싱 토큰을 만들지 못해 상호배제를 보장할 수 없다(단, 이는 논쟁 중인 주장이다)
- 출처: Martin Kleppmann "How to do distributed locking"(2016-02-08) https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html : 카탈로그의 두 인용이 원문과 일치함을 확인. GC — "if the GC pause lasts longer than the lease expiry period, and the client doesn't realise that it has expired, it may go ahead and make some unsafe change." 펜싱 토큰 — "However, this leads us to the first big problem with Redlock: it does not have any facility for generating fencing tokens." / "The algorithm does not produce any number that is guaranteed to increase every time a client acquires a lock." 결론 — "if you need locks for correctness, please don't use Redlock. Instead, please use a proper consensus system such as ZooKeeper." (원문)
- 출처: antirez "Is Redlock safe?" http://antirez.com/news/101 : 반박 확인. 지연/정지 논증에 대해 — "Whatever delay happens in the network or in the processes involved, after acquiring the majority we *check again* that we are not out of time." 펜싱 토큰에 대해 — "a unique identifier for each lock can be used for the same goals, but is much more practical in terms of not requiring strong guarantees from the store." 한 가지는 수용 — "I think Martin has a point about the monotonic API, Redis and Redlock implementations should use it to avoid issues due to the system clock being altered." (원문, 단 페이지 전문이 아니라 발췌 형태로 회수됨)
- 출처: Redis 공식 문서 "Distributed Locks with Redis" https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/ : 재현 시나리오의 핵심 전제를 공식 문서가 명시 — "it is guaranteed only as long as the client holding the lock terminates its work within the lock validity time (as obtained in step 3), minus some time (just a few milliseconds in order to compensate for clock drift between processes)." "Disclaimer about consistency" 절에서 Redis 스스로 펜싱 토큰 권고 — "You should implement fencing tokens. This is especially important for processes that can take significant time and applies to any distributed locking system." 또한 "Redis is not using monotonic clock for TTL expiration mechanism. That means that a wall-clock shift may result in a lock being acquired by more than one process." 하단 "Analysis of Redlock" 절에 Kleppmann 글과 antirez 반박이 양쪽 다 링크됨 (원문). 참고: 흔히 쓰이는 구 URL(/docs/latest/develop/use/patterns/distributed-locks/)은 현재 404이므로 위 URL을 쓸 것
- 판정: E2 유지(근거 강함, 사실상 승격 수준) : 논쟁의 양쪽 1차 문헌이 모두 존재하고 인용문이 원문과 일치하며, 결정적으로 Redis 공식 문서가 별도 절을 만들어 펜싱 토큰 구현을 직접 권고한다. E2 정의를 정확히 충족
- 메모: 인용 가능 = Kleppmann 원문 3문장, antirez의 monotonic clock 양보, Redis 공식 문서의 "You should implement fencing tokens" 및 "terminates its work within the lock validity time". **인용 금지 = "Redlock은 안전하지 않다"를 확정 사실처럼 쓰는 것** — 이건 Kleppmann의 결론이고 antirez가 정면 반박한 미해결 논쟁이므로 반드시 "Kleppmann은 ~라고 주장한다 / antirez는 ~라고 반박한다"로 화자를 붙일 것. 글의 안전한 축은 "누가 옳은가"가 아니라 Redis 공식 문서가 이미 수용한 지점 — (1) 상호배제는 작업이 락 유효시간 안에 끝난다는 조건부 보장이고 (2) 그 조건이 깨질 수 있으니 펜싱 토큰을 쓰라는 것 — 으로 잡으면 양쪽 다 동의하는 영역이라 반박당하지 않는다. 수치 주의 = 문서의 N=5, 타임아웃 5~50ms, TTL 10초/30000ms는 모두 공식 문서의 예시값이지 권장 튜닝값이 아니다. 실험의 TTL 2초/sleep 3초는 실험 설정으로만 표기할 것

## B25 @Transactional self-invocation
- 주장: 같은 클래스 안에서 `this.method()`로 호출하면 Spring AOP 프록시를 우회해 `@Transactional`이 붙어 있어도 트랜잭션이 시작조차 되지 않고, 따라서 예외가 나도 롤백 없이 부분 저장된다

As of 6.0, `protected` or package-visible methods can also be made transactional for class-based proxies by default. Note that transactional methods in interface-based proxies must always be `public` and defined in the proxied interface." — 버전 경계(6.0)가 있는 서술이라 "private/비public은 무조건 무시된다"고 단정하면 틀린다 (원문)
- 판정: E2 유지(확정) : 벤더 공식 문서가 정확히 그 문장으로 서술한다. "does not lead to an actual transaction at runtime"은 "트랜잭션이 시작조차 안 됨"이라는 카탈로그 표현과 의미가 일치. 이번 묶음에서 근거가 가장 깔끔하다
- 메모: 인용 가능 = 위 self-invocation 문장 전체(영문 그대로 박고 한 줄 번역 붙이는 게 안전), AspectJ 모드 대안, `@PostConstruct` 함정, 6.0부터 protected/package-private 지원. **인용 금지 = `readOnly = true`가 "그냥 힌트일 뿐 쓰기를 막지 않는다"는 통설** — 이 페이지에 그 서술이 없고 확인된 문장은 "Read-write versus read-only transaction. Only applicable to values of `REQUIRED` or `REQUIRES_NEW`."뿐이다. readOnly 함정을 묶어 쓰려면 `@Transactional` javadoc이나 Hibernate 문서를 따로 확인한 뒤 쓰고, 확인 전에는 "실험으로 확인한 동작"이라고만 적을 것. 전파(propagation) 오설정도 마찬가지로 이 페이지에 함정 서술이 없으니 실험 결과를 근거로 삼고 공식 문서를 인용한 것처럼 쓰지 말 것. 가시성 규칙은 Spring 6.0 전후가 다르므로 실험에 쓴 버전을 반드시 명시할 것

## B26 트랜잭션 안에서 외부 API 호출
- 주장: `@Transactional` 안에서 HTTP 등 외부 호출을 하면 DB 커넥션을 쥔 채 네트워크 대기를 하게 되어 커넥션 풀이 고갈되고, 외부 호출 자체는 DB 롤백으로 되돌릴 수 없다
- 출처: Spring Framework 공식 레퍼런스 "Controlling Database Connections" https://docs.spring.io/spring-framework/reference/data-access/jdbc/connections.html : 메커니즘은 공식 서술됨 — "The `DataSourceTransactionManager` class is a `PlatformTransactionManager` implementation for a single JDBC `DataSource`. It binds a JDBC `Connection` from the specified `DataSource` to the currently executing thread, potentially allowing for one thread-bound `Connection` per `DataSource`." 다만 **"외부 호출을 트랜잭션 안에서 하지 마라" 같은 경고 문장은 이 페이지에 없음** (원문, 경고 부재를 직접 확인)
- 출처: Spring Framework javadoc `LazyConnectionDataSourceProxy` https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/jdbc/datasource/LazyConnectionDataSourceProxy.html : 스프링이 이 문제를 완화하는 별도 기능을 공식 제공한다는 근거 — "This DataSource proxy allows to avoid fetching JDBC Connections from a pool unless actually necessary. JDBC transaction control can happen without fetching a Connection from the pool or communicating with the database; this will be done lazily on first creation of a JDBC Statement." 단, 명시된 동기는 "실제 데이터 접근이 없는 빈 트랜잭션"이지 "외부 API 호출 중 점유"가 아님 (원문)
- 출처: HikariCP 공식 wiki "About Pool Sizing" https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing : 기대했던 경고가 없음을 확인. 확인된 것은 풀 사이징 공식 "connections = ((core_count * 2) + effective_spindle_count)"와 "You want a small pool, saturated with threads waiting for connections."뿐이고, DB 외 작업으로 커넥션을 오래 쥐는 것에 대한 경고는 이 페이지에 없다 (원문, 부재를 직접 확인)
- 출처: 웹 검색 결과 전반(Vlad Mihalcea "Spring Transaction and Connection Management" 등) : 트랜잭션 경계가 외부 호출을 감싸면 커넥션이 점유된다는 서술은 블로그·GitHub 이슈 레벨에서만 반복 확인됨 (2차, 검색 결과로만 확인·직접 접속 안 함)
- 판정: E2 유지(조건부) — 근거 문장을 반드시 교체할 것 : **"공식 문서가 이 안티패턴을 경고한다"는 검증에 실패했다.** 어떤 벤더 문서도 "트랜잭션 안에서 외부 API를 호출하지 마라"고 쓰지 않는다. 대신 (1) 커넥션이 트랜잭션 동안 스레드에 바인딩된다는 메커니즘, (2) 스프링이 커넥션 조기 획득을 피하려고 `LazyConnectionDataSourceProxy`라는 전용 기능을 공식 제공한다는 사실 두 가지가 공식 문서로 확인된다. "공식 기능을 만들 정도의 문제"라는 선에서 E2를 유지할 수 있으나, "공식 경고문 존재"를 E2의 필수 요건으로 엄격히 본다면 이 항목은 E2 미달이며 그 경우 폐기가 아니라 "메커니즘은 공식·경고는 업계 통념"으로 등급 각주를 달아 낮춰 표기하는 게 맞다. 재현 실험 자체가 1차 근거를 스스로 만들어내는 주제라 폐기는 권고하지 않는다
- 메모: 인용 가능 = `DataSourceTransactionManager`의 "binds a JDBC `Connection` ... to the currently executing thread" 문장, `LazyConnectionDataSourceProxy` javadoc 2문단. **인용 금지 = "Spring/HikariCP 공식 문서가 트랜잭션 내 외부 호출을 경고한다"는 문장** — 사실이 아니며 확인해봤고 없었다. 글에는 "공식 문서는 이 안티패턴을 직접 경고하지 않는다. 다만 커넥션이 트랜잭션 내내 스레드에 묶인다는 것과, 스프링이 커넥션 지연 획득 기능을 따로 제공한다는 것은 공식 문서에 있다"고 정직하게 쓰는 편이 오히려 신뢰도를 올린다. `LazyConnectionDataSourceProxy`를 해법으로 소개할 때 주의 — 첫 Statement까지 커넥션 획득을 미룰 뿐, 이미 쿼리를 한 번 날린 뒤 외부 호출을 하면 아무 도움이 안 된다. 근본 해법은 여전히 외부 호출을 트랜잭션 밖으로 빼는 리팩터링이라고 못 박을 것. HikariCP의 공식은 PostgreSQL 프로젝트 유래로 표기해야 하고 이 실험의 풀 고갈 재현에 튜닝 근거로 끌어오면 논점이 흐려진다. "외부 호출은 롤백 불가"는 어떤 출처도 확인하지 않았다 — 자명한 논리로 서술하되 보상 트랜잭션/Saga 문헌을 인용하려면 별도 확인이 필요하다
