## B14 Cloudflare 2019 정규식 백트래킹
- 주장: 정규식 하나의 백트래킹으로 27분 글로벌 다운·트래픽 82% 급락, CPU 보호장치가 리팩토링에서 제거돼 있었고 카나리 없이 전 세계 동시 배포
- 출처: Cloudflare 공식 포스트모템 "Details of the Cloudflare outage on July 2, 2019" https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/ : 문제 정규식 원문 수록, 13:42 배포→14:07 WAF 킬→14:09 정상화(약 27분), CPU 보호장치가 "리팩토링 중 실수로 제거" 명시, WAF 룰은 SOP상 카나리 없이 글로벌 푸시 명시, RE2/Rust regex 전환 계획 명시 (원문)
- 판정: E1 유지 : 행의 주장 전부 원문에서 확인. 트랙 대표 편으로 손색없음
- 메모: 본문 일화 인용은 "lost 80% of our traffic"(SE 리더 발언). 82%는 같은 포스트의 트래픽 그래프 수치라 "약 80%대 급락"으로 쓰면 안전

## B15 ORDER BY RAND() 폭탄
- 주장: StackOverflow 단골 함정, 100만 행에서 58분 vs 대안 0.6초
- 출처: WarpConduit "Selecting Random Rows Using MySQL + Benchmark Results"(2011) https://www.warpconduit.net/2011/03/23/selecting-a-random-record-using-mysql-benchmark-results/ : 125만 행 실측에서 Inner Join·User Variable 대안이 약 0.001초, ORDER BY RAND()는 스케일 불가 판정. 단 1M행 ORDER BY RAND()의 정확한 시간은 본문에서 미확인 (2차·자체 벤치마크)
- 출처: sqlpey "Efficient SQL Techniques to Replace Slow ORDER BY RAND" https://sqlpey.com/mysql/efficient-sql-techniques-replace-slow-order-by-rand/ : 전 행 난수 생성+전체 정렬이라는 메커니즘 설명만, 수치 없음 (2차)
- 판정: E2 유지 : 함정 실재·대안 벤치마크 다수 확인. 단 "58분 vs 0.6초" 조합 수치는 안정된 원출처 고정 실패
- 메모: 검색 스니펫에는 1M행 58:20 표가 돌아다니나 원저자 불명. 블로그에는 이 수치 인용 대신 세션 자체 실측치(EXPLAIN+시간)를 쓸 것. "수치 인용 금지 목록"에 준해 취급 권장

## B16 Soft Delete unique 충돌
- 주장: 탈퇴(soft delete)한 이메일로 재가입 불가 + deleted_at 필터 누락 시 삭제 데이터 누수. 해법은 PG partial index vs MySQL generated column
- 출처: php[architect] "Advanced Unique Index Patterns for Soft Deletes (MySQL and PostgreSQL)"(2026-02) https://www.phparch.com/2026/02/advanced-unique-index-patterns-for-soft-deletes-mysql-and-postgresql/ : 재가입 차단 시나리오, PG `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`, MySQL generated column+복합 unique 우회까지 행의 재현 설계와 정확히 일치 (2차·실무 문서)
- 판정: E2 유지 : 특정 사건 아닌 반복 함정으로서 실무 문서 다수 확인. 행의 두 DB 해법 대비 구도 그대로 유효
- 메모: "deleted_at 누락 시 누수"는 위 글엔 없고 별도 글들(dev.to 'Why Soft Delete Can Backfire on Data Consistency' 등 검색 확인)에서 다루는 일반 패턴. 블로그에선 메커니즘 설명으로 충분, 사건 인용 불필요
