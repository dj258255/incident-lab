# 실험 6. 회수에 승인을 붙인다

  usp_RequestReclaim / usp_ApproveReclaim / usp_ReclaimCurrencyGated 설치 완료
  로그인 maker / checker 생성, 각자 자기 프로시저만 실행 가능
  로그인 operator 생성. 둘 다 할 수 있어 자기 승인 로직만 따로 시험합니다

  앞 실험이 남긴 운영 DB 밖 계정 1개를 걷어냈습니다

  조건                   결과                                 회수액
## 6-1. 네 조건

  A 요청→승인→실행 통과                                 360000
  B 승인 없이 실행   **거부 — 승인되지 않은 요청** 0
  C 요청자가 자기 승인 **거부 — 자기 요청은 자기가 승인 못 함** 0
  D 승인 뒤 대상 추가 **거부 — 승인 뒤 대상이 바뀜** 0

## 6-2. 권한 분리

  maker 가 승인 시도                  **거부 — 권한 없음**
  checker 가 요청 시도                **거부 — 권한 없음**
  maker 가 게이트를 건너뛰고 직접 실행 **거부 — 권한 없음**

==================================================================
## 정리
==================================================================

  승인 대기를 붙이자 셋이 막힙니다. 승인 없는 실행, 자기 승인, 그리고 게이트를
  건너뛰고 원래 프로시저를 직접 부르는 것까지.

  **막는 층이 둘로 나뉩니다.** 권한이 막는 것과 로직이 막는 것은 다릅니다.
  maker 가 승인을 시도하는 것은 권한이 막고(Msg 229), 둘 다 할 수 있는 계정이
  자기 요청을 승인하는 것은 로직이 막습니다(Msg 50022). 역할 분리가 된 조직이면
  권한만으로 충분해 보이지만, 한 사람이 둘 다 맡는 조직에서는 로직만 남습니다.
  둘 다 있어야 합니다. 그리고 원래 프로시저에 DENY EXECUTE 를 안 걸면 게이트는
  우회하면 그만입니다.

  **D 가 이 실험의 요점입니다.** 승인만 붙이면 거기가 뚫립니다. 승인을 받아 둔 뒤
  회수 대상 표에 행을 하나 더 넣으면, 승인은 그대로 유효한 채로 다른 목록이
  실행됩니다. 승인은 "이 목록을 회수해도 된다"는 뜻이지 "언제든 회수해도 된다"는
  뜻이 아닙니다.

  그래서 승인 시점의 대상 지문(건수·합계·체크섬)을 저장해 두고 실행할 때 다시
  대조합니다. 실험 5에서 이관 검증에 쓴 것과 같은 지문입니다. 한 번은 서버를
  건너올 때, 한 번은 시간을 건너올 때 씁니다.
