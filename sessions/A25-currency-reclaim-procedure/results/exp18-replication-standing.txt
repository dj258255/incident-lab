# 실험 18. 복제를 상시 구성으로 세우면 무엇이 더 붙는가

  실험 15는 표 하나를 **한 번** 넘기는 비용을 쟀고, 결론에서 "복제를 쓸 자리는
  조사 DB 를 운영에서 계속 떠먹이는 구성"이라고 적었습니다. **그 자리를 권해
  놓고 그 구성은 안 세워 봤습니다.** 여기서 세웁니다.

  실험 15는 스냅샷 복제였습니다. 상시 구성은 트랜잭션 복제고 그것부터 다릅니다.

==================================================================
## 18-1. 세우는 단계
==================================================================

  #   한 일                                        결과
  1   발행 DB 와 상시 공급 표를 만든다   됨
  2   구독 DB 를 만든다                        됨
  3   표를 채운다                               됨
  4   배포자를 세운다                         됨
  5   배포 DB 를 만든다                        됨
  6   배포 DB 에 마스터 키를 만든다       됨
  7   발행자를 배포자에 등록               됨
  8   발행 DB 에 복제를 켠다                 됨
  9   로그 판독기 에이전트를 붙인다 (sp_addlogreader_agent) 됨
  10  발행 항목을 트랜잭션 복제로 만든다 (@repl_freq=continuous) 됨
  11  스냅샷 에이전트를 붙인다            됨
  12  표를 발행 목록에 넣는다              됨
  13  구독을 만든다                            됨
  14  배포 에이전트를 붙인다 (SQL 인증)  됨
  15  그 에이전트가 SQL 인증으로 잡혔는지 되읽는다 됨
  16  배포 에이전트에 -EncryptionLevel 0 을 붙인다 됨

  실험 15(한 번 넘기기)                   15단계
  이번(상시 구성)                          16단계

  늘어난 것은 단계 수만이 아닙니다.

  스냅샷 에이전트   A25-REPL-PUB-repl_src-pub_standing-1
  로그 판독기 에이전트 A25-REPL-PUB-repl_src-1
  배포 에이전트      a25-repl-pub-repl_src-pub_standing-A25-REPL-SUB-3

  **로그 판독기가 이번에 새로 생긴 것입니다.** 발행 DB 의 트랜잭션 로그를 계속
  읽어 바뀐 것을 배포 DB 로 옮깁니다. 이 에이전트가 멈추면 **발행 DB 의 로그가
  안 잘립니다.** 복구 모델이 SIMPLE 이어도 그렇습니다.

==================================================================
## 18-2. 바뀐 것이 따라오는가
==================================================================

  스냅샷 생성               완료
  첫 적재 2000행 도착      됨
  그 뒤 500행 추가분이 따라옴 됨

  **이것이 실험 15와 다른 점입니다.** 스냅샷 복제는 스냅샷을 다시 떠야 하고,
  트랜잭션 복제는 로그 판독기가 바뀐 것만 계속 흘려보냅니다. 조사 DB 를 상시로
  떠먹이려면 이쪽이어야 합니다.

==================================================================
## 18-3. 구독자가 죽으면 무엇이 쌓이는가
==================================================================

  상시 구성의 진짜 비용은 여기 있습니다. 한 번 넘기고 끝나는 구성에는
  이 질문 자체가 없습니다.

  구독자를 내리기 전 배포 DB 22MB
    보관 중인 명령 / 미전달 546건 / 0건
  구독자를 내렸습니다       0대 떠 있음
  그 사이 발행자에 넣은 행 20000행
  보관 중인 명령               546건 -> 20592건
  그중 미전달                   0건 -> **20045건**
  배포 DB 크기                   22MB -> **86MB**

  배포 에이전트가 말하는 것:
    ERR: Unspecified error
    ERR: Unspecified error

  **구독자가 없는 동안 그 부담은 배포자가 집니다.** 미배포 명령이 배포 DB 에
  쌓이고 그만큼 자랍니다. 보존 기간(@retention, 기본 72시간)을 넘기면 구독이
  만료되고, 그때는 스냅샷을 다시 떠서 **처음부터 다시 밀어야** 합니다.

==================================================================
## 18-4. 다시 붙으면 알아서 따라잡는가
==================================================================

  구독자를 다시 올렸습니다 READY
  구독자 행 수                  22500 / 22500
  미전달 명령                   20045건 -> **0건**
  따라잡았는가                 **됨**

  그런데 보관 중인 명령     20592건 -> 20592건
  그리고 배포 DB 크기         86MB -> 86MB

  **알아서 따라잡습니다.** 배포 에이전트가 다시 붙어 쌓인 명령을 순서대로
  밀어 넣습니다. 사람이 할 일은 없습니다. **다만 그것은 보존 기간 안에서만
  참입니다.** 넘기면 구독이 만료되고 스냅샷부터 다시입니다.

  그런데 **전달이 끝났는데도 배포 DB 는 안 줄었습니다.** 미전달은 0 인데
  보관 중인 명령과 크기는 그대로입니다. @immediate_sync = true 로 만든
  발행이라 **새 구독자가 스냅샷 없이 붙을 수 있게** 명령을 보존 기간 내내
  들고 있기 때문입니다. 정리 작업이 돌아 보존 기간이 지나야 줄어듭니다.

  그래서 배포 DB 크기는 **구독자의 상태가 아니라 발행 설정과 변경량이**
  정합니다. 구독자가 멀쩡해도 쓰기가 많으면 그만큼 자랍니다.

==================================================================
## 18-5. 로그 판독기가 멈추면
==================================================================

  구독자가 죽으면 배포자가 부담을 진다고 했습니다. 그러면 로그 판독기가
  멈추면 누가 집니까. **발행자, 즉 운영 DB 입니다.**

  같은 쓰기를 두 번 합니다. 한 번은 로그 판독기가 도는 채로, 한 번은 멈춘
  채로. 복구 모델은 둘 다 SIMPLE 입니다.

  A 로그 판독기가 도는 채로 200000행
    쓰인 로그                    0.5MB -> 1.2MB
    로그 파일                    8.0MB -> 72.0MB
    재사용 대기                 SIMPLE/NOTHING

  B 로그 판독기를 멈춘 채로 200000행 (같은 양)
    쓰인 로그                    1.2MB -> **23.8MB**
    로그 파일                    72.0MB -> **72.0MB**
    재사용 대기                 **SIMPLE/REPLICATION**

  **복구 모델이 SIMPLE 인데도 로그가 안 잘립니다.** SIMPLE 이면 체크포인트가
  알아서 자른다고 알기 쉬운데, 복제가 걸린 DB 는 **로그 판독기가 읽어 가기
  전까지는 그 구간을 못 버립니다.** log_reuse_wait_desc 가 그것을 말합니다.
  판독기가 도는 A 에서는 같은 쓰기를 하고도 쓰인 로그가 제자리로 돌아옵니다.

  판독기를 다시 켜면         SIMPLE/NOTHING
    쓰인 로그                    23.8MB -> 7.9MB

  판독기를 다시 켜자 회수됐습니다. **원인이 판독기라는 것이 이것으로 섭니다.**
  사람이 손댈 것은 없지만, 그때까지 자란 로그 파일은 **안 줄어듭니다.**
  줄이려면 따로 축소해야 하고 그것은 또 다른 작업입니다.

  이것이 상시 구성에서 제일 위험한 자리입니다. 구독자가 죽으면 배포 DB 가
  자라지만 그것은 **옆 서버**입니다. 로그 판독기가 죽으면 **운영 DB 의 로그가**
  자랍니다. 로그가 디스크를 채우면 그 DB 는 쓰기를 못 받습니다.

==================================================================
## 정리
==================================================================

  실험 15의 결론은 "복제를 쓸 자리는 조사 DB 를 상시로 떠먹이는 구성"이었습니다.
  그 자리를 실제로 세워 보니 값이 이렇습니다.

                               한 번 넘기기(실험 15) 상시 구성(이번)
  세우는 단계             15                     16
  에이전트                 2개                   **3개(로그 판독기)**
  발행 DB 로그             안 묶임             **판독기가 멈추면 SIMPLE 이어도 안 잘림**
  구독자가 죽으면       해당 없음          **배포 DB 에 적체**
  그 적체의 한계         해당 없음          보존 기간(기본 72시간)
  전달이 끝나면          파일을 지우면 끝 **배포 DB 는 안 줄어듦**
  끊겼다 붙으면          해당 없음          알아서 따라잡음

  **상시 구성은 세우는 비용보다 유지하는 비용이 큽니다.** 한 번 넘기기는
  끝나면 끝이지만, 상시 구성은 구독자·배포자·로그 판독기 셋이 계속 살아 있어야
  하고 하나가 멈추면 다른 쪽에 부담이 갑니다. 특히 로그 판독기가 멈추면
  **발행 DB 의 로그가 안 잘려** 운영 DB 쪽 디스크가 찹니다.

  그래서 실험 15의 결론에 조건을 하나 붙입니다. 조사 DB 를 상시로 떠먹이는
  구성이 맞기는 하지만, **그것은 이관 문제를 없애는 대신 상시 감시 대상을
  셋 늘리는 거래입니다.** 회수가 1년에 몇 번인지에 따라 답이 갈립니다.
