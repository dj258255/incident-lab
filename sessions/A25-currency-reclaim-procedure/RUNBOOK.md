# 운영 절차서: 재화 회수 실행

대상: 확정된 회수 대상 목록을 실제로 되돌리는 작업
근거: 같은 디렉토리의 [README.md](README.md) 실측.

앞 단계(대상을 뽑는 절차)는 [A24 운영 절차서](../A24-currency-anomaly-detection/RUNBOOK.md),
배치 크기의 근거는 [A04 운영 절차서](../A04-mssql-lock-escalation/RUNBOOK.md)입니다.

---

## 0. 한 줄 요약

**표시를 남기고, 5,000행 미만 배치로 끊고, 계정마다 전후 값을 적고, 끝나면 검산한다.**
이미 쓴 재화는 빚 컬럼으로 남긴다. 제약을 빼는 것은 마지막 수단이다.

---

## 1. 시작 전 확인

| # | 확인 | 통과 기준 |
|---|---|---|
| 1 | 회수 대상 표에 계정과 **금액**이 다 있는가 | 계정만으로는 시작할 수 없다 |
| 2 | 대상 표를 표본 검증했는가 | 상위 몇 계정의 원장을 손으로 확인 |
| 3 | 복구 모델이 FULL 인가 | `SELECT recovery_model_desc FROM sys.databases` |
| 4 | 로그 백업 체인이 이어져 있는가 | 최근 로그 백업 시각 확인 |
| 5 | 전체 백업을 방금 떴는가 | 되돌릴 기준점 |
| 6 | 잔액 제약이 무엇인가 | `CHECK (balance >= 0)` 이 있으면 2번 항목의 설계 결정 필요 |
| 7 | 승인을 받았는가 | 회수는 이용자 자산을 줄이는 작업이다 |

---

## 2. 잔액이 모자란 계정의 처리 (설계 결정)

| 설계 | 언제 쓰나 | 대가 |
|---|---|---|
| **빚 컬럼 (권장)** | 기본 | 획득 경로마다 상계 로직이 들어가야 한다 |
| 음수 잔액 | 빚 컬럼을 넣을 수 없을 때 | 제약을 빼야 하고, 음수를 읽는 코드를 전부 확인해야 한다 |

빚 컬럼을 고르면 `적용액 + 빚 = 대상액` 이 항상 성립해야 하고, 그것이 검산식이 됩니다.

> 음수 잔액을 고른다면 **언제 제약을 되돌릴지 함께 정합니다.** 제약이 빠져 있는 동안
> 다른 버그가 음수를 만들어도 아무도 모릅니다.

---

## 2-2. 회수 대상이 다른 서버에서 왔다면

조사는 로그 DB, 보정은 운영 DB에서 도는 것이 보통입니다. 목록을 옮겼다면 **회수를
시작하기 전에 원본과 대조합니다.**

```sql
-- 조사 DB 와 운영 DB 양쪽에서 같은 값을 뽑아 셋 다 비교한다
SELECT COUNT(*)                                                    AS rows,
       SUM(extra_amount)                                           AS total,
       CHECKSUM_AGG(BINARY_CHECKSUM(account_id, extra_rows, extra_amount)) AS chk
  FROM reclaim_target;
```

세 값이 모두 같아야 넘어갑니다. **건수만 보면 안 됩니다.** 값이 바뀐 채 건수만 맞는
경우를 체크섬이 잡습니다.

> **이 대조가 유일한 방어선인 사고가 있습니다.** 파일이 잘려 절반만 넘어오면 `bcp` 는
> 오류를 내지 않고, 회수 프로시저의 검산도 통과합니다. 받은 만큼 정확히 회수했으니
> 프로시저 입장에서는 성공입니다. 절반이 사라진 것은 원본과 대조할 때만 드러납니다.

## 2-3. 승인

**회수는 승인을 받고 돕니다.** 이용자 자산을 줄이는 작업이라 한 사람이 결정하지 않습니다.

```sql
-- 요청자(maker)
DECLARE @r INT;
EXEC usp_RequestReclaim @reason = N'<사고 번호와 조사 근거>', @request_id = @r OUTPUT;

-- 승인자(checker). 요청자와 같은 사람이면 프로시저가 거부한다.
EXEC usp_ApproveReclaim @request_id = <요청 번호>;

-- 실행. 승인 시점 대상 지문과 지금 지문을 대조한 뒤에만 돈다.
EXEC usp_ReclaimCurrencyGated @request_id = <요청 번호>, @mode = 'DEBT', @chunk = 4000;
```

지켜야 할 것 넷입니다.

| # | 무엇 | 안 하면 |
|---|---|---|
| 1 | 요청과 승인 권한을 로그인으로 나눈다 | 한 사람이 요청하고 승인한다 |
| 2 | 자기 승인을 프로시저 로직으로도 막는다 | 한 사람이 둘 다 맡는 조직에서 1번이 무력해진다 |
| 3 | 원래 프로시저에 `DENY EXECUTE` 를 건다 | 게이트를 우회해 직접 부르면 그만이다 |
| 4 | **승인 시점의 대상 지문을 저장하고 실행 때 대조한다** | 승인 뒤 목록을 바꿔치기할 수 있다 |

4번이 제일 놓치기 쉽습니다. 승인은 "이 목록을 회수해도 된다"는 뜻이지 "언제든 회수해도
된다"는 뜻이 아닙니다. 실측에서 승인 뒤 대상 표에 행을 하나 넣자 승인이 그대로 유효한
채로 다른 목록이 실행되려 했고, 지문 대조가 그것을 막았습니다.

## 3. 실행

```sql
-- 되돌릴 지점에 이름을 붙인다. 이 트랜잭션은 아무것도 안 바꿔도 된다.
BEGIN TRAN before_reclaim WITH MARK '<사유> 보정 직전';
    INSERT INTO correction_batch (reason, status) VALUES (N'[표시] 보정 직전', 'MARK');
COMMIT TRAN before_reclaim;

-- 회수
DECLARE @b INT;
EXEC usp_ReclaimCurrency
     @reason   = N'<사유. 사고 번호와 조사 근거를 적는다>',
     @mode     = 'DEBT',      -- 또는 NEGATIVE
     @chunk    = 4000,
     @batch_id = @b OUTPUT;
```

프로시저가 지키는 것 넷입니다. 직접 쿼리로 돌리면 이것들이 빠집니다.

1. 배치마다 커밋해 락을 놓는다 (`@chunk >= 5000` 은 아예 거부)
2. 진행 지점을 배치와 **같은 트랜잭션**에서 옮긴다 (이중 회수 방지)
3. 계정마다 전후 값과 적용액·빚을 남긴다
4. 끝나면 `회수 합계 = 대상 합계` 를 검산하고 안 맞으면 던진다

## 4. 작업 중 감시

```sql
-- 진행률
SELECT batch_id, status, last_done,
       (SELECT COUNT(*) FROM correction_detail d WHERE d.batch_id = b.batch_id) AS done
  FROM correction_batch b WHERE batch_id = @b;

-- 락이 승격했는가. OBJECT + X 가 보이면 즉시 멈추고 배치를 줄인다
SELECT resource_type, request_mode, COUNT(*)
  FROM sys.dm_tran_locks WHERE resource_database_id = DB_ID()
 GROUP BY resource_type, request_mode;
```

---

## 5. 중간에 죽었을 때

**같은 `@batch_id` 를 넘겨 다시 실행합니다.** 진행 지점부터 이어서 돕니다.
실측에서 5번째 배치에서 죽인 뒤 이어 돌려 두 번 처리된 계정 0개, 빠진 계정 0개였습니다.

```sql
DECLARE @b INT = <죽은 batch_id>;
EXEC usp_ReclaimCurrency @reason = N'이어 돌리기', @mode = 'DEBT',
                         @chunk = 4000, @batch_id = @b OUTPUT;
```

**절대 하지 않을 것**: 처음부터 다시 돌리기. 앞 배치가 이미 커밋돼 있어 이중 회수가 됩니다.

## 6. 회수가 잘못됐을 때

```sql
-- 표시 지점까지만 복원한다
RESTORE DATABASE [<복원본>] FROM DISK='<전체백업>'
   WITH MOVE ..., NORECOVERY;
RESTORE LOG [<복원본>] FROM DISK='<로그백업>'
   WITH STOPATMARK = 'before_reclaim', RECOVERY;
```

복원본에서 잔액 합계를 보정 전 값과 대조해 맞는지 먼저 확인합니다.

> **운영 데이터베이스를 그대로 되돌리는 것은 별개의 판단입니다.** 표시 지점 이후의
> 정상 트랜잭션까지 함께 사라집니다. 회수만 취소하고 싶다면 복원본에서 원래 잔액을
> 읽어 되돌리는 보정을 다시 도는 쪽이 보통 낫습니다.

---

## 7. 작업 후

- [ ] 배치 상태가 `DONE` 인가 (`MISMATCH` 면 검산이 틀린 것이다)
- [ ] 회수 합계가 대상 합계와 같은가
- [ ] 감사 로그 행 수 = 대상 계정 수인가
- [ ] `적용액 + 빚 = 대상액` 이 모든 행에서 성립하는가
- [ ] 제약을 뺐다면 되돌렸는가
- [ ] 빚이 남은 계정 수를 기록했는가 (상계가 끝날 때까지 추적한다)
- [ ] 회수 내역을 공지 가능한 형태로 정리했는가 (계정 수, 총액, 근거)

---

## 8. 이 절차가 답하지 못하는 것

- **승인 이력을 누가 고칠 수 있는지 안 봤습니다.** 요청과 승인을 표에 남기지만 그 표
  자체의 권한은 다루지 않았습니다. 승인 기록을 지울 수 있으면 절차가 의미를 잃습니다.
- **상계 로직은 이 문서 밖입니다.** 빚을 어떤 획득 경로에서 갚을지는 애플리케이션
  결정이고, 경로가 하나라도 빠지면 빚이 영원히 남습니다.
- **소요 시간을 모릅니다.** 이 랩은 에뮬레이션이라 시간을 재지 않았습니다. 실제
  환경에서 한 번 재서 이 문서에 적어 두는 편이 좋습니다.
