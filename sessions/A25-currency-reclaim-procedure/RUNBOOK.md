# 운영 절차서: 재화 회수 실행

대상: 확정된 회수 대상 목록을 실제로 되돌리는 작업
근거: 같은 디렉토리의 [README.md](README.md) 실측.

앞 단계(대상을 뽑는 절차)는 [A24 운영 절차서](../A24-currency-anomaly-detection/RUNBOOK.md),
배치 크기의 근거는 [A04 운영 절차서](../A04-mssql-lock-escalation/RUNBOOK.md)입니다.

## 0. 한 줄 요약

**표시를 남기고, 5,000행 미만 배치로 끊고, 계정마다 전후 값을 적고, 끝나면 검산한다.**
이미 쓴 재화는 빚 컬럼으로 남긴다. 제약을 빼는 것은 마지막 수단이다.

---

## 1. 시작 전 확인

| # | 확인 | 통과 기준 |
|---|---|---|
| 1 | 회수 대상 표에 계정과 **금액**이 다 있는가 | 계정만으로는 시작할 수 없다 |
| 2 | 대상 표를 표본 검증했는가 | 상위 몇 계정의 원장을 손으로 확인 |
| 3 | 복구 모델이 FULL 인가 | `SELECT recovery_model_desc FROM sys.databases` |
| 4 | 로그 백업 체인이 이어져 있는가 | 최근 로그 백업 시각 확인 |
| 5 | 전체 백업을 방금 떴는가 | 되돌릴 기준점 |
| 6 | 잔액 제약이 무엇인가 | `CHECK (balance >= 0)` 이 있으면 2번 항목의 설계 결정 필요 |
| 7 | 승인을 받았는가 | 회수는 이용자 자산을 줄이는 작업이다 |

---

## 2. 잔액이 모자란 계정의 처리 (설계 결정)

| 설계 | 언제 쓰나 | 대가 |
|---|---|---|
| **빚 컬럼 (권장)** | 기본 | 획득 경로마다 상계 로직이 들어가야 한다 |
| 음수 잔액 | 빚 컬럼을 넣을 수 없을 때 | 제약을 빼야 하고, 음수를 읽는 코드를 전부 확인해야 한다 |

빚 컬럼을 고르면 `적용액 + 빚 = 대상액` 이 항상 성립해야 하고, 그것이 검산식이 됩니다.

> 음수 잔액을 고른다면 **언제 제약을 되돌릴지 함께 정합니다.** 제약이 빠져 있는 동안
> 다른 버그가 음수를 만들어도 아무도 모릅니다.

---

## 2-2. 회수 대상이 다른 서버에서 왔다면

조사는 로그 DB, 보정은 운영 DB에서 도는 것이 보통입니다. 목록을 옮겼다면 **회수를
시작하기 전에 원본과 대조합니다.**

```sql
-- 조사 DB 와 운영 DB 양쪽에서 같은 값을 뽑아 셋 다 비교한다
SELECT COUNT(*)                                                    AS rows,
       SUM(extra_amount)                                           AS total,
       CHECKSUM_AGG(BINARY_CHECKSUM(account_id, extra_rows, extra_amount)) AS chk
  FROM reclaim_target;
```

세 값이 모두 같아야 넘어갑니다. **건수만 보면 안 됩니다.** 값이 바뀐 채 건수만 맞는
경우를 체크섬이 잡습니다.

> **이 대조가 유일한 방어선인 사고가 있습니다.** 파일이 잘려 절반만 넘어오면 `bcp` 는
> 오류를 내지 않고, 회수 프로시저의 검산도 통과합니다. 받은 만큼 정확히 회수했으니
> 프로시저 입장에서는 성공입니다. 절반이 사라진 것은 원본과 대조할 때만 드러납니다.

## 2-3. 승인

**회수는 승인을 받고 돕니다.** 이용자 자산을 줄이는 작업이라 한 사람이 결정하지 않습니다.

```sql
-- 요청자(maker)
DECLARE @r INT;
EXEC usp_RequestReclaim @reason = N'<사고 번호와 조사 근거>', @request_id = @r OUTPUT;

-- 승인자(checker). 요청자와 같은 사람이면 프로시저가 거부한다.
EXEC usp_ApproveReclaim @request_id = <요청 번호>;

-- 실행. 승인 시점 대상 지문과 지금 지문을 대조한 뒤에만 돈다.
EXEC usp_ReclaimCurrencyGated @request_id = <요청 번호>, @mode = 'DEBT', @chunk = 4000;
```

지켜야 할 것 넷입니다.

| # | 무엇 | 안 하면 |
|---|---|---|
| 1 | 요청과 승인 권한을 로그인으로 나눈다 | 한 사람이 요청하고 승인한다 |
| 2 | 자기 승인을 프로시저 로직으로도 막는다 | 한 사람이 둘 다 맡는 조직에서 1번이 무력해진다 |
| 3 | 원래 프로시저에 `DENY EXECUTE` 를 건다 | 게이트를 우회해 직접 부르면 그만이다 |
| 4 | **승인 시점의 대상 지문을 저장하고 실행 때 대조한다** | 승인 뒤 목록을 바꿔치기할 수 있다 |

4번이 제일 놓치기 쉽습니다. 승인은 "이 목록을 회수해도 된다"는 뜻이지 "언제든 회수해도
된다"는 뜻이 아닙니다. 실측에서 승인 뒤 대상 표에 행을 하나 넣자 승인이 그대로 유효한
채로 다른 목록이 실행되려 했고, 지문 대조가 그것을 막았습니다.

## 3. 실행

```sql
-- 되돌릴 지점에 이름을 붙인다. 이 트랜잭션은 아무것도 안 바꿔도 된다.
BEGIN TRAN before_reclaim WITH MARK '<사유> 보정 직전';
    INSERT INTO correction_batch (reason, status) VALUES (N'[표시] 보정 직전', 'MARK');
COMMIT TRAN before_reclaim;

-- 회수
DECLARE @b INT;
EXEC usp_ReclaimCurrency
     @reason   = N'<사유. 사고 번호와 조사 근거를 적는다>',
     @mode     = 'DEBT',      -- 또는 NEGATIVE
     @chunk    = 4000,
     @batch_id = @b OUTPUT;
```

프로시저가 지키는 것 넷입니다. 직접 쿼리로 돌리면 이것들이 빠집니다.

1. 배치마다 커밋해 락을 놓는다 (`@chunk >= 5000` 은 아예 거부)
2. 진행 지점을 배치와 **같은 트랜잭션**에서 옮긴다 (이중 회수 방지)
3. 계정마다 전후 값과 적용액·빚을 남긴다
4. 끝나면 `회수 합계 = 대상 합계` 를 검산하고 안 맞으면 던진다

---

## 4. 작업 중 감시

```sql
-- 진행률
SELECT batch_id, status, last_done,
       (SELECT COUNT(*) FROM correction_detail d WHERE d.batch_id = b.batch_id) AS done
  FROM correction_batch b WHERE batch_id = @b;

-- 락이 승격했는가. OBJECT + X 가 보이면 즉시 멈추고 배치를 줄인다
SELECT resource_type, request_mode, COUNT(*)
  FROM sys.dm_tran_locks WHERE resource_database_id = DB_ID()
 GROUP BY resource_type, request_mode;
```

---

## 5. 중간에 죽었을 때

**같은 `@batch_id` 를 넘겨 다시 실행합니다.** 진행 지점부터 이어서 돕니다.
실측에서 5번째 배치에서 죽인 뒤 이어 돌려 두 번 처리된 계정 0개, 빠진 계정 0개였습니다.

```sql
DECLARE @b INT = <죽은 batch_id>;
EXEC usp_ReclaimCurrency @reason = N'이어 돌리기', @mode = 'DEBT',
                         @chunk = 4000, @batch_id = @b OUTPUT;
```

**절대 하지 않을 것**: 처음부터 다시 돌리기. 앞 배치가 이미 커밋돼 있어 이중 회수가 됩니다.

## 6. 회수가 잘못됐을 때

```sql
-- 표시 지점까지만 복원한다
RESTORE DATABASE [<복원본>] FROM DISK='<전체백업>'
   WITH MOVE ..., NORECOVERY;
RESTORE LOG [<복원본>] FROM DISK='<로그백업>'
   WITH STOPATMARK = 'before_reclaim', RECOVERY;
```

복원본에서 잔액 합계를 보정 전 값과 대조해 맞는지 먼저 확인합니다.

> **운영 데이터베이스를 그대로 되돌리지 않습니다.** 표시 지점 이후의 정상 트랜잭션까지
> 함께 사라집니다. 실측에서 보정 뒤 정상 활동이 3억이었고, 통째로 되돌리면 그것이
> 전부 없어집니다.

복원본에서 원래 값을 읽어 **되돌리는 보정을 한 번 더 돕니다.**

```sql
-- 잘못 회수한 계정만 골라 되돌린다. 정상 회수분과 그 뒤 활동은 그대로 둔다.
UPDATE a
   SET a.balance = a.balance + d.applied_amount + d.debt_amount,
       a.debt    = a.debt    - d.debt_amount
  FROM account_currency a
  JOIN correction_detail d ON d.account_id = a.account_id
 WHERE d.account_id IN (<잘못 포함된 계정>);
```

되돌리기도 보정이므로 같은 규칙을 지킵니다. 배치를 쪼개고, 감사 로그를 남기고, 끝나면
검산합니다. **검산식을 세울 때 "무엇을 되돌리고 무엇을 두는가"를 먼저 정합니다.**
정상 회수분까지 되돌리는 식으로 검산하면 맞는 절차가 틀린 것으로 나옵니다.

---

## 7. 작업 후

- [ ] 배치 상태가 `DONE` 인가 (`MISMATCH` 면 검산이 틀린 것이다)
- [ ] 회수 합계가 대상 합계와 같은가
- [ ] 감사 로그 행 수 = 대상 계정 수인가
- [ ] `적용액 + 빚 = 대상액` 이 모든 행에서 성립하는가
- [ ] 제약을 뺐다면 되돌렸는가
- [ ] 빚이 남은 계정 수를 기록했는가 (상계가 끝날 때까지 추적한다)
- [ ] 회수 내역을 공지 가능한 형태로 정리했는가 (계정 수, 총액, 근거)

---

## 8. 이 절차가 답하지 못하는 것

- **승인 이력을 누가 고칠 수 있는지 안 봤습니다.** 요청과 승인을 표에 남기지만 그 표
  자체의 권한은 다루지 않았습니다. 승인 기록을 지울 수 있으면 절차가 의미를 잃습니다.
- **상계 로직은 이 문서 밖입니다.** 빚을 어떤 획득 경로에서 갚을지는 애플리케이션
  결정이고, 경로가 하나라도 빠지면 빚이 영원히 남습니다.
- **소요 시간을 모릅니다.** 이 랩은 에뮬레이션이라 시간을 재지 않았습니다. 실제
  환경에서 한 번 재서 이 문서에 적어 두는 편이 좋습니다.

## 상계 규칙과 제약

회수 뒤 이용자가 재화를 얻으면 빚이 먼저 갚혀야 합니다. **그 규칙은 DB 에 두고 집합으로
짭니다.** 실측에서 네 가지를 견줬고 둘이 틀렸습니다(계정 5,000개 기준).

| 규칙의 위치 | 어긋난 계정 |
|---|---|
| 앱 경로마다(넷 중 하나가 빠뜨림) | 1,250개 |
| 트리거, 한 행 기준 | **4,996개** |
| 트리거, 집합 기준 | 0개 |
| 프로시저 강제(직접 UPDATE 를 DENY) | 0개 |

```sql
-- 이렇게 짜면 안 됩니다. inserted 가 여러 행이면 마지막 하나만 남습니다.
DECLARE @acc INT, @gain BIGINT;
SELECT @acc = i.account_id, @gain = i.balance - d.balance FROM inserted i JOIN deleted d ...;

-- 변수에 담지 않고 조인합니다. 행이 몇 개든 같습니다.
UPDATE t
   SET debt    = t.debt    - CASE WHEN t.debt >= g.gain THEN g.gain ELSE t.debt END,
       balance = t.balance - CASE WHEN t.debt >= g.gain THEN g.gain ELSE t.debt END
  FROM account_currency t
  JOIN (SELECT i.account_id, i.balance - d.balance AS gain
          FROM inserted i JOIN deleted d ON d.account_id = i.account_id
         WHERE i.balance > d.balance) g ON g.account_id = t.account_id
 WHERE t.debt > 0;
```

**한 행씩 지급하는 동안에는 멀쩡하다가 지급을 묶는 순간 틀립니다.** 오류도 경고도
없으므로 배포 뒤 한참 지나 총량 대사에서야 드러납니다.

### `CHECK (balance >= 0)` 를 빼지 않습니다

음수 잔액을 허용하면 회수는 편해지지만 셋이 깨집니다(계정 10만 개 기준 실측).

| | NEGATIVE | DEBT |
|---|---|---|
| 유통 중인 재화 총량 | 2억 6,000만 | 2억 8,000만 |
| 조건을 빠뜨린 대량 차감 | 통과 | **`Msg 547` 차단** |
| 그 뒤 미회수 잔량 | 97억 | 1,999만 |

**제약은 비용이 아니라 마지막 방어선입니다.** 회수 때문에 뺐는데 그 제약이 원래 막던
다른 버그도 함께 풀립니다. 그리고 **한 번 음수가 들어간 표에는 다시 붙일 수 없습니다.**

## 상계 규칙은 프로시저가 제일 싸다

같은 2만 행 지급을 네 방식으로 잰 값입니다.

| 방식 | 어긋난 계정 | 로그 | 들고 있는 락 |
|---|---|---|---|
| 규칙 없음(기준선) | 20,000 | 2.1MB | 2 (테이블 락) |
| `AFTER` 트리거 | 0 | 4.5MB | 2 (테이블 락) |
| `INSTEAD OF` 트리거 | 0 | 2.5MB | **20,121 (행 락 유지)** |
| 프로시저 한 문장 | 0 | 2.3MB | 2 (테이블 락) |

**로그가 제일 싼 `INSTEAD OF` 가 락에서 제일 비쌉니다.** 승격이 안 일어나 행 락 2만
개를 끝까지 들고 갑니다. 그리고 갱신을 가로채므로 **그 표의 모든 갱신을 떠안습니다.**

세 번째 대가가 여기 있습니다. 지급만 다루는 `INSTEAD OF` 를 걸고 다른 갱신을 던지면
**오류 없이 사라집니다.**

| 던진 갱신 | `INSTEAD OF` | `AFTER` |
|---|---|---|
| 지급 (`balance` 증가) | 반영됨 | 반영됨 |
| 등급 변경 (`grade`) | **사라짐** | 반영됨 |
| 운영툴 메모 (`note`) | **사라짐** | 반영됨 |
| 빚 직접 조정 (`debt`) | **사라짐** | 반영됨 |

트리거가 다루는 조건에 안 걸리면 그 갱신은 통째로 버려지고, 호출한 쪽은 성공했다고
알고 넘어갑니다. **표에 컬럼이 늘거나 갱신 경로가 추가될 때마다 트리거를 같이 고쳐야
하고, 안 고치면 그 경로가 조용히 죽습니다.**

| 상황 | 고를 것 |
|---|---|
| 지급 경로를 통제할 수 있다 | 프로시저. 제일 싸고 제일 단순하다 |
| 경로를 통제 못 한다 | `AFTER` 트리거. 대가는 로그 2배 |
| — | `INSTEAD OF` 는 권하지 않는다 |

중간 상태는 존재하지만 `READ COMMITTED` 로는 안 보입니다(`LCK_M_S` 로 대기).
**`NOLOCK` 으로 읽을 때만 보입니다.**

## 승인은 받게 하는 것과 우회 못 하게 하는 것이 다르다

| 구멍 | 막는 법 | 실측 |
|---|---|---|
| 이력을 고친다 | 표에 쓰기 권한을 아무에게도 안 준다 | `Msg 229` |
| 한 사람이 두 번 눌러 정족수를 채운다 | `UNIQUE (req_id, approved_by)` | `Msg 2627` |
| 오래된 승인이 계속 통한다 | **승인 시점과 실행 시점 둘 다** 유효 기간을 본다 | `Msg 50062` / `50065` |
| 되돌리기가 절차를 안 탄다 | 되돌리기를 **같은 표에 같은 모양으로** 올린다 | `Msg 50064` |

둘째와 셋째가 실무에서 빠지는 자리입니다. 승인자 수를 세는 로직은 있는데 같은 사람이
두 번 누르는 것은 안 막고, 유효 기간은 승인할 때만 보고 실행할 때는 안 봅니다.
**둘 다 로직이 아니라 제약과 재확인으로 막습니다.**

## 이관은 스냅샷을 뜨고 옮긴다

옮기는 동안 원본이 자라면 사본은 어느 시점의 것도 아니게 됩니다.

| | 행 수 | 합계 | 지문 |
|---|---|---|---|
| 그냥 옮긴다 | 5,300 | 31,800,000 | **어긋남** |
| 스냅샷을 뜨고 옮긴다 | 5,000 | 30,000,000 | 일치 |

**행 수와 합계만 보면 그럴듯해 보입니다.** 지문을 대조해야 드러나고, 그 지문은
**스냅샷 기준**으로 만들어야 합니다. 대조할 기준이 움직이면 대조가 성립하지 않습니다.

| 방법 | 안 남는 것 | 남는 것 |
|---|---|---|
| 링크드 서버 | 파일 | 두 서버 사이의 **경로** |
| bcp | 경로 | **파일** |

회수 대상 목록은 이용자 식별자와 금액이 담긴 파일입니다. **이관이 끝난 뒤 치우는
절차**를 안 만들면 둘 중 하나가 그대로 남습니다.

## 음수를 허용하더라도 앱은 뷰로 지킨다

```sql
CREATE OR ALTER VIEW v_account_currency AS
SELECT account_id,
       CASE WHEN balance < 0 THEN 0 ELSE balance END AS balance,
       CASE WHEN balance < 0 THEN -balance ELSE 0 END AS debt
  FROM account_currency;

DENY  SELECT ON account_currency    TO app_role;   -- 기저 표는 막는다
GRANT SELECT ON v_account_currency  TO app_role;   -- 뷰만 연다
```

뷰를 통과하면 최소 잔액·유통 총량·미회수 잔량이 DEBT 설계와 같아집니다.
**다만 뷰는 표시를 고치지 무결성을 지키지 않습니다.** 조건을 빠뜨린 차감이 그대로
통과하고, 그 음수는 회수로 생긴 음수와 구분되지 않습니다.

그리고 뷰로 `balance`/`debt` 를 나눠 내주는 순간 DEBT 설계와 하는 일이 같아집니다.
**같은 결과를 제약 없이 얻는 셈이라 애초에 컬럼을 나누는 쪽이 낫습니다.**

## 이관 방법을 고르는 표

| | bcp | 링크드 서버 | 복제 |
|---|---|---|---|
| 세우는 단계 | 0 | 3 | **15** |
| 필요한 인스턴스 | 1 | 2 | **3**(배포자 포함) |
| SQL Server 에이전트 | 불필요 | 불필요 | **필요** |
| 끝난 뒤 남는 것 | 파일 | 경로 | 에이전트 작업 2개 + 배포 DB 22MB |
| 그 표에 묶이는 것 | 없음 | 없음 | **`DROP TABLE` 이 `Msg 3724`** |

셋 다 지문은 맞습니다. **데이터가 도착하는 것 자체는 다르지 않습니다.**

**일회성 회수 목록에 복제를 쓰지 않습니다.** 그 표가 영구히 발행 대상이 되어 치우려면
발행부터 내려야 합니다. 안 맞는 이유는 번거로워서가 아니라 **도구의 목적이 다르기**
때문입니다. 복제는 표를 계속 따라다니게 만드는 것이고 이관은 한 번 옮기고 끝내는 것입니다.

### 복제를 세울 일이 생기면 단계마다 되읽어 확인합니다

15단계 중 **둘이 조용히 죽었습니다.** 둘 다 그 자리에서는 아무 표시가 없었고,
맨 끝에서 `The process could not connect to Subscriber` 한 줄로만 나타났습니다.

| 무엇이 | 어떻게 나타났나 |
|---|---|
| `EXEC` 매개변수에 식을 썼다 (`Msg 102`) | `-EncryptionLevel` 이 안 붙음 |
| 없는 매개변수(`@publisher_security_mode`)를 넘겼다 | SQL 인증이 안 걸려 `Cannot generate SSPI context` |

- 세팅 프로시저는 **되읽어 확인합니다.** 예: `distribution.dbo.MSdistribution_agents`
  의 `subscriber_security_mode` 가 `0` 인지.
- 배포 에이전트가 실패하면 **표를 둘 봅니다.** `MSdistribution_history.comments` 는
  요약이라 원인이 잘려 있고, 원문은 `distribution.dbo.MSrepl_errors.error_text` 에
  있습니다.
- Linux 인스턴스끼리는 **통합 인증이 안 됩니다.** Kerberos 가 없어 SSPI 컨텍스트를
  못 만듭니다. `@subscriber_security_mode = 0` 으로 SQL 인증을 씁니다.

> 어느 방법을 쓰든 **스냅샷을 뜨고 그것을 옮깁니다.** 옮기는 동안 원본이 자라면
> 행 수와 합계는 그럴듯한데 지문이 어긋납니다.
