실행한 명령과 출력을 그대로 붙입니다. 도커 컴포즈가 찍는 컨테이너 생성 줄은 분량만 차지해서
`grep -v`로 걷어낸 곳이 있고, 그 경우 명령줄에 그대로 남겼습니다.

## 1. 환경 기동

```console
$ cd sessions/A08-buffer-pool-sizing
$ BP_SIZE=2G docker compose build load

$ BP_SIZE=2G docker compose up -d --wait mysql

 Container a08-mysql  Starting
 Container a08-mysql  Started
 Container a08-mysql  Waiting
 Container a08-mysql  Healthy
```

설정이 의도대로 잡혔는지 먼저 봅니다. 특히 버퍼 풀 인스턴스가 1인지, 기동 시 풀 로드가 꺼져
있는지가 중요합니다. 인스턴스가 8이면 스윕 값이 조용히 반올림되고, 풀 로드가 켜져 있으면
직전 조건의 워킹셋을 물려받습니다.

```console
$ BP_SIZE=2G docker compose run --rm load python -c "..."
테이블 (('orders',),)
('8.4.3', 2147483648, 134217728, 1, 'O_DIRECT', 0)
```

순서대로 버전, `innodb_buffer_pool_size`, `innodb_buffer_pool_chunk_size`,
`innodb_buffer_pool_instances`, `innodb_flush_method`,
`innodb_buffer_pool_load_at_startup`입니다.

`id 범위 1~7,412,245`에 `행 수 7,000,000`이므로 41만 개의 id가 비어 있습니다. 벌크 적재가
AUTO_INCREMENT를 블록 단위로 잡아 쓰면서 생긴 구멍입니다. 부하 스크립트는 `MIN(id)`와
`MAX(id)`를 직접 읽어 그 범위에서 조회하므로, 구멍에 걸린 조회는 행을 찾지 못하고 돌아옵니다.
B-Tree를 타고 리프 페이지를 읽는 것은 같아서 버퍼 풀 관점의 측정에는 영향이 없습니다.

중에 실행 셸이 끊겨서, `SIZES` 환경변수로 남은 크기만 지정해 이어 돌렸기 때문입니다. 스크립트
자체는 여섯 크기를 한 번에 도는 것이 기본이고, 조건마다 컨테이너를 새로 띄우므로 나눠 돌린
결과와 한 번에 돈 결과가 같습니다. 출력을 손대지 않는다는 규약대로 그 흔적을 그대로 두었습니다.

```console
$ SIZES="512M 1G" bash scripts/run-sweep.sh
$ SIZES="1536M 2G" bash scripts/run-sweep.sh
```

`버퍼 풀 128MB (chunk 128M x instances 1)` 줄이 매번 찍히는 이유는, 지정한 값이 그대로
잡혔는지를 조건마다 확인하기 위해서입니다. 인스턴스가 기본값인 8이었다면 1536M은 2G로
올라갔을 겁니다.

`측정 창 블록 I/O` 줄은 `docker stats`의 BlockIO를 워밍업이 끝나는 시점과 측정이 끝나는

60초 동안 InnoDB는 2,882.2MB를 파일에서 읽었다고 셌습니다.

첫 실행에서는 블록 I/O를 컨테이너 생애 전체로 재서 워밍업과 기동 구간이 섞였습니다.
측정 창 경계에서 찍도록 스크립트를 고치고 다시 돌린 것이 위 출력입니다.
