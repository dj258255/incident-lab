## 2) 이미 큰 테이블에 넣으면
==================================================================
  빈 테이블과 2000000행이 든 테이블에 같은 20000행을 넣습니다.
  빈 테이블                              8.92초  쿼리   20090개  넣은 행 20000
  2000000행 미리 적재 중...
  적재 완료: 2000000행
  테이블 크기 = 0MB
  2000000행이 든 테이블                8.19초  쿼리   20090개  넣은 행 20000

  두 값의 비율이 1에 가까우면 삽입 비용이 테이블 크기에 둔감한 것입니다.
  클러스터드 인덱스가 id 순으로 이어 붙는 조건이라 그럴 수 있습니다.
  비율이 크면 B-Tree 가 깊어진 몫입니다.

==================================================================
## 3) created_at 이 겹치는 데이터에서 커서 페이지네이션
==================================================================
  6절은 PostgreSQL 에서만 밟았습니다. MySQL 쪽 데이터를 같은 모양으로 만듭니다.
  총 2000행, 서로 다른 시각 10개 (한 시각에 200행)

  created_at 만   페이지  9회에   900행 읽음 (전체 2000행)  **1100행을 건너뛰었습니다**
  created_at 과 id 페이지 20회에  2000행 읽음 (전체 2000행)  전부 읽었습니다

  created_at 만 커서로 쓰면 같은 시각의 나머지 행을 건너뜁니다.
  100행씩 끊는데 한 시각에 200행이 있으므로, 페이지 경계가 그 안에 떨어지면
  다음 질의의 > 조건이 남은 행을 통째로 넘깁니다. 타이브레이커로 id 를 더하면
  같은 시각 안에서도 순서가 정해져 경계가 안전해집니다.
