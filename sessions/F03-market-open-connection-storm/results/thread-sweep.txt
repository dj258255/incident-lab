# Tomcat max-threads를 바꿔 가며 중앙값의 계층별 몫을 가른 결과  [2026-07-29]
#
# 물음: 버그 경로의 응답 중앙값 가운데 커넥션 풀 대기(상한 2초)의 몫은 얼마이고,
#       스레드 계층(작업 스레드를 기다리는 시간)의 몫은 얼마인가.
#
# 재는 법:
#   k6 med           클라이언트가 잰 응답 시간의 중앙값. 소켓을 열고 응답을 다 받을 때까지.
#   inapp_200 p50    서블릿 필터 진입부터 응답 완료까지. 이미 Tomcat 작업 스레드를 잡은 뒤다.
#   pool p50         그 안에서 HikariCP 커넥션 획득에만 쓴 시간.
#   query p50        커넥션을 잡은 뒤 쿼리에 쓴 시간(pg_sleep 0.05 모형).
#   따라서  스레드 계층의 몫 = k6 med - inapp_200 p50  이다.
#
# 조건: /quote/buggy, 초당 400건 스파이크(5s 램프 + 20s 유지 + 5s 감소),
#       preAllocatedVUs = maxVUs = 5,000, pool=10, connection-timeout=2000ms, accept-count=1000.
#       네 조건 모두 dropped_iterations 0, http_reqs 약 9,999건.
#
# max-threads  http_reqs  k6 med   k6 p95   inapp_200 p50   pool p50   query p50   500 응답  hikari_waiting 최대  tomcat_queue 최대
#         10       9999  13.54s   25.74s         51.28ms     0.00ms     50.77ms          0                   0               4947
#         50       9999  13.38s   25.23s         59.66ms     0.04ms     50.84ms         26                  41               4864
#        200       9999  11.42s   20.96s       1014.66ms   962.97ms     50.61ms        761                 191               4335
#       1000       9999  11.17s   18.86s       1701.09ms   1589.14ms     52.45ms       3945                 901                745
#
# 읽는 법
# 1. 획득 대기 큐(hikari_waiting)의 최대치가 max-threads에서 풀 크기 10을 뺀 값과 거의 같다.
#    0 / 41 / 191 / 901. 커넥션을 기다릴 수 있는 요청 수는 작업 스레드 수가 정한다.
# 2. max-threads 200(Spring Boot 기본값)에서 중앙값 11.42초 가운데 앱 안에서 쓴 시간은 1.01초다.
#    그 1.01초의 대부분인 0.96초가 풀 획득 대기이고 쿼리가 0.05초다.
#    나머지 약 10.4초는 서블릿 필터에 닿기도 전, 즉 작업 스레드를 기다린 시간이다.
#    중앙값의 약 9%가 풀 계층, 약 91%가 스레드 계층이다.
# 3. max-threads를 풀 크기와 같은 10으로 낮추면 풀 대기가 사실상 0이 되고(중앙값 0.00ms)
#    커넥션 획득 타임아웃 500도 0건이 된다. 기다림이 전부 스레드 계층으로 옮겨 갈 뿐이다.
# 4. 반대로 1000으로 올리면 풀 대기 중앙값이 1.59초까지 오르고 2초 상한을 넘긴 3,945건이 500이 된다.
#    스레드를 늘리는 것은 대기를 없애는 것이 아니라 대기를 풀 계층으로 옮기는 것이다.
# 5. 네 조건 모두 처리량은 초당 180~224건에 머문다. 처리량의 상한을 정하는 것은 풀이고,
#    지연의 대부분을 만드는 것은 기본 설정에서 스레드 계층이다. 둘은 다른 질문이다.
#
