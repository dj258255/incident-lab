# 버그 경로(/quote/buggy) 부하 중 앱 로그 발췌.
# docker logs lab-f03-app | grep "Connection is not available"
# 풀 10개가 전부 active, idle 0, 획득 대기 큐에 약 189건이 쌓여 있다. 전형적인 커넥션 풀 고갈이다.
# 2초(connection-timeout) 안에 커넥션을 못 받은 요청은 아래 예외로 500이 된다.

java.sql.SQLTransientConnectionException: quote-pool - Connection is not available, request timed out after 2000ms (total=10, active=10, idle=0, waiting=189)
	at com.zaxxer.hikari.pool.HikariPool.createTimeoutException(HikariPool.java)
	at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java)
	at com.zaxxer.hikari.HikariDataSource.getConnection(HikariDataSource.java)
	... (JdbcTemplate -> QuoteService.lookup -> QuoteController.buggy)

# 이 실행에서 위 예외로 처리된 500이 27건. 부하 차단(/quote/fixed)에서는 0건이었다.

# ------ 아래는 나중에 붙인 주석. 위 원문과 수치는 손대지 않았다. ------
# 위 "27건"이 무엇을 센 값인지 갈라내지 못했다. 같은 세션의 reproduce.md는 같은 실행에 대해
#   $ docker logs lab-f03-app | grep -c "Connection is not available"
#   541
# 을 기록해 두었다. 앱 로그 쪽 집계가 이 저장소 안에서 541과 27 두 값으로 갈린다.
#
# 확정된 것은 k6 쪽 집계다. results/buggy-k6.txt의 응답 상태 분포가
#   200 = 6,057건 / 500 = 541건 / 503 = 0건, 합 6,598 = http_reqs
# 로 정확히 맞고 http_req_failed도 "8.19% 541 out of 6598"이다. 따라서 541은 버그 경로가 돌려준
# HTTP 500의 개수이며 503이나 응답을 받지 못한 요청은 섞여 있지 않다. 그 541건 가운데 몇 건이
# 위 예외였는지는 세지 못했다.
#
# 이 파일은 스택트레이스를 줄여 놓은 발췌라 docker logs 원문 출력 그대로가 아니다. 위 waiting=189도
# reproduce.md에 한동안 188로 잘못 옮겨져 있었다. 27이 다른 시도의 기록이거나 발췌가 잘린 결과일
# 가능성이 있으나, 남은 파일로는 가려내지 못했다.
