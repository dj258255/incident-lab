# R04 CDC 컨슈머가 죽으면 프로덕션 DB의 디스크가 찬다

> 근거 등급: `E2`
> 출처: [PostgreSQL 17, Replication Slots](https://www.postgresql.org/docs/17/warm-standby.html#STREAMING-REPLICATION-SLOTS) · [pg_replication_slots (wal_status, safe_wal_size)](https://www.postgresql.org/docs/17/view-pg-replication-slots.html) · [max_slot_wal_keep_size](https://www.postgresql.org/docs/17/runtime-config-replication.html)

## 1. 유명한 이유

CDC(Change Data Capture)는 이제 흔한 구성입니다. Debezium이든 자체 구현이든, PostgreSQL의 논리 복제 슬롯을 열어 변경분을 읽어 갑니다.

문제는 **컨슈머가 죽어도 슬롯은 남는다**는 점입니다. 슬롯은 "내가 아직 여기까지밖에 못 읽었다"는 위치(`restart_lsn`)를 서버에 등록해 두는 장치이고, 서버는 그 위치 이후의 WAL을 지우지 못합니다. 컨슈머가 살아 있을 때는 위치가 따라 움직이니 문제가 없습니다. 죽으면 위치가 그 자리에 멈추고, 쓰기는 계속되므로 WAL이 쌓이기만 합니다.

이 구조가 위험한 이유는 **장애의 방향이 반대**이기 때문입니다. 보통은 프로덕션이 아프면 부가 파이프라인이 영향을 받습니다. 여기서는 부가 파이프라인이 죽어서 프로덕션 DB의 디스크가 찹니다. 디스크가 차면 PostgreSQL은 쓰기를 거부하고, 그때는 이미 늦습니다.

이 세션은 그 과정을 초 단위로 재고, PostgreSQL 13부터 있는 안전장치가 무엇을 지키고 무엇을 버리는지를 실측합니다.

## 2. 재현

### 환경

| 항목 | 값 |
|---|---|
| 호스트 | macOS 26.3.1, Apple M2 Pro, 12코어(논리), 32GB |
| DB | PostgreSQL 17.5 (Debian 빌드), 컨테이너 `cpus: 4`, `mem_limit: 2g` |
| 설정 | `wal_level=logical`, `max_wal_size=256MB`, `min_wal_size=64MB`, `checkpoint_timeout=30s` |
| 쓰기 | 컨테이너 안에서 psql 루프, 0.2초마다 200행(행당 약 1KB) |
| 관측 | 1초 간격으로 `pg_ls_waldir()` 합계와 슬롯 지연 기록 |

체크포인트를 30초마다 돌게 한 이유는 **WAL 재활용이 정상 동작하는 상태**를 먼저 만들기 위해서입니다. 그래야 "슬롯 때문에 못 지운다"를 슬롯 탓으로 분리할 수 있습니다.

### 타임라인

```
0~30초    슬롯 없이 쓰기만
30초      논리 복제 슬롯 생성 + pg_recvlogical 시작
30~60초   컨슈머가 살아 있는 구간
60초      컨슈머 강제 종료 (CDC 파이프라인이 죽은 상황)
60~180초  쓰기는 계속된다
180초     슬롯 삭제 + CHECKPOINT
```

## 3. 결과: 슬롯이 붙잡은 WAL

![WAL과 슬롯 지연](results/chart-wal.png)

| 경과 | pg_wal | 파일 | 슬롯 지연 | 컨슈머 |
|---|---|---|---|---|
| 30초 | 48MB | 3 | 0.2MB | 살아 있음 |
| 52초 | 64MB | 4 | 6.3MB | 살아 있음 |
| **63초** | 80MB | 5 | 7.0MB | **죽음** |
| 103초 | 80MB | 5 | **47.1MB** | 죽음 |
| 155초 | 112MB | 7 | **97.5MB** | 죽음 |
| 172초 | 128MB | 8 | **114.5MB** | 죽음 |
| 189초 | **96MB** | **6** | **0MB** | 슬롯 삭제 후 |

컨슈머가 살아 있는 30초 동안 슬롯 지연은 6.3MB에서 멈춰 있습니다. 읽어 가는 만큼 위치가 따라 움직이기 때문입니다.

컨슈머를 죽인 뒤로는 지연이 **120초 만에 7MB에서 126MB로** 단조 증가합니다. 초당 약 1MB씩입니다. 이 실험의 쓰기는 초당 2,000행 정도인데, 실제 서비스 규모라면 이 기울기가 그대로 커집니다.

`pg_wal`은 t=63부터 t=121까지 80MB에 묶여 있습니다. 체크포인트는 30초마다 돌았는데도 회수되지 않았습니다. 슬롯의 `restart_lsn` 이후를 지울 수 없기 때문입니다. 그 뒤로는 새 WAL이 계속 생겨 128MB까지 갔습니다.

**슬롯을 지우고 체크포인트를 돌리자 128MB가 96MB로 즉시 줄었습니다.** 붙잡고 있던 것이 슬롯이었다는 증거입니다.

## 4. 안전장치는 무엇을 버리는가

PostgreSQL 13부터 `max_slot_wal_keep_size`가 있습니다. 슬롯이 붙잡을 수 있는 WAL 양의 상한이고, 넘으면 슬롯을 무효화합니다. 64MB로 걸고 컨슈머 없는 슬롯을 만들어 봤습니다.

![슬롯 무효화](results/fig-lost.png)

```console
t=1s    WAL  80MB   슬롯지연   0MB   상태 reserved     여유  70MB
t=10s   WAL  96MB   슬롯지연  73MB   상태 unreserved   여유  -1MB
t=19s   WAL 128MB                    상태 lost         여유   0MB
```

상태가 세 단계로 바뀝니다.

- **`reserved`**: 정상. `safe_wal_size`가 남은 여유입니다.
- **`unreserved`**: 상한을 넘었습니다. 아직 WAL이 남아 있어 살아날 수 있지만 `safe_wal_size`가 **음수**입니다.
- **`lost`**: 무효화. 그 슬롯으로는 더 읽을 수 없습니다.

무효화된 슬롯에 컨슈머를 다시 붙이면 이렇게 됩니다.

```console
$ pg_recvlogical --slot=cdc_slot --start
ERROR:  can no longer get changes from replication slot "cdc_slot"
DETAIL:  This slot has been invalidated because it exceeded the maximum reserved size.
```

**디스크는 지켜지고 CDC는 버려집니다.** 컨슈머를 고쳐서 다시 붙여도 소용없고, 슬롯을 새로 만들어 전체 재동기화를 해야 합니다. 다운스트림이 데이터 웨어하우스라면 몇 시간짜리 재적재입니다.

이것이 이 설정의 정확한 거래 조건입니다. 상한을 걸면 프로덕션은 살고 파이프라인이 죽습니다. 안 걸면 파이프라인은 나중에 이어받을 수 있지만 그전에 프로덕션 디스크가 찹니다. **어느 쪽이 나은지는 도메인이 정하는 것이고, 정하지 않으면 기본값(무제한)이 후자를 고릅니다.**

## 5. 해소

| 항목 | 내용 |
|---|---|
| 슬롯 지연을 경보 대상으로 | `pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)`. 이 값이 단조 증가하면 컨슈머가 죽은 것이다 |
| `active` 플래그를 함께 본다 | 지연이 커도 `active=t`면 느린 것이고, `active=f`면 아무도 안 읽는 것이다 |
| 상한을 명시적으로 정한다 | `max_slot_wal_keep_size`. 기본값은 `-1`(무제한)이라 아무 보호가 없다 |
| `wal_status`를 감시한다 | `unreserved`가 마지막 경고다. `lost`가 되면 되돌릴 수 없다 |
| 안 쓰는 슬롯을 남기지 않는다 | 테스트로 만든 슬롯 하나가 몇 달 뒤 사고가 된다 |

## 6. 예상과 달랐던 점

### 컨슈머가 살아 있어도 지연이 0은 아니었습니다

컨슈머가 붙어 있는 구간에서도 슬롯 지연이 0.2MB에서 6.3MB까지 올랐습니다. `pg_recvlogical`이 출력을 `/dev/null`로 버리고 있었는데도 그렇습니다. 논리 디코딩은 WAL을 읽어 변경 집합으로 바꾸는 작업이라 그 자체로 시간이 걸리고, 쓰기 속도가 디코딩 속도를 넘으면 뒤처집니다. **컨슈머가 붙어 있다는 것과 따라잡고 있다는 것은 다릅니다.**

### 무효화가 예상보다 빨랐습니다

상한을 64MB로 걸었는데 19초 만에 `lost`가 됐습니다. 슬롯 지연이 73MB에 닿은 시점이 10초였고, 그다음 관측에서 이미 무효화였습니다. `unreserved`에 머무는 시간이 9초뿐이라 **경보를 받고 대응할 여유가 거의 없습니다.** 상한을 실무에서 쓰려면 쓰기량 대비 충분히 크게 잡고, `unreserved`가 아니라 `safe_wal_size`가 줄어드는 추세를 봐야 합니다.

### 디스크가 차는 것까지는 재현하지 못했습니다

원래 계획은 디스크를 채워 PostgreSQL이 쓰기를 거부하는 것까지 보이는 것이었습니다. Docker Desktop이 컨테이너별 블록 장치 쿼터를 지원하지 않아 볼륨 크기를 제한할 수 없었습니다. 대신 `max_slot_wal_keep_size`로 상한 도달을 재현했는데, **이건 디스크가 차는 것과 다른 사건**입니다. 전자는 PostgreSQL이 스스로 판단해 슬롯을 버리는 것이고 후자는 파일 시스템이 막는 것입니다. 후자는 재현하지 못했습니다.

## 못 한 것

- **디스크 포화까지 가지 못했습니다.** 위에 적은 이유입니다. Linux 호스트에 loop 장치로 작은 파일 시스템을 만들어 마운트하면 가능합니다.
- **Debezium 같은 실제 CDC 도구를 쓰지 않았습니다.** `pg_recvlogical`로 대신했고, 실제 도구는 하트비트나 자동 재연결 같은 완충 장치가 있습니다.
- **물리 복제 슬롯을 다루지 않았습니다.** 스탠바이가 죽었을 때도 같은 일이 벌어지는데, 이 세션은 논리 슬롯만 봤습니다.
- **`hot_standby_feedback`으로 인한 VACUUM 지연은 별개입니다.** 슬롯이 붙잡는 것은 WAL이고, 그 설정이 붙잡는 것은 죽은 튜플입니다. 둘 다 "다운스트림이 프로덕션을 붙잡는" 구조지만 대상이 다릅니다.
