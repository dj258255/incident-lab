```console
$ ./scripts/exp1-wait-stats.sh
# 실험 1. 대기 통계는 누적이라 지금을 못 본다

  계정 300000개. 보정 배치가 도는 동안 대기가 어떻게 쌓이는지 봅니다.

## 1-1. 사고 전에 누적된 대기

  인스턴스를 띄우고 데이터를 적재한 직후입니다. 아직 사고는 없습니다.

    LCK_M_IS  323068ms
    AZURE_IMDS_VERSIONS  62486ms
    PWAIT_EXTENSIBILITY_CLEANUP_TASK  60000ms

  적재 자체가 만든 대기가 쌓여 있습니다. 이 위에 사고가 얹힙니다.

## 1-2. 사고를 만든다
  보정 배치가 테이블을 20초 잡고, 그 사이 조회 6건이 줄을 섰습니다.

## 1-3. 누적으로 보면 vs 차분으로 보면

  누적 전체 상위 3개:
    LCK_M_IS  430521ms
    AZURE_IMDS_VERSIONS  62486ms
    PWAIT_EXTENSIBILITY_CLEANUP_TASK  60000ms

  사고 구간 차분 상위 3개:
    LCK_M_IS  107453ms
    PREEMPTIVE_OS_AUTHENTICATIONOPS  50ms
    PAGELATCH_UP  38ms

==================================================================
## 정리
==================================================================

  누적 1위와 차분 1위가 LCK_M_IS 로 같습니다. 유형은 같은데 **크기가 다릅니다.**

    누적                 430521 ms
    이번 사고가 만든 것 107453 ms

  나머지는 앞선 실행들이 남긴 것입니다. 이 랩은 같은 스크립트를 여러 번 돌려
  그렇지만, 운영에서는 어제 사고와 지난주 배치가 거기 섞여 있습니다.
  **누적만 보면 이번 사고의 크기를 실제보다 크게 봅니다.** 원인 유형이 우연히
  같아도 크기를 잘못 읽으면 대응 규모를 잘못 잡습니다.

  그래서 대기 통계는 **두 번 떠서 차분**으로 봅니다. 사고가 의심되면 먼저
  스냅샷을 뜨고, 몇 분 뒤 다시 떠서 그 사이에 늘어난 것만 봅니다.

  DBCC SQLPERF('sys.dm_os_wait_stats', CLEAR) 로 초기화하는 방법도 있지만
  운영에서는 쓰지 않습니다. 다른 사람이 보고 있던 기준이 사라집니다.

  **무시 목록이 부실하면 차분을 떠도 소용없습니다.** 이 실험을 처음 돌렸을 때
  SOS_WORK_DISPATCHER 와 DISPATCHER_QUEUE_SEMAPHORE 가 상위를 전부 차지해
  사고가 만든 LCK_M_IS 가 3위 밖으로 밀려 있었습니다. 둘 다 시스템이 놀 때
  쌓는 대기라 사고와 무관합니다. 목록에 넣고서야 신호가 보였습니다.

  운영에서는 잘 알려진 무시 목록을 쓰되, 처음 보는 대기 유형이 상위에 오면
  그것이 진짜인지 유휴인지부터 확인합니다. 유휴를 안 빼면 매번 같은 것이
  1위로 나와 대기 통계가 쓸모없어집니다.
```

## 3. exp2-blocking-chain

```console
$ ./scripts/exp2-blocking-chain.sh
# 실험 2. 막은 세션이 아니라 뿌리를 찾는다

  세 세션으로 사슬을 만듭니다.
    A  트랜잭션을 열고 한 행을 갱신한 뒤 아무것도 안 한다 (뿌리)
    B  같은 행을 갱신하려다 A 에게 막힌다
    C  같은 행을 조회하려다 B 뒤에 줄을 선다

## 2-1. 순진한 조회

  막힌 세션마다 blocking_session_id 를 그대로 봅니다.

    세션 61 이(가) 세션 51 에게 막힘  (LCK_M_X, 7067ms)
    세션 62 이(가) 세션 61 에게 막힘  (LCK_M_S, 4066ms)

  여기 나오는 세션을 죽이면 될 것 같지만, 그중 하나는 자기도 막혀 있습니다.
  그것을 죽여도 뿌리가 그대로라 다시 같은 일이 납니다.

## 2-2. 재귀로 뿌리까지

    사슬: 62 <- 61 <- 51

  뿌리 세션: 51

## 2-3. 뿌리는 무엇을 하고 있었나

    상태 sleeping / 마지막 요청 2026-08-09 08:52:11.653 / 열린 트랜잭션 1개

  dm_exec_requests 에 이 세션이 있는가: **없음**

==================================================================
## 정리
==================================================================

  **순진한 조회는 중간 세션을 가리킵니다.** blocking_session_id 를 그대로 읽으면
  "B 가 막고 있다"고 나오는데 B 도 막혀 있습니다. B 를 죽여도 A 가 그대로라
  다시 같은 일이 납니다.

  재귀로 사슬을 따라가면 뿌리가 나옵니다. 그리고 **뿌리는 아무것도 안 하고
  있습니다.** 상태가 sleeping 이고 실행 중인 요청이 없어 dm_exec_requests 에
  안 나옵니다. 실행 중인 것만 보는 도구로는 못 찾습니다.

  처음에는 뿌리를 WAITFOR DELAY 로 버티게 짰다가 이 결론을 못 낼 뻔했습니다.
  그것은 실행 중인 요청이라 dm_exec_requests 에 그대로 나옵니다. 실제 사고의
  뿌리는 클라이언트가 트랜잭션을 열어 둔 채 노는 세션이고, 그것을 재현하려면
  서버가 아니라 **연결이** 놀아야 합니다.

  그래서 뿌리를 찾을 때는 dm_exec_sessions 와 dm_tran_session_transactions 를
  함께 봅니다. "요청은 없는데 트랜잭션은 열려 있는 세션"이 그것입니다.

  게임 운영으로 옮기면 흔한 모양이 하나 있습니다. 운영툴에서 조회를 던지고
  트랜잭션을 안 닫은 채 자리를 뜬 세션입니다. 그 하나가 보정 배치를 막고,
  보정 배치가 서비스 조회를 막습니다. 신고는 서비스에서 들어오는데 원인은
  두 단계 위에 있습니다.
```

## 4. exp3-plan-cache

```console
$ ./scripts/exp3-plan-cache.sh
# 실험 3. 순위에 안 잡히는 범인

  같은 부하를 두 방법으로 겁니다. 읽는 양과 횟수는 같고 값을 넘기는 방법만 다릅니다.
    A 파라미터로 넘긴다
    B 값을 리터럴로 박는다
  각각 60회씩. 조인을 넣어 **자동 파라미터화가 안 걸리게** 했습니다.

## 3-1. 부하를 건다
  각 60회 실행 완료

## 3-2. 계획 캐시에 어떻게 들어갔나

                     계획 개수  총 실행 횟수
  A 파라미터     1개           60회
  B 리터럴        60개          60회

  같은 횟수를 돌렸는데 A 는 계획 하나에 모이고 B 는 흩어집니다.

## 3-3. 총 논리 읽기 상위를 보면

  정석대로 total_logical_reads 로 정렬해 상위 3개를 봅니다.

    실행 60     논리읽기 151326       (@t INT)/*PARAM*/ SELECT COUNT(*) 
    실행 1      논리읽기 2546         SET NOCOUNT ON;       /*LITERAL*/ 
    실행 1      논리읽기 2546         SET NOCOUNT ON;       /*LITERAL*/ 

  A 는 한 줄로 크게 잡힙니다. B 는 각 계획이 1회·소량이라 상위에 못 옵니다.
  **부하는 절반을 B 가 주는데 순위에는 A 만 보입니다.**

## 3-4. query_hash 로 묶으면

    계획 61     실행 120      논리읽기 304086
    계획 1      실행 1        논리읽기 554
    계획 1      실행 1        논리읽기 0

  같은 모양의 쿼리는 값이 달라도 query_hash 가 같습니다. 파라미터로 넘긴 것과
  리터럴로 박은 것도 모양이 같으므로 한 줄로 모입니다.

  묶기 전 상위 1위         151326
  query_hash 로 묶은 뒤      304086

  **묶기 전에는 실제 부하의 절반만 보였습니다.**

==================================================================
## 정리
==================================================================

  **엔진이 알아서 파라미터화해 주는 구간이 있습니다.** 처음에는 단순한
  SELECT COUNT(*) ... WHERE tag = <값> 으로 쟀는데 리터럴 쪽도 계획 하나에
  모였습니다. 캐시 텍스트가 (@1 tinyint)SELECT ... WHERE [tag]=@1 이었습니다.
  단순 매개 변수화가 걸린 것이고, 그 구간에서는 리터럴을 써도 안 흩어집니다.

  다만 그것은 엔진이 안전하다고 판단하는 아주 단순한 쿼리에만 걸립니다.
  조인 하나만 넣어도 안 해 줍니다. 실무의 조사 쿼리는 대부분 그쪽입니다.

  대기가 락이 아니면 많이 읽는 쿼리를 찾아야 하는데, **total_logical_reads 로
  정렬한 상위 N 은 리터럴 쿼리를 못 잡습니다.** 값마다 다른 계획으로 흩어져
  각각은 실행 1회에 소량이기 때문입니다. 부하는 다 주면서 순위에는 안 잡힙니다.

  **query_hash 로 묶어서 봅니다.** 같은 모양이면 값이 달라도 해시가 같습니다.
  묶고 나면 흩어져 있던 것이 한 줄로 모여 상위에 올라옵니다.

  덧붙여 계획이 많이 흩어지는 것 자체가 문제입니다. 계획 캐시가 부풀고,
  매번 컴파일하느라 CPU 를 씁니다. 근본 해소는 진단이 아니라 **애플리케이션이
  값을 파라미터로 넘기게 고치는 것**입니다.

  대기 통계와 같은 함정이 하나 더 있습니다. query_stats 도 누적이고, 게다가
  **계획이 캐시에서 밀려나면 그 통계도 함께 사라집니다.** 사고가 지나간 뒤에
  들여다보면 범인이 이미 없을 수 있습니다.
```

## 5. exp4-query-store

```console
$ ./scripts/exp4-query-store.sh
# 실험 4. 캐시가 비면 범인도 사라진다

  실험 3은 계획 캐시로 범인을 찾았습니다. 그 방법에는 전제가 있습니다.
  **계획이 캐시에 남아 있어야 합니다.** 사고가 지나간 뒤에 들여다보면
  이미 밀려났을 수 있는데, 그 상황을 안 만들어 봤습니다.

==================================================================
## 4-1. Query Store 를 켠다
==================================================================

  Query Store 상태       READ_WRITE / capture ALL

  캡처 모드를 ALL 로 둡니다. 기본값 AUTO 는 가벼운 쿼리를 안 담는데,
  **조사에서 찾고 싶은 것이 늘 무거운 쿼리인 것은 아닙니다.**
  리터럴로 흩어진 쿼리는 하나하나가 가벼워서 AUTO 에서 빠질 수 있습니다.

==================================================================
## 4-2. 부하를 걸고 두 곳에서 본다
==================================================================

  시점                         DMV 계획     DMV 논리읽기 QS 쿼리      QS 논리읽기
  부하 직후                  3              187800           6              187805

==================================================================
## 4-3. 캐시가 비면
==================================================================

  사고가 지나가고 시간이 흐르면 계획이 밀려납니다. 메모리 압박, 통계 갱신,
  인덱스 변경, 재시작이 전부 그 원인입니다. 여기서는 그 결과만 만듭니다.

  계획 캐시를 비운 뒤    0              0                7              187819

  **DMV 쪽은 통째로 사라졌습니다.** 3개 계획, 논리 읽기 187800 이
  0 이 됐습니다. `dm_exec_query_stats` 는 이름 그대로 **캐시에 있는 계획의**
  통계이고, 계획이 없어지면 통계도 함께 없어집니다.

  **Query Store 는 그대로 있습니다.** 7개 쿼리, 논리 읽기 187819.
  디스크에 쓰기 때문입니다. 사고가 지나간 뒤에 들여다봐도 남아 있습니다.

==================================================================
## 4-4. Query Store 가 대신 못 하는 것
==================================================================

  그러면 DMV 를 버리고 Query Store 만 보면 되는가. **아닙니다.**

  물어보는 것                   DMV              Query Store
  지금 무엇이 돌고 있나     dm_exec_requests 못 한다
  지금 누가 누구를 막고 있나 dm_tran_locks    못 한다
  지난 사고의 범인 쿼리     캐시에 남아야 **남아 있다**
  그때의 실행 계획            밀려나면 없음 **버전별로 보관**
  계획이 바뀌어 느려진 것  못 본다       **계획 회귀로 본다**

  **Query Store 는 지난 일을 보는 도구이고 DMV 는 지금을 보는 도구입니다.**
  실험 2의 블로킹 사슬은 Query Store 로 못 찾습니다. 지금 누가 누구를 막고
  있는지는 저장되는 값이 아니기 때문입니다.

  그래서 순서가 이렇게 갈립니다.
    사고가 **지금** 나고 있다        DMV. 대기 -> 사슬 -> 뿌리
    사고가 **지나갔다**              Query Store. 그 구간의 쿼리와 계획
    같은 쿼리가 **갑자기 느려졌다**  Query Store 의 계획 회귀

==================================================================
## 정리
==================================================================

  실험 3의 방법에는 전제가 있었습니다. **계획이 캐시에 남아 있어야 합니다.**
  캐시를 비우자 3개 계획과 논리 읽기 187800 이 통째로 사라졌습니다.
  사고 대응이 늦어지면 범인이 이미 없을 수 있습니다.

  **Query Store 는 그 자리를 메웁니다.** 디스크에 쓰므로 재시작에도 남고,
  구간별로 쪼개 두므로 "어제 그 시간대"를 물을 수 있습니다.

  다만 **대체재가 아니라 짝**입니다. 지금 누가 막고 있는지는 Query Store 가
  모릅니다. 진단 순서에서 DMV 는 앞자리, Query Store 는 뒷자리입니다.

  켤 때 주의할 것이 하나 있습니다. **캡처 모드 기본값 AUTO 는 가벼운 쿼리를
  안 담습니다.** 실험 3에서 본 리터럴로 흩어진 범인은 하나하나가 가벼워서
  그 그물에서 빠질 수 있습니다. 그런 조사를 할 생각이면 ALL 로 둡니다.
```

## 5-1. 같은 처방이 왜 안 통하는가

  대기가 가리키는 것 블로킹 사슬을 따라가면 대신 볼 것
  락                    뿌리 세션이 나온다 그 세션이 무엇을 하던 중인지
  메모리·디스크   **막는 세션이 없다** 읽는 페이지 수. 인덱스와 메모리
  로그 쓰기          **막는 세션이 없다** 커밋 횟수. 배치로 묶을 수 있는지
  병렬 처리          **막는 세션이 없다** 이 대기는 정상일 수 있다

  **락이 아닌 셋은 블로킹 사슬을 따라가 봐야 아무도 안 나옵니다.**
  실험 2의 재귀 쿼리를 돌리면 빈 결과가 나오고, 그것을 "막는 세션이 없으니
  DB 문제가 아니다"로 읽으면 그때부터 헤맵니다.

  넷째가 특히 함정입니다. 병렬 대기는 **일을 나눠 하는 중**이라는 뜻이지
  문제가 아닐 수 있습니다. 상위에 올랐다고 손대면 멀쩡한 것을 건드립니다.

  B 에서 1위가 PAGEIOLATCH 가 아니라 **SLEEP_BPOOL_STEAL** 로 나왔습니다.
  버퍼 풀이 표보다 작아 페이지를 계속 빼앗기는 상태이고, PAGEIOLATCH_SH 는
  그 아래에 붙습니다. **더 정확한 진단입니다.** 디스크가 느린 것이 아니라
  메모리가 모자라 같은 페이지를 반복해 올리고 있다는 뜻이기 때문입니다.
  디스크를 바꿔도 안 낫고 메모리를 늘리거나 읽는 양을 줄여야 합니다.

  이 조건을 만들려고 **버퍼 풀을 1024MB 로 두고 표를 그보다 크게** 만들었습니다.
  버퍼 풀이 표보다 크면 한 번 읽어 올린 뒤로는 디스크를 안 갑니다.
  조사 쿼리가 실제 운영에서 느린 이유가 이것이고, 랩에서 재려면 같은 비율이
  필요합니다. 처음에 풀을 256MB 까지 조였다가 컨테이너가 죽었습니다.

  RESOURCE_SEMAPHORE(메모리 부여 대기)는 이 랩에서 못 만들었습니다.
  큰 정렬을 여럿 동시에 돌려야 하는데 이 컨테이너 규모에서는 부여가 다 났습니다.

## 정리
==================================================================

  대기 유형은 **어느 처방으로 갈지를 정하는 갈림길**입니다.
  실험 1·2가 만든 순서(대기 -> 사슬 -> 뿌리)는 그 갈림길에서 락 쪽으로 간
  경우이고, 나머지 셋에서는 사슬을 따라가 봐야 아무도 안 나옵니다.

  그래서 진단 순서의 2단계에 분기를 넣습니다.

    LCK_M_*         블로킹 사슬을 따라 뿌리를 찾는다 (실험 2)
    PAGEIOLATCH_* / SLEEP_BPOOL_STEAL  많이 읽는 쿼리와 버퍼 풀 여유를 본다 (실험 3)
    WRITELOG        커밋 횟수를 본다. 한 건씩 커밋하는 루프를 배치로 묶는다
    CXPACKET 계열   먼저 정상인지 의심한다. 병렬도가 문제면 MAXDOP 을 본다

  **어느 쪽이든 3단계는 같습니다.** 무엇을 하던 세션인지, 어떤 쿼리인지
  기록하고 나서 손댑니다. 기록 없이 죽이면 같은 일이 반복됩니다.

  회차당 수집 행           81

  **한 번 수집이 논리 읽기 153 입니다.** 읽는 것이 DMV 한 개뿐이라

  대신 **보존 기간을 안 정하면 쌓입니다.** 1분 주기로 1년이면 4620MB 이고,
  30일만 남기면 380MB 입니다. 수집기를 만들 때 지우는 작업을 같이 만듭니다.
  들여다보는 값이 비싸면 못 켜는데 이것은 그 걱정이 없고, **관리 안 하면 쌓이는
  쪽**이 문제입니다.

## 정리
==================================================================

  실험 1의 "두 번 떠서 차분"에는 **사고가 진행 중이어야 한다**는 전제가
  있었습니다. 신고가 늦으면 기준으로 삼을 앞 스냅샷이 없습니다.

  수집기를 주기적으로 돌려 두면 그 전제가 없어집니다. 누적값을 회차마다
  그대로 적어 두고 **읽을 때 구간을 골라 차분**하면, 사고가 끝난 뒤에도
  그 구간만 떼어 볼 수 있습니다.

  설계에서 정한 것 둘입니다.

    누적값을 그대로 적는다. 수집할 때 차분을 내면 구간을 다시 못 고르고
    회차 사이의 재시작(누적값이 0 으로 돌아가는 것)도 못 가른다

    유휴 대기는 **읽을 때가 아니라 담을 때** 뺀다. 담아 두면 표가 커지고
    매번 같은 것을 걸러야 한다

  운영에서는 SQL Server 에이전트 작업으로 1분마다 돌리고, 보존 기간이 지난
  회차를 지우는 정리를 함께 겁니다. Query Store(실험 4)가 쿼리 쪽을 맡는다면
  이것은 **대기 쪽을 맡습니다.** 둘 다 "지난 일을 보는" 자리입니다.
