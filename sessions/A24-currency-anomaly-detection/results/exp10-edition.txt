# 실험 10. 낮은 에디션에서는 무엇이 막히는가

  이 랩 본체 Developer Edition (64-bit)
  비교 대상  Express Edition (64-bit)
  빌드         RTM / 16.0.4265.3

  표는 50000행짜리 작은 것입니다. **거부는 표 크기가 아니라 에디션이 정합니다.**

  기능                             Developer      Express        Express 가 뱉은 것
  CREATE INDEX (기본)              됨            됨            
  CREATE INDEX WITH ONLINE = ON      됨            거부         Msg 1712  Online index operations can only be performed in Enterprise edition of
  CREATE INDEX WITH SORT_IN_TEMPDB = ON 됨            됨            
  필터드 인덱스                됨            됨            
  파티션 함수·스킴           됨            됨            
  데이터 압축(PAGE)             됨            됨            
  확장 이벤트 세션            됨            됨            

## 10-1. 거부 전문

  ONLINE = ON 을 던졌을 때 Express 가 돌려준 것입니다.
    Msg 1712, Level 16, State 3, Server 2d4116a82f1b, Line 3
    Online index operations can only be performed in Enterprise edition of SQL Server or Azure SQL Edge.

## 10-2. Express 가 실제로 조인 자원 제약

  한글을 SQL 에서 그대로 돌려받으면 sqlcmd 를 거치며 깨집니다. ASCII 로 받아
  셸에서 옮깁니다(이 저장소의 규칙인데 여기서 한 번 어겼다가 다시 고쳤습니다).

  보이는 스케줄러 4
  max server memory      2147483647 MB
  버퍼 풀 현재 목표 141 MB

  같은 것을 본체(Developer)에서도 봅니다.
  본체 스케줄러    12
  본체 버퍼 풀 상한 1956 MB

  스케줄러 수가 갈립니다. 컨테이너에 Express 는 2코어, 본체는 4코어를 줬는데
  **SQL Server 가 보는 수는 컨테이너 설정과 다릅니다.** 본체는 호스트의 12개를
  그대로 보고, Express 는 4개에서 잘립니다. compose 의 cpus 는 CFS 할당량이라
  보이는 코어 수를 안 바꾸고, 4 라는 수는 Express 자신의 상한입니다.

  **버퍼 풀 값은 상한이 아니라 지금 잡고 있는 크기입니다.** 방금 뜬 인스턴스라
  작게 나온 것이고 부하가 쌓이면 늡니다. Express 의 실제 상한(1,410MB)은 이
  DMV 로 안 보이므로 여기서 잰 값으로 상한을 말할 수 없습니다.

  DB 파일 크기 상한(Express 10GB)은 이 랩에서 안 쟀습니다. 채우려면 10GB 를
  써야 하는데 그만한 값이 없다고 봤습니다. 다만 **이 세션의 원장이 879MB 라
  그 상한 안에 든다는 것**과, 실제 게임 원장은 그렇지 않다는 것은 짚어 둡니다.

## 정리
==================================================================

  문서로만 알던 것을 실제 오류로 확인했습니다.

  **ONLINE = ON 은 Express 에서 거부됩니다.** 인덱스 자체는 만들어지므로,
  낮은 에디션에서 조사용 인덱스를 만드는 것은 가능하되 **그동안 쓰기가 막힙니다**
  (실험 4에서 13.7초). 재화 원장은 append-only 라 그 시간 동안 지급과 소모가
  전부 줄을 섭니다.

  그래서 낮은 에디션의 선택지는 인덱스를 만드느냐가 아니라 이렇게 됩니다.

    조사 창을 좁혀 전체 스캔으로 버틴다        실험 3의 229,614 를 감수한다
    클러스터드 키를 평소에 시간 순으로 잡는다  실험 8에서 창을 좁힌 진짜 힘
    점검 시간에 인덱스를 만든다                쓰기가 없는 창을 잡는다

  두 번째가 제일 낫습니다. **평소에 정하는 것이라 사고 때 아무 대가가 없습니다.**
  실험 8에서 조사 쿼리를 114,353 에서 638 로 내린 것이 그것이었고, 파티션이나
  온라인 빌드 같은 에디션을 타는 기능이 하나도 필요 없습니다.

  파티션·필터드 인덱스·압축·확장 이벤트가 Express 에서도 되는 것을 확인했습니다.
  2016 SP1 이후로 열린 것들이라, **에디션 때문에 못 한다고 미리 접을 자리가
  생각보다 좁습니다.** 실제로 걸리는 것은 온라인 빌드 쪽입니다.
