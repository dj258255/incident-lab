# R03 재현 기록

## 환경

| 항목 | 값 |
|---|---|
| 호스트 | macOS 26.3.1, Apple M2 Pro, 12코어(논리), 32GB |
| 자원 한도 | 걸지 않았습니다. `compose.yml`에도 `scripts/run.sh`의 `docker run`에도 `cpus`·`mem_limit`이 없고 `-Xmx`도 주지 않았습니다 |
| DB | MySQL 8.4.3 × 3 (172.32.0.11/12/13, `compose.yml`의 `--server-id` 1/2/3) |
| 리더 엔드포인트 | CoreDNS 1.11.3, hosts 플러그인 + `loadbalance round_robin`, TTL 1초 |
| 앱 | Spring Boot 3.4.1 + HikariCP, eclipse-temurin:21-jre 컨테이너, Java 21 |
| 조인 값 | `POOL=12`(`maximum-pool-size`와 `minimum-idle` 둘 다), `MAXLIFE=30000`, `connection-timeout=3000`, ttl0 조건만 `JAVA_TOOL_OPTIONS=-Dsun.net.inetaddr.ttl=0` |
| 일시 | 2026-07-29 |

호스트 사양은 위 표에 적었지만 `uname -srm`·`nproc`·`free -g` 출력을 파일로 캡처하지는 않았습니다.
이 저장소의 다른 macOS 세션(R04·R13·R16)과 같은 장비입니다.

이 세션이 재는 값은 커넥션 12개가 세 인스턴스에 갈리는 **비율**이라 호스트 성능에 좌우되지 않습니다.
시간 수치는 관측 간격 3초와 `maxLifetime` 30초뿐이고 둘 다 설정값입니다.

## 실행

```console
$ docker compose up -d
$ cd app && gradle bootJar && cd ..
$ ./scripts/run.sh cached POOL=12 MAXLIFE=30000
$ ./scripts/run.sh ttl0   POOL=12 MAXLIFE=30000 JAVA_TOOL_OPTIONS=-Dsun.net.inetaddr.ttl=0
$ python3 scripts/report.py
```

두 조건 사이에서 바뀐 것은 `JAVA_TOOL_OPTIONS` 하나뿐입니다. 풀 크기와 `maxLifetime`은 같습니다.

`run.sh`는 라벨마다 앱 컨테이너를 새로 띄우고 3초 간격으로 40회 `/distribution`을 호출한 뒤 컨테이너를 지웁니다.
조건마다 **한 번씩만** 돌렸습니다. 조건별 반복 실행은 하지 않았습니다.

측정 시각은 `results/*.jsonl`의 첫 필드(epoch)에 남아 있습니다.

| 라벨 | 시작 | 종료 | 표본 |
|---|---|---|---|
| `short` | 1785324036 | 1785324155 | 40 |
| `cached` | 1785324619 | 1785324738 | 40 |
| `ttl0` | 1785324782 | 1785324901 | 40 |

## DNS가 실제로 도는지 먼저 확인

```console
$ for i in 1..6; do nslookup reader.internal | grep -m1 "^Address: 172"; done
Address: 172.32.0.13
Address: 172.32.0.13
Address: 172.32.0.12
Address: 172.32.0.11
Address: 172.32.0.11
Address: 172.32.0.11
```

주석 두 가지를 답니다. 출력 여섯 줄은 손대지 않았습니다.

1. 명령줄의 `for i in 1..6`은 bash에서 한 번만 도는 문법이라 출력 여섯 줄과 맞지 않습니다.
   실행 당시 명령을 옮겨 적으며 중괄호(`{1..6}`)를 빠뜨린 것으로 보입니다. 출력은 그대로 두고 이 사실만 밝힙니다.
2. 확인한 것은 "응답마다 순서가 바뀐다"까지입니다. `.13 .13 .12 .11 .11 .11`은 세 주소를 두 번씩 정확히
   돌린 모양이 아니므로, 엄밀한 순환인지는 이 출력으로 말할 수 없습니다.

dnsmasq(`address=` 항목)에서는 조회할 때마다 같은 순서가 돌아왔습니다. 그 시절의 조회 출력은 파일로 남기지 않았습니다.
CoreDNS로 바꾼 뒤 순서가 바뀌는 것을 확인하고 본 측정을 했습니다.

### 40회는 40번의 독립 시행이 아닙니다

`maxLifetime`이 30초라 풀은 약 30초마다 통째로 재생성되고, 그 사이에는 분포가 바뀌지 않습니다.
3초 간격 표본 40개는 결국 **풀 세대 다섯 개**(마지막 하나는 재생성 도중에 찍힌 한 표본)를 반복해 찍은 것입니다.
평균 83.5%와 47.9%를 유효 표본 40개짜리 평균으로 읽으면 안 됩니다.

## 쿼리 단위가 아님을 확인

`scripts/run.sh`가 측정 시작 전에 같은 풀로 20번 연속 조회를 던집니다.

```bash
echo "  같은 풀에서 20번 조회: $(for _ in $(seq 1 20); do curl -s http://127.0.0.1:18081/one | sed -n 's/.*"server_id":"\([0-9]*\)".*/\1/p'; done | sort | uniq -c | tr '\n' ' ')"
```

기록한 결과는 20번 모두 `server_id=1`입니다. 다만 `run.sh`의 표준출력을 파일로 저장하지 않아
**그 줄의 원문은 저장소에 없습니다.** 재현할 때 화면에서 다시 확인해야 하는 항목입니다.

풀에서 빌려 쓰고 반납하는 패턴이라 같은 커넥션이 계속 나오고, 그 커넥션은 한 인스턴스에 고정돼 있습니다.

### `compose.yml`에 `--server-id`가 빠져 있었습니다

저장소에 커밋된 `compose.yml`대로 올리면 이 세션이 재현되지 않습니다. `mysql:8.4.3`의 `server-id`
기본값이 1이라 세 대가 전부 1을 돌려주고, 그러면 `SELECT @@server_id`로는 쏠림이 아예 보이지 않습니다.
`results/*.jsonl`에는 1·2·3이 모두 남아 있으므로 실제 측정 당시에는 셋이 갈려 있었고,
커밋된 파일에서 그 설정만 빠진 것입니다.

리눅스 호스트(Linux 5.14.0 aarch64, 2코어, 11GB)에서 확인한 내용입니다. 측정을 다시 한 것이 아니라
설정이 맞는지만 본 것이라 이 호스트의 사양은 본문 수치와 무관합니다.

```console
$ docker run --rm mysql:8.4.3 mysqld --verbose --help | grep -E "^server-id "
server-id                                                    1
```

고치기 전에는 세 컨테이너가 모두 `server_id=1`이었고, `db-1`/`db-2`/`db-3`에
`command: ["--server-id=N"]`을 넣은 뒤 각각 1·2·3이 나오는 것을 확인했습니다.
같은 호스트에서 CoreDNS 응답 순서가 조회마다 바뀌는 것도 다시 확인했습니다
(`172.32.0.11 → .12 → .11 → .11 → .12 → .13`). 이 확인들은 설정 검증이고,
본문의 83.5%·47.9%는 macOS에서 잰 원래 실행값 그대로입니다.
