# R03 리더 엔드포인트가 돌려줘도 커넥션은 한 대로 몰린다

> 근거 등급: `E2`
> 출처: [AWS, Reader endpoints for Amazon Aurora](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Endpoints.Reader.html) · [AWS, Amazon Aurora endpoint connections](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.Endpoints.html) · [AWS SDK for Java, DNS caching](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/java-dg-jvm-ttl.html) · [HikariCP #1247, Mass extinction of connections impacting AWS Aurora reader endpoint load balancing](https://github.com/brettwooldridge/HikariCP/issues/1247)

## 1. 유명한 이유

Aurora의 리더 엔드포인트는 읽기 부하를 리플리카들에 나눠 주는 장치입니다. 그런데 나누는 단위가 **커넥션**이지 쿼리가 아닙니다. AWS 문서가 그 자리에서 못을 박습니다.

> The reader endpoint balances connections to available Aurora Replicas in an Aurora DB cluster. It doesn't balance individual queries. If you want to balance each query to distribute the read workload for a DB cluster, open a new connection to the reader endpoint for each query.

쿼리마다 나누고 싶으면 쿼리마다 새 커넥션을 맺으라는 말인데, 커넥션 풀은 바로 그것을 하지 않으려고 존재합니다.

커넥션을 맺을 때 DNS가 리플리카 하나를 골라 주고, **그 커넥션은 닫힐 때까지 그 인스턴스에 고정됩니다.** 커넥션 풀을 쓰는 애플리케이션에서는 이 차이가 큽니다. 풀이 커넥션 12개를 유지하면 분산은 그 12개를 만드는 순간에 한 번 결정되고, 그 뒤로는 아무리 쿼리를 많이 보내도 비율이 바뀌지 않습니다.

이 세션은 그 구조를 로컬에서 재현하고, **분산이 실제로 되는지**를 셉니다. 결과부터 말하면 기본 설정에서는 되지 않았습니다.

## 2. 재현

### 환경

| 항목 | 값 |
|---|---|
| 호스트 | macOS 26.3.1, Apple M2 Pro, 12코어(논리), 32GB. `uname -srm`·`nproc`·`free -g` 출력을 파일로 캡처하지는 않았습니다 |
| 자원 한도 | 걸지 않았습니다. `compose.yml`에도 `scripts/run.sh`의 `docker run`에도 `cpus`·`mem_limit`이 없고 `-Xmx`도 주지 않았습니다 |
| DB | MySQL 8.4.3 세 대 (`172.32.0.11/12/13`, `--server-id` 1/2/3) |
| 리더 엔드포인트 | CoreDNS 1.11.3, `reader.internal`에 A 레코드 3개, `loadbalance round_robin`, TTL 1초 |
| 앱 | Spring Boot 3.4.1, Java 21, HikariCP 풀 12(`minimum-idle`도 12), `maxLifetime` 30초, `connection-timeout` 3초 |
| 관측 | 3초마다 풀 안 커넥션 12개를 전부 꺼내 각각 `@@server_id`를 확인 |

이 세션이 재는 값은 커넥션 12개가 세 인스턴스에 갈리는 비율이라 호스트 성능에 좌우되지 않습니다. 본문의 시간 수치는 관측 간격 3초와 `maxLifetime` 30초뿐이고 둘 다 설정값입니다.

**센 것은 커넥션 수입니다.** 쿼리 수도 아니고 CPU도 아닙니다. 아래에서 말하는 "최대 점유"는 한 인스턴스에 붙은 커넥션 수를 풀 크기 12로 나눈 값입니다. 부하를 걸지 않았으므로 쏠린 인스턴스가 실제로 얼마나 힘들었는지는 이 세션이 모릅니다.

풀의 분포를 보려면 커넥션을 **동시에** 붙잡아야 합니다. 하나씩 꺼내 반납하면 같은 커넥션만 계속 나오기 때문입니다. `/distribution` 엔드포인트는 `maximumPoolSize`만큼 커넥션을 한꺼번에 잡고 각각에 `SELECT @@server_id`를 던집니다.

### DNS부터 확인해야 했습니다

처음에는 dnsmasq로 만들었는데 재현이 되지 않았습니다. 원인은 DNS 쪽이었습니다. dnsmasq의 `address=` 항목은 A 레코드 순서를 고정해서 돌려줍니다. 조회할 때마다 같은 순서가 나왔고, Java의 `InetAddress.getByName()`은 그중 첫 번째만 쓰므로 커넥션이 전부 한 곳으로 갔습니다. **이건 Aurora의 동작이 아니라 제 DNS 설정 문제였습니다.** 다만 그 시절의 조회 출력은 파일로 남기지 않아 저장소에 없습니다. 그래서 여기에 콘솔 블록으로 싣지 않습니다.

CoreDNS의 `loadbalance` 플러그인으로 바꾼 뒤 남긴 출력은 이것입니다.

```console
$ for i in 1..6; do nslookup reader.internal | grep -m1 "^Address: 172"; done
Address: 172.32.0.13
Address: 172.32.0.13
Address: 172.32.0.12
Address: 172.32.0.11
Address: 172.32.0.11
Address: 172.32.0.11
```

두 가지를 밝힙니다. 첫째, 명령줄의 `for i in 1..6`은 bash에서 한 번만 도는 문법이라 출력 여섯 줄과 맞지 않습니다. 실행 당시 명령을 옮겨 적으며 중괄호(`{1..6}`)를 빠뜨린 것으로 보이고, 출력은 손대지 않고 그대로 둡니다. 둘째, 이 출력으로 확인한 것은 "응답마다 순서가 바뀐다"까지입니다. `.13 .13 .12 .11 .11 .11`은 세 주소를 두 번씩 정확히 돌린 모양이 아니므로 엄밀한 순환인지는 말할 수 없습니다. 순서가 바뀐다는 것만 확인하고 본 측정을 했습니다.

## 3. 결과

![분산 비교](results/chart-skew.png)

조건마다 **한 번씩** 돌렸고, 3초 간격으로 40회씩 관측했습니다. 첫 표본과 마지막 표본 사이가 118.9초입니다. 두 조건 사이에서 바뀐 것은 `JAVA_TOOL_OPTIONS` 하나뿐이고 풀 크기와 `maxLifetime`은 같습니다.

| 조건 | 최대 점유 평균 | 범위 | 마지막 분포 |
|---|---|---|---|
| JVM 캐시 기본값 | **83.5%** | 58.3~100.0% | `{2: 12}` |
| `sun.net.inetaddr.ttl=0` | **47.9%** | 33.3~66.7% | `{1: 3, 2: 6, 3: 3}` |

기본 설정에서는 12개 커넥션 중 **최대 12개 전부가 한 인스턴스**에 붙었습니다. 리플리카 세 대를 띄우고 리더 엔드포인트를 두었는데 커넥션은 한 대에만 걸려 있었다는 뜻입니다. 그 상태에서 애플리케이션이 쿼리를 보내면 전부 그 한 대로 갑니다.

원인은 R02에서 다룬 그 JVM DNS 캐시입니다. 보안 관리자가 없을 때 JVM은 이름 해석 결과를 30초 캐시합니다. 리더 엔드포인트가 응답마다 다른 인스턴스를 앞에 놓아도, 그 30초 안에 맺히는 커넥션은 전부 같은 주소를 씁니다. `maxLifetime`이 30초라 풀이 주기적으로 재생성되는데, **재생성 시점이 캐시 만료 주기와 뭉치면 12개가 한꺼번에 같은 곳으로 갑니다.**

캐시를 끄면 최대 점유가 47.9%로 내려가고 최소 33.3%(4/4/4 균등)까지 갑니다. 완전 균등은 아닌데, 커넥션이 만들어지는 순간마다 독립적으로 뽑기 때문에 표본 12개에서는 편차가 남습니다.

### 40회는 40번의 독립 시행이 아닙니다

`maxLifetime`이 30초라 풀은 약 30초마다 통째로 재생성되고, 그 사이에는 분포가 바뀌지 않습니다. 3초 간격 표본 40개는 결국 **풀 세대 다섯 개**를 반복해 찍은 것입니다. 마지막 하나는 재생성 도중에 찍힌 표본 한 개입니다.

```
cached
    0.0~ 27.6s  {"1": 12}                 100.0%  n=10
   30.6~ 58.1s  {"1": 3, "3": 9}           75.0%  n=10
   61.1~ 85.4s  {"2": 5, "3": 7}           58.3%  n=9
   88.5~ 88.5s  {"2": 8, "3": 4}           66.7%  n=1   (재생성 도중)
   91.5~118.9s  {"2": 12}                 100.0%  n=10

ttl0
    0.0~ 27.6s  {"1": 8, "2": 1, "3": 3}   66.7%  n=10
   30.6~ 58.0s  {"1": 5, "2": 5, "3": 2}   41.7%  n=10
   61.1~ 88.4s  {"1": 4, "2": 4, "3": 4}   33.3%  n=10
   91.5~115.8s  {"1": 6, "2": 4, "3": 2}   50.0%  n=9
  118.9~118.9s  {"1": 3, "2": 6, "3": 3}   50.0%  n=1   (재생성 도중)
```

세대만 평균 내면 cached 80.0%, ttl0 48.3%입니다. 표본 가중 평균인 83.5%와 47.9%와 방향은 같지만, **83.5%를 표본 40개짜리 평균으로 읽으면 안 됩니다.** 유효한 관측은 조건당 다섯 세대이고, 그래서 이 세션의 결론은 "두 조건의 차이가 크다"까지입니다. 배수를 정밀하게 말할 표본이 아닙니다.

### 쿼리 단위가 아니라는 것

`scripts/run.sh`는 측정을 시작하기 전에 같은 풀로 `/one`을 20번 연속 호출합니다. 기록한 결과는 20번 모두 `server_id=1`이었습니다. 다만 `run.sh`의 표준출력을 파일로 저장하지 않아 **그 줄의 원문은 저장소에 없습니다.** 화면에서 읽고 옮겨 적은 값이라 콘솔 블록으로 싣지 않습니다.

풀에서 커넥션을 하나 빌려 쓰고 반납하는 패턴이라 같은 커넥션이 계속 나오고, 그 커넥션은 한 인스턴스에 고정돼 있습니다. **"리더 엔드포인트를 썼으니 부하가 나뉜다"는 가정이 성립하려면 커넥션 수준에서 나뉘어야 합니다.**

## 4. 해소

| 처방 | 근거 | 이 세션에서 쟀나 |
|---|---|---|
| `networkaddress.cache.ttl`을 0으로 | 최대 점유 평균 83.5% → 47.9% | 쟀습니다. 다만 잰 값은 0 하나뿐이고 5초나 10초 같은 중간값은 재지 않았습니다 |
| `maxLifetime`에 흔들림을 준다 | 만료 시각이 흩어지면 재생성도 흩어집니다 | 안 쟀습니다. DNS 캐시를 끈 상태에서 `maxLifetime`만 바꾸는 조건을 두지 않았습니다 |
| 풀 크기를 리플리카 수보다 넉넉히 | 표본이 작으면 균등해지지 않습니다 | 안 쟀습니다. 풀 12 하나로만 돌렸습니다 |
| 분산이 됐는지 실제로 센다 | 리플리카별 커넥션 수를 보지 않으면 쏠림을 모릅니다 | 이 세션이 한 일입니다. 다만 센 것은 커넥션 수뿐입니다 |

가장 중요한 것은 마지막입니다. **이 쏠림은 에러를 내지 않습니다.** 리플리카 세 대 중 한 대에만 커넥션이 붙어도 애플리케이션은 정상 동작하고, 그 한 대가 버티는 한 아무 신호가 없습니다. 트래픽이 늘어 그 한 대가 한계에 닿을 때 처음 드러나는데, 그때 보이는 것은 "리플리카를 늘렸는데 안 나아진다"입니다.

## 5. RDS와 Aurora에서 달라지는 것

이 재현은 CoreDNS와 독립된 MySQL 세 대로 만든 흉내입니다. 실제 Aurora에서는 다음이 달라집니다.

**분산 단위는 같습니다.** 위에 인용한 대로 AWS 문서가 커넥션 단위라고 명시하고, 쿼리 단위로 나누려면 쿼리마다 커넥션을 새로 맺으라고 안내합니다. 이 세션이 흉내 낸 것은 그 구조이고, 이 부분은 로컬이든 클라우드든 같습니다.

**응답 정책과 TTL은 확인하지 못했습니다.** CoreDNS의 TTL 1초와 `loadbalance round_robin`은 제가 정한 값입니다. Aurora 리더 엔드포인트가 실제로 어떤 순서로, 어떤 TTL로 돌려주는지는 이 세션에서 확인하지 않았습니다. 따라서 83.5%라는 숫자를 Aurora의 수치로 읽으면 안 됩니다. **이 세션이 보인 것은 "커넥션 단위 분산 + 클라이언트 측 이름 캐시"라는 조합이 쏠림을 만든다는 메커니즘입니다.**

**쏠림을 보는 방법이 달라집니다.** 로컬에서는 `SELECT @@server_id`로 셌지만, 관리형에서는 호스트에 들어갈 수 없으므로 인스턴스별 지표로 봅니다. CloudWatch의 `DatabaseConnections`는 인스턴스 단위 지표이고(정의는 "The number of client network connections to the database instance"), `CPUUtilization`과 `BufferCacheHitRatio`도 인스턴스 단위입니다. 클러스터 평균만 보는 대시보드로는 이 쏠림이 보이지 않습니다. 세 대 중 한 대가 100%여도 평균은 33%입니다. Aurora MySQL 안에서 지금 붙은 인스턴스를 확인하려면 `@@server_id` 대신 `@@aurora_server_id`를 읽습니다.

**RDS Proxy는 DNS 캐시 문제를 없애지만 커넥션 고정을 없애지는 않습니다.** AWS 문서는 프록시의 read-only 엔드포인트에 대해 "There isn't a delay due to DNS caching when an instance becomes unavailable"라고 적습니다. 이 세션이 잰 병목이 바로 그 DNS 캐시이므로 여기서는 유효한 처방입니다. 다만 같은 문서가 "Where practical, RDS Proxy uses the same reader DB instance for all the queries issue using a particular reader endpoint connection"이라고도 적습니다. 커넥션 하나가 리더 한 대에 붙는다는 성질은 프록시에서도 그대로이고, 달라지는 것은 인스턴스가 사라졌을 때의 전환 속도입니다.

### 비용

쏠림이 만드는 비용은 성능 지표가 아니라 청구서에서 먼저 보입니다. 아래는 AWS 요금 문서의 구조이고, **이 세션은 AWS 계정에서 아무것도 돌리지 않았으므로 실제 청구서를 재지 않았습니다.**

- **리플리카는 트래픽과 무관하게 인스턴스 시간으로 과금됩니다.** Aurora 요금 문서는 "Instance charges apply to both Aurora primary instances and replicas"라고 적습니다. 이 세션의 cached 조건에서 커넥션이 한 대에 100% 몰린 구간이 두 세대 있었는데, 그 구간 동안 나머지 두 대는 아무 일도 하지 않으면서 같은 시간당 요금을 냅니다. **리플리카를 늘리는 것이 곧 처리량을 늘리는 것이 아니고, 요금은 확실히 늘어납니다.**
- **읽기 I/O 총량은 쏠림으로 크게 달라지지 않습니다.** Aurora Standard는 읽기와 쓰기 I/O를 건수로 과금하고(요금 페이지가 미국 동부 버지니아 북부 예시로 100만 I/O당 0.20달러를 듭니다), Aurora I/O-Optimized는 I/O 과금을 없애는 대신 인스턴스와 스토리지 단가를 올립니다. 같은 쿼리가 어느 인스턴스에서 처리되든 필요한 페이지 수는 비슷하므로, 쏠림 자체가 I/O 건수를 몇 배로 만들지는 않습니다. 다만 풀이 재생성되며 붙는 인스턴스가 통째로 바뀌면 새 인스턴스의 버퍼 캐시는 비어 있고, 그 세대의 초반에는 스토리지에서 읽어 오는 페이지가 늘어납니다. **이 세션은 부하를 걸지 않았으므로 그 증가분을 재지 않았습니다.** 구조만 적습니다.
- **처방에도 값이 붙습니다.** RDS Proxy는 데이터베이스 인스턴스의 vCPU 시간 단위로 과금되고, 프록시 엔드포인트를 추가하면 PrivateLink 인터페이스 엔드포인트가 하나 더 생겨 요금이 붙습니다. 반면 `networkaddress.cache.ttl`을 0으로 두는 처방은 요금이 0원입니다. **이 세션이 잰 83.5%에서 47.9%로의 이동은 그 0원짜리 처방이 만든 것입니다.** 돈 드는 처방을 검토하기 전에 이쪽을 먼저 확인하는 편이 낫습니다.

## 6. 예상과 달랐던 점

### 커넥션 풀 설정이 아니라 DNS 캐시가 원인이었습니다

이 세션을 시작할 때는 `maxLifetime` 동기화가 주범일 것으로 봤습니다. 모든 커넥션의 수명이 같으면 만료가 뭉치고, 한꺼번에 재생성되면서 몰린다는 가설입니다. 이 가설은 제가 지어낸 것이 아니라 HikariCP 이슈 #1247이 보고한 그림입니다. 제목이 "Mass extinction of connections impacting AWS Aurora reader endpoint load balancing"이고, 실제 Aurora에서 풀 한 세대가 통째로 리플리카 한 대로 가는 일이 30분마다 반복되는 그래프가 붙어 있습니다.

재 보니 `maxLifetime`은 그대로 두고 DNS 캐시만 꺼도 83.5%가 47.9%로 내려갔습니다. HikariCP는 실제로는 `maxLifetime`에 소량의 흔들림을 자체적으로 주므로 만료 자체는 완전히 뭉치지 않습니다. 그 흔들림의 크기는 이 세션에서 따로 재지 않았습니다. 그런데도 몰린 이유는 **재생성이 흩어져 일어나도 그 사이 DNS 응답이 같은 값으로 캐시돼 있으면 결과가 같기 때문**입니다.

이 결과로 이슈 #1247이 틀렸다고 말할 수는 없습니다. `maxLifetime`만 따로 바꾸는 조건을 두지 않았기 때문입니다. 여기서 말할 수 있는 것은 **DNS 캐시 하나만으로도 같은 그림이 만들어진다**는 것입니다.

R02에서 "커넥션 풀 설정을 만져도 안 나아진다"를 확인했는데, 여기서도 같은 결론입니다. 두 세션 모두 병목이 이름 해석 캐시였습니다.

### 캐시를 꺼도 완전 균등은 아니었습니다

`ttl=0`에서도 최대 점유가 평균 47.9%이고 66.7%(8/12)까지 올라간 세대가 있습니다. 커넥션 12개를 세 곳에 무작위로 뿌리면 4/4/4가 나올 확률이 오히려 낮습니다. **라운드로빈 DNS는 균등 분배를 보장하지 않습니다.** 요청 순서대로 돌려줄 뿐이고, 커넥션 생성 시점이 불규칙하면 결과도 불규칙합니다.

### 재현 환경의 DNS가 먼저 문제였습니다

처음 두 번의 측정이 100% 쏠림으로 나와 재현에 성공한 줄 알았습니다. 확인해 보니 dnsmasq가 순서를 안 돌리고 있었고, 제가 만든 환경이 리더 엔드포인트가 아니었습니다. **재현 대상을 재기 전에 재현 환경이 그 대상을 흉내 내는지부터 확인해야 합니다.** 100%라는 극적인 숫자가 나왔을 때 의심했어야 했습니다.

## 7. 반복 3회, 쿼리 축, maxLifetime 분리 (2026-07-31)

`scripts/exp-repeat-load.sh`, 결과는 `results/exp-repeat-load.txt` 입니다.
조건마다 3회, 회차마다 3초 간격 40표본입니다.

### 네 조건의 커넥션 점유

| 조건 | `maxLifetime` | DNS 캐시 | run1 | run2 | run3 |
|---|---|---|---|---|---|
| short | 30초 | 켬 | 83.3% | 100.0% | 91.7% |
| long | 600초 | 켬 | **100.0%** | **100.0%** | **100.0%** |
| short-nocache | 30초 | 끔 | **50.0%** | **50.0%** | **50.0%** |
| long-nocache | 600초 | 끔 | 50.0% | 41.7% | 50.0% |

**캐시를 끄면 절반으로 떨어집니다.** 83.3~100%가 41.7~50%가 됩니다. 6절이 잰
83.5% → 47.9% 와 방향도 크기도 맞고, 이번에는 조건마다 세 회차입니다.

**`maxLifetime` 의 몫은 캐시를 끈 뒤에야 보입니다.** 캐시를 켠 채로는 short 가
83.3~100%, long 이 100% 로 갈립니다. 캐시를 끄면 short 가 50.0%, long 이 41.7~50.0%
로 **구별되지 않습니다.**

그러니까 6절의 "`maxLifetime` 만 따로 바꾸는 조건을 두지 않았다"는 자리에 답이
붙습니다. **`maxLifetime` 은 캐시가 켜져 있을 때만 결과를 바꿉니다.** 캐시가 없으면
재생성이 잦든 드물든 그때그때 DNS 를 새로 물으므로 분포가 같아집니다.

`long` 조건이 세 회차 모두 100.0% 이고 최소도 100.0% 인 것이 그 그림의 극단입니다.
600초 동안 재생성이 한 번도 없으니 처음 잡은 IP 가 관측 창 내내 유지됩니다.

### 커넥션 쏠림은 쿼리 쏠림입니다

각 리플리카의 `Com_select` 증분입니다.

| 조건 | run | db-1 | db-2 | db-3 |
|---|---|---|---|---|
| short | 1 | 353 | 45 | 201 |
| short | 2 | 171 | 1 | 423 |
| short | 3 | 1 | 202 | 392 |
| long | 1 | **503** | 1 | 1 |
| long | 2 | **503** | 1 | 1 |
| long | 3 | **503** | 1 | 1 |
| short-nocache | 1 | 234 | 144 | 219 |
| short-nocache | 2 | 242 | 107 | 252 |
| short-nocache | 3 | 177 | 151 | 269 |
| long-nocache | 1 | 253 | 125 | 125 |
| long-nocache | 2 | 209 | 83 | 207 |
| long-nocache | 3 | 251 | 83 | 167 |

**`long` 조건은 세 회차 모두 503 대 1 대 1 입니다.** 한 대가 쿼리의 99.6% 를 받고
나머지 두 대는 각각 한 건씩입니다(그 한 건은 관측용 질의입니다). 커넥션이 100% 몰린
것이 쿼리 축에서 그대로 나타납니다.

**캐시를 끄면 세 대에 퍼집니다.** `short-nocache` 는 234/144/219 처럼 나뉘고
`long-nocache` 도 253/125/125 입니다. 완전 균등은 아니지만 한 대가 독점하지 않습니다.

이것이 "리더 엔드포인트의 분산은 커넥션 단위"라는 이 세션의 주장을 쿼리 축에서
확인한 값입니다. **커넥션이 몰리면 그 인스턴스가 실제로 그만큼 더 일합니다.**
나머지 두 대는 놀면서 같은 시간당 요금을 냅니다.

### 밟은 결함

**옵션 이름을 잘못 넘겨 "캐시 끔" 조건이 캐시 켠 채로 돌았습니다.**
`networkaddress.cache.ttl` 은 `java.security` 파일이 읽는 **보안 속성**이라 `-D` 로
넘기면 조용히 무시됩니다. 시스템 속성으로 같은 일을 하는 것은 `sun.net.inetaddr.ttl`
입니다. 처음 실행에서 세 회차가 전부 중앙 100% 로 나와 캐시 조건과 구별되지 않았고,
**에러가 안 나므로 결과만 보면 알 수 없었습니다.** 6절이 `sun.net.inetaddr.ttl=0` 에서
47.9% 라고 적어 둔 덕에 어긋남을 잡았습니다.

### maxLifetime 을 다섯 점 더 찍으면 (2026-07-31)

`maxLifetime` 을 30초와 600초 두 값으로만 봤습니다. 그 사이가 계단인지 곡선인지 갈리지 않습니다. DNS 캐시를 끈 상태에서 다섯 점을 더 찍었습니다. 캐시가 켜져 있으면 재생성 시각이 흩어져도 같은 IP 로 가므로 이 축이 안 보입니다.

인스턴스가 셋이므로 완전 균등은 33.3% 입니다.

| DNS 캐시 | `maxLifetime` | 커넥션 최대 점유 | 쿼리 최대 점유 |
|---|---|---|---|
| 켬 | 30초 | 87.5% | 62.8% |
| 켬 | 600초 | **100.0%** | **99.6%** |
| 끔 | 5초 | 50.0% | 49.7% |
| 끔 | 10초 | 41.7% | 41.9% |
| 끔 | 30초 | 50.0% | 36.1% |
| 끔 | 60초 | **37.5%** | 37.7% |
| 끔 | 120초 | 50.0% | 48.8% |
| 끔 | 300초 | 50.0% | 49.9% |
| 끔 | 600초 | 50.0% | 50.3% |

**캐시를 끄면 `maxLifetime` 이 축이 아닙니다.** 5초부터 600초까지 120배를 움직였는데 37.5%~50.0% 사이를 오갑니다. 단조 관계가 없고 회차 폭 안입니다.

**캐시가 켜져 있을 때만 축입니다.** 30초에서 87.5%, 600초에서 100.0% 입니다.

두 사실을 합치면 `maxLifetime` 이 하는 일이 정확해집니다. **`maxLifetime` 을 줄이는 것이 듣는 이유는 커넥션을 자주 재생성해 이름을 다시 묻게 만들기 때문입니다.** 캐시가 이미 꺼져 있으면 매번 다시 묻고 있으므로 더 줄일 이득이 없습니다.

그래서 둘 중 하나를 고르라면 **캐시 쪽입니다.** `maxLifetime` 을 30초로 줄여도 캐시가 켜져 있으면 87.5% 가 남습니다. 캐시를 끄면 `maxLifetime` 이 600초여도 50.0% 로 내려옵니다.

**어느 조건도 33.3% 에 안 닿습니다.** 가장 좋은 조건이 37.5% 이고 대부분 50% 근처입니다. 6절에 적은 "캐시를 꺼도 완전 균등은 아니었습니다" 가 아홉 조건에서 다시 확인됩니다. 커넥션 40개를 인스턴스 3개에 나누는데 라운드로빈 순서와 풀 초기화 시점이 겹치면 한 인스턴스가 절반을 가져갑니다. **DNS 라운드로빈은 요청 단위 분산이 아니라 이름 해석 단위 분산입니다.**

## 못 한 것

- **`maxLifetime` 스윕은 조건마다 3회 실행입니다.** 회차 폭이 조건 사이 차이만큼 커서 개별 칸의 값은 인용하면 안 되고, "축이 아니다" 라는 방향만 읽어야 합니다.
- **실제 Aurora로 검증하지 않았습니다.** 리더 엔드포인트의 DNS 동작을 CoreDNS로 흉내 냈고, AWS의 실제 응답 정책과 TTL은 다를 수 있습니다.
- **인스턴스별 CPU 와 지연은 재지 않았습니다.** 7절에서 쿼리 수는 셌지만, 몰린 인스턴스의 CPU 나 응답 시간이 어떻게 되는지는 안 쟀습니다. 조회가 `SELECT @@server_id` 라 비용이 거의 0 이라 이 부하로는 드러나지 않습니다.
- **유효 표본은 여전히 얇습니다.** 7절에서 조건마다 3회로 늘렸지만 회차마다 풀 세대가 다섯 개라 조건당 열다섯 개입니다.
- **`maxLifetime` 을 두 값으로만 봤습니다.** 7절은 30초와 600초입니다. 그 사이 값에서 캐시 TTL 과 어떻게 맞물리는지는 재지 않았습니다.
- **리플리카가 실제 Aurora 복제본이 아닙니다.** 독립된 MySQL 세 대라 복제 지연이나 읽기 전용 제약은 재현하지 않았습니다.
- **클라우드 비용을 계산하지 않았습니다.** 위 비용 절은 AWS 요금 문서의 구조를 옮긴 것이고, 인스턴스 클래스도 금액도 산정하지 않았습니다.
