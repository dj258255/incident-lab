# A18 Uber의 PostgreSQL 쓰기 증폭 주장, 경계선을 실측으로 긋기

> 근거 등급: `E1` (원문과 반론 전부 공개 문서로 실재)
> 출처: [Uber, Why Uber Engineering Switched from Postgres to MySQL (2016)](https://www.uber.com/blog/postgres-to-mysql-migration/) · 반론: [Markus Winand](https://use-the-index-luke.com/blog/2016-07-29/on-ubers-choice-of-databases), [Simon Riggs](https://www.enterprisedb.com/blog/thoughts-on-ubers-list-of-postgres-limitations), [Robert Haas](http://rhaas.blogspot.com/2016/08/ubers-move-away-from-postgresql.html), [Christophe Pettus](https://thebuild.com/presentations/uber-perconalive-2017.pdf) · [PostgreSQL, Heap-Only Tuples](https://www.postgresql.org/docs/current/storage-hot.html)

## 1. 유명한 이유

2016년 Uber가 PostgreSQL에서 MySQL로 옮긴 이유를 공개했고, DB 커뮤니티에서 손꼽히는 논쟁이 됐습니다. 핵심 주장은 이렇습니다. PostgreSQL의 세컨더리 인덱스는 행의 물리 위치(ctid)를 직접 가리키므로, **컬럼 하나만 바꿔도 새 행 버전이 생기고 모든 세컨더리 인덱스에 새 엔트리가 필요하다.** 인덱스가 많은 테이블에서는 이것이 막대한 비효율이고, 물리 WAL 복제를 타고 대역폭 문제로 번진다는 것입니다.

반론이 곧바로 나왔습니다. Winand, Riggs, Pettus가 공통으로 지적한 것은 Uber 글이 **HOT(Heap-Only Tuples, 2007년 8.3부터)를 한 번도 언급하지 않았다**는 점입니다. 인덱스가 참조하는 컬럼을 건드리지 않고 페이지에 여유 공간이 있으면, 새 버전은 같은 페이지 안에 만들어지고 인덱스는 갱신되지 않습니다. Pettus는 이 주장에 "절반만 참" 판정을 내렸고, Haas는 커뮤니티 내부에서도 non-HOT 쓰기 증폭이 실제 약점임을 인정했습니다.

그래서 이 세션은 누가 옳았는지 편들지 않습니다. **어떤 조건에서 증폭이 실제로 발생하는지 경계선을 계측으로 긋습니다.** 재현 대상이 스토리지 엔진 동작이라 드라이버는 순수 SQL입니다.

## 2. 재현

PostgreSQL 17.5, 같은 스키마의 테이블 6개를 만들었습니다. 다른 것은 세컨더리 인덱스 수(0·3·6·10)와 fillfactor(100 = 페이지 꽉 채움, 70 = 여유 30%)뿐입니다. 각 50만 행.

컬럼은 13개입니다. `id BIGINT`, `val INT`, `c1`부터 `c10`까지 `INT` 10개, 그리고 `pad TEXT`에 `repeat(md5(...), 3)`으로 만든 96바이트 문자열입니다. 힙 튜플 헤더 24바이트에 데이터를 얹고 MAXALIGN하면 튜플 176바이트, 라인 포인터 4바이트를 더해 페이지 위에서 한 행이 차지하는 자리는 **약 180바이트**입니다. 초고에는 130바이트라고 적었는데 DDL과 맞지 않는 수치였습니다. 계산 과정은 [reproduce.md](reproduce.md)에 있습니다.

측정 단위는 "50만 행 전체를 UPDATE 한 문장으로 갱신"이고, 전후의 `pg_current_wal_lsn()` 차이로 WAL 증가량을, `pg_stat_user_tables`의 `n_tup_hot_upd`로 HOT 비율을 잽니다.

### 환경

| 항목 | 값 |
|---|---|
| PostgreSQL | 17.5 컨테이너, `shared_buffers=1GB`, `wal_compression=off` |
| 컨테이너 자원 한도 | 없습니다. `compose.yml`에 `cpus`도 `mem_limit`도 두지 않았습니다 |
| autovacuum | 끄지 않았습니다. 기본값 그대로 켜져 있었습니다 |
| 호스트 사양 | 2026-07-31 재측정 회차는 macOS 26.3.1, Apple M2 Pro 12코어, 32GB에서 돌았고 컨테이너 런타임 VM은 12코어 7.7GB 입니다(`results/00-host.txt`). 그 이전 회차의 호스트는 기록이 없어 확인되지 않습니다 |
| 데이터 | 테이블 6개 × 50만 행, 행 하나가 페이지에서 차지하는 자리 약 180바이트 |

호스트를 기록하지 않았으므로 **아래 표의 소요 시간은 같은 실행 안의 상대 비교로만 읽어야 합니다.** 다른 세션의 절대 시간과 나란히 놓으면 안 됩니다.

`wal_compression=off`는 WAL 크기를 지표로 쓰기 때문에 압축이 비교를 왜곡하지 않게 하려고 끈 것입니다. 대신 이 글의 모든 배수는 압축이 꺼진 조건에서만 성립합니다. 켜면 full-page image가 압축되는데, 뒤에서 보듯 이 실험에서 FPI가 WAL의 큰 몫을 차지하므로 배수가 전부 달라집니다.

### 측정 순서에 개입한 것

측정마다 `UPDATE` 직전에 `CHECKPOINT`를 실행했습니다. 초고에는 이것을 "full-page image 부담을 같은 조건으로 맞췄다"고 적었는데 사실은 반대입니다. 체크포인트 직후에는 손대는 모든 페이지가 그 체크포인트 이후 첫 변경이 되므로 **전부 full-page image를 씁니다.** 조건을 같게 맞추는 조작이 아니라 **FPI를 최대로 만드는 조작**입니다. 그래서 이 실험의 WAL 수치는 FPI가 가장 많이 실린 상태의 값이고, 운영 중 체크포인트 사이 구간에서는 더 작게 나옵니다.

`pg_current_wal_lsn()`은 테이블별 값이 아니라 **인스턴스 전역 LSN**입니다. autovacuum을 끄지 않았으므로 앞 조건이 남긴 50만 건의 죽은 튜플을 정리하러 뜬 autovacuum과 autoanalyze의 WAL이 뒤 조건의 측정 창에 섞여 들어갔을 수 있습니다. 측정 순서가 인덱스 0 → 3 → 6 → 10이라 **오염 방향이 결론 방향과 같습니다.** 이 세션은 그 몫을 분리하지 못했습니다.

### 커밋된 스크립트로 재현되는 범위

`results/measure.csv`에는 9행이 있는데, 이 수치를 만든 시점의 `scripts/run-experiments.sh`가 정의하는 측정은 7개였습니다. **CSV의 마지막 두 줄인 2차 갱신 측정은 스크립트에 없었습니다.** 스크립트가 끝난 뒤 같은 셸 함수를 손으로 한 번 더 불러 덧붙인 것입니다. 하필 그 두 줄이 블로그 헤드라인이었습니다. 지금은 두 호출을 스크립트에 넣어 두었으므로 재실행하면 아홉 줄이 다 나옵니다. 다만 원래 실행에서 스크립트 종료와 수동 실행 사이의 간격은 기록하지 않았습니다.

## 3. 내부 원리

HOT이 성립하려면 조건 두 개가 **동시에** 맞아야 합니다.

1. **갱신하는 컬럼 중 어느 것도 인덱스에 들어 있지 않을 것.** 하나라도 인덱스 컬럼이면 인덱스가 가리키는 값이 바뀌므로 새 엔트리가 필요하고, HOT은 원천 불가능합니다. fillfactor를 아무리 낮춰도 소용없습니다.
2. **새 행 버전이 원래 행과 같은 페이지에 들어갈 자리가 있을 것.** 자리가 없으면 다른 페이지로 나가고, ctid가 바뀌므로 모든 세컨더리 인덱스에 새 엔트리가 들어갑니다.

두 번째 조건은 "여유 공간이 있느냐"가 아니라 **"그 시점에 그 페이지에 몇 바이트가 남았느냐"**라서 페이지 기하학으로 정확히 계산됩니다.

```
쓸 수 있는 공간 = 8192 - 페이지 헤더 24 - 새 라인 포인터 4 = 8164
fillfactor 100: 8164 / 180 = 45.4  -> 페이지당 45행
fillfactor  70: 8192의 30%인 2457바이트를 비워 두고 멈춘다
                31행 = 5580바이트, 남은 공간 2584 < 176 + 2457 = 2633
                -> 페이지당 31행
HOT 여지      : 남긴 2584 / 180 = 14개, 14 / 31 = 45.16%

t0: 500000 / 45 = 11,112페이지 = 86.8MB + PK 인덱스 11.2MB = 98MB   (실측 98 MB)
u0: 500000 / 31 = 16,130페이지 = 126.0MB + PK 인덱스 11.2MB = 137MB (실측 137 MB)
```

`results/00-sizes.txt`의 t0 98MB, u0 137MB가 이 계산을 그대로 확인해 줍니다. fillfactor 70 페이지가 남겨 둔 2,584바이트는 180바이트짜리 새 버전 **14개**를 받아 주고 그 페이지에 사는 행은 31개이므로, 14 ÷ 31 = **45.16%**입니다. 이것이 뒤에 나오는 HOT 비율 45.2%의 정체입니다.

**페이지 프루닝**은 이 자리를 VACUUM 없이 되찾아 주는 장치입니다. 어떤 페이지에 쓰려는데 자리가 모자라면 PostgreSQL은 먼저 그 페이지를 그 자리에서 정리합니다. HOT 체인 중간의 죽은 버전은 인덱스가 가리키지 않기 때문에 라인 포인터까지 회수할 수 있고, 그래서 VACUUM을 기다리지 않고도 공간이 돌아옵니다. 같은 갱신을 두 번째로 돌릴 때 HOT 비율이 오르는 이유가 이것입니다.

### 인덱스 수는 곱해지지 않고 더해집니다

꽉 찬 페이지에서 인덱스를 0 → 3 → 6 → 10으로 늘리면 WAL이 267 → 364 → 462 → 595MB로 갑니다. **인덱스 하나가 더해질 때마다 32MB에서 34MB 사이가 붙습니다**(0→3에서 인덱스당 32.6MB, 3→6에서 32.4MB, 6→10에서 33.5MB).

비례가 아니라 **고정비 267MB 위에 인덱스마다 일정량이 얹히는 구조**입니다. 비례라면 인덱스 10개는 0개의 10배여야 하는데 실측은 2.2배입니다. 고정비의 정체는 힙 자체를 다시 쓰는 비용입니다. 인덱스가 하나도 없어도 50만 개의 새 행 버전을 쓰고 그만큼 힙 페이지에 FPI가 실립니다.

이 구조는 실무 판단을 바꿉니다. 인덱스가 3개인 테이블에서 하나 더 늘릴 때 예상해야 하는 것은 33% 증가가 아니라 33MB, 곧 이 워크로드에서 9% 증가입니다. 다만 기울기가 일정하다고 확인한 범위는 인덱스 0개에서 10개까지입니다. 그 바깥은 재지 않았습니다.

초고의 표에는 인덱스 3개와 6개가 없었습니다. 0개와 10개만 남기면 "2.2배"라는 배수만 보이고 기울기가 안 보입니다. 기울기는 이 두 줄에서만 보입니다.

### 쿼리 단위 증거와 full-page image

`EXPLAIN (ANALYZE, WAL)`로 1만 행을 갱신한 결과입니다. 꽉 찬 페이지 기준입니다.

```
Update on t10   WAL: records=132851 fpi=1434 bytes=17683522
Update on t0    WAL: records=30017  fpi=224  bytes=5245672
```

초고는 `records`와 `bytes`만 인용하고 `fpi`를 지웠습니다. **WAL 크기를 지표로 쓰면서 FPI를 빼놓으면 안 됩니다.** `wal_compression=off`이므로 FPI 하나는 최대 8,192바이트를 씁니다. 그 상한으로 계산하면 인덱스 10개는 11.2MB로 전체 16.9MB의 **약 66%**, 인덱스 0개는 1.75MB로 전체 5.0MB의 **약 35%**입니다. FPI를 빼고 나머지만 비교하면 5.7MB 대 3.3MB로 **약 1.7배**이고, 원문 바이트로 비교한 3.4배의 절반입니다. `EXPLAIN`이 FPI 바이트를 따로 내주지 않아 이 계산은 8,192바이트 상한을 쓴 추정이고, 그래서 정확한 분리가 아니라 **"배수의 절반쯤은 FPI가 만든 것"이라는 규모 감각까지**가 이 데이터로 말할 수 있는 전부입니다. 앞서 적었듯 측정마다 `CHECKPOINT`를 앞에 둔 것이 이 FPI 비중을 최대로 끌어올렸습니다.

### 경계선

1. **Uber가 옳은 조건.** HOT이 성립하지 않으면(꽉 찬 페이지, 또는 인덱스 컬럼 갱신) 비인덱스 컬럼 하나를 바꿔도 인덱스 수만큼 WAL이 더해집니다. 0개 대비 10개가 2.2배, 인덱스 컬럼을 직접 갱신하면 651MB로 최악입니다. 다만 "인덱스 수에 비례한다"는 아니고, 인덱스당 33MB씩 더해진 결과입니다.
2. **반론이 옳은 조건.** 여유 공간이 있으면 HOT이 돌고 그만큼 인덱스가 갱신되지 않습니다. fillfactor 70의 첫 갱신에서 인덱스 0개와 10개가 같은 45.2%를 보였고, 두 조건 다 꽉 찬 페이지보다 WAL이 작습니다(267 → 210MB, 595 → 419MB).
3. **둘 다 놓친 것.** HOT 비율은 공짜가 아니라 페이지 여유 공간의 함수입니다.

## 5. 해소

Uber처럼 DB를 갈아타는 것은 해소 축에 두지 않았습니다. PostgreSQL 안에서의 처방은 다음과 같고, 전부 위 표의 실측이 근거입니다.

| 처방 | 근거 실측 |
|---|---|
| 갱신이 잦은 테이블은 fillfactor를 낮춰 HOT 여지를 만든다 | 같은 인덱스 10개에서 꽉 찬 페이지 595MB, ff70 첫 갱신 419MB |
| 낮출 값은 감이 아니라 행 크기로 정한다 | 180바이트 행에서 ff70은 페이지당 45행을 31행으로 줄이고 HOT 여지 14개를 만든다 (45.2%) |
| 갱신되는 컬럼에는 인덱스를 걸지 않는다 | 인덱스 컬럼 갱신이 651MB로 최악이고 이때 fillfactor는 무의미하다 |
| 인덱스 하나를 더할 때의 비용은 배수가 아니라 증분으로 잡는다 | 인덱스 0·3·6·10에서 267·364·462·595MB, 인덱스당 32~34MB |
| HOT 비율을 관측한다 (`n_tup_hot_upd / n_tup_upd`) | 이 비율이 떨어지면 위 처방이 무너지고 있다는 신호다 |

초고의 표에는 "HOT이 실패하는 순간 인덱스 수가 그대로 곱해진다"는 줄이 있었습니다. 자기 데이터가 반증하는 문장이었습니다. 곱해졌다면 10개가 0개의 10배여야 하는데 2.2배였습니다.

## 6. 예상과 달랐던 점

### fillfactor 70의 첫 갱신에서 HOT이 45%에 멈췄습니다

여유 공간을 만들었으니 HOT이 거의 다 성립할 것으로 예상했는데, 첫 회차에서는 45.2%였습니다(225,807 / 500,000).

초고는 이것을 "30/70이 딱 그만큼이기 때문"이라고 설명했는데 틀렸습니다. 30/70은 42.86%이고 실측은 45.16%라 2.3포인트가 남습니다. **맞는 설명은 3절의 페이지 기하학입니다.** 정원 45행에 적재 31행이고 남긴 2,584바이트가 새 버전 14개를 받으므로, 14 ÷ 31 = 45.16%로 실측과 소수점 둘째 자리까지 같습니다. 행이 정수 개수로만 들어가서 fillfactor 비율이 그대로 행 수 비율이 되지 않기 때문입니다. 여기에 갱신 도중 페이지 프루닝이 되찾아 준 공간 몫도 섞여 있을 수 있는데 따로 재지 않았습니다.

어느 쪽이든 결론은 같습니다. HOT은 "여유 공간이 있으면 성립"이 아니라 "**그 시점에 남은** 여유 공간만큼 성립"입니다. 대량 일괄 갱신은 여유 공간을 한 번에 소진하므로 HOT의 수혜가 절반에 그칩니다.

### 2차 갱신에서 비율이 뛰었지만, 두 조건을 나란히 놓을 수 없었습니다

같은 갱신을 한 번 더 돌리자 인덱스 10개 테이블의 HOT이 83.5%로 오르고 WAL이 419MB에서 249MB로 줄었습니다. 인덱스 0개 테이블도 방향은 같습니다(210 → 176MB, HOT 45.2% → 69.9%).

문제는 **초고가 이 두 줄을 나란히 놓고 "정상 상태에서 인덱스 10개의 비용은 1.4배"라고 헤드라인으로 뽑았다**는 것입니다. `results/measure.csv`의 누적 카운터를 보면 두 조건의 갱신 이력이 다릅니다.

| 테이블 | 2차 갱신 직전까지 받은 누적 갱신 | 2차 갱신의 HOT |
|---|---|---|
| u0 (인덱스 0) | 50만 건 (1회차) | 69.9% |
| u10 (인덱스 10) | 100만 건 (1회차 + 인덱스 컬럼 갱신) | 83.5% |

u10은 인덱스 걸린 컬럼을 갱신하는 조건에 한 번 더 동원돼서, 2차 갱신 시점에 u0의 두 배인 100만 건의 갱신을 이미 받은 상태였습니다. 그만큼 죽은 버전이 많았고 프루닝이 되찾을 공간도 많았습니다. **HOT 비율이 83.5% 대 69.9%로 다른 이유가 인덱스 수가 아니라 이것입니다.** 인덱스 수만 다른 비교가 아니므로 1.4배를 인덱스 효과로 귀속할 수 없습니다. 이 배수는 내립니다.

인덱스 수만 다른 비교로 성립하는 것은 갱신 이력이 같은 두 쌍뿐입니다. 꽉 찬 페이지의 첫 갱신 2.2배(267 대 595MB, HOT 둘 다 0%), 그리고 ff70 첫 갱신의 2.0배(210 대 419MB, HOT 둘 다 45.2%)입니다.

### 정상 상태에서도 증폭은 남습니다

HOT이 83.5% 돌아도 나머지 16.5%의 non-HOT 갱신이 인덱스 10개를 끌고 갑니다. "HOT이 있으니 인덱스 수는 무관하다"는 반론의 강한 버전은 실측과 다릅니다. 증폭은 사라지는 게 아니라 HOT 비율만큼 희석됩니다. 다만 이 세션은 **정상 상태에서 남는 증폭이 몇 배인지 재지 못했습니다.** 그러려면 두 테이블에 같은 횟수의 갱신을 먹인 뒤 재야 하는데, 위에서 적었듯 그렇게 하지 않았습니다.

## WAL을 레코드와 FPI로 가르고 압축까지 (2026-07-31)

`scripts/exp2-waldump.sh`, 결과는 `results/exp2-waldump.txt` 입니다.
호스트 macOS 26.3.1, Apple M2 Pro 12코어, 32GB. 컨테이너 `--cpus 4 --memory 4g`,
`autovacuum=off`, 50만 행, 조건마다 1회 실행입니다.

### FPI를 바이트로 갈랐습니다

`EXPLAIN` 이 FPI 개수만 주고 바이트를 안 줘서 상한 추정까지만 했습니다.
`pg_waldump --stats` 로 리소스 매니저별 레코드 바이트와 FPI 바이트를 갈랐습니다.
`wal_compression=off`, `fillfactor=100`, 비인덱스 컬럼 갱신입니다.

| 조건 | 리소스 매니저 | 건수 | 레코드 | FPI | FPI 비중 |
|---|---|---|---|---|---|
| 인덱스 0개 | Heap | 1,000,000 | 132.1MB | 86.1MB | 39.4% |
| 인덱스 0개 | Btree | 506,835 | 36.5MB | 9.6MB | 20.9% |
| 인덱스 10개 | Btree | **5,588,889** | **348.0MB** | 19.7MB | 5.4% |
| 인덱스 10개 | Heap | 1,000,000 | 132.1MB | 86.1MB | 39.4% |

**힙 쪽은 두 조건이 완전히 같습니다.** 132.1MB 레코드와 86.1MB FPI입니다. 같은 행을
같은 방식으로 갱신하니 당연합니다. **인덱스가 늘린 것은 전부 Btree 쪽입니다.**
36.5MB에서 348.0MB로, 건수는 50만에서 559만으로 늘었습니다.

인덱스 10개면 갱신 한 건마다 인덱스 항목 열 개를 지우고 열 개를 새로 넣습니다.
559만 건이 그 수(50만 × 약 11)입니다. **인덱스 하나당 대략 31MB씩 붙습니다.**

FPI 비중도 갈립니다. 인덱스 0개 조건은 Heap의 39.4%가 FPI 인데, 인덱스 10개 조건은
Btree가 348MB로 커지면서 전체에서 FPI 비중이 5.4%로 희석됩니다. **인덱스가 많을수록
WAL에서 FPI가 차지하는 몫이 줄어듭니다.** 이것이 다음 절의 압축 효과를 정합니다.

### 정상 상태 비교를 다시 하니 HOT이 같아졌습니다

1차 실행에서 `u10` 을 인덱스 컬럼 갱신에 한 번 더 써서 갱신 이력이 `u0` 의 두 배가
됐고, 그 상태로 2차 갱신을 비교해 HOT이 83.5% 대 69.9%로 갈렸습니다.
인덱스 컬럼 갱신에 별도 테이블 `v10` 을 두고 다시 쟀습니다.

| 조건 | WAL | HOT |
|---|---|---|
| 2차 갱신 인덱스 10개 | 280.8MB | **57.5%** |
| 2차 갱신 인덱스 0개 | 179.3MB | **57.5%** |

**HOT 비율이 같습니다.** 갱신 이력을 맞추니 인덱스 수가 HOT 비율을 바꾸지 않는다는
것이 드러납니다. 이전 표의 83.5% 대 69.9%는 인덱스가 아니라 **갱신을 두 번 한 테이블과
한 번 한 테이블의 차이**였습니다. 이 세션이 "설계 결함"이라고 적어 둔 것이 그대로
확인됐습니다.

### 압축을 켜면 배수가 오히려 커집니다

"`wal_compression=off` 조건에서만 성립한다"고 적었습니다. 켜고 같은 조건을 다시 쟀습니다.

| 조건 | 압축 끔 | 압축 켬 | 줄어든 비율 |
|---|---|---|---|
| 인덱스 0개(ff100) | 266.6MB | 212.2MB | **20.4%** |
| 인덱스 10개(ff100) | 589.3MB | 531.0MB | **9.9%** |
| 인덱스 0개(ff70) | 209.6MB | 154.1MB | **26.5%** |
| 인덱스 10개(ff70) | 392.0MB | 332.5MB | **15.2%** |
| 인덱스 컬럼 갱신(v10) | 598.3MB | 530.9MB | 11.3% |
| 2차 갱신 인덱스 10개 | 280.8MB | 219.6MB | 21.8% |
| 2차 갱신 인덱스 0개 | 179.3MB | 121.6MB | **32.2%** |

**인덱스가 많을수록 압축이 덜 듭니다.** 인덱스 0개는 20.4~32.2% 줄고 인덱스 10개는
9.9~15.2% 줄어듭니다. 압축이 줄이는 것은 FPI 인데, 앞 절에서 본 대로 인덱스가 많으면
FPI 비중이 5.4%로 희석되기 때문입니다.

그러면 배수가 어떻게 되는지가 이 절의 답입니다.

| 조건 | 분모 | 압축 끔 | 압축 켬 |
|---|---|---|---|
| 인덱스 10개(ff100) | 인덱스 0개(ff100) | 2.21배 | **2.50배** |
| 인덱스 10개(ff70) | 인덱스 0개(ff70) | **1.87배** | **2.16배** |
| 인덱스 컬럼 갱신(v10) | 인덱스 0개(ff100) | 2.24배 | **2.50배** |

처음 발행할 때 세 행을 전부 `인덱스 0개(ff100)` 로 나눠 ff70 행이 1.47배와 1.57배로 나왔습니다. **fillfactor와 인덱스 수를 동시에 바꾼 비교라 인덱스 효과로 귀속할 수 없는 값이었습니다.** 6절에서 `u10` 의 1.4배를 정확히 같은 이유로 철회해 놓고 같은 오류를 냈습니다. 분모를 맞춰 고쳤습니다.

**압축을 켜면 배수가 커집니다.** 인덱스가 만드는 WAL이 상대적으로 더 두드러집니다.
"압축을 켜면 이 세션의 배수가 달라진다"는 경고가 맞았고, 방향은 **완화가 아니라
강화**입니다. `wal_compression` 을 켜 둔 운영 환경에서 이 세션의 결론은 약해지지 않고
오히려 세집니다.

`fillfactor=70` 조건에서 인덱스 0개가 압축을 켜면 0.79배에서 0.73배로 내려가는 것도
같은 이유입니다. HOT이 45.2% 라 Btree 쪽이 작고 FPI 비중이 높아 압축이 잘 듭니다.

## 압축 알고리즘 넷과 FPI 분해 (2026-07-31)

`wal_compression` 이 받는 네 값을 같은 워크로드로 돌렸습니다. 앞 절까지는 `on` 하나로만 봤습니다. PostgreSQL 15부터 `wal_compression` 은 `pglz`, `lz4`, `zstd` 를 받습니다. `on` 은 `pglz` 의 별칭입니다. 넷을 같은 워크로드로 돌렸습니다. 50만 행 `UPDATE`, 인덱스 0개, fillfactor 100 조건입니다.

| 방식 | WAL | off 대비 | 소요 | off 대비 |
|---|---|---|---|---|
| `off` | 266.6MB | 기준 | 1.71초 | 기준 |
| `pglz`(=`on`) | 212.2MB | -20.4% | 2.88초 | **+68%** |
| `lz4` | 215.9MB | -19.0% | 1.75초 | **+2%** |
| `zstd` | **198.6MB** | **-25.5%** | 1.99초 | +16% |

**`on` 이 세 방식 중 가장 나쁜 선택입니다.** `pglz` 는 `lz4` 와 압축률이 사실상 같은데(212.2 대 215.9MB, 1.7% 차이) 시간은 훨씬 더 씁니다. `off` 1.71초 대비 `lz4` 는 +2%(1.75초)이고 `pglz` 는 +68%(2.88초)입니다. **두 축 모두에서 `lz4` 에 지배당합니다.**

두 증가분의 비(1.17초 대 0.04초)를 배수로 적었다가 뺐습니다. 분모가 유효숫자 한 자리인 1회 측정값이라 반올림만으로 배수가 크게 흔들립니다. **결론에 배수가 필요하지 않습니다.**

FPI 비중이 가장 큰 조건에서는 격차가 더 벌어집니다.

| 방식 | WAL(2차 갱신, 인덱스 0개) | off 대비 | 소요 | off 대비 |
|---|---|---|---|---|
| `off` | 179.3MB | 기준 | 1.20초 | 기준 |
| `pglz` | 121.6MB | -32.2% | 2.25초 | **+88%** |
| `lz4` | 124.8MB | -30.4% | 1.28초 | **+7%** |
| `zstd` | **106.8MB** | **-40.4%** | 1.66초 | +38% |

**고를 것은 둘입니다.** WAL 대역폭이 병목이면 `zstd`, 쓰기 지연이 병목이면 `lz4` 입니다. `pglz` 를 고를 이유가 이 측정에는 없습니다. 그런데 문서를 보고 `on` 을 켜면 그것이 걸립니다.

### 압축이 무엇을 줄이는지가 분해에 그대로 보입니다

`pg_waldump --stats` 를 리소스 매니저별로 갈랐습니다. 같은 조건의 `off` 와 `pglz` 입니다.

| 방식 | Heap 레코드 | Heap FPI | Btree 레코드 | Btree FPI |
|---|---|---|---|---|
| `off` | 132.1MB | **86.1MB** | 36.5MB | **9.6MB** |
| `pglz` | 132.2MB | **36.5MB** | 36.5MB | **4.9MB** |

**레코드 바이트는 132.1과 132.2MB로 그대로이고 FPI만 58% 줄었습니다.** `wal_compression` 이 전체 페이지 이미지만 압축한다는 문서의 서술이 바이트로 확인됩니다. 인덱스 쪽 FPI도 9.6에서 4.9MB로 같은 비율로 줍니다.

그래서 **압축 효과는 조건마다 다릅니다.** 위 표의 `off 대비 최선` 열(네 조건 다 `zstd`)이 12.7%부터 40.4%까지 벌어지는데, FPI 비중을 보면 이유가 나옵니다.

| 조건 | Heap FPI 비중 | Btree 레코드 | 압축 최대 이득 |
|---|---|---|---|
| 인덱스 0개(ff100) | 39.4% | 36.5MB | 25.5% |
| 인덱스 10개(ff100) | 39.4% | **348.0MB** | **12.7%** |

인덱스가 10개면 Btree 레코드가 348.0MB로 전체의 절반을 넘습니다. **인덱스 갱신 레코드는 압축 대상이 아니므로 그만큼이 통째로 남습니다.** FPI 비중이 5.4%로 떨어지고 압축 이득도 절반이 됩니다.

### 압축을 켜면 인덱스의 대가가 더 커 보입니다

인덱스 0개 대비 인덱스 10개의 WAL 배수입니다.

| 조건 | 분모 | `off` | `pglz` | `lz4` | `zstd` |
|---|---|---|---|---|---|
| 인덱스 10개(ff100) | 인덱스 0개(ff100) | 2.21배 | 2.50배 | 2.48배 | **2.59배** |
| 인덱스 컬럼 갱신(v10) | 인덱스 0개(ff100) | 2.24배 | 2.50배 | 2.49배 | 2.56배 |
| 인덱스 10개(ff70) | 인덱스 0개(ff70) | **1.87배** | 2.16배 | 2.14배 | **2.26배** |
| 2차 갱신 인덱스 10개 | 2차 갱신 인덱스 0개 | **1.57배** | 1.81배 | 1.79배 | **1.90배** |

**분모를 조건마다 맞춰야 합니다.** 처음에는 네 행을 전부 `인덱스 0개(ff100)` 로 나눴고, 그래서 ff70 행이 1.47배로 나왔습니다. 그 값은 fillfactor와 인덱스 수를 **동시에** 바꾼 비교라 인덱스 효과로 귀속할 수 없습니다. 6절에서 `u10` 의 1.4배를 정확히 같은 이유로 철회해 놓고 여기서 같은 오류를 냈습니다. 분모를 맞추면 1.87배입니다.

**압축 방식을 무엇으로 고르든 배수는 커집니다.** 네 행 전부에서 `off` < `pglz` ≈ `lz4` < `zstd` 입니다. 인덱스가 없는 쪽은 FPI 비중이 커서 많이 줄고, 인덱스가 많은 쪽은 압축 안 되는 Btree 레코드가 남기 때문입니다.

이건 인덱스가 더 나빠진 것이 아니라 분모가 더 줄어든 것입니다. **압축 설정이 다른 두 서버의 배수를 나란히 놓으면 안 됩니다.** 절대 바이트로 비교해야 합니다.

## 못 한 것

- **압축 넷은 각각 1회 실행입니다.** 소요 시간은 같은 호스트에서 이어 돌린 값이라 회차 폭이 없습니다. 시간 차이가 2%인 조건은 방향만 읽어야 합니다.
- **FPI를 레코드 종류까지 갈라 보지는 않았습니다.** 위 절은 리소스 매니저 단위(Heap·Btree)까지입니다. `--stats=record` 로 레코드 종류별로 더 쪼개면 HOT_UPDATE와 일반 UPDATE의 몫을 가를 수 있는데 하지 않았습니다.
- **첫 실행분의 오염은 그대로 남습니다.** 위 절은 `autovacuum=off` 로 다시 잰 값이고, 본문 앞쪽 표의 수치는 autovacuum이 켜진 채로 잰 것입니다. 두 표를 섞어 읽으면 안 됩니다.
- **1차 갱신과 2차 갱신 사이의 시간을 통제하지 않았습니다.** 위 절에서 `v10` 을 분리해 갱신 이력은 맞췄지만, 두 갱신 사이에 페이지 프루닝이 얼마나 진행됐는지는 재지 않았습니다.
- **첫 실행분의 호스트는 여전히 기록이 없습니다.** 위 절만 사양과 자원 한도를 남겼습니다.
- **복제 증폭은 재지 않았습니다.** Uber 주장의 후반부는 스탠바이 구성이 필요해 범위에서 뺐습니다.
- **MySQL 대조는 하지 않았습니다.** binlog(논리)와 WAL(물리)이라는 서로 다른 것을 비교하게 됩니다.
- **행 크기와 인덱스 카디널리티를 한 가지로 고정했습니다.** 인덱스 컬럼이 `g%97`부터 `g%53`까지라 서로 다른 값이 53개에서 97개뿐이고 btree 중복 제거가 강하게 걸립니다. "인덱스당 33MB"를 카디널리티 높은 인덱스에 그대로 옮길 수 없습니다.
