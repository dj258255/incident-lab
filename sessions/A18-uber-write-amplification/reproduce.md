# A18 재현 기록

## 환경

| 항목 | 값 |
|---|---|
| PostgreSQL | 17.5 (컨테이너), shared_buffers 1GB, wal_compression=off |
| autovacuum | 끄지 않았습니다. 기본값 그대로 켜져 있었습니다 |
| 컨테이너 자원 한도 | 없습니다. compose.yml에 cpus도 mem_limit도 두지 않았습니다 |
| 호스트 사양 | **기록하지 않았습니다.** 어느 장비에서 돌렸는지 확인되지 않습니다 |
| 데이터 | 동일 스키마 테이블 6개 x 50만 행 (인덱스 0·3·6·10 x fillfactor 100·70) |
| 행 크기 | 튜플 176바이트 + 라인 포인터 4바이트 = 페이지에서 약 180바이트 |
| 일시 | 2026-07-29 |

호스트를 기록하지 않았으므로 **아래 소요 시간은 같은 실행 안의 상대 비교로만 유효합니다.**
다른 세션의 절대 시간과 비교하지 마십시오.

### 행 크기 계산 (약 180바이트)

DDL은 `id BIGINT`, `val INT`, `c1`~`c10 INT`, `pad TEXT`(96바이트)입니다.

```
힙 튜플 헤더 t_hoff        24 바이트 (NULL이 하나도 없어 널 비트맵 없음)
id      BIGINT              8
val     INT                 4
c1..c10 INT x 10           40
pad     TEXT               97 (1바이트 짧은 varlena 헤더 + 96)
                        -----
                          173 -> MAXALIGN 176
라인 포인터                 4
                        -----
페이지에서 한 행이 쓰는 자리 180 바이트
```

`results/00-sizes.txt`가 이 계산을 확인해 줍니다.

```
쓸 수 있는 공간 = 8192 - 페이지 헤더 24 - 새 라인 포인터 4 = 8164
fillfactor 100: 8164 / 180 = 45.4  -> 페이지당 45행
                (45행이 8100바이트, 남은 64에 46번째 튜플 176이 안 들어간다)
fillfactor  70: 8192의 30%인 2457바이트를 비워 두고 멈춘다
                31행 = 5580바이트, 남은 공간 2584 < 176 + 2457 = 2633
                -> 페이지당 31행
HOT 여지      : 남긴 2584 / 180 = 14개, 14 / 31 = 45.16%
                (실측 225,807 / 500,000 = 45.16%)

t0: 500000 / 45 = 11,112페이지 = 86.8MB + PK 인덱스 11.2MB = 98MB   (실측 98 MB)
u0: 500000 / 31 = 16,130페이지 = 126.0MB + PK 인덱스 11.2MB = 137MB (실측 137 MB)
```

## 실행

```console
$ docker compose up -d
$ ./scripts/run-experiments.sh     # 적재 + 9개 변형 측정, 약 5분
$ python3 scripts/report.py
```

측정 원문은 `results/measure.csv` (변형별 WAL 바이트, 소요 초, pg_stat 전후값).

### 재현 절차의 정정

기록된 `results/measure.csv`는 9행인데, **그 수치를 만든 시점의 `run-experiments.sh`는
측정을 7개만 정의했습니다.** 마지막 두 줄(`ff70-idx10-2ndpass`, `ff70-idx0-2ndpass`)은
스크립트가 끝난 뒤 같은 셸 함수를 손으로 한 번 더 불러 CSV에 덧붙인 것입니다.

```bash
measure ff70-idx10-2ndpass u10 "val = val + 1"
measure ff70-idx0-2ndpass  u0  "val = val + 1"
```

하필 이 두 줄이 블로그 헤드라인(정상 상태 1.4배)이었습니다. 커밋된 스크립트로
재현되지 않는 수치가 헤드라인에 올라가 있었다는 뜻입니다. 지금은 두 호출을
스크립트에 넣어 두었으므로 재실행하면 아홉 줄이 다 나옵니다.

**원래 실행에서 스크립트 종료와 수동 실행 사이에 얼마나 시간이 지났는지,
그 사이 autovacuum이 얼마나 돌았는지는 기록하지 않았습니다.**

## 측정 방법

변형마다 다음 순서로 잽니다.

```sql
CHECKPOINT;                              -- 아래 주의 참고
SELECT pg_current_wal_lsn();             -- lsn0
UPDATE <table> SET <col> = <col> + 1;    -- 50만 행 전체
SELECT pg_current_wal_lsn();             -- lsn1
SELECT pg_wal_lsn_diff(lsn1, lsn0);      -- WAL 증가량
-- HOT 비율은 pg_stat_user_tables.n_tup_hot_upd 전후 차이
```

### 이 방법의 한계 두 가지

**1. 앞의 CHECKPOINT는 FPI를 같게 맞추는 것이 아니라 최대로 만듭니다.**
초고에는 "full-page image 부담을 같은 조건으로 맞췄다"고 적었는데 반대입니다.
체크포인트 직후에는 손대는 모든 페이지가 그 체크포인트 이후 첫 변경이 되므로
전부 full-page image를 씁니다. 여기 적힌 WAL은 FPI가 가장 무겁게 실린 값이고,
운영 중 체크포인트 사이 구간에서는 더 작게 나옵니다.

**2. `pg_current_wal_lsn()`은 인스턴스 전역입니다.**
autovacuum을 끄지 않았으므로, 앞 조건이 남긴 50만 건의 죽은 튜플을 정리하러 뜬
autovacuum과 autoanalyze의 WAL이 뒤 조건의 측정 창에 섞여 들어갔을 수 있습니다.
측정 순서가 인덱스 0 → 3 → 6 → 10이라 **오염 방향이 결론 방향과 같습니다.**
이 몫은 분리하지 못했습니다.

## 결과 (results/measure.csv 집계)

```console
인덱스 0 · 꽉 찬 페이지                     267      1.6      0.0%    첫 갱신
인덱스 3 · 꽉 찬 페이지                     364      3.5      0.0%    첫 갱신
인덱스 6 · 꽉 찬 페이지                     462      5.3      0.0%    첫 갱신
인덱스 10 · 꽉 찬 페이지                    595      8.5      0.0%    첫 갱신
인덱스 0 · 여유 공간(ff70)                  210      1.2     45.2%    첫 갱신
인덱스 10 · 여유 공간(ff70)                 419      5.8     45.2%    첫 갱신
인덱스 10 · ff70 · 인덱스 컬럼 갱신           651     10.3      0.0%    2회차 (u10)
인덱스 10 · ff70 · 2차 갱신(정상 상태)        249      2.0     83.5%    3회차 (u10, 누적 100만 건)
인덱스 0 · ff70 · 2차 갱신(정상 상태)         176      1.0     69.9%    2회차 (u0, 누적 50만 건)
```

### 인덱스 수는 곱해지지 않고 더해집니다

꽉 찬 페이지의 네 조건이 267 → 364 → 462 → 595MB입니다. 인덱스 하나마다
32MB에서 34MB 사이가 더해집니다(0→3에서 인덱스당 32.6MB, 3→6에서 32.4MB,
6→10에서 33.5MB). **비례가 아니라 고정비 267MB 위에 인덱스마다 일정량이
얹히는 구조입니다.** 비례라면 10개가 0개의 10배여야 하는데 실측은 2.2배입니다.

### 정상 상태 1.4배는 철회합니다

마지막 두 줄을 나란히 놓고 "정상 상태에서 인덱스 10개는 1.4배"라고 쓸 수 없습니다.
`measure.csv`의 누적 카운터가 두 조건의 갱신 이력이 다르다고 말합니다.

```
u10  ff70-idx10           upd0=0       -> upd1=500000     hot 0      -> 225807
u10  ff70-idx10-indexedcol upd0=500000 -> upd1=1000000    hot 225807 -> 225807
u10  ff70-idx10-2ndpass   upd0=1000000 -> upd1=1500000    hot 225807 -> 643357   (HOT 83.5%)

u0   ff70-idx0            upd0=0       -> upd1=500000     hot 0      -> 225807
u0   ff70-idx0-2ndpass    upd0=500000  -> upd1=1000000    hot 225807 -> 575443   (HOT 69.9%)
```

u10은 인덱스 컬럼 갱신 조건에 한 번 더 동원돼서 2차 갱신 시점에 u0의 두 배인
100만 건을 이미 받은 상태였습니다. 죽은 버전이 그만큼 많아 페이지 프루닝이
되찾을 공간도 많았고, 그래서 HOT 비율이 83.5% 대 69.9%로 갈렸습니다.
**인덱스 수만 다른 비교가 아니므로 1.4배를 인덱스 효과로 귀속할 수 없습니다.**

인덱스 수만 다른 비교로 성립하는 것은 갱신 이력이 같은 두 쌍뿐입니다.

- 꽉 찬 페이지 첫 갱신: 267 대 595MB = 2.2배 (HOT 둘 다 0%)
- ff70 첫 갱신: 210 대 419MB = 2.0배 (HOT 둘 다 45.2%)

### HOT 45.2%의 정체

30/70(42.86%)이 아닙니다. 페이지 기하학입니다.

```
꽉 찬 페이지 정원 45행, ff70 적재 31행
31행을 넣고 남긴 공간 2584바이트 / 행 슬롯 180바이트 = 새 버전 14개
14 / 31 = 45.16%
실측 225,807 / 500,000 = 45.16%
```

행이 정수 개수로만 들어가기 때문에 fillfactor 비율이 그대로 행 수 비율이 되지
않습니다. 여기에 갱신 도중 페이지 프루닝이 되찾아 준 공간 몫도 섞여 있을 수
있는데 따로 재지 않았습니다.

## 쿼리 단위 증거 (results/02-explain-wal.txt)

```console
-- 인덱스 10개(ff100), 1만 행 갱신
Update on t10  (actual time=192.693..192.693)
  WAL: records=132851 fpi=1434 bytes=17683522

-- 인덱스 0개(ff100), 같은 갱신
Update on t0   (actual time=23.195..23.196)
  WAL: records=30017 fpi=224 bytes=5245672
```

**`fpi`를 빼고 읽으면 안 됩니다.** `wal_compression=off`이므로 FPI 하나는 페이지에서
빈 구멍을 뺀 나머지, 최대 8,192바이트를 씁니다. 그 상한으로 계산하면

```
t10  1434 x 8192 = 11.2MB / 전체 16.9MB = 약 66%가 FPI
t0    224 x 8192 =  1.75MB / 전체  5.0MB = 약 35%가 FPI
FPI를 뺀 나머지  5.7MB 대 3.3MB = 약 1.7배 (원문 바이트 비교는 3.4배)
```

EXPLAIN이 FPI 바이트를 따로 내주지 않아 이것은 상한을 쓴 추정입니다.
정확히 가르려면 `pg_waldump`로 레코드 종류별 바이트를 집계해야 하는데 하지 않았습니다.

## 못 한 것 / 다시 잴 때 고칠 것

- `autovacuum=off`로 띄우고 조건마다 컨테이너를 새로 만들 것.
- 인덱스 컬럼 갱신에 별도 테이블을 써서 u10을 오염시키지 말 것. 그래야 정상 상태에서
  인덱스 수만 다른 비교가 성립한다.
- `pg_waldump`로 힙·인덱스·FPI 바이트를 분리할 것.
- 호스트 사양(`uname -srm`, `nproc`, `free -g`)과 컨테이너 자원 한도를 기록할 것.
- 인덱스 컬럼이 `g%97`부터 `g%53`까지라 서로 다른 값이 53~97개뿐이다. btree 중복 제거가
  강하게 걸리는 조건이므로 "인덱스당 33MB"를 카디널리티 높은 인덱스에 옮길 수 없다.
