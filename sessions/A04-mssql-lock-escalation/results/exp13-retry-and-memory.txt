# 실험 13. 재시도 간격과 메모리 압박
# optimized locking: ABSENT

==================================================================
## 13-1. 승격은 트랜잭션이 아니라 문장 단위로 판정된다
==================================================================

  재시도 간격을 재려고 트랜잭션 하나에서 300행씩 나눠 갱신하며 락을 쌓았습니다.
  **1만 8천 개를 쌓았는데 승격이 안 났습니다.** 실패한 설계인 줄 알았는데
  그 자체가 답이었습니다.

  쌓은 방법            총 락 수    테이블 X
  300행씩 60문장       18050          0
  18000행을 한 문장으로 1              1

  **같은 락 수인데 한쪽만 승격합니다.** 승격은 트랜잭션이 든 락이 아니라
  **문장 하나가 잡은 락**으로 판정되기 때문입니다. 문장을 작게 나누면
  트랜잭션이 락을 아무리 많이 들고 있어도 각 문장은 임계값에 안 닿습니다.

  **이것이 배치 분할이 통하는 진짜 이유입니다.** 실험 3에서 4,000행씩 나눠
  승격이 0회가 된 것을 "배치가 작아서"라고만 적었는데, 정확히는 **판정 단위가
  문장이라서**입니다. 배치마다 커밋하지 않고 한 트랜잭션에 묶어 두어도
  승격은 안 납니다. 다만 락은 그대로 쌓이므로 커밋해서 놓아 주는 것이 맞습니다.

==================================================================
## 13-1-2. 승격이 실패한 뒤 언제 다시 시도하는가
==================================================================

  이제 한 문장으로 갑니다. 옆 세션이 테이블 락을 막고 있는 동안 큰 갱신을
  돌리고, 옆 세션이 물러난 뒤 승격까지 락을 얼마나 더 잡는지 봅니다.

  **승격 시점이나 옆 세션이 사라진 시점을 못 잡았습니다.**
  갱신이 표본 간격보다 빨리 끝났거나 승격이 이미 일어난 뒤였습니다.
  실패한 시도는 이벤트를 안 남기므로 **이 각도로도 간격을 못 좁혔습니다.**

## 13-2. DISABLE 인데도 메모리 압박으로 승격하는가
==================================================================

  실험 3의 3번은 DISABLE 로 20만 락을 들고도 승격하지 않았습니다. 그것이
  DISABLE 때문인지 메모리에 여유가 있어서인지 안 갈랐습니다.
  락을 훨씬 더 쌓아 봅니다. 2000000행 표를 통째로 갱신합니다.

  갱신 행   테이블 X    총 락 수    락 메모리  승격 이벤트
  200000       0              200545         76MB           0건
  600000       0              1632           76MB           0건
  1200000      0              3262           76MB           0건
  2000000      0              5436           76MB           0건

  가장 많이 쌓은 락       200545개 (200000행)
  그때 락 매니저 메모리 76MB
  메모리 압박 승격        없음

  행 수별 락                 200000행 200545락; 600000행 1632락; 1200000행 3262락; 2000000행 5436락

  **행을 늘렸는데 락이 오히려 줄었습니다.** 락을 더 쌓으려던 시도가 반대로
  갔습니다. 실험 4에서 본 것이 여기서 되돌아왔습니다. 갱신 규모가 커지면
  엔진이 처음부터 **행 락 대신 페이지 락**을 고르고, 페이지 하나가 행 수백 개를
  덮으므로 락 개수가 자릿수로 줄어듭니다.

  **그래서 이 방향으로는 락 메모리를 못 채웁니다.** 행을 아무리 늘려도 엔진이
  알아서 굵은 단위로 잡아 버립니다. 압박을 만들려면 페이지 락으로 못 가게
  막으면서(힌트나 좁은 조건으로) 행 락을 강제해야 하는데 그것은 안 했습니다.

  **200545개를 들고도 승격이 안 났습니다.** 실험 3의 20만과 같은 규모입니다.
  이 컨테이너(6g)에서 락 매니저는 76MB 를 쓰고 있고, 메모리 압박에
  의한 승격 조건에 안 닿았습니다.

  그러면 실험 3의 "DISABLE 이면 승격이 안 난다"는 **이 규모까지는 맞습니다.**
  다만 이것이 "DISABLE 이면 절대 안 난다"를 뜻하지는 않습니다. 문서는 메모리
  압박에서는 예외라고 적고, 이 랩은 그 압박을 못 만들었습니다.
  **DISABLE 을 켜 두고 락을 무한정 쌓아도 된다고 읽으면 안 됩니다.**
