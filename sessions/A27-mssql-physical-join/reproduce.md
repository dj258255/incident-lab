## 4. exp4-stale-stats

```console
$ ./scripts/exp4-stale-stats.sh
# 실험 4. 통계가 낡으면 연산자를 잘못 고른다

  첫 설계가 틀렸습니다. 행을 100만으로 늘리고 통계를 안 갱신했는데
  연산자가 안 바뀌었습니다. 계획을 열어 보니 이유가 둘이었습니다.

    TableCardinality 가 이미 맞았습니다. **행 수 메타데이터는 통계와 별개로
    항상 최신**이고, 낡는 것은 히스토그램(값의 분포)입니다.
    그리고 쿼리가 집계라 조인 앞에서 미리 줄어들었습니다.

  그래서 **히스토그램이 못 보는 값**을 만듭니다. 통계를 뜬 뒤에 들어온
  새 값은 히스토그램에 없으므로 옵티마이저가 거의 없다고 추정합니다.
  배치가 새 batch_id 로 적재할 때 그대로 나는 모양입니다.

==================================================================
## 히스토그램에 없는 값이 들어오면
==================================================================

  상태                     연산자      추정행수 실제행수 논리읽기  CPU(ms)
  A 통계를 안 갱신     Hash Match          1224.74       500000       1623      239
  B 통계만 갱신         Hash Match           500000       500000       1623       48

  A 와 B 는 **같은 데이터, 같은 쿼리, 같은 인덱스**입니다.
  바뀐 것은 통계 하나뿐입니다.

==================================================================
## 정리
==================================================================

  **추정은 크게 어긋나는데 연산자는 안 바뀌었습니다.**

  통계를 뜬 뒤에 들어온 값은 히스토그램에 없습니다. 그래서 추정이 실제의
  1/408 로 떨어집니다. 그런데도 옵티마이저는 Hash Match 를 유지했습니다.

  SQL Server 2022 의 기본 카디널리티 추정기가 히스토그램 밖 값을 0 으로
  보지 않고 밀도 벡터로 1,224 를 잡아 주기 때문입니다. 연산자가 뒤집히려면
  추정이 **1행 수준**까지 떨어져야 하는데 그 정도로는 안 틀립니다.

  "통계가 낡으면 계획이 뒤집힌다"는 흔한 설명인데, **이 규모와 이 엔진에서는
  그렇게까지 안 갔습니다.** 대신 추정이 408배 어긋난 채로 돕니다. 메모리 부여와
  병렬 판단이 그 추정을 근거로 하므로 위험은 다른 자리에 남습니다.
```
