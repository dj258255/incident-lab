# A27 옵티마이저가 조인 연산자를 고르는 기준을 재봤다

MSSQL 물리 조인 / SQL Server 2022 (RTM-CU26) 16.0.4265 / 근거 등급 **E2**

> **이 세션이 필요한 상황.** 개발자가 가져온 쿼리를 보고 "이거 나가도 됩니까"를
> 판단해야 할 때. 조인 하나에 옵티마이저가 고를 수 있는 물리 연산자는 셋뿐이고,
> 무엇이 골라졌고 왜 그것인지를 알아야 그 판단이 섭니다.

## 결론부터

| 지금 알면 되는 것 | 근거 |
|---|---|
| **조인 키에 인덱스가 있으면 Merge 가 메모리를 0 쓴다.** 이미 정렬돼 있어 정렬 연산자가 안 붙는다 | 인덱스 있음 0KB / 없음 3,968KB ([근거](#3-메모리-요구량은-조건에-따라-뒤집힌다)) |
| **`OPTION (MERGE JOIN)` 을 무심코 걸면 메모리 요구가 17배가 될 수 있다.** 논리 읽기는 같은데 | Hash 4,208KB 대 Merge 69,840KB ([근거](#4-merge-강제가-메모리를-17배-요구하는-자리)) |
| **인덱스 하나가 연산자 선택을 바꾼다.** 같은 데이터에서 논리 읽기가 8 대 3,119 | ([근거](#2-인덱스-하나가-연산자를-바꾼다)) |
| **옵티마이저가 논리 읽기 기준 최적을 안 고르는 구간이 있다** | 5~10%에서 Nested Loops 3,317, Merge/Hash 3,119 ([근거](#5-옵티마이저가-최적을-안-고르는-구간)) |
| **통계가 408배 어긋나도 이 규모에서는 연산자가 안 뒤집혔다** | ([근거](#6-통계가-낡으면-연산자가-뒤집히는가)) |

## 재현

| 항목 | 값 |
|---|---|
| 호스트 | Darwin 25.3.0 arm64, 12코어, 32GiB |
| 컨테이너 | `mcr.microsoft.com/mssql/server:2022-latest`, Developer, `cpus: 4`, `mem_limit: 6g` |
| 주문 | 100만 행 (`orders` 는 `grade_id` 에 인덱스 + `amount` 포함, `orders_noidx` 는 같은 내용에 그 인덱스만 없음) |
| 등급 | 1,000행, PK |
| 조인 | `orders.grade_id = grade.grade_id` |

**시간 수치는 판정 보조로만 씁니다.** ARM 에뮬레이션이라 절대 시간이 이 호스트의 값이
아닙니다. 기준은 **논리 읽기**와 **계획에 적힌 메모리 요구량**입니다.

메모리 값은 계획의 `SerialDesiredMemory` 이고 **옵티마이저가 요구한 값**입니다.
실행 중 실제 부여량이 아닙니다. 쿼리가 짧아 `dm_exec_query_memory_grants` 에는
안 잡혀서 그렇게 했고, 표에도 그렇게 적었습니다.

## 1. 셋을 강제하면 무엇이 달라지는가

조인에 고를 수 있는 물리 연산자는 셋뿐입니다.

| 연산자 | 방식 | 맞는 자리 |
|---|---|---|
| Nested Loops | 바깥 행마다 안쪽을 찾는다 | 바깥이 작을 때 |
| Merge Join | 양쪽을 정렬해 놓고 한 번씩 훑는다 | 양쪽이 이미 정렬돼 있을 때 |
| Hash Match | 한쪽으로 해시 표를 만들고 다른 쪽을 던진다 | 둘 다 크고 정렬이 없을 때 |

```
$ ./scripts/exp1-three-operators.sh

  [orders] 등급 1000개 (주문 100만행 전부)
  조건            실제 연산자   논리읽기
  옵티마이저 선택  Merge Join       2,743
  LOOP 강제       Nested Loops     4,737
  MERGE 강제      Merge Join       2,743
  HASH 강제       Hash Match       2,743
```

**Hash 가 한 번도 안 골라졌고 논리 읽기도 Merge 와 같습니다.** 여기서 멈추고
"Hash 는 별로다"라고 적으면 틀립니다. 조인 키에 양쪽 다 인덱스가 있어서
**Merge 가 정렬 비용을 안 내는 조건**만 만들어 놓았기 때문입니다.

## 2. 인덱스 하나가 연산자를 바꾼다

같은 데이터로 인덱스만 없앤 표를 하나 더 만들어 견줬습니다.

```
$ ./scripts/exp2-when-each-wins.sh

                     A: 인덱스 있음            B: 인덱스 없음
  등급 1개 (0.1%)     Nested Loops        8     Nested Loops   3,119
  등급 100개 (10%)    Merge Join        279     Nested Loops   3,317
  등급 1000개 (100%)  Merge Join      2,743     Hash Match     3,172
```

**같은 데이터인데 0.1% 구간에서 8 대 3,119 입니다.** 그리고 100% 구간에서만
옵티마이저가 Hash 를 고릅니다. 정렬이 없으면 Merge 가 정렬 비용을 내야 하므로
그때부터 Hash 가 이깁니다.

## 3. 메모리 요구량은 조건에 따라 뒤집힌다

```
$ ./scripts/exp3-grant-and-misjudge.sh

  [orders] 인덱스 있음
  LOOP 강제   Nested Loops       0 KB
  MERGE 강제  Merge Join         0 KB
  HASH 강제   Hash Match     1,344 KB

  [orders_noidx] 인덱스 없음
  LOOP 강제   Nested Loops   3,296 KB
  MERGE 강제  Merge Join     3,968 KB
  HASH 강제   Hash Match     4,640 KB
```

**Nested Loops 는 원래 메모리를 안 씁니다.** 바깥 행마다 안쪽을 찾을 뿐이라 중간
자료구조가 없습니다. 인덱스 없는 표에서 3,296KB 가 잡힌 것은 조인 자체가 아니라
그 앞에 붙은 정렬 때문입니다.

**Merge 가 0KB 인 것이 이 절의 요점입니다.** 조인 키에 인덱스가 있으면 이미 정렬돼
있으므로 정렬 연산자가 안 붙습니다. 인덱스를 빼면 3,968KB 를 요구합니다.
같은 연산자가 조건에 따라 0 과 3,968 사이를 오갑니다.

## 4. Merge 강제가 메모리를 17배 요구하는 자리

```
  [orders_noidx] 등급 200개 (전체의 20%)
  조건        연산자        요구메모리    논리읽기
  옵티마이저   Hash Match     4,208 KB       3,119
  MERGE 강제  Merge Join    69,840 KB       3,119
  HASH 강제   Hash Match     4,208 KB       3,119
```

**논리 읽기는 셋이 같은데 메모리 요구가 17배입니다.** 정렬 연산자가 20만 행을
들고 있어야 하기 때문입니다.

힌트를 걸 때 보통 논리 읽기나 실행 시간만 봅니다. 그러면 이 차이가 안 보입니다.
운영에서 메모리 부여 대기(`RESOURCE_SEMAPHORE`)를 만드는 쪽은 이 값입니다.
**"읽기가 같으니 어느 쪽이든 상관없다"가 틀리는 자리입니다.**

## 5. 옵티마이저가 최적을 안 고르는 구간

인덱스 없는 표에서 선택도를 좁혀 봤습니다.

```
  [orders_noidx]     옵티마이저 선택        Merge 강제   Hash 강제
  등급 50개 (5%)     Nested Loops  3,217        3,119       3,119
  등급 100개 (10%)   Nested Loops  3,317        3,119       3,119
  등급 200개 (20%)   Hash Match    3,119        3,119       3,119
  등급 400개 (40%)   Hash Match    3,121        3,121       3,121
```

**5~10% 구간에서 옵티마이저가 논리 읽기 기준 최적이 아닌 것을 고릅니다.**
추정 행수는 정확합니다(50 → 실제 50,000, 100 → 실제 100,000 으로 맞음).

추정이 맞는데도 이렇게 되는 이유는 옵티마이저가 **논리 읽기가 아니라 비용 모델**로
고르기 때문입니다. 그 모델은 CPU·메모리·I/O 를 섞은 값이라 논리 읽기 하나로는
안 갈립니다. **"추정만 맞으면 최적이 나온다"가 틀립니다.**

이 차이는 3,317 대 3,119 로 6% 입니다. 실무에서 이걸 뒤집겠다고 힌트를 걸면
4절에서 본 메모리 대가를 대신 내게 됩니다.

## 6. 통계가 낡으면 연산자가 뒤집히는가

여기서 예상이 두 번 빗나갔습니다.

**첫 설계가 틀렸습니다.** 표에 행을 1,000에서 100만으로 늘리고 통계를 안 갱신했는데
연산자가 안 바뀌었습니다. 계획을 열어 보니 이유가 둘이었습니다.

- `TableCardinality="1e+06"` 이 이미 맞습니다. **행 수 메타데이터는 통계와 별개로 항상
  최신**이고, 낡는 것은 히스토그램(값의 분포)입니다
- 쿼리가 집계라 조인 앞에서 `Stream Aggregate` 가 1,000행으로 줄여 버렸습니다

그래서 **히스토그램이 못 보는 값**으로 다시 짰습니다. 통계를 뜬 뒤에 새 `batch_id` 로
50만 행을 넣습니다.

```
$ ./scripts/exp4-stale-stats.sh

  상태             연산자        추정행수    실제행수   논리읽기
  A 통계 안 갱신   Hash Match    1,224.74     500,000      1,623
  B 통계만 갱신    Hash Match     500,000     500,000      1,623
```

**추정이 408배 어긋나는데 연산자는 안 바뀌었습니다.**

SQL Server 2022 의 기본 카디널리티 추정기가 히스토그램 밖 값을 0 으로 보지 않고
밀도 벡터로 1,224 를 잡아 주기 때문입니다. 연산자가 뒤집히려면 추정이 **1행 수준**까지
떨어져야 하는데 그 정도로는 안 틀립니다.

**"통계가 낡으면 계획이 뒤집힌다"는 흔한 설명인데 이 규모와 이 엔진에서는 그렇게까지
안 갔습니다.** 대신 추정이 408배 어긋난 채로 돕니다. 메모리 부여와 병렬 판단이 그
추정을 근거로 하므로 위험은 다른 자리에 남습니다.

## 표준 처방

1. **연산자를 힌트로 강제하기 전에 메모리 요구량을 본다.** 논리 읽기가 같아도
   `OPTION (MERGE JOIN)` 이 17배를 요구할 수 있다. 계획의 `SerialDesiredMemory` 를 본다.
2. **조인 키에 인덱스가 있으면 Merge 가 메모리를 안 쓴다.** 인덱스를 지우기 전에
   그 인덱스가 정렬을 대신하고 있는지 확인한다.
3. **Nested Loops 가 골라졌는데 바깥이 크면 의심한다.** 이 랩에서 인덱스 없는 표의
   0.1% 구간이 3,119 였다. 바깥 크기를 추정이 아니라 실제로 센다.
4. **6% 차이를 힌트로 뒤집지 않는다.** 옵티마이저가 최적을 안 골라도 그 차이가
   작으면 그대로 둔다. 힌트는 계획을 고정시키므로 데이터가 바뀌면 같이 안 바뀐다.
5. **통계 갱신은 계획을 뒤집으려고 하는 게 아니다.** 이 랩에서는 안 뒤집혔다.
   추정을 맞추려고 하는 것이고, 그 추정이 메모리 부여와 병렬 판단의 근거가 된다.

## 예상과 달랐던 점

### Hash 가 이길 조건을 안 만들어 놓고 잴 뻔했습니다

실험 1은 조인 키에 양쪽 다 인덱스가 있어 **Merge 가 정렬 비용을 안 내는 판**이었습니다.
그래서 Hash 가 한 번도 안 골라졌고 논리 읽기도 Merge 와 같았습니다. 여기서 멈췄으면
"Hash 는 안 좋다"는 틀린 결론이 표에 들어갔을 것입니다. 조건을 나누자 100% 구간에서
Hash 가 골라졌습니다.

### 통계가 낡아도 연산자가 안 바뀌었습니다

"통계가 낡으면 계획이 뒤집힌다"를 재려고 두 번 설계했는데 두 번 다 안 뒤집혔습니다.
첫 번째는 제 설계가 틀렸고(행 수 메타데이터는 안 낡음), 두 번째는 설계가 맞았는데
**엔진이 그 정도로는 안 속았습니다.** 못 만든 것이 아니라 안 일어나는 것이었습니다.

### 자기 코드 버그가 결과를 통째로 가렸습니다

실험 3에서 메모리와 추정 행수 칸이 전부 비어 나왔습니다. 원인은 이 한 줄입니다.

```bash
local op="${p%%|*}" rest="${p#*|}" grant="${rest%%|*}" est="${rest##*|}"
```

**`local` 은 인자를 전부 먼저 확장합니다.** `grant` 를 만들 때 `rest` 가 아직 비어
있어서 빈 값이 들어갔습니다. 나눠 쓰자 값이 나왔습니다. 처음에는 SQL 쪽을 의심해서
계획 XML 파싱을 두 번 고쳤는데 거기는 멀쩡했습니다.

### 3중 CROSS JOIN 이 계획을 못 세우고 멈췄습니다

100만 행을 만들려고 `sys.all_objects` 를 세 번 교차했는데(2,641³ = 184억) `TOP` 이
있어도 11분 넘게 안 끝났습니다. 숫자 표를 먼저 만들고 거기서 뽑자 바로 끝났습니다.

## 못 한 것

- **연산자가 실제로 뒤집히는 조건을 못 만들었습니다.** 추정을 1행 수준까지 떨어뜨려야
  하는데 기본 CE 에서는 그렇게 안 됩니다. 레거시 CE(추적 플래그 9481)로 바꾸면 나올 수
  있지만, 그것은 이 엔진의 기본 동작이 아니라 안 했습니다.
- **실제 메모리 부여량을 못 쟀습니다.** 계획의 요구량만 봤습니다. 쿼리가 짧아
  `dm_exec_query_memory_grants` 에 안 잡혔고, 부여 대기를 만들려면 큰 정렬을 여럿
  동시에 돌려야 하는데 이 컨테이너 규모에서는 부여가 다 났습니다(A26 과 같은 한계).
- **병렬 계획을 안 봤습니다.** `cpus: 4` 환경에서 이 규모는 병렬로 안 갔습니다.
  병렬이 붙으면 연산자 선택과 메모리 요구가 달라지는데 그 구간은 못 만들었습니다.
- **Adaptive Join 을 안 봤습니다.** SQL Server 2017 부터 Loop 과 Hash 를 실행 시점에
  고르는 연산자가 있는데, 컬럼스토어 인덱스가 있어야 나와서 이 세션 범위 밖입니다.
