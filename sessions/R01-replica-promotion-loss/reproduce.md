# R01 재현 기록

## 환경

| 항목 | 값 |
|---|---|
| 호스트 | **기록하지 않았습니다.** `uname -srm`, `nproc`, `free -g`를 남기지 않았습니다. 어느 장비였는지 확인되지 않아 추정해 채우지 않습니다. 다른 세션과 절대 시간을 비교하면 안 됩니다 |
| MySQL | 8.4.3 x 2노드 (source 13310, replica 13311), GTID, binlog. 컨테이너 CPU·메모리 한도 없음 |
| 복제 | 비동기 → 실험 B부터 semisync 플러그인 (AFTER_SYNC, timeout 8000ms) |
| 소스 설정 | `innodb_flush_log_at_trx_commit=1` |
| 레플리카 설정 | `replica_net_timeout=20` (기본 60초에서 축소. 관측 편의를 위한 변경) |
| 분단 방법 | 복제 전용 네트워크에서 `docker network disconnect`. 관측 경로는 유지 |
| 쓰기 | Python 1 프로세스·커넥션 1개, 후원 1건씩 직렬 커밋, 커밋 성공 건만 로그. 커밋 사이 `time.sleep(0.02)` |
| 일시 | 2026-07-29 |

쓰기 속도는 클라이언트가 정한 값입니다. 커밋 사이 20밀리초 고정 대기만으로 상한이 초당 50건이고, 실측 커밋 간격 중앙값이 27밀리초(p95 30밀리초)라 실험 A의 실효 커밋률이 초당 37.09건이 됐습니다. 이 문서의 어떤 수치도 하드웨어 성능으로 읽으면 안 됩니다.

## 실험 A: 비동기 (results/async-timeline.txt)

```console
[06:52:29] 쓰기 시작 (40초 예정)
[06:52:39] 복제망 분단 (docker network disconnect)
[06:52:54] 소스 강제 종료 (docker kill)
[06:52:54] 쓰기 종료: 커밋 성공 927건, 합계 8,628,000원, 마지막 seq 927
[06:52:58] 승격본 상태: 행수/최대seq/합계 = 372  372  3596000
[06:53:39] GTID 차집합(옛 소스에만 있는 트랜잭션): 7bddaea1-...:380-934
[06:53:39] 옛 소스의 행수/최대seq/합계: 927  927  8628000
```

유실 = 927 - 372 = 555건, 8,628,000 - 3,596,000 = 5,032,000원.

이 555는 분단 15초 동안 커밋된 건수 그대로입니다. 927건을 24.99초에 커밋했으므로 초당 37.09건이고, 37.09 × 15 = 556입니다. `results/async-writer.csv`에서 살아남은 마지막 커밋은 seq 372(06:52:39.533)이고 사라진 첫 커밋은 seq 373(06:52:39.560)이라, 그 간격 27밀리초가 이 실행의 커밋 간격 중앙값과 같습니다. 레플리카는 분단 직전까지 한 건도 밀리지 않고 따라와 있었고, 분단 이전의 복제 지연은 이 실험의 해상도로는 보이지 않습니다. "유실 창 = 분단 시간 + 분단 직전의 전송 지연"이라고 적었던 초기 설명은 이 검산으로 철회했습니다.

확정 커밋의 59.9%라는 비율은 쓰기 25초 중 분단이 15초를 차지한 결과라, 분단을 늘리면 100%에 가까워지는 값입니다. 옮겨 적을 형태는 "초당 37건짜리 워크로드에서 복제가 끊긴 1초마다 약 37건이 유실 후보"입니다.

`Seconds_Behind_Source` 1초 시계열(`results/async-sbs.csv`): 분단(10초 지점) 후에도 29초 지점까지 0을 표시. `replica_net_timeout=20` 경과 후에야 IO 스레드가 No로 전환.

## 실험 C: 강등 후 종료

```console
[06:55:19] 복제망 분단. 8초 뒤 강등을 기다린다
Rpl_semi_sync_source_status  OFF                    ← 비동기로 강등됨
[06:55:37] 쓰기 종료: 커밋 성공 707건
[06:55:39] 승격본: 이번 실험 분 373건만 보유        → 334건(3,240,000원) 유실
```

334도 실험 A와 같은 식입니다. 강등으로 커밋이 다시 성공하기 시작한 06:55:27.98부터 소스가 죽은 06:55:37.15까지 9.16초이고, 그 사이 성공한 커밋이 334건입니다. 창의 시작점만 분단 시각에서 강등 시각으로 옮겨 간 것입니다. 반동기가 사 준 것은 분단 후 8초, 이 워크로드로는 약 300건입니다. 47.2%라는 비율도 실험 A의 59.9%와 마찬가지로 창의 길이가 정한 값이라 그대로 옮겨 적을 결론이 아닙니다.

분단 직후 진행 중이던 커밋 한 건은 8.030초 동안 멈췄습니다. `rpl_semi_sync_source_timeout`에 준 8,000밀리초와 일치합니다. 실험 B에서는 마지막 성공 커밋(06:54:53.009)부터 소스 사망(06:54:58.14)까지 5.13초 동안 한 건도 통과하지 못했습니다. 반동기의 실측된 대가는 평상시 왕복이 아니라 이 정지 구간입니다. 평상시 커밋 지연은 따로 계측하지 않았고, 커밋 간격으로는 비동기와 반동기가 구분되지 않았습니다(양쪽 다 중앙값 27밀리초, p95 30밀리초).
