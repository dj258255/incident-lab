# AFTER_COMMIT 대조, 반동기의 평상시 지연, 복구 경로

# MySQL 8.4.3

## 1) 반동기의 평상시 커밋 지연
  커밋 간격이 아니라 커밋 문장 자체의 왕복을 잽니다.

  [비동기] 커밋 100건 중앙값 5.22ms, p95 6.22ms, 최대 7.67ms
  [반동기 AFTER_SYNC] 커밋 100건 중앙값 5.40ms, p95 6.34ms, 최대 7.69ms
  [반동기 AFTER_COMMIT] 커밋 100건 중앙값 5.24ms, p95 6.45ms, 최대 6.89ms

  두 노드가 같은 호스트의 컨테이너라 이 왕복은 실제 가용영역 사이보다 짧습니다.
  절대값이 아니라 세 조건의 상대 비교로만 읽어야 합니다.

## 2) AFTER_COMMIT: 다른 클라이언트가 읽은 값이 사라지는가

### wait_point = AFTER_SYNC
  wait_point = AFTER_SYNC
  반동기 상태 = ON
  커밋이 매달린 상태에서 다른 세션이 읽은 행 수 = 0
  → 아직 안 보입니다. 복제본이 ack 하기 전에는 다른 세션도 못 읽습니다.
  승격한 복제본에 남은 행 수 = 0
  → 읽히지 않았으므로 사라질 것도 없습니다. AFTER_SYNC 가 막는 자리입니다.

### wait_point = AFTER_COMMIT
  wait_point = AFTER_COMMIT
  반동기 상태 = ON
  커밋이 매달린 상태에서 다른 세션이 읽은 행 수 = 1
  → 이미 읽혔습니다. 여기서 소스가 죽으면 읽힌 값이 사라집니다.
  승격한 복제본에 남은 행 수 = 0
  → **읽힌 값이 사라졌습니다.** AFTER_COMMIT 의 lossy 구간입니다.

## 3) 복구: 옛 소스에서 차집합을 뽑아 병합한다

  먼저 유실을 만든다. 비동기로 두고 복제망을 끊은 채 쓰기를 넣은 뒤 소스를 죽인다.
  분단 직전 양쪽 행 수 = 600 / 600
  분단 중 소스에만 들어간 쓰기 50건 (클라이언트는 전부 성공을 받았다)
  소스 강제 종료 후 복제본을 승격했다
  옛 소스 행 수 = 650, 승격된 복제본 행 수 = 600
  차이 = 50행 (이것이 유실량입니다)
  옛 소스에만 있는 id 를 뽑아 새 소스로 옮깁니다.
  뽑은 행 수 = 50
  병합 후 새 소스 행 수 = 650 (병합 전 600)
  회수한 행 = 50행 / 유실 50행

  **이 경로가 성립하는 조건이 좁습니다.** 옛 소스가 다시 떠야 하고, id 가 겹치지
  않아야 하고, 그 사이 새 소스에 들어온 쓰기와 순서가 뒤섞여도 되는 데이터여야
  합니다. 후원 정산처럼 순서가 의미를 갖는 데이터에서는 이 병합이 답이 아닙니다.

## 정리
  각 조건 1회 실행입니다.
